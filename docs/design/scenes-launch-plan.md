# 场景产品首发推进计划

日期：2026-09-20。依据当前工作区代码，以及已确认的“旧实验数据无需保留”决策。

本文是后续实施顺序与验收清单，不表示所列能力已经完成。与 [技术设计](./scenes-technical-design.md) 和 [实施记录](./scenes-implementation-progress.md) 配合使用。

## 实施状态（2026-09-20）

用户已确认按此顺序执行。L1 正式启动替换及旧实现删除已落地；L2 新用户接口、L3 Web Push 与设置、L4 最小可靠性和诊断已实现并进行离线验收。真实账号、设备接收、7 天试点和发布仍未完成，详见[最新实施记录](./scenes-implementation-progress.md)。下文的“当前代码实况”为实施前的问题快照，保留用于对应验收项。

## 1. 实施前判断

已有：领域契约、持久执行、权限／来源复查、两个只读模板、独立宿主、Web 隔离闭环、成果 outbox、页面通知与摘要策略、正常数据库初始化。

尚未形成：正式产品启动 → 新用户授权 → 持续检查 → 实际收到成果 → 使用成果 → 停止／恢复／排障的生产闭环。

旧实验历史转换不再是上线条件。旧表清理只需可靠的一次性结构升级；不得重新引入历史映射、快照、配置 journal 或历史 UI。

此前 Gateway 启动 smoke 证明存储／配置简化没有阻塞当前服务启动，不能替代正式 SceneRuntime 已接线的端到端验收。

## 2. 已采用的首发边界

| 维度 | 建议首发 | 后续再做 |
| --- | --- | --- |
| 场景 | Gmail 指定线程跟进；用户提供资料的家庭周安排 | 会议准备、项目风险、综合日常巡查 |
| 行为 | 授权内只读检查、草稿／建议、用户查看和复制使用 | 自动发送、创建任务、跨系统写入 |
| 运行环境 | 单 Gateway、单 SQLite；明确本机服务需要持续运行 | 分布式调度、跨设备执行 |
| 身份 | 明确支持当前本地主体及 workspace；模型选择有可见规则 | 多主体共享、家庭成员共享、隐式跨 Agent 授权 |
| 首发客户端 | Web／Electron 管理与成果查看 | 移动端完整编辑可延后，已发布客户端至少不能出现无效通知入口 |
| 提醒 | 页面持久 Inbox + 至少一种首发环境可用的离线提醒途径 | 同时覆盖所有外部渠道 |

首发不承诺自动发送，就不把完整 Effect 平台作为阻断项；一旦承诺任何外部写入，审批、幂等、执行账本和 unknown 对账立即成为上线前置条件。

范围缩小意味着未支持功能明确隐藏或停用，不能继续通过旧执行器承接。已有 Task／Project／Automation 的独立功能应保持可用。

## 3. 必须先解决的依赖

| 当前代码实况 | 产品影响 | 所需决策／处理 |
| --- | --- | --- |
| `GatewayService` 仍启动旧三个 worker、构造旧 Heartbeat 和旧事件发布者 | 正常启动没有新场景执行闭环 | 成套接线并删除旧装配 |
| 场景 HTTP 为可选注入，正式入口未提供新服务 | 路由存在但返回 503 | 正式服务提供真实 `SceneHttpServices` |
| `xopc_use` 仍提供 proactive 命令 | 对话委托进入旧链路 | 新 scene 模式复用同一应用服务；删除旧说明和命令 |
| 项目监控、自动化和 Connector 发布者仍依赖旧域 | 直接删目录／表会破坏其他入口 | 对每个调用者选择：接入首发支持的新事件，或删除不支持的监控能力与入口；保留独立业务 |
| 邮件 picker 查询 `knowledge_source_items` | 仅连接邮箱的新用户可能无可选线程 | 明确授权下通过 Connector 搜索／选择线程，并持久化最小线程身份，不依赖后台学习 |
| 邮件实际读取额外限制 Gmail、Composio 和确认策略 | 可能出现“可以选择但不能运行” | picker、预检、执行共享能力判断，并给出具体修复操作 |
| 偏好／presence 有领域实现，缺完整 API／客户端 | 用户无法实际控制已实现的打扰策略 | 接入偏好设置、presence 租约与多端一致行为 |
| 宿主只发布 in_app 通知 | 用户关闭页面后无法可靠得知成果 | 明确并完成首发提醒渠道，覆盖订阅、回执与深链接 |

## 4. 实施批次与完成标准

### L1：正式运行链与旧依赖收口（P0）

目标：普通产品启动即可使用唯一新场景链路。

工作：

- 列出旧域全部运行时调用者、事件生产者、工具、路由、配置、导航和通知偏好，并逐个指定替代或删除方案。
- Gateway 在数据库初始化后构造宿主，注入 HTTP 与 realtime，纳入 start／stop／失败清理。关闭 SQLite 前等待执行与读取结束。
- 明确宿主 principal、workspace、模型和配置更新的处理；登录会话刷新不能改变归属。
- `xopc_use` 的场景查看、开启、检查、暂停、恢复与结束复用同一应用服务，遵守相同幂等和修订约束。
- 删除旧 worker、Heartbeat 的专有调用链、旧 API 和产品入口；项目／自动化所需能力完成解耦后才删除其旧依赖。
- 删除旧表结构及内置目录的版本升级与最后一个调用者删除同批交付；正常初始化同时覆盖新装和旧状态。

验收：

- 从真实 `GatewayService.start` 启动，通过鉴权 HTTP 开启家庭场景，定时生成成果；重启后仍继续。
- 对话开启和 Web 查看操作同一实例；暂停后没有晚到成果发布。
- 旧产品入口不能再创建旧委托；运行时依赖检查不再指向旧 Proactive／助理 Heartbeat。
- Task／Project／Automation／聊天／连接器回归通过。
- 不需要手工建表、测试注入或特殊启动脚本。

### L2：新用户首次价值闭环（P0，接口设计可与 L1 并行）

目标：空数据库、没有历史同步的新用户能独立获得第一份可用成果。

工作：

- 邮箱连接 → 明确授权的线程搜索／选择 → 目标和时间 → 开启。账号、对象范围和确认策略在开启前解释清楚。
- 将稳定的 Connector 账号／线程身份与场景委托绑定，避免把已学习的邮件记录当作使用前提。
- 检查模型可用性，提供未配置、凭据失效、来源不可用、预算不足的可操作反馈。
- 家庭安排提供简短输入示例与明确时区／时间设置，空输入不会消耗模型。
- 成果显示更新时间、依据、建议／草稿与使用操作；状态区分无变化、等待来源、失败和暂停。
- 支持修改目标／时间、暂停、恢复、结束和删除范围说明；用户无需知道内部状态名。
- 首发文案明确：草稿未发送；Gateway 关闭／设备休眠时不持续检查，恢复遵循有限补偿。

验收：

- 空知识库也可委托 Gmail 线程；不必开启后台学习。
- 真实测试邮箱与真实模型完成一次到期跟进、已回复静默、新回复使旧草稿失效。
- 断开账号、重新授权、切换账号不会越权或永久卡在无解释状态。
- 首次成果可以复制或用于真实判断，不只是出现一张卡片。

### L3：提醒与客户端体验（P0）

目标：用户能收到成果、理解为何没被提醒，并控制打扰。

工作：

- 接入检查暂停、通知静音、免打扰、摘要时间、每日提醒上限的鉴权 API 和 UI。
- 接入页面／客户端 presence 租约、过期与身份隔离；正在查看时抑制重复提醒。
- 按首发环境选定至少一种页面关闭后仍可送达的方式，例如 Electron 系统通知或 Web Push；权限拒绝时解释退化行为。
- 实际渠道投递继续使用通用通知账本和发送前复查，不重新建设第二套通知系统。
- Web／Electron 通知定位到具体成果；已发布移动客户端要么接入查看与暂停，要么明确限制支持范围并阻止发送无法打开的目标。
- 改期、撤权、成果撤回、通知延迟到达时，点击进入的页面展示当前事实。

验收：

- 页面开启／关闭、前后台、断线重连、权限拒绝、多端同时在线、重复事件各有正确行为。
- “静音通知”不等于“停止检查”；两者在 UI 与实际执行一致。
- 真实设备收到一次提醒、正确打开成果；重启／重连不重复投递。
- 系统接受请求、设备收到通知、用户查看是不同状态，不虚报送达。

### L4：持续运行和维护能力（P0 的最小集合）

目标：问题可发现、可解释、可恢复，成本和数据规模可控。

工作：

- 验证逐项邮件扫描的 30 秒批次超时与游标推进。慢线程不能让后续事项长期得不到检查；设置逐项超时、可继续的进度和账号级退避。
- 对 Connector 429／5xx、断网、模型超时、额度不足、SQLite busy、关机／休眠恢复进行故障注入。
- 在单 Gateway 内验证长模型调用下的队列公平性与截止延迟；按首发负载设定容量，必要时做有界并发，暂不引入分布式队列。
- 日志／指标关联 activation、intent、run 和通知；记录有限失败原因，不把邮件正文或凭据写入日志。
- 增加待执行深度、排队时长、连续失败、来源不可用、模型实际 token／费用、Connector 请求量和通知重复率。
- 定义运行／成果／通知账本的留存与清理规则；保留当前有效引用和去重所需窗口，避免越清理越重放。
- 在 UI 提供重新授权、修改配置、重试或暂停；没有新成果不能成为所有失败的统一表现。

验收：

- 重启、迟到事件和撤权不产生重复成果或越权读取。
- 慢账号不长期阻塞其他已委托事项。
- 用户能知道最近检查时间、下一次检查、当前阻塞原因和处理方法。
- 建议至少 7 天小范围真实试点，记录错误、成本与打扰；具体容量和时延门槛根据首发负载制定，不以模型调用次数作为成功指标。

### L5：发布候选验收（发布门禁）

目标：验证最终安装包和普通启动流程，而非仅验证测试宿主。

- 使用最终 npm／Electron 产物完成新装、受支持旧版本升级、旧错误配置、重复启动与卸载重装相关验证。
- 执行核心回归、前后端检查、真实鉴权 API、真实账号／模型与选定通知渠道的端到端测试。
- 确认无旧定时器、旧入口、兼容适配和旧域运行时依赖；正常使用不依赖手工修库。
- 发布说明说明旧实验数据被清理、首发模板／平台／渠道范围、后台运行要求和关闭方式。
- 试点记录首次成果、明确采用反馈、误报／漏报、被打扰反馈和单次有效帮助成本。
- 保留全局停止检查和停止投递能力；数据库升级后不得自动启动不支持新 schema 的旧二进制。具体发布恢复策略使用产品现有发布机制，禁止重放旧实验 outbox。

## 5. 开发与发布顺序

1. 先确认上述首发边界，并完成旧依赖清单。
2. L1 建立普通启动闭环；同时设计 L2 的邮件身份／授权接口。
3. L2 打通新用户真实场景，L3 打通提醒和受支持客户端。
4. L4 的诊断、预算和故障测试贯穿以上批次；候选版本进行连续运行试点。
5. L5 通过后发布。开发可以拆 PR，首次产品发布不能留下旧引擎兜底。

本计划最先实施的任务是 L1：正式宿主接线与旧运行时调用者收口。先用不依赖外部邮箱的家庭场景验证生产执行链，再用 L2 的真实邮箱验证授权和成果质量。

## 6. 不进入本轮的事项

- 历史数据导入、跨配置 journal、历史资料恢复界面。
- 模板市场、社区代码、通用 DAG 编辑器和第三方沙箱。
- 多用户家庭共享、跨设备分布式调度。
- 首发没有承诺的自动发送或其他外部 Effect。
- 以预留能力为理由扩大抽象；只有第二个真实需求出现时才抽取通用层。
