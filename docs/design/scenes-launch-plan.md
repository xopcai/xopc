# 场景推进计划：通用任务跟进，以 Slack 事项验证

> 2026-09-21 架构修订：当前实现以[通用场景任务跟进方案](./scene-task-follow-up.md)为准。Slack 编码只是首个验证配置；执行复用现有 embedded Agent harness，文档无需 Git，文件修改无需 Docker。下文早期 Slack 专用执行器／强制验证安排不再作为实现约束，长期需求与历史分析保留。

更新：2026-09-21。当前状态：通用链路已实现，真实 Slack＋内部 BYOK Agent 的 worktree 编码和无 Git 文档两类验收通过，均不配置 Docker、不授予命令执行权限。个人持续试用、真实通知及发布门禁未完成；主实例尚未启用。以下 S0—S5 保留早期推进历史，当前代码范围和验收事实以[实施记录](./scenes-implementation-progress.md)为准。

当前交付通用来源接口、目标／指令／能力授权、原 Task 持续推进、三类任务资源及本地分支关联；后续先使用真实业务样本验证长期跟进价值，再推进频道事项发现。更多来源和可安装能力包不能以替换当前主链路的方式另建执行器。早期首版见[历史实现说明](./slack-development-implementation.md)。

本计划以用户自己的 Slack → 排查 → 编码 → 分支管理闭环为第一目标，取代此前以 Gmail／家庭只读场景或其他目标人群验证为新增能力主线的顺序。已完成的场景基础不重做，历史事实见[实施记录](/Users/micjoyce/develop/github/xopc/docs/design/scenes-implementation-progress.md)及[只读场景发布评审](/Users/micjoyce/develop/github/xopc/docs/design/scenes-production-readiness-review.md)。

当前产品与技术范围以[通用场景任务跟进方案](./scene-task-follow-up.md)为准。

## 1. 首发承诺与边界

> 接手一个明确的 Slack 事项后，持续吸收讨论并推进排查与开发；代码、分支、执行和验证都回到同一事项，用户不再反复复制消息、盯线程或凭记忆找分支。

| 维度 | 首条闭环 | 后续 |
| --- | --- | --- |
| 用户／来源 | 当前用户，明确授权 Slack thread | 指定频道内新事项发现，再考虑其他来源 |
| 执行 | 一种开发执行器；默认内部 BYOK Agent 路线 | 用户选择且满足能力要求的 Codex 等适配 |
| 工作资源 | 单事项单仓库，独立工作区／分支，显式绑定 | 多仓库、复杂依赖和更多并发 |
| 自动行为 | 授权读取、排查、内部 Task 更新、工作区修改、约定验证 | 审批后的 push、PR、Slack 回写 |
| 人工介入 | 目标／范围冲突、授权、无法恢复的阻塞 | 不以逐步审批替代真实自治 |
| 完成 | 代码及约定验证可交付，或有证据无需修改 | 合并、部署及线上验证另行约定 |
| 运行 | 单 Gateway／SQLite，在线工作、恢复补同步 | 按需求选择常在线宿主 |

不默认扫描所有频道／私信，不整理删除历史分支，不自动合并／部署，不先做多 Agent、通用场景编译器或能力包市场。

## 2. S0：真实样本与实现边界确认

目标：用用户真实工作定义验收，不把外部市场访谈作为启动门槛。

工作：

- 选择 3—5 个有代表性的 thread：简单修复、持续补充、冲突待决定、重复反馈、已有分支待关联。
- 确认 Slack 账号／读取范围、目标仓库、基线规则、开发执行器、允许动作和完成条件。
- 只读检查已有 Connector、Task、workspace／Git 及 executor 接口，避免重复造基础设施。
- 验证 Slack thread 完整读取、消息修订、附件、撤权、断线补同步的接入可行性，确定事件或有界轮询。
- 执行器验证启动、会话身份、输入更新、应用确认、观察、停止、恢复及结果证据。外部 Codex 未通过时不宣称自动控制可用，也不无提示切换。
- 固化脱敏样本和基准：现在复制多少消息、盯多少次 thread、如何找到对应分支。

门槛：仓库与授权不靠猜测；选定一种可行执行器；每个样本有可观察验收标准。未提供真实访问时可开发脱敏回放，但不能声称真实接入通过。

## 3. S1：明确 thread 接手与只读排查

目标：不复制正文，只给 thread 即能建立可追溯事项并获得排查结果。

工作：

- 读取完整性、稳定来源身份、最后成功同步和健康状态。
- Task 幂等创建／关联，有版本工作说明，保留证据和假设区别。
- Scene 权限贯穿受限只读 Agent；默认不能写代码或执行高风险命令。
- 事项卡链接源线程、工作说明和执行结果，展示待决定事项。
- 来源更新持久化与基础合并，避免重复事件产生重复 Task。

门槛：真实 thread → 原始依据 → 一个 Task → 一份有用排查结果；重复点击、分页不完整、授权失效均正确处理。通过鉴权 Gateway 真实路由，而非只测内部 handler。

S1 是安全增量，不是最终交付；仅摘要和待办不能算三个用户问题已解决。

## 4. S2：资源绑定与受控编码

目标：在正确且隔离的工作区完成一次真实修改和验证。

工作：

- Task 与仓库、worktree、分支、base commit、执行会话建立耐久绑定。
- 创建资源先预留操作身份，失败恢复先核对，不能重复建分支或误删目录。
- 使用已有 TaskRun 与 Agent／Workflow 能力；先一个活动写者，继承 Scene 权限。
- 约束可写目录、命令、网络与凭据；不把 worktree 当安全沙箱。
- 接入代码／diff、真实测试与未验证项回执，明确“运行结束”和“编码可交付”。

门槛：thread → Task → 工作区／分支 → 实际代码 → 验证证据全链可查；保护用户修改；重试不重复启动写者。没有合并／部署授权时不能越界。

## 5. S3：持续讨论、恢复与交付新鲜度

目标：开发中 Slack 变化无需用户转述，也不会错误覆盖已确认目标。

工作：

- 新消息、编辑／删除形成说明修订，按检查点向原执行任务投递。
- 区分 pending、delivered、applied、unknown 等状态；记录应用确认与版本。
- 补充证据自动更新；冲突、取消及越权范围变更进入明确决策。
- 交付前核对当前验收版本、来源健康与未处理变更，旧需求结果不能报当前完成。
- 暂停、撤权、超时、重启、掉线恢复核对活动写者及资源状态。
- 正常进展安静入账，必要问题合并提醒，可交付提醒依用户偏好。

门槛：用户在 thread 补充复现条件后，同一 Task／分支内吸收并验证；无需复制到 Agent。注入事件重放、乱序、旧执行晚回报和来源失效，不产生重复开发或过时完成。

**S1—S3 全部通过才算“持续推进到编码完成”的首条闭环。**

## 6. S4：已有分支关联与受限事项发现

目标：解决当前分支难管理，并减轻未来消息发现负担。

工作：

- 只读盘点已有分支／worktree／未提交修改／PR，提出有依据的来源关联候选。
- 用户确认后绑定 Task，无法确认保留“待关联”；不自动清理、改名、提交、变基或合并。
- 事项列表支持按来源、仓库、分支、执行和需关注状态定位，双向追溯。
- 单独授权指定频道发现，优先明确给用户的请求和现有事项更新。
- 重复反馈合并，模糊信息不立刻变 Task；跨事项关系不凭同名推断。

门槛：用户能从已有分支反查对应需求，不能确认的有明确状态；抽样原频道人工核对发现／遗漏／重复，不以消息量或任务数当成功。

## 7. S5：个人真实试用与发布门禁

先让用户在真实工作中连续使用一周，覆盖多个事项；这是一段建议的观察窗口，不是统计意义上的市场验证。代码开发不必等待这段试用结束，扩大自动行为及正式发布需要相应证据。

至少覆盖：

- 完整 thread 接手、持续补充、冲突决策、编码验证和历史分支反查。
- 真实账号／模型／执行器、正式 Gateway 与最终产品启动链路。
- 断线、休眠、撤权、额度耗尽、工作区被手动修改、执行器存活未知。
- 通知收到并能打开正确事项；静音／暂停语义明确，没有重复提醒。
- Scene／Task／Workflow／Project／现有只读模板回归，无重复旧迁移和数据丢失。
- 若新增鉴权 API，lazy-bundle matcher、映射测试与实际鉴权请求全部通过。

度量：消息复制和手动盯 thread 次数、补充指令次数、查分支耗时、错配／遗漏、修错时间、单位事项成本。验收重点是用户明确确认三项负担下降，且无越权和重复写执行；不预先虚构节省比例。

## 8. 依赖和范围决策

S0 → S1 → S2 → S3 构成首条主线。已有资源只读盘点可提前用于确认设计，自动接管必须等权限和绑定机制到位。S4 的频道发现不得替代 S3 的跟进可靠性。

执行器选择是实现预检决定：默认内部 Agent；用户明确要求保留 Codex 且能力达标时可优先适配 Codex，但同一迭代不要求两套都完成。此选择影响适配工作，不改变 Task／来源／分支和回执的产品契约。

先明确真实线程、仓库、允许动作和执行器；架构细节通过代码核查确定。不为没有证据的团队容量承诺固定工期。

## 9. 已有只读场景的维护边界

2026-09-20 的 L1—L5 工作属于 Gmail／家庭场景基础建设历史：正式宿主、旧实验删除、只读成果、Web Push、健康与诊断已有实现；实际发布门禁仍以原评审为准。

本计划不撤回这些完成事实，也不把“真实 Gmail、设备通知和持续试点尚未完成”改成通过。Gmail 专属门禁不阻塞 Slack 原型；共享发布包同时开放的能力必须分别具备证据，未通过的保持原限制。

不再执行旧数据清理，不用新需求覆盖实现记录，不把文档方案当作已发布功能。
