# 通用场景任务跟进：实现方案

## 目标与用户价值

用户授权一次来源和目标，后续变化持续进入同一个任务，不再复制讨论、重新说明上下文或手动寻找分支。Slack 问题开发是验证实例，不是新的产品领域。讨论整理、文档维护等任务使用同一条执行链。

用户流程：选来源 → 描述目标与处理指令 → 确认能力范围 → 自动跟进。只有缺少权限、需要真实判断或恢复失败时请求介入。检查结果没有变化时不重复运行、不重复提醒。

## 分层与复用

```
来源适配器（Slack / 后续其他来源）
  → 持久化来源版本、去重与权限检查
  → Scene 的目标和自然语言指令
  → 既有 Task / TaskRun 调度器
  → 既有 embedded Agent harness（预算、工具策略、持久化会话）
  → Task receipt / 用户等待 / 下一次来源变化
```

- **Scene** 保存目标、指令、来源引用与能力授权；不实现排查→开发→测试的业务状态机。
- **来源注册表** 处理来源解析、身份和只读快照；来源正文不构成授权。Webhook 将来可以唤醒相同读取入口，而不是建立第二套执行逻辑。
- **任务跟进协调器** 只管理来源版本、同一 Task 的关联、单写入者、取消、重试和恢复；Task / TaskRun 仍是任务状态的唯一事实来源。
- **执行** 复用 `createDelegateChildHandle` / `runXopcEmbeddedTurn`、SQLite transcript 和既有结构化结果工具，不再直接创建 Slack 专用 pi Agent。这里是受限后台任务的运行适配器，不是新 workflow 引擎。
- **能力** 是授权工具集合。提示词决定如何完成事情，但不能增加工具权限。初版提供受限文件读取/写入和可选的已批准验证命令；不自动授予发布、发消息或任意 shell 权限。
- **资源** 与目标独立：无文件资源、任务产物目录、Git worktree。Git 仅是资源提供方式；文档任务不要求项目或 Git。Worktree 隔离分支，不等于操作系统安全沙箱。
- **验证** 与执行分离。未授权命令或未配置隔离后端不阻止文件编辑；结果明确标记 `unverified`，绝不宣称测试通过。Docker 仅是当前可选验证工具的隔离后端，不是场景或编码前提。也不自动降级为宿主机执行仓库脚本。

## 第一批配置实例

| 实例 | 指令 | 资源 | 能力 |
| --- | --- | --- | --- |
| 讨论排查 | 梳理问题、证据与仍需判断的事项 | 无 | 仅来源上下文 |
| 持续文档 | 随讨论更新一份 Markdown 决策记录 | 任务产物目录 | 文件读写 |
| 问题开发 | 根据当前需求修改实现，报告未验证项 | Git worktree | 文件读写；验证命令可选 |

这些实例不得成为运行时 `if coding / Slack / document` 分支。项目、分支、产物与原讨论在任务详情中可追溯。暂不推测旧分支归属，旧分支关联需要用户确认。

## 一致性与安全边界

1. 身份包含 owner、workspace、来源 provider 和规范化 locator。重复接管不会创建新任务；不同目标/授权冲突不得静默覆盖。
2. 每次模型/工具动作前重查场景状态、授权、源版本、Task contract 和单写入者。暂停/撤权/新来源使旧运行失效。
3. 已观察、已交付、已处理分别记录。已处理表示当前版本完成一次有效执行（可能产生待判断问题），不是宣称任务已完成或经过独立验收。验证证据另列。模型显式返回 `continueAutomatically` 决定当前授权内是否还有可立即推进的工作；不能仅凭非空的“剩余工作”推断需要循环运行。
4. 来源更新复用任务、会话及资源。来源变化或用户回答可唤醒任务；关闭任务不会自行重开。
5. 有界轮询、预算与指数退避；重启遇到不确定副作用保留资源并暂停恢复，不自动重做。
6. 结构化结果表达总结、剩余工作、是否需要用户判断、是否请求立即继续。每个来源版本至多自动推进三轮，每任务每日十轮。平台不把“没有测试”自动转换成必须用户介入，也不把模型自述转换成已验证。

## 兼容与范围

v190 的实验性 Slack 开发表使用追加迁移转换为通用跟进绑定。保留任务、快照、分支、资源和历史回执；旧实例暂停，需明确恢复，避免迁移自动扩权。旧专用 API / UI / Agent 不继续作为第二条执行路径。

本轮不合并 Scene 与 Extension、不新建 DAG 引擎、不实现全 Slack 收件箱语义分流或任意用户代码插件加载。来源、工具与资源接口预留扩展边界；面向用户的扩展先通过可编辑指令和明确能力授权。Skill 包、Workflow 引用以及签名 Extension 注册可沿现有扩展机制接入，不能绕过授权。

## 扩展顺序与用户体验

1. **现在：用户修改行为，不写流程代码。** 通过目标、指令和资源／能力授权组合场景；后台持久化、去重、权限和重试仍由确定性代码保障。不能依靠模型自行决定是否绕过这些边界。
2. **新增来源：适配器接入同一协调器。** 实现来源规范化、账号可见性、授权检查、快照读取及可选链接解析；邮箱或后续 webhook 只改变事件与证据入口，不改变 Task 或执行循环。当前生产注册的跟进适配器只有 Slack；mail fixture 仅验证接口可替换性。
3. **已有 Skill／Workflow 的声明式引用。** 后续增加经过校验的引用配置，由既有能力解析与工具策略加载；场景只声明需求和版本，不复制 Skill／Workflow 引擎。缺少依赖时展示具体设置项，新增能力需要确认，不静默扩大旧授权。
4. **最终能力包。** Extension 可以提供来源、指令模板、Skill／Workflow 引用和资源需求。用户安装时看到用途、依赖和权限差异；配置升级保留已有 Task、历史与资源，并支持暂停或回退。初期先把前两种真实场景跑稳，不提前交付任意插件执行平台。

评价重点是减少复制上下文、手动盯讨论和寻找产物／分支的次数，以及需要人判断的提醒是否准确；不是生成任务的数量。短期个人试用记录漏跟进、无效重复运行、无效提醒和完成一件事的人工介入次数，作为后续扩展门槛。

## 验收

- 无 Docker 配置也能修改 worktree，并如实保留未验证状态。
- 非编码文档任务无项目/无 Git，能够持续更新相同产物。
- 两类任务走同一协调器与 Agent harness；更换来源适配器不改变调度器。
- 重复事件、更新中取消、暂停/恢复、撤权、用户回答、重启恢复、迁移、鉴权及 lazy route 均有回归验证。
- 真实模型与真实 Slack 验证单列记录；fixture 测试不得描述成线上已验证。
