# 语音体验分阶段交付与验收

日期：2026-09-05。对应 [交互设计](./voice-experience-redesign.md)。本记录区分代码验证、模拟音频验证和真实声学验收，不把模拟结果当作通话质量达标。

## 阶段 1：入口与设置

- Chat 保留“听写”和“语音通话”两个入口。通话一次点击开始，删除通话内模式选择、二次开始和重复服务配置。
- 默认方案存入网关 `voice.realtime.defaultEngine`，默认 `agent`；原生方案明确标注无工具。创建接口省略 engine 时使用该配置，不猜测或自动切换引擎。
- 小型非模态窗口保留麦克风、停止回复、挂断；字幕和设置在更多选项中。最小化和切换页面保持当前 Chat 和连接。
- 设置按说话与聆听、输入与显示、音频设备、语音服务、排查问题分组。字幕/麦克风为浏览器偏好；服务配置仍使用唯一网关配置 API。
- 听写、助手通话和原生语音分别判断配置状态。诊断的 STT/TTS 实测不会把原生通话误标为已验证。

自查修复：结束后权限请求迟到不污染新通话；默认引擎真实落到后端；原生音色使用对应配置；返回设置保留对话入口；通话中禁用另一路麦克风诊断。

## 阶段 2：输入与取消边界

- 听写 final 先保存在临时稿，完成后统一调用现有润色接口再填入编辑器，不发送。取消不会修改原稿；润色期间取消会丢弃迟到结果。润色失败保留原文并提示。
- 断线后保留已完成识别的文本，用户可以完成或取消。达到录音时限时执行正常提交识别流程。
- 新增 `input.mute`，移除通过补发静音音频结束识别的逻辑。
- Agent 静音/手动停止会废弃输入代次、排队轮次和旧识别流。重置期间最多暂存两秒新音频；旧连接及尚在初始化的旧识别请求都会取消。静音保持当前助手回复。
- 原生方案使用 `input_audio_buffer.clear`，屏蔽旧输入和迟到回复，收到清空确认及新语音后恢复。清空确认通常等待五秒；仍有上传未完成时延长为十五秒，上传本身十秒超时。
- 取消当前回复仍等待工具/TTS 清理，避免旧轮次清理与新轮次执行冲突。

自查修复：旧 final 尚未出现 speech_started 的情况也通过识别流代次隔离；快速静音不会遗留多个初始化连接；空听写和重复 close 不会重复插入；等待澄清时附和不会触发新轮次。

## 阶段 3：口语、工具与任务

- 语音呈现约束只作用于当前模型轮次的系统上下文，不写成用户消息，不修改全局 Agent 性格。默认简短回答，长内容留在 Chat。
- 流式播报过滤代码块、表格、Markdown 标记和链接目标，字幕使用已有安全 Markdown 组件。语音轮次不再触发普通消息自动朗读。
- 工具活动按真实开始/结束事件显示；澄清复用 `ClarifyPrompt` 和现有响应 API；连接器批准/拒绝复用现有审批接口，并按 Chat 过滤。
- 等待澄清期间，环境语音不会代替明确答复或自动打断确认；停止/挂断仍可取消当前轮次。
- 从任务对话发起通话保留 taskId，复用现有任务状态订阅和详情/决策入口。任务运行、证据、暂停和后续输入继续遵循现有任务机制，不新增一套语音任务系统。

边界：当前助手的工具调用仍按现有轮次执行；没有新增任意后台任务并发或原生模型工具桥接。长任务转后台、不中断执行地口头追问进度属于后续能力，不能由解除 Chat 锁冒充实现。

自查修复：澄清只由显式操作提交；已取消轮次的迟到工具状态被 responseId 隔离；停止回复不宣称撤销已完成动作；口语约束不会泄漏到下一文字轮次。

## 阶段 4：测量与验证

已完成的工程验证：

- 主仓库全量：1059 个测试文件通过，5926 项测试通过；1 项付费语音测试跳过。
- Web 生产构建、Node 构建、核心/Web 类型检查和相关 lint 通过。
- Chrome 使用真实 React 组件、浏览器模拟麦克风、隔离假网关，验证一键通话、停止不提交、静音、设置往返、明确澄清、390px 布局、听写取消/完成/润色。此测试不使用真实服务账户。
- 新增 `session.metric`，采集客户端收到首音频的延迟及本地停止耗时，日志标明来源，单通话去重并限量。已有服务端 ready、首文字、首音频指标保留。
- 本地停止测的是播放器取消调用耗时；首音频测的是客户端收到音频，不包含物理扬声器、回声消除或真实语音终点检测，不能拿它替代端到端声学延迟。

重跑浏览器检查：`node scripts/voice-browser-smoke.mjs`。默认使用 macOS Chrome，可用 `XOPC_VOICE_SMOKE_BROWSER` 指定 Chromium 路径。脚本启动独立 Vite、创建并清理临时入口、拦截测试 API 和 WebSocket；截图输出在系统临时目录的 xopc-voice-production 文件中。

真实音频验收仍需实际设备和服务采样：

| 条件 | 操作 | 记录 |
| --- | --- | --- |
| 内置麦克风 + 外放 | 短问答、自我修正、长停顿、背景电视 | 误打断、抢话、回声、漏识别 |
| 有线/蓝牙耳机 | 连续问答，切换系统输出设备 | 声音路由、首次播放、设备中断恢复 |
| 两种引擎 | 各 20 分钟、30 轮、10 次打断、5 次静音、页面往返 | 同一 Chat、是否异常挂断、重复请求 |
| 弱网/断网 | 回复中断网、重连后继续 | 不重放旧音频、不重复执行工具 |
| 工具/审批 | 查询、长任务、批准/拒绝、等待时说“嗯” | 授权边界、状态正确性、已完成动作记录 |

采样后再比较 P50/P95 和调整默认判停参数。目前保留标准 700ms，不依据模拟测试宣称声学调优完成。

## 托管语音的同步交付

跨仓库检查确认旧平台转发层会拒绝 `input_audio_buffer.clear`。已在相邻 `xopc-platform` 的 `apps/model-gateway/src/omni-relay.ts` 放行这个无参数事件，保留白名单和字段清洗；新增真实本地 WebSocket 转发/回复计费回归。平台相关 7 项测试和类型检查通过。

上线顺序：先更新平台 model-gateway，再更新 XOPC 网关及 Web。此轮只完成本地代码与构建验证，未发布或重启你的服务。

原生清空事件依据 [阿里云 Qwen-Omni 客户端协议](https://www.alibabacloud.com/help/en/model-studio/client-events)；真实云端对清空、快速打断及账单的表现仍属于上述服务验收。

## 自有 API Key 直连上传修复

用户反馈自有 Key 的原生通话出现 `Omni upload backpressure`，切换 Cloud 正常。代码确认原实现持续调用 WebSocket send，超过 512 KB 即关闭通话；现有日志无法判断直连网络堵塞的具体原因。

上传改为每次等待一次写入完成，排队和在途 PCM 总量限制为 65,536 字节。短暂阻塞保留顺序；超过上限时清除该段输入并提示重说，等待清空确认后继续同一通话；连续十秒无法完成写入才报告 `OMNI_UPLOAD_TIMEOUT`。静音、停止和挂断同时清理排队输入，避免网络恢复后误发旧内容。新增日志只包含服务商、端点主机和积压量。

Groq 警告来自配置保存时对未安装扩展的状态探测，与原生通话链路无关。移除 Web 默认写入的 Groq/本地 CLI 扩展配置，未安装扩展的状态探测返回不可用；显式执行无效服务仍保留故障日志。

本地 WebSocket 回归覆盖短暂阻塞、顺序、输入丢弃与恢复、静音清理、写入超时和异步错误。本轮 32 个测试文件、191 项测试通过，1 项付费实测跳过；核心/Web 类型检查、相关 lint 和 Node/Web 构建通过。尚未使用用户自有 Key 验证真实直连质量，也未修改用户当前 Cloud 配置或重启网关。
