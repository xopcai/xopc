# 语音体验打磨方案

日期：2026-09-05。状态：产品与技术设计提案；交互原型为本地模拟，本轮未修改生产交互或接入新语音服务。

## 1. 产品决策

用户只需要理解两个动作：**语音输入**和**语音通话**。

- 语音输入：把说的话变成可编辑草稿，完成后由用户发送。
- 语音通话：直接和当前助手交流，同一 Chat 的上下文持续有效。
- 现有“语音助手 / 自然对话”属于实现与能力差异，退出日常操作入口。
- 默认保留当前助手的办事能力。自然语音独立引擎仍可在设置中选择，明确标注目前不支持工具；不能隐藏能力缩水。
- 服务、凭据、模型、独立端点统一放进设置。通话失败显示原因与下一步，不出现另一份配置表单。
- 保留两种内部引擎是因为能力确实不同；不为了界面统一强行重写成熟路径，也不加入运行中猜意图、偷偷换引擎的路由器。

默认定位暂按 XOPC 的个人助手定位制定；用户若明确偏向陪聊，可调整默认配置，不影响两个入口和同一会话的整体设计。

## 2. 现状审计：复杂发生在哪里

以下依据当前工作区代码与用户反馈；此前已完成的修复不重复列为待开发。

| 层面 | 当前实现 / 已观察问题 | 对用户的影响 | 处理方向 |
| --- | --- | --- | --- |
| 概念 | Dictation、Agent conversation、Omni conversation 三个概念 | 用户先判断自己需要哪条技术路径 | 外部两个动作，内部保留真实能力差异 |
| 启动 | 打开通话窗口 → 选择模式 → 再点开始 | 点通话没有直接开始 | 配置完成后一次点击发起；首次只处理权限或必要设置 |
| 配置 | 通话窗口有服务和 API Key 表单；设置页也有 | 修改入口重复、状态不透明 | 删除通话内配置写入，转向唯一设置页 |
| 模式记忆 | 模式仅为 Provider 内存状态，初始 Agent | 刷新后选择消失 | 网关保存默认通话方案；连接建立后冻结本次选项 |
| 聊天方式 | Agent 路径直接接普通文字 Agent，逐段交给 TTS | “嗯”可能触发长篇回复，Markdown 暴露在字幕中 | 独立的口语呈现约束、短回复、适合听的内容 |
| 判停 | STT final 的非空文本直接排队；自动打断只看语音事件 | 停顿、附和、噪声与真正请求混在一起 | 明确轮次策略，真实音频验证，不堆关键词补丁 |
| 状态 | 通话只呈现听、想、说；工具事件缺少专门映射 | 查资料、等待确认看起来像卡住 | 从真实任务事件映射“正在查询 / 等待确认 / 已完成” |
| 控制 | 静音、方形停止、挂断并列；停止的影响不够可见 | 用户难以预测按钮结果 | 固定三个语义：麦克风、停止回复、挂断；状态反馈明确 |
| 设置分组 | 基础卡片、自然对话高级、朗读、高级 STT；音色可重复设置 | 依然按管线组织，修改关联不直观 | 按“体验 → 设备 → 服务 → 排查”组织 |
| 诊断 | 主要验证 STT / TTS，Omni 不在同一就绪状态中 | “语音可用”不代表所选通话方案可用 | 按用户能力显示检查结果，再展开技术原因 |
| 润色 | 设置存在；实时听写 hook 直接回填，未经过 refine 接口 | 配了但当前入口未生效 | 接通该设置或移除该入口的承诺；禁止继续留下无效选项 |
| 连续性 | 已有全局通话 Provider、同一 Chat、转写持久化 | 方向正确 | 保留；不恢复通话列表和每次新建 Chat |

代码定位：

- `web/src/features/chat/composer/composer-toolbar.tsx`：听写与通话入口。
- `web/src/features/voice/realtime/voice-call-provider.tsx`：二次启动、模式选择、字幕与控制。
- `web/src/features/voice/realtime/voice-call-setup.tsx`：通话内重复配置。
- `web/src/features/settings/voice-settings.tsx`、`voice-setup.tsx`、`omni-voice-settings.tsx`：当前设置组织。
- `web/src/features/voice/realtime/use-realtime-voice.ts`：权限、音频、听写回填、状态。
- `src/voice/realtime/agentEngine.ts`：识别结果排队、普通 Agent 回复、TTS。
- `src/gateway/service.ts`：通话调用 Agent 时仅传取消信号，尚无独立口语呈现契约。
- `src/voice/realtime/conversation-context.ts`：原生语音已有简洁对话指令与有界历史。

前序已经修复：通话跨页面存活、同一 Chat 续聊、静音停止上传、积压播放中断不结束通话、取消清理与转写等待、手动停止清除旧输入队列、删除重复通话列表。新设计应保留这些回归检查。

## 3. 参考产品：借鉴交互，区分公开事实与推导

调研时间为 2026-09-05，依据官方网页，未登录逐端体验所有客户端。不能据此声称各版本的按钮布局完全一致，也不把厂商公布的性能当作 XOPC 实测结果。

### Codex / OpenAI 桌面语音

原 Codex 文档入口目前重定向到 OpenAI 的 ChatGPT 桌面文档。官方明确区分：听写先产生待发送文本；实时语音用于讨论和协调工作，并可承接既有任务上下文。文档也描述了通话中检查进度、改变方向的能力。来源：[官方语音说明](https://learn.chatgpt.com/docs/features/voice)。

借鉴：语音是一种操作当前助手的方式。用户不必先把工作改造成新的语音会话；办事进度也应能通过语音获知。

### 豆包

豆包官方功能介绍列出语音输入、自然声音和对话打断。Seed 的全双工研究介绍进一步强调判停、抗干扰、倾听与回复节奏。来源：[豆包功能介绍](https://www.doubao.com/legal/feature_intro)、[Seed 全双工语音介绍](https://seed.bytedance.com/zh/blog/introducing-seed-full-duplex-speech-llm-attentive-listening-robust-interference-suppression-enabling-more-natural-interaction)。

借鉴：停顿、附和、背景说话不应一律变成新请求。自然感首先来自轮次与语气，而不是波形动画。不能把调整静音阈值当作已经实现原生全双工理解。

### Grok

官方产品页强调自然语音交流；语音模型说明特别强调短句、一次一个问题，以及工具调用与交流的结合。消费产品体验与开发者 API 能力需分开评估。来源：[Grok 产品页](https://x.ai/grok)、[语音模型对话能力说明](https://x.ai/news/grok-voice-think-fast-2)。

借鉴：短而有用地说话，让执行复杂度留在后台。可选择音色和表达偏好，但不必把复杂人设、视觉、克隆等能力同时塞进首版通话。

## 4. 新的日常交互

### 4.1 输入框

保留麦克风和通话两个可区分入口，桌面有标签提示，移动端保证可点击面积。名称统一为“语音输入”“语音通话”；不再把录音过程命名成独立“录制”产品。

语音输入流程：

1. 点麦克风，显示正在听写、输入反馈和“取消 / 完成”。
2. 中间识别结果只作为当前听写预览。
3. 点完成：结束收音，合并完整听写，按设置处理标点，插入原光标位置。
4. 用户可改字、补文件，手动点发送。
5. 点取消：撤销这次听写，不影响进入前的草稿。服务中断时保留可恢复文本，不自动发送。

当前实现会逐条 final 回填草稿；要实现以上“取消整次听写”语义，需要暂存听写片段。不能只改按钮文字。

### 4.2 通话入口

已配置且权限允许：点通话 → 连接 → 可以说话，去掉模式选择和第二次开始按钮。浏览器权限提示由系统处理，连接过程中可以取消。

未配置：显示“先设置语音服务”及“前往设置”。带回当前 Chat 的返回位置；保存后返回原 Chat，用户点击开始。不能在用户仅保存配置时偷偷打开麦克风。

已有通话：同一 Chat 的入口展开当前通话；其他 Chat 的入口显示“返回当前通话”。不悄悄切换上下文。

### 4.3 通话界面

采用紧凑通话面板，避免当前大弹窗把聊天内容完全盖住。桌面可最小化，移动端使用固定结构的面板；详细文字在 Chat，通话内最多显示最近一轮、适合阅读的字幕。

- 顶部：助手名称、当前状态、最小化。
- 中部：听说反馈和当前字幕；工具任务或确认出现时提供具体状态。
- 底部常用动作：麦克风开关、条件出现的“停止回复”、挂断。
- 字幕设置移入“更多”；首次显示字幕，记住个人偏好。
- 音色、默认方案、模型、服务配置不进入通话主界面。
- 麦克风关闭与助手仍在说话可以同时显示，不用“麦克风关闭”覆盖全部状态。

### 4.4 控制语义

| 操作 | 收音 | 当前回复 | 未处理输入 / 任务 | 会话 |
| --- | --- | --- | --- | --- |
| 完成听写 | 关闭 | 不产生回复 | 形成草稿，不发送 | 原 Chat |
| 取消听写 | 关闭 | 不产生回复 | 撤销本次临时听写 | 原草稿保留 |
| 关闭麦克风 | 停止上传真实采样 | 可继续播放 | 默认不提交未完成的新一句；先前已提交的轮次可完成 | 通话保持 |
| 停止回复 | 保持当前麦克风状态 | 停止生成与播放 | 丢弃停止前未执行输入；取消属于当前回复且可取消的工作 | 通话保持 |
| 自动打断 | 保持 | 让出话权 | 保留触发打断的有效新输入 | 通话保持 |
| 挂断 | 释放 | 停止 | 等待清理与持久化；独立后台任务需另有明确状态 | 原 Chat 保存 |
| 最小化 / 切页 | 不变 | 不变 | 不变 | 不变 |
| 断线 | 停止上传 | 停止 | 不重放可能已提交的请求 | 显示“重新连接” |

注意：当前静音为完成 VAD 会发送一小段合成静音，可能使未完成语音得到 final。若采用上表“静音不提交未完成输入”的契约，必须增加明确输入取消边界并覆盖两条引擎，不能只关闭本地音轨。停止不能撤销已完成的外部动作；状态需如实说明。

## 5. 设置的信息架构

统一入口：设置 → 语音。一个页面、一个配置写入路径；日常偏好先于服务细节。UI 重组不等于立即把所有历史存储字段迁移进新命名空间。

| 分组 | 默认展示 | 折叠或按需展示 | 作用域 |
| --- | --- | --- | --- |
| 说话与聆听 | 音色、试听、语言、自然插话 | 回应节奏：快 / 标准 / 从容 | 音色/行为为网关偏好；连接开始时冻结 |
| 输入与显示 | 听写标点、字幕偏好 | 快捷键（支持的客户端）、听写高级处理 | 显示与快捷键按设备；文本处理为网关配置 |
| 音频设备 | 麦克风、输入测试、输出测试 | 支持时选择扬声器，默认跟随系统 | 当前设备，不把设备 ID 同步到其他机器 |
| 语音服务 | 使用 XOPC / 自有服务、连接状态 | 凭据、默认通话方案、模型和独立覆盖 | 网关配置；授权继承现有账户体系 |
| 排查问题 | 检查语音 | 听写 / 通话 / 朗读的详细结果、错误编号、诊断日志 | 一次检查结果，不增加常驻开关 |

语音服务中的默认方案说明：

- 当前助手：沿用当前 Chat 的模型与工具能力；先作为默认。
- 原生语音：更直接的音频对话；当前 XOPC 适配不执行工具。缺失能力直接标注，不宣称两者完全等价。
- 常规消息朗读为独立使用场景，归入“输入与显示”的“消息朗读”折叠项，避免和通话音色绑定。通话播放期间抑制重复朗读。

配置规则：

1. 基础服务只填一份凭据。独立覆盖必须默认折叠，并显示当前是否继承。
2. 默认方案必须有持久化字段，不能用“哪个服务配置了”猜用户偏好。
3. UI 就绪状态按听写、所选通话方案、消息朗读分别计算；原生通话不能依赖无关 STT 就绪结果。
4. 服务选择不自动覆盖用户明确设定的音色或账户；切换服务时只清除不兼容的覆盖。
5. 只显示已实现且当前路由可用的控制项。速度、设备选择和润色尚未打通时，不做可点击但无效的设置。
6. 现有配置 API 是唯一持久化入口。显示偏好可以本地保存；服务配置不额外复制一份到前端 store。
7. 对连接、权限、余额、服务缺失分别给出恢复动作。用户页显示短原因；端点、状态码等进入诊断详情。

## 6. 能力打磨的核心

### 6.1 先让助手说得像在交流

默认先回答重点，一次一到三句；需要长说明时先给概览，用户要求后继续。闲聊不列清单、不复述一串旧任务、不每句都追问。涉及办事时，简短告诉用户正在做什么，完成后说结果；长文、代码、来源留在 Chat。

Agent 先复用现有运行链，增加显式的语音呈现上下文，不把通话指令写成用户消息，也不改全局 Agent 性格。音频内容的实际播报与 Chat 详细内容需要对应：长期可使用结构化的口语摘要与正文；首期先做好短回复和 Markdown/链接的播报处理，不额外串联一个总结模型增加延迟。

### 6.2 轮次管理优先于新音色

不能把任何非空识别结果都立即当作请求，也不能把“嗯”“好”永远丢掉：它们可能是附和，也可能是明确回答。应结合是否有待回答问题、是否正在播报、是否包含新意图来判断；需要依赖声学/语义能力的部分要实测，不能伪装为前端已解决。

第一步建立输入事件、完成轮次、回复取消的明确边界，默认停止积压输入；第二步用真实音频集评估快 / 标准 / 从容三档；第三步比较具有语义判停/全双工能力的服务。长时间无言允许安静，不循环问“还在吗”。

### 6.3 让办事过程可交流

当前 Agent 引擎可调用工具，但通话呈现没有相应的工具与审批状态。先把现有任务事件映射为“正在查路线”“等待你的确认”等，不把所有状态统称为思考。

- 短任务在当前轮次完成，先一句行动说明，随后结果。
- 审批出现在同一可见通话区域，复用现有授权机制，不能把环境里一个“嗯”自动等同于批准。
- 长任务后续接入现有任务体系：用户继续说话可查进度、补条件。需要明确任务标识、状态订阅、取消边界，不能仅解除 Chat 锁就宣称支持并发。
- 当前 native 适配没有工具通道；后续若要同一自然语音流内办事，需要工具桥接与可验证的动作结果。建立同一入口并不能自动获得该能力。

### 6.4 持续会话与恢复

同一 Chat 是唯一持久对话。连接 ID、回复 ID、任务 ID 各自服务其生命周期。重连加载规范化上下文，保持助手身份，不重复欢迎和执行旧指令。

短暂抖动可以展示“连接中”并限制等待；真正断线后释放采集并显示明确重连动作。自动续连仅在未来有不重复输入、上游恢复能力和用户预期保障时考虑。禁止音频盲重放。

### 6.5 多模态放在基本体验之后

看当前页面、共享屏幕、拍照交流对工作场景有价值，但增加权限和媒体链路。先把语音稳定性、任务反馈、设备路由打磨好；之后在通话“更多”中按客户端能力加入。暂不添加音色克隆、人设商城、通话历史等额外产品层。

## 7. 技术演进与删除清单

保留现有全局 Provider、统一采集 hook、Agent/Omni 引擎和 SQLite 会话。按需要扩展能力，不引入一套新的 Session 系统或通用配置平台。

| 阶段 | 交付 | 删除 / 收敛 | 自我 review 与验收 |
| --- | --- | --- | --- |
| 1. 入口和设置 | 两个入口命名；一键通话；默认方案持久化；设置分组；缺配置引导 | 通话模式选择器、二次开始页、VoiceCallSetup 配置写入及孤立文案 | 同一 Chat、初次权限、设置往返、设备范围、缺服务的明确提示 |
| 2. 输入和控制 | 听写临时稿；完成/取消清晰；麦克风、停止、挂断的完整取消边界；错误恢复 | 即时 final 回填造成的不可撤销听写；多处重叠状态来源 | 正在判停时静音、停止后迟到 final、快速连点、断网、切页 |
| 3. 口语与办事 | 口语呈现约束；自然字幕；工具与审批状态；长任务协调的最小实现 | 普通文字无差别逐段播报；吞掉工具状态的映射 | 长文/代码/查询/需要确认的操作，确认前不执行，停止不宣称回滚 |
| 4. 音频质量 | 延迟测量、真机音频矩阵、服务对比与默认轮次调优 | 无效设置和仅通过 mock 才成立的默认值 | 内置麦克风/耳机/外放/弱网的完整真实通话 |

每阶段先完成最小闭环，自我 review 并修复，再进入下一阶段。删除依据调用图和测试确认的无用代码；已经存在的持久数据保留正确过滤，不为“无 legacy”破坏用户会话。

## 8. 质量门槛与测量

下面是建议目标，不是当前测量结果。正式上线前应先采集基线，再按设备、网络、引擎分别统计。

| 指标 | 建议门槛 / 观察方式 |
| --- | --- |
| 日常启动 | 已配置且已授权后一个动作开始通话；无模式选择 |
| 本地停止响应 | 点击停止到本地静音 P95 < 150 ms |
| 首句延迟 | 从有效语音结束到首个可听音频，普通短问答目标 P50 < 1.2 s、P95 < 2.5 s；工具耗时另计 |
| 停止正确性 | 回归集中停止前排队内容不触发新请求；新输入仍可响应 |
| 误打断 / 抢话 | 单独标注停顿、附和、噪声样本；记录误中断率、漏打断率及用户评分，不只看 ASR 字准确率 |
| 持续性 | 连续 20 分钟、至少 30 轮、10 次打断、5 次静音、页面往返，不产生新 Chat 或异常结束 |
| 听写 | 完成不发送；取消不污染原稿；标点设置实际生效；中断不丢可恢复文本 |
| 任务边界 | 一条请求只执行一次；确认/取消状态可见；迟到工具结果不覆盖新轮次 |
| 配置 | 默认用户只需选服务或登录一次；诊断结果与当前使用路径一致 |

最小样本集：中文短问答、长停顿、句中自我修正、数字/英文混说、附和“嗯”、回答“好”、背景电视、外放回声、耳机切换、模型正在查工具、审批等待、断线重连。自动化测试覆盖状态与竞态；真实麦克风评测决定自然度、回声与延迟是否达标。
