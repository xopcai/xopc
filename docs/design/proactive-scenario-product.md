# xopc 主动性：场景优先产品方案

日期：2026-09-15。状态：首发产品结构已实现。本文取代以“交给我的事”列表为中心的主动性产品结构；既有事件、调度、判断、卡片和权限能力继续作为内部基础设施。

已实现的首发闭环包括：工作台按项目、会议和沟通时刻呈现场景；项目入口原地建立安排；提醒方式和行动边界按安排控制；结果卡片支持采用、编辑、纠正和继续对话；对话在一次帮助成功后询问是否形成长期习惯。自动从大量历史行为发现场景仍需真实使用数据，不在首发中预设推断规则。

## 结论

主动性不是一个需要用户管理的对象，也不是一个单独的工作区。它是助理在**特定情境到来时，理解此刻对用户意味着什么，并完成最合适的一小段工作**。

产品基本单位从“委托”改为“场景”：

> 当某个时刻到来，基于用户和当下工作的上下文，助理判断是否值得介入；若值得，就先完成安全且有用的工作，再通过最自然的界面交付，并从用户反应中调整下一次行为。

用户感知到的是“它在这个时刻懂我、帮到了我”，不会感知订阅、扫描、运行、卡片类型或状态机。

## 为什么现有方案仍偏工程化

当前方案已经隐藏了一部分技术词，但产品骨架仍然来自后台模型：

1. 让用户先进入「交给我的事」，再理解进行中、暂停和结束；这是订阅管理器的映射。
2. 新建入口先收集目标，再落到固定 `scenarioKey`；自然语言只是表单前置层，没有真正理解场景。
3. 每项都展示当前状态、下一次核对和最近运行；这些信息适合诊断，不是日常价值。
4. “项目交付、会议准备、邮件跟进”被做成同一种列表项，但它们发生的时刻、上下文、交付形态和用户动作完全不同。
5. 全局主动程度试图控制所有场景。用户实际会接受“会前主动准备”，同时拒绝“每个项目变化都提醒”，主动性应按场景学习。
6. 工作台承担汇总，助理工作区承担管理，但真正发生工作的项目、会议、邮件和对话没有成为主要入口。

这套结构技术上可控，却要求用户先理解系统如何运行，再获得帮助。产品应反过来：先让帮助自然发生，只在用户想调整时显露控制。

## 竞品给出的关键判断

### Muse：目标持续推进，但价值在具体时刻交付

Muse 以对话接受任务和目标，随后按时间或相关事件继续工作；后台工作完成后再次判断是否值得打断用户。它保留 Goals 视图用于解释计划和进度，但主要体验仍是对话、主动消息和针对任务生成的成果，而不是运行列表。其 Ideas 也来自目标、模式和长期对话，而非固定模板目录。

对 xopc 的启发：长期目标可以作为上下文，但主动出现必须由具体时刻和可交付成果驱动。目标页负责信任与追踪，不应成为主动性的首页。

### Town：把“发生了什么”和“要不要我处理”拆成两个场景结果

Town 首页将 Need to Know 与 Suggestions 分开：前者只说明值得知道的变化，后者提出可以代办的具体动作；建议开始后才成为任务。Routines 面向重复劳动，用户用自然语言描述，先试跑、看结果、再调整。每个 Routine 可以有不同的信任程度。

对 xopc 的启发：主动性至少有“告知”和“代办提议”两种不同关系，不能都塞进一种消息卡。重复场景应从一次成功帮助中升级，而不是让用户先配置自动化。

### Instinct：主动性嵌在生活和工作原有界面中

Instinct 强调没有新的交互界面，通过短信、电话、电脑和手机参与用户本来的生活，并以“跟进被遗忘的对话”为典型能力。

对 xopc 的启发：主动性应出现在用户原本处理该事情的地方。工作台是兜底入口，消息渠道是触达方式，项目、会议、邮件和对话才是场景的归属。

## 场景模型

一个可发布的场景必须同时定义七件事：

| 场景要素 | 产品问题 | 示例：会前准备 |
|---|---|---|
| 时刻 | 什么情况到来？ | 明天有一场重要会议 |
| 意义 | 为什么与这个用户相关？ | 对方是客户，会议关联当前交付风险 |
| 上下文 | 此刻必须理解什么？ | 参会人、历史沟通、项目状态、未决问题 |
| 判断 | 什么情况值得出现？ | 有遗漏材料、承诺冲突或需要决定的问题 |
| 帮助 | 助理先做什么？ | 整理一页简报和三个建议议题 |
| 触达 | 在哪里、何时交付？ | 会前一天进工作台；两小时前仍未查看才提醒 |
| 学习 | 用户反应如何改变下次？ | “技术细节少一点”只更新会前准备偏好 |

内部实现可以继续使用事件、计划任务、订阅和运行记录，但必须编译自场景定义。任何只有触发器和 Prompt、没有用户时刻与交付承诺的配置，都不算产品场景。

## 产品结构

### 1. 工作台是“此刻的助理”，不是主动消息收件箱

工作台按生活和工作时刻组织，不按卡片类型组织。例如：

- **开始今天**：今天最重要的三个安排、必须回复的人、可能影响目标的变化。
- **下场会议**：已经准备好的简报、还缺的一项材料、一个需要确认的问题。
- **正在推进**：一个项目阻塞和助理已经准备的解决建议。
- **等人回复**：哪些承诺到了该跟进的时间，草稿是否已经准备好。

同一时刻只呈现一个完整场景块。场景块可以包含信息、成果和动作，不再把它拆成“需要决定、已准备、值得知道”三张互相独立的卡。

### 2. 场景入口长在对象旁边

- 项目详情出现「让助理帮我守住这个目标」，并直接说明它会关注什么、何时出现、先做到哪里。
- 会议详情出现「以后重要会议都这样准备」，它来自用户使用过一次会前简报之后。
- 邮件或对话出现「如果两天没回复，帮我继续跟进」，范围天然是当前线程。
- 对话里用户说“以后每周五都这样”，系统把一次成功工作提升为可重复场景。

不存在面向普通用户的场景模板市场。推荐来自当前上下文，例如打开项目时推荐项目场景，而不是跳转到通用模板选择页。

### 3. 「交给我的事」降级为助理记住的安排

它不再是主导航中的主动性首页，而是一个二级的“助理安排”页面，用于回答：

- 助理长期记住了哪些目标和习惯；
- 哪些场景会自动发生；
- 哪些外部动作仍需要确认；
- 如何暂停某个场景或全部提醒。

默认展示自然语言承诺，例如：“重要会议前一天准备一页简报；如果两小时前仍有关键缺口，再提醒我。”高级诊断和运行历史进入日志，不作为产品内容。

### 4. 对话是创建与纠偏方式

用户通过对话建立新场景，助理需要复述四件事：

1. 在什么情况下开始；
2. 会使用哪些上下文；
3. 会先完成什么；
4. 什么情况才会打断用户。

助理先展示一次示例结果。用户接受后才保存为重复场景。对一次性请求，不制造长期场景。

## 首发场景

首发只做三个完整场景，每个场景都必须从触发到真实成果闭环。

### 场景一：会前不再临时抱佛脚

**时刻**：24 小时内有一场重要会议。

助理结合日历、参会人、相关邮件、项目和上次会议记录，准备一页简报：会议目的、最近变化、未兑现承诺、建议议题和需要用户决定的问题。普通会议保持安静；缺少材料或两小时内仍有关键风险时才提醒。

首次入口放在日历连接完成后和会议详情。用户看过简报后询问：“以后和客户的会都这样准备吗？”由用户确认范围。

### 场景二：项目偏离目标前先准备解决办法

**时刻**：里程碑临近，并出现阻塞、负责人缺失、承诺冲突或连续无进展。

助理先判断该变化是否会影响用户关心的目标，然后准备影响说明、证据和最小解决方案。只有需要用户选择方向、调整承诺或联系他人时才打断。普通状态变化只更新项目内的助理摘要。

首次入口放在项目详情。默认承诺是“守住某个里程碑或结果”，不是“扫描项目”。

### 场景三：重要对话不再掉地上

**时刻**：用户发出需要结果的消息后，在约定时间内没有得到有效回复，或对方回复带来新的承诺和问题。

助理理解当前线程的目标，区分“已回复”和“问题已解决”。到时先准备符合用户语气的跟进草稿；涉及发送时等待确认。用户在邮件或聊天线程里一句“这件事帮我跟到底”即可建立。

## 卡片与触达

不建立一种通用万能卡。每个场景拥有自己的最小呈现：

- 会前简报是可快速浏览的一页内容；
- 项目风险是“变化—影响—已准备方案—需要决定”的决策面板；
- 沟通跟进是带上下文的草稿审阅；
- 每日开场是跨来源的短摘要。

通知只表达“为什么现在值得打开”，点击后进入场景所在的项目、会议或对话，不跳到统一列表。工作台保留同一场景的当前投影，处理后自然退出。

## 主动程度改为渐进信任

取消一个全局的“主动程度”作为主要控制。用户需要控制两个互相独立的维度：

1. **什么时候出现**：只进工作台、重要时提醒、每次有实质进展都提醒。
2. **可以做到哪里**：只观察、先准备再确认、对明确的低风险动作自动完成。

默认按场景保存。系统根据重复行为建议升级，例如用户连续五次原样发送会前邀请，可以建议“以后这类邀请是否直接发出”；系统不能自行扩大权限。

## 技术边界

保留现有可靠性基础：事件主干、时间触发、上下文授权、幂等执行、判断阈值、卡片持久化、推送一致性和审计记录。

产品层新增一个薄的 `SceneDefinition`，只描述：

```ts
type SceneDefinition = {
  moment: MomentMatcher;
  relevance: RelevancePolicy;
  contextRecipe: ContextRequirement[];
  promise: UserFacingPromise;
  outcome: OutcomeRenderer;
  interruption: InterruptionPolicy;
  learningScope: string;
};
```

现有 `scenarioKey` 可以暂时作为内部实现键，但不能继续决定页面结构。页面消费“当前场景结果”，不消费运行、订阅和模板 DTO。场景结果至少包含：场景归属、当前时刻、为何与用户相关、已完成的帮助、下一动作、是否需要用户，以及返回原始工作对象的路由。

## 分阶段调整

### 第一阶段：把产品重心从列表移到三个场景

- 保留后台管线，停止扩展通用委托管理 UI。
- 工作台改为场景块，合并同一场景的信息、成果与决定。
- 项目和邮件入口原地建立场景；会前准备补充原地入口。
- `/assistant-work` 从主入口降级为“助理安排”，移入更多或设置。

### 第二阶段：一次帮助升级为重复场景

- 对一次成功的会前准备、项目分析或跟进草稿提供“以后都这样”入口。
- 通过对话确认时刻、范围、触达和权限。
- 提供一次试跑结果，用户接受后保存。

### 第三阶段：场景级学习与建议

- 将用户编辑、忽略、采用和主动纠偏记录到对应场景。
- 从重复行为中提出新场景建议，但接受前不后台运行。
- 用实际采用率和打扰后行为调整场景触达阈值。

## 验收指标

不以订阅数、运行数或卡片数衡量主动性。首发关注：

- 场景触发后产生可用成果的比例；
- 用户直接采用或轻改后采用成果的比例；
- 主动出现后带来决定或行动的比例；
- 被忽略、收起或要求减少的比例；
- 从一次帮助升级为重复场景的比例；
- 重要事情被提前发现的时间；
- 每个场景从首次使用到形成信任的次数。

产品成立的判断是：用户会说“它知道什么时候该帮我，而且已经先做了一步”，而不是“我配置了一个主动任务”。
