# Web 麦克风连续保存时长修复（2026-10-16）

## 问题与结果

真实麦克风样本中，Opus 帧累计到 2940 ms 时，WebM 时间戳为 2939 ms；之后在累计 20040 ms 时，时间戳又回到 20040 ms。旧实现逐包比较“本包时间戳是否等于上包结束时间”，第一次提前便永久标为 gap，回归帧时钟也被误判为跳时。

同一原音的连续保存范围从 **2940 ms 修复为 55320 ms**，与 ffmpeg 解码得到的 55320 ms 一致。使用 1、7、4093 字节和完整文件四种切分重放，结果一致；没有重写音频，没有上传供应商。见 [真实样本重放结果](technical/note-web-microphone-timing-replay-2026-10-16.json)。

## 判断规则

- 用完整 Opus 包所代表的累计采样时长作为整段基准，不以 UI 计时、回调时间、分片长度或上一包的已量化结束时间作为连续性基准。
- 只接受时间戳相对累计帧时钟**提前至多一个 WebM tick，且最多 1 ms**；不接受正向容差。量化误差不会在每个包或分片重置、累积。
- 已确认保存范围取累计采样时长和实际媒体结束位置中的较小值，不把未来帧、未完成的包或尚未落盘的数据算入。
- 正向跳时、缺包、超界偏移和非单调时间戳仍冻结连续前缀；之后时间戳回归也不抹除已经确认的缺口。两个录音段仍分别校验，不跨越中断续录的边界。
- 这些证据证明已编码音频的连续范围。麦克风不可用、页面冻结等真实采集中断仍由既有异常收尾处理，不用时间戳容差掩盖。

恢复时，对已有 gap 标记的草稿和中断续录的各段原音逐分片重新校验，使旧的低估结果也能修正；实际缺口继续保留。重新校验只更新返回的保存证明，不修改原音、Note 关联、录音 ID 或中断结果，内存只保留当前分片与解析器状态。
