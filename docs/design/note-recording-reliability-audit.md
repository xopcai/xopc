# 笔记录音可靠性审视与演进方案

日期：2026-10-15。范围：当前工作区 Web/Electron、HarmonyOS、iOS、Android，以及 Gateway 的录音保存、转写和分析链路。

这是代码审视与现有自动化测试的结果，不代表已完成移动真机、浏览器后台或两小时连续麦克风采集验收。本文的改进项尚未实现。当前会话未提供 codebase-memory 图工具，因此使用源码搜索与直接阅读。

## 1. 产品判断

服务端已有分片持久化、校验、幂等提交、异步合成、租约恢复、原音补转写，以及带证据的分章分析，具备继续加固的基础。客户端的采集持久化与恢复能力尚未统一，不能把服务端允许两小时理解为所有端都能可靠录两小时。

优先建立明确的产品承诺：原音可恢复；网络、实时文字、AI 整理失败不阻断原音保存；用户能看到已录制、已在本机保存、已在服务端保存的区别。

建议先把两小时做成可验证能力，再扩展到四小时。时长上限增加必须伴随资源预算、故障恢复和真机验收。

## 3. 优先风险

### P0：鸿蒙的本地安全性依赖网络队列吞吐

`flushChunk()` 把 WAV 加到 `pending`，随后通过 `uploadQueue` 调用 `uploadChunk()`。`writeChunk()` 在这个上传任务内部，且同一个任务要完成原音上传和实时转写分片上传。前一项网络阻塞时，后一项音频尚未写入本地文件。待传项同时保留 `wav`，没有有界内存控制。

后果：弱网长录音会持续积压内存；进程退出可能丢失尚未写盘的分片。已写缓存文件也缺少启动扫描、manifest 和读盘恢复入口。`fail()` 释放音频但不主动 flush 末尾缓冲；后续必须靠用户重试停止来处理。

改进：采集→独立本地写入队列→持久 manifest→独立上传队列。上传任务只持有文件路径与少量元数据，原音确认与 STT 确认分别记录。启动扫描恢复会话，保留文件直到服务端确认完整原音。写入失败时保留已确认分片并明确停止原因。

### P0：停止、异常和落盘必须形成闭环

Web `stopOnce()` 先等待 `segmenter.stop()`，之后才调用 `MediaRecorder.stop()`。前者会等待 PCM 捕获停止及待处理 segment 回调，缺少整体超时与统一 finally 清理。持久化错误时停止媒体轨道，但录音 clock 未同步暂停；原音 recorder 已 inactive 时又直接返回当前 draft。异常路径需要专门收敛，避免显示时长、草稿状态与实际音频不一致。

改进：收到停止指令立即停止采集；原音尾片落盘作为独立屏障；实时转写独立收尾并允许超时降级。所有错误分支进入同一幂等收尾流程，完成时钟冻结、尾片处理、状态持久化和资源释放。错误态明确提供“保存已录部分 / 重试同步 / 导出”。

### P0：iOS 录音器的成功状态与长录音能力不可靠

`VoiceNoteFlowView` 复用 `VoiceRecorder`。后者调用 `record()` 后直接设为录音中，未检查返回值，也未在该路径配置录音 AudioSession。其他播放功能会修改全局 AudioSession，存在显示录音中却未成功开始的风险，需补针对性测试与真机复现。

120 秒后自动暂停且 timer 被 invalidate；用户恢复录音不会重建 timer，时长与上限行为也需修复。录制中的临时文件没有关联到可重建的 pending 会话；停止时全量 Data 处理，直接放宽到两小时会放大内存占用。

改进：笔记使用独立的长录音会话；开始前建立持久 session 与音频位置；明确 AudioSession 所有权并核实启动成功；分片文件/流式上传；中断与路由变化留事件记录；重启恢复前缀。系统强制结束后的恢复目标是恢复已保存片段，不承诺继续采集。

### P1：离线启动与后台能力没有形成一致承诺

Web `prepareStart()`、iOS `prepareRecording()` 在采集前获取网关设置；鸿蒙还要求先创建服务端 discussion。已经完成首次确认的用户仍会被服务端不可用阻止录音。

改进：首次确认策略本地持久化；已确认用户先开始本地会话，后台幂等建服务端对象并补传。后台录音支持状态必须可见；鸿蒙后台申请失败显示“仅前台录音”；浏览器休眠/冻结/关闭后的行为按平台验收，不能与原生后台录音等同承诺。

### P1：长录音上传与收尾的工作量随长度放大

Web 每次原音上传都会查询服务端分片并从 0 遍历、读取、计算本地分片 checksum，再跳过已存在项。持续录制且每轮能及时完成时，会重复扫描历史分片，累计工作量可能接近二次增长。上传进度按分片数量计算，也不能说明本机尚未落盘或服务端尚未合成。

改进：持久化分片 checksum、已确认游标与字节数；只排新分片，恢复时对账；有界并发、网络错误退避和连通恢复触发重试。上传、服务端校验、转写、整理分别显示进度。

Gateway 收尾补转写默认按 20 秒分段串行执行，新补齐内容保存在内存列表，所有段完成后才 `replaceTranscriptSegments()`。两小时极端补转写可能约 360 次请求；后部失败后前面新补齐工作没有独立检查点。sealer 同一 tick 先处理合成任务再处理一个 capture，长补转写会推迟其他录音的合成处理。

改进：原音合成与转写独立调度；补转写按音频范围持久化检查点与重试状态；限制并发并可取消。保留已有人工纠错与 revision 检查。分析层已有分章缓存，应继续复用。

### P1：用户看到的安全状态不够准确

Web 错误/停止状态的标题兜底仍可能显示“正在录音”；有些错误文案统一称“本地草稿仍然安全”，但磁盘写入失败时不能这样承诺。恢复入口只展示最新草稿。鸿蒙错误提示容易被展示为转写延迟，无法说明采集是否已停止；标记目前只保存在内存数组中，未看到提交持久化。

改进：用已确认的采集与持久化事实驱动状态文案；恢复列表展示所有会话、时间、可恢复时长与操作。持久保存重点标记，关联音频时间轴。

### P1：Android 产品入口尚未闭环

主 NotesScreen 调用未提供 `onStartVoice`，新建语音记录卡片据此禁用。已有附件录音不具备 discussion 创建、原音分片提交与整理闭环，不能作为完整笔记录音能力对外表述。

改进：接入与其他端一致的 discussion 协议和可恢复本地会话，生命周期独立于 NotesScreen。后台能力、时长与进程重启恢复单独验收。

## 4. 产品交互目标

1. 开始：点击即开始本机采集；权限/首次确认除外。网关离线时显示“离线录音，联网后同步”。显示输入电平与输入设备，区分环境安静、设备不可用、采集回调停止。
2. 录制：持续显示计时、暂停/继续、结束、重点标记。可展开“本机已保存至 42:10；服务端已保存至 41:55”。不要求用户盯着实时转写判断是否录成功。
3. 后台或中断：状态说明“录音已中断，已保存至 42:10”，提供继续或结束；将中断时段保留为缺口。暂停时长不算有效录音时长。
4. 结束：先明确“录音已在本机保存”，可离开页面；后台显示同步、转写、整理的独立状态。同步失败保留重试和导出；AI 失败仍能播放原音。
5. Note：随时访问原音与已有文字；分析结果引用可回放的时间段；缺口和未转写区间可见，不把缺失内容伪装成完整分析。
6. 恢复：启动主动发现未结束会话；只在确实具备原音或完整服务端文件时标记可恢复。支持恢复已录部分、补传、导出和明确确认后的丢弃。

建议把采集状态、原音持久化状态、同步状态、转写状态、分析状态分开存储和展示，避免一个 `error` 同时代表麦克风故障与 AI 整理失败。

## 5. 演进顺序与验收门槛

### 第一批：原音安全与状态真实性

- 鸿蒙本地写入与网络分离、manifest 与重启恢复；尾片统一收尾。
- Web 停止独立于实时转写，异常态统一收尾，真实保存状态与错误操作。
- iOS 核实录音启动成功、独立笔记会话、录制中恢复索引与流式文件处理；之后调整时长。
- 所有端完成首次确认后可以离线采集；不依赖 AI/STT 可用。

验收：断网 30 分钟不会导致采集堆积在内存；在任意分片写入/确认步骤强杀后，重启能找回已持久化连续前缀；停止不依赖 STT 请求完成；低存储时准确报告已保存范围。普通进程终止的拟定尾部损失目标不超过一个 3–5 秒分片加写入延迟，须通过实测确认。

### 第二批：两小时作为正式能力

- Web 增量上传、服务端合成与补转写分离、补转写检查点。
- iOS、HarmonyOS 后台/锁屏/蓝牙/电话中断验收；Android 接通完整闭环。
- 在安全前缀/恢复机制成立后，完善本地原音导出和恢复列表。

验收矩阵：15/60/120 分钟；持续说话与长静音；离线启动；中途断网再恢复；锁屏/切后台；蓝牙拔插；电话/语音通话抢占；存储将满与写入失败；进程终止/重启；网关重启；上传确认丢失；停止时断网；STT 限流/超时；AI 失败。

每个案例核对：原音可解码且时长与预期一致；可恢复前缀连续；时间轴无未说明的丢段/重叠；重复提交不重复建 Note；已确认部分不重做；资源释放；内存不随录音总时长线性增长。合成音频测试补充真实人声，才能检查转写、时间轴与后续分析质量。

### 第三批：扩时与分析质量

在两小时通过上述矩阵后，评估四小时上限与存储预算；补充说话人跨段一致性、全文检索、章节、重点标记和分析证据回放。四小时 16kHz/16bit/mono PCM 净音频约 460.8 MB；还需计入原音、合成/解码临时文件、数据库与本地恢复副本的峰值空间。

不建议一开始把所有端原音统一成无压缩 WAV。统一会话协议、分片确认、连续覆盖范围与恢复契约；编码可按平台选择，独立分片可恢复性与解码能力需验证。

## 6. 持续稳定性指标

- 成功开始采集率：以真实音频回调/采集数据确认，不能只看点击后 UI 状态。
- 持久化落后：采集末端与本机/服务端连续安全前缀的差值，不能用最新一个分片时间替代连续覆盖。
- 超过 30/60/120 分钟录音完成率、可恢复率、恢复后缺口时长。
- 停止到本机保存的 P50/P95，原音同步成功率，停止到服务端可播放的延迟。
- 按失败阶段拆分：权限、采集、存储、同步、解码、STT、分析。
- 补转写队列年龄、已持久化覆盖率、请求重试量；AI 结果的证据可回放率。
- 设备/应用版本、输入路由变化、后台申请结果、分片字节数/序号/耗时；不记录音频与转写正文。
