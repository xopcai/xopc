# 移动端能力配置：优先在本机完成

适用于能力中心和聊天中的 Plugin、Connector、Channel 配置入口。各入口进入同一种配置面板，并恢复原来的配置进度。面板统一的是操作和状态，服务商仍决定用户如何授权。

## 移动端怎么呈现

列表入口用「配置」或「连接」。面板首屏说明正在配置哪项能力、下一步要去哪里，底部只显示一个主操作。「其他方式」只在确有替代路径时出现。桌面端可以继续把跨设备扫码放在显眼位置。

| 当前步骤支持什么 | 移动端主操作 | 其他方式与细节 |
| --- | --- | --- |
| 官方授权页面或可直达授权页的应用链接 | 「前往授权」或「在 {应用名} 中授权」 | 点按后用系统打开。只有服务商提供等效网页时，App 未安装或无法唤起才回退到网页。OAuth 使用系统授权会话或外部浏览器。 |
| 设备码验证入口 | 「打开验证页」 | 展示服务商返回的用户码与「复制」。支持完整验证链接时优先用它，仍展示用户码供核对。若支持异机扫码，将它收进「其他方式」。 |
| XOPC 能完成的配置 | 「填写配置」 | 在同一个面板填写凭据或验证码。按步骤切换：如果扫码后服务商要求验证码，此时主操作变成「提交验证码」。 |
| 仅支持扫码，且目标 App 支持从相册识别 | 「保存二维码」 | 只保存二维码，再给出「打开 {应用名}」和清楚的下一步，例如「扫一扫 → 相册 → 选刚保存的二维码」。从相册识别和 App 打开方式分别验证；打开 App 本身不代表打开授权页。 |
| 仅支持扫码，且无已验证的本机识别方式 | 「显示二维码」 | 明示「请用另一台设备扫码」。仅当用户拥有连到同一 Gateway 的授权桌面端、并且支持恢复同一次配置时，才提供「在电脑上继续」。 |

「保存二维码」由用户点击触发，应用把二维码单独保存到系统相册。提示用户按目标 App 支持的方式从相册识别，或用另一台设备扫码。若用户展开其他方式或收起二维码，面板保留当前尚有效的配置尝试。

支持本机跳转的面板示例：

```text
连接 {服务名}                         ×
将在 {服务名} 中完成授权。
完成后返回 XOPC，连接状态会自动更新。

             [ 前往授权 ↗ ]
                其他方式 ›
```

跳转后显示「等待授权」及「重新打开授权页」；回到 XOPC 时立即查状态，等待期间仅按服务商允许的频率查询。关闭面板保留仍有效的尝试，可从原入口继续；「取消配置」才主动结束。拒绝、超时、服务不可用各给对应的提示和操作。链接失效后通过「重新开始」发起新尝试；瞬时网络错误先重查原流程。打开外部页面和扫到二维码都只是中间状态，Gateway 确认授权、保存配置并完成当前能力要求的校验后，才显示「已连接」或「可使用」。

## 如何接入现有配置流程

Android、iOS、HarmonyOS 共用 Gateway 面板响应。它返回表单、`authorizationUrl`、`qrUrl` 和 `pollAction`，本次加入可选的设备验证码与有效期。客户端根据字段选择当前主操作。服务适配器继续处理授权、轮询和配置写入。见 [移动端面板](../../src/gateway/hono/routes/mobile-capability-panels.ts)。

- 当前面板可以返回授权入口、设备验证码、表单或二维码。授权入口和二维码同时返回时，移动端突出授权入口，将二维码收进「其他方式」。
- **可打开的授权地址与二维码内容分开声明。** 有效的 HTTPS 也可能只供扫码。只有适配器明确声明、宿主校验过的授权入口才能打开；二维码内容始终只交给渲染器。优先使用官方 HTTPS / 应用关联链接。自定义应用 scheme 仅在有官方文档且宿主明确允许时启用，任意插件声明和 CLI 输出不直接触发跳转。
- 用现有 `flow` / `revision` 和服务商尝试标识关联状态，绑定发起身份、能力和目标账号。回调只用于续接同一次尝试，成功以 Gateway 查到的服务商结果为准。凭据和短期授权资料不写入日志、聊天或通用分享入口。
- 新字段缺失时，新客户端沿用现有显示与操作；旧客户端继续消费原字段。新增契约沿用原路由，不为每一个供应商建新页面和新 API。

## 首批验证与上线顺序

| 样本 | 验证目的 |
| --- | --- |
| 钉钉 Channel | [当前实现](../../extensions/dingtalk/src/index.ts#L16) 已拿到 `verification_uri_complete` 但用于渲染二维码；[上游连接器](https://github.com/DingTalk-Real-AI/dingtalk-openclaw-connector/blob/main/src/onboarding.ts) 也提供授权 URL。优先验证三端从手机打开后能在同一次尝试中完成授权，保留扫码降级。若服务返回用户码，按 [RFC 8628 §3.3.1](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.3.1) 展示并可复制。 |
| 一个现有 OAuth Connector 和一个 OAuth Plugin | 沿用已有授权 URL，核对两个入口使用同一个面板、跳出返回后都能查到结果。原生 OAuth 的外部打开方式参考 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html)。 |
| 微信 Channel 或扫码型 Plugin | 微信当前 [iLink 协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md) 公开描述的是二维码展示与状态查询，当前实现没有已验证的同机直达授权入口。分别验证相册识别、跳回 XOPC 和需要验证码的分支；未验证的平台保留跨设备扫码。飞书、企业微信和其他扫码适配器也按同样标准逐个验证。 |
| 一个表单型 Channel（如 Telegram） | 验证仍能在本机填写并保存，用同样的等待、失败与就绪反馈，不经过扫码。 |

首版验收覆盖 Android、iOS、HarmonyOS 的跳转成功、未装目标 App、拒绝、取消、过期、切回恢复及旧 Gateway 兼容。核心结果：已验证支持本机授权的方式无需截图、扫码或第二台设备；仅扫码方式能清楚告诉用户可用的最短路径。上线后按服务和操作类型观察配置完成率及耗时，不记录链接、二维码或用户码。
