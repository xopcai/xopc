# 下一阶段插件补强调研

调研日期：2026-10-19。依据线上 Store 公开目录、本地 xopc-plugins 清单/Skill/实现说明，以及下列厂商公开文档。竞品能力是文档核查，没有登录竞品账号逐项实测；优先级和实现建议是 XOPC 的产品判断。本文不代表已经实现或验收这些新插件。

## 结论

下一阶段应同时推进「增加高频办公数据源」和「把现有交付能力做深」。优先考虑 Microsoft 365、Google Workspace、国内邮箱、腾讯文档；腾讯生态先做接入可行性验证，避免发布只有操作说明的空壳插件。无需账号的 OCR、文件整理和信息简报可以更快形成用户价值。

产品对外继续统一称插件。宿主只增加跨服务通用的协议与交互能力，服务专有权限判断、登录程序和数据转换留在插件中。不要因为引入某个厂商而在安装器里新增专用分支。

## 当前基线

实时查询 `https://store.xopc.ai/api/v1/packages?type=plugin&pageSize=200` 返回 35 个包，其中正式插件 32 个、测试包 3 个。xopc-plugins README 的 32 个正式包与目录一致。原生 Extension 另有目录，不混入这一数量。


核对本地插件 Skill 和 `docs/office-expansion-2026-10-19.md` 后，主要深度缺口如下：

- PDF：有文本提取和页码，没有 OCR；不能把扫描 PDF 的空提取结果视为文档无内容。
- Word/Excel/PPT：以基础文件读写为主；Excel 尚无完整公式计算，文档和演示没有完整视觉渲染验收。
- 网页剪藏：支持静态公开 HTML，没有登录页面和 JavaScript 页面完整采集能力。
- Gmail：用户自行配置 Google Desktop OAuth Client，普通用户首次准备成本较高。
- ICS：读导出/公开订阅，不等同于 Google、Outlook 在线日历读写。

上述依据是仓库实际声明的边界，不是对所有插件逐项生产验收的结论。

## 竞品能借鉴什么

### QwenWork

公开文档列出了浏览器、Mac 原生应用和 Microsoft 365，并列出钉钉、飞书等集成市场能力。最值得借鉴的是将日历、邮件、文件与任务结合成日常办公场景；平台账号连接与本机系统授权分别处理。[连接器说明](https://docs.qwenwork.ai/desktop/connectors)

资源安装后可在对话中选择使用，部分技能提供预设任务输入。XOPC 可采用少量自然语言示例与轻量输入表单，帮助用户完成第一次任务。[资源使用说明](https://docs.qwenwork.ai/features/extensions)

文档目录明确包含国际版产品指南，不能默认其国际版集成列表在中国区或所有账号均相同。[文档目录](https://docs.qwenwork.ai/llms.txt)

### WorkBuddy

连接器文档列出 QQ 邮箱、腾讯文档、腾讯会议、腾讯乐享、TAPD、腾讯网盘。产品支持任务执行中展示连接引导，授权后继续任务。这比要求用户先退出任务、找市场、完成连接后重新描述需求更值得借鉴。[连接器产品指南](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Connector)

开发规范明确区分 MCP+Skill 和 CLI+Skill；Token 表单、多步 CLI 登录、Device Flow、运行时准备、版本兼容等都有声明式表达。XOPC 已有相近的准备/授权基础，可以继续完善通用协议，不必照搬其私有格式。[连接器开发规范](https://open.workbuddy.cn/docs/connector)

专家包可以声明连接器依赖，已连接的依赖不再重复引导。这个思路适用于 XOPC 的场景插件复用已有服务连接，而非每个「日报」「会议」插件再保存一套飞书凭据。[依赖声明](https://open.workbuddy.cn/docs/expert)


企微机器人接入与企微办公数据读取要分开评估：官方企业版文档描述的办公数据范围，与企业开通、席位和授权有关，不能推断普通机器人凭据具备相同能力。[企业接入说明](https://cloud.tencent.com/document/product/1831/139456)

### 豆包工作

豆包开放平台官网明确区分 Skill、Plugin 和 OpenAPI，将插件描述为 Skill、MCP、CLI 的组合；页面同时显示平台内测、提交入驻意向。这支持我们采用通用组合包的方向，但本轮没有取得公开完整市场目录和可复用的安装协议，不能列出未经证实的豆包插件清单或宣称直接兼容其全部插件。[豆包开放平台](https://open.doubao.com/)

豆包浏览器扩展的公开入口强调网页、视频和长内容阅读。这可以作为信息收集体验参考，但它是浏览器扩展产品，不应与豆包工作插件清单混为一谈。[浏览器扩展](https://www.doubao.com/browser-extension/landing)

## 候选插件与实施优先级

以下为建议的产品包划分，不代表每个能力都必须独立建包。P0 表示优先验证并推进；存在平台准入的项目先完成接入验证再排正式交付。

| 优先级 | 插件/增强 | 用户任务 | 实现路线 | 首要边界 |
|---|---|---|---|---|
| P0 | Microsoft 365 | 邮件摘要、会前准备、查找 OneDrive 材料、转待办 | 自研 MCP 适配 Microsoft Graph；本地 OAuth | XOPC 应用注册、个人/企业账号差异、管理员同意 |
| P0 | Google Workspace | Drive 检索、在线日历、Docs/Sheets 协作 | 复用 Google API，评估 gws；沿用/整合 Gmail 账号 | OAuth 应用发布、scope 和 API 启用，不把控制台配置转嫁给普通用户 |
| P0 | 国内通用邮箱 | QQ/163/企业邮箱摘要、附件整理、回复草稿 | IMAP/SMTP 或服务商正式 API，插件内做账号检测 | 各邮箱授权码/开通规则；先草稿、后显式发送 |
| P0 | PDF OCR 增强 | 扫描件、截图和表格变成有页码依据的资料 | 升级 pdf-reader；本地 OCR 资源或用户选定云 OCR | 中文精度、版面和表格还原、模型下载体积、云上传选择 |
| P0 | 腾讯文档 | 找文档、读表格、整理会议材料、写回结果 | 官方开放平台/API；先验证授权与实际读写 | 应用申请、用户可见文件范围及接口权限需专项核实 |
| P1 | 企业微信工作助手 | 接收任务、查获授权资料、同步待办/结果 | Channel 处理消息入口，Plugin 提供业务工具，复用连接 | 机器人消息、办公数据、历史会话是不同权限范围 |
| P1 | 高德出行助手 | 客户拜访排路线、地点信息、出行准备 | 官方 MCP + 一个 Key + 场景 Skill | Key 配额/许可；明确读取用户提供地点，不自动取实时位置 |
| P1 | 会议整理 | 转写稿→纪要→决策→待办→文档 | 复用钉钉/飞书/Zoom；提供 TXT/SRT 等导入兜底 | 平台录制、转写、导出权限；不要承诺读到所有会议 |
| P1 | 本地文件整理 | 批量归类、命名、查重复、整理附件 | 独立本地 MCP，预览操作计划、冲突检查和回滚记录 | 明确选定目录，禁止默认扫描全盘 |
| P1 | Office 交付增强 | 保留模板的 Word、可计算表格、可预览 PPT | 升级现有三个插件，增加计算/渲染资源和样本集 | 打开成功、内容正确和视觉正确需要分别验证 |
| P1 | 跨来源资讯简报 | RSS/网页/知识库→去重→证据→简报 | 复用现有工具，增加场景包及可选定时任务 | 来源日期、去重、付费/登录内容边界 |
| P2 | Slack / Linear / Jira / TAPD | 项目状态、决策检索、周报 | 优先官方 MCP/API，自研最小适配 | 账号准入、应用审核、工作空间权限，先按用户需求排序 |
| P2 | macOS 个人办公 | 系统日历、提醒、备忘录、邮件 | 单独原生 Extension + 小型平台适配程序 | 系统隐私授权、签名、平台差异；不影响跨平台基础插件 |

Microsoft Graph 提供跨 Microsoft 365 的统一数据入口；授权应以用户委托访问为起点，具体 scope 在插件中按任务选择，企业租户策略仍可能要求管理员批准。[Graph 概览](https://learn.microsoft.com/en-us/graph/overview)、[权限](https://learn.microsoft.com/en-us/graph/permissions-overview)、[OAuth PKCE](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

gws 位于 googleworkspace 组织，覆盖多个 Workspace API 并带技能，但仓库明确声明不是 Google 官方支持的产品。可评估复用其实现，不能在我们的产品中称为“Google 官方支持的 CLI”；它也没有消除 OAuth 客户端准备成本。[仓库与认证说明](https://github.com/googleworkspace/cli)、[Google 桌面 OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)

高德官方提供远程 MCP 和 Node stdio 接入，可用现有 Key 表单机制包装；这是接入可行性相对清楚的国内增量。[高德 MCP](https://developer.amap.com/api/mcp-server/gettingstarted)

Slack 官方 MCP 当前不支持 DCR，要求固定应用身份，并限定目录已发布或内部应用。需要先解决 XOPC 应用接入，不能直接填一个 URL 就承诺所有用户能登录。[Slack MCP](https://docs.slack.dev/ai/slack-mcp-server/)

腾讯文档开放生态入口可以确认，但本轮其动态 API 页面没有返回可审查正文。腾讯文档因此是优先开展 PoC 的候选，尚不是已证明可直接完成低门槛接入的项目。[官方入口](https://docs.qq.com/open/)

## 先做成哪些精品场景

建议先以四个场景判断新增插件是否有价值，而不是以 MCP 工具数判断：

1. **每天开工简报**：今日会议、重要邮件、未完成任务，附原始链接；默认生成草稿，不自动外发。
2. **开会前准备**：选定会议后查相关文件和历史材料，生成会前一页纸；缺哪个账号只连接哪个。
3. **资料到成果**：上传扫描 PDF/截图→OCR→来源核对→Excel/Word；每一步有可预览产物。
4. **会后落实**：导入转写/获授权会议内容→生成纪要和待办建议→确认后写回现有钉钉/飞书工具。


## 宿主需要继续补强的通用能力

这些是待评估的增量，不是已确认全部缺失；实现前应逐项复核现有代码。

- **对话内连接与继续**：把工具返回的缺账号/缺权限状态映射为连接卡片；完成后继续安全的读取步骤。对发送、写入、提交操作不得因恢复而重复执行。
- **轻量场景入口**：插件声明 2～4 个自然语言示例及少量任务参数；安装完成只提供“开始使用”，不要求选 Agent。
- **连接复用与依赖**：场景包声明依赖现有服务，明确默认账号/企业；授权在账号层共享，卸载一个场景包不会删掉其他包使用的账号。
- **验证状态分层**：区分“资源就绪”“账号已连接”“当前操作有权限”“曾通过真实调用”。不要用一个绿色标记覆盖所有状态。
- **发行与兼容元数据**：标明最低宿主版本、平台、所需运行时、外部付费前提、是否需要管理员；让市场安装前即可理解。
- **资源与权限恢复**：沿用当前声明式准备和 issues 恢复机制。OCR 模型等大资源有下载进度、取消、重试；服务权限问题由插件返回范围和恢复方法。
- **统一结果证据**：工具结果保留来源、账号、时间、页码等必要元数据；产物支持预览与回读，避免只显示“执行成功”。

Token、CLI、手动 ClientKey/Secret 和标准 MCP OAuth 继续复用已验证的安装路径。固定 OAuth Client 注册、Device Flow 或系统隐私授权如需扩展，增加通用协议能力；不要加入 `if provider === ...` 的宿主分支。

## 建议实施顺序与放行条件

第一批先推进 PDF OCR、文件整理、Microsoft 365 的最小只读版本，并并行验证腾讯文档和国内邮箱的真实账号准入。Google Workspace 与 Gmail 授权体验整合单独评估，避免重复存储同一账号和增加两个几乎相同的市场包。第二批再做会议、资讯与在线文件交付闭环；第三批按实际用户数据选择项目管理与 Mac 原生能力。

每个插件发布前至少完成：线上 Store 实包安装；无凭据跳过；详情补授权；错误凭据/取消/过期；真实账号业务读取；对话中实际工具调用；账号范围不串用；重启后继续使用；卸载不破坏共享连接。涉及写操作时，用明确授权的测试对象验证预览、确认、回读和重复执行保护。

市场建议展示“无需账号 / 需要登录 / 需要管理员”“支持平台”“验证范围”，先将合成测试通过与真实账号验收分开。暂不优先堆叠换名称的电商模板、未经验证的网页逆向登录或只依赖私有服务的竞品包。

本轮仅产出调研方案，未改插件代码、Store 数据或部署，也未新增提交。
