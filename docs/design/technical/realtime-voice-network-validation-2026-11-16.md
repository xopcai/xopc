# 实时语音链路与本机验证

## 三端恢复和鸿蒙真机

Android 和鸿蒙的实时语音通过取票返回可选的计时能力，省去预检。客户端用已通过协议校验的控制帧和音频帧更新活跃时间，平时最多保持一个未确认心跳，15 秒无入站达到断线阈值。重连在后台清理旧票据，收到结构化 `SESSION_CONFLICT` 时继续有界重试。短时音频入队仍受积压和过期限制，队列短暂变长时不再立即静音并重启识别。

Android 和鸿蒙监听系统默认网络变化。发生变化时主动探测当前 WebSocket，2 秒没有有效入站才启动恢复。原连接持续收到数据时保留通话。监听仅在语音连接期间注册。鸿蒙真机验证了该逻辑，Android 使用同一恢复策略并通过构建和定向单测。[HarmonyOS 默认网络监听](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/net-connection-manager/)

### 鸿蒙物理手机与原 FRP

设备为 BRA‑AL00、HarmonyOS 7，安装并验签本地 HAP。通话日志确认每次重连仍走同一台 Mac 的原 FRP。通过 USB 执行 Wi‑Fi 开关，系统默认网络 ID 确认两次切换。以下为单次端侧诊断，从发起切换到 App 报告麦克风输入就绪。

| 方向 | 默认网络探测前 | 加入探测后 | 观察 |
| --- | ---: | ---: | --- |
| Wi‑Fi → 蜂窝 | 11.75 秒 | 12.28 秒 | 发现断线从 5.66 秒缩短到 3.33 秒，后续清理、重拨及音频启动用了 8.95 秒 |
| 蜂窝 → Wi‑Fi | 18.91 秒 | 14.00 秒 | 手机在切换命令后 6.86 秒报告新默认网络，约 1.05 秒后进入恢复 |

暂停本机 `frpc` 约 21.15 秒模拟静默断线，期间保持原有 FRP 进程。进程恢复后 6.36 秒，手机报告原 FRP 上的麦克风输入恢复。再次发声得到回复。最终版本用生成中的报数任务再测一次。暂停后 16.87 秒手机报告断线，FRP 恢复后 5.77 秒麦克风就绪。核对数据库，原来处于 `running` 的任务以原输入 ID 和运行 ID 完成一次，恢复后的新输入只创建一个不同任务。测试结束后恢复设备 Wi‑Fi 和原 FRP 进程。

测试会话中，六条已识别的测试输入各对应一个持久化输入和一个已完成的 Agent 任务。原来报数的任务只执行一次。外放时播放报数回复，口述「暂停一下」触发手机停止播放，未新增 Agent 输入。初测的鸿蒙诊断记录从首 PCM 到写入 AudioRenderer 为 16 ms、到播放进度为 399 ms，外部录音未能可靠分离手机声音。

#### 靠近麦克风后的外放补测

同一台鸿蒙真机和原 FRP，使用阿里直连 ASR、TTS、800 ms 判停及 Cherry 音色。Mac 麦克风在同一条波形上录下合成提问和手机外放。用提问参考音频对齐最后的发声，再结合设备接收与播放事件，在录音中识别手机首声。以下为同一问题每组两轮，声学时间按约 0.1 秒精度报告。

| 语音 Agent 模型 | 说完到扬声器首声 | 回复创建到手机收到首 PCM | 首 PCM 到播放进度 |
| --- | ---: | ---: | ---: |
| 测试会话原模型 xopc-cloud / GPT 6.1 Sol | 约 6.3–7.2 秒 | 3.83–3.91 秒 | 70–102 ms |
| 临时固定 DeepSeek Flash | 约 3.7–3.9 秒 | 1.27–1.61 秒 | 84–96 ms |

从持久化回复核对了实际模型。临时固定 DeepSeek Flash 后，两个短句的声学首声中间值约比原模型缩短 3 秒，差异主要出现在回复创建到首 PCM。对照结束后恢复原语音模型配置。

DeepSeek 对照中的两轮「暂停一下」都在外部麦克风录到手机正在播报之后才发出。设备在插话开始后约 3.1–3.3 秒确认停播。录音保留了插话前的手机外放与停播后的安静段。两个声源重叠，声学停止边界暂无法可靠给出精确数值。每组四条正常测试输入均各产生一个已完成任务，纯停播各为零新增任务。另测了更轻、更短的「暂停」，其中一次被识别成「行」并产生了额外任务。完整口令的两轮成功仅覆盖本次环境。

#### 固定语音模型与短口令回归

本机 Gateway 持久化 `voice.realtime.assistant.model = deepseek/deepseek-flash`。同一个测试会话中的真实语音回复记录为 DeepSeek Flash，普通文字任务的持久化回复仍为 `xopc-cloud/openai-codex/gpt-6.1-sol`。重启前后核对了 FRP 注册、入口和公网健康检查，手机继续使用原入口。

识别到明确停播短句时，非回声的部分转写稳定 100 ms 即可通知停播。普通插话的部分转写稳定期为 180 ms，任务只接收最终转写。语音引擎保留 ASR 上报说话开始时的播放状态，因此重叠期间出现的孤立「行」即使在播放结束后才最终转写，也不会提交任务。在播放结束后才开始说的「行」和带实质内容的追问仍按正常逻辑处理。鸿蒙补测中还出现过「暂停」被识别成「停」，播放期间单独的「停」也作为停播口令处理。

阿里直连会话识别在启用插话时使用中等权重的「暂停」「停一下」即时热词。热词随原连接的识别参数发送。只有识别出明确停播短句或实质的插话内容才中止当前播放，孤立的「行」仍按短应答处理。[阿里实时识别客户端事件](https://help.aliyun.com/zh/model-studio/qwen-audio-asr-streaming-client-events)

| 鸿蒙真机与原 FRP | 观测结果 | 持久化任务 |
| --- | --- | --- |
| 两轮正常短问句 | 说完到麦克风录到手机首声约 4.6、4.7 秒 | 每轮一条，模型均为 DeepSeek Flash |
| 轻声「暂停」 | 一轮能从录音中分辨停播，约 2.6 秒，设备约 2.8 秒确认取消。最终版另一次确认停播，录音中口令起点匹配置信度较低 | 以上两轮均零新增任务 |
| 播放中单说「行」 | 原回复完整播完 | 零新增任务 |
| 最终版「暂停，法国的首都是哪里」 | 从录到插话开始到设备确认停播约 3.7 秒，随后播放「巴黎」 | 一个原始任务和一个完整追问，各执行一次 |
| 最终版轻声单字「停」 | 有一轮未触发取消，极短、极轻的声学输入仍会漏判 | 零新增任务 |

短问句使用同一合成普通话，麦克风同时记录问句和扬声器输出。带追问时两个声音重叠，表中报告设备取消事件。需要先确认扬声器在播，录音无法确认已有外放的轮次未计入。核对每轮 SQLite 输入、运行 ID 和持久化回复，验证停播口令不进入 Agent、完整追问只产生一个运行。相关的 90 个测试、TypeScript 类型检查和改动文件的 ESLint 均通过。

#### 首声与停播分段

同一鸿蒙设备继续通过原 FRP，语音 Agent 固定 DeepSeek Flash，ASR/TTS 走阿里直连。将录音波形、手机播放事件与网关时间戳对齐。分段数值有不同的采样精度，声学对齐按约 0.1–0.2 秒计。

此前的两条 4.6–4.7 秒短问句中，从声学句尾到手机收到识别结束事件估算为 **2.5–2.8 秒**（含手机上行与识别）；从识别结束事件到首 PCM 为 **1.76–1.99 秒**（含 Agent、TTS 和回程）；收到 PCM 到设备首次上报播放进度为 **82–95 ms**。加上网关追踪后，一条波动较大的基线短问句测到约 6.6 秒，其中声学句尾到最终转写约 2.8 秒，最终转写到首正文约 2.8 秒，首正文到网关收到首 PCM 为 356 ms，剩余是传输和播放。

此前录音中可分辨的约 2.6 秒停播样本，口令声起到网关写下取消审计约 1.6 秒，之后约 1 秒听到声音停止。近场组的一次带追问插话另外记录了口令发起至 ASR 初报约 970 ms、至明确停播候选约 1.34 秒、候选稳定到网关发送取消约 100 ms、网关发送取消到手机记录约 620 ms。

阿里近场模型在同样的手机外放条件下，轻声「停」「暂停」各测试两次，四次均未停播。随后恢复远场模型，将阿里的 `speech_noise_threshold` 设为 `-0.3`，保持原 800 ms 判停。同一短问句两轮实测首声为 **3.7、4.2 秒**，其中声学句尾到最终转写估算为 **1.8–1.9 秒**，最终转写到首正文为 **1.0–1.7 秒**，首正文到首 PCM 约 **0.38 秒**。两轮结果为同机小样本，时延仍受模型首字波动影响。[阿里 ASR 噪声阈值](https://help.aliyun.com/zh/model-studio/qwen-audio-asr-streaming-client-events)

在 `-0.3` 组，低声「暂停」停播 1/2，低声「停」停播 0/2，均零新增任务。一次「暂停」的手机上行音量约为 −74 dBFS（20 ms 帧 RMS 的第 90 百分位），识别器返回空文本。另两次「停」的上行约为 −40、−45 dBFS，识别结果被归类为短应答。数字回声过滤未丢弃这些样本的帧。对同一上行片段试加输入增益，空文本仍为空，另一次识别反而变差。正例中 ASR 初报约 0.8 秒，网关发取消约 2.1 秒，手机约 2.7 秒记录取消。该正例录音混有其他声音，停播时间采用手机事件。两次单说「行」均让原回复播完，两个带追问的样本均持久化一个追问运行并播出「巴黎」。

额外加入「停」单字热词时，两个低声「停」和两个低声「暂停」均未停播。其中一次单说「行」被识别成孤立「新」，造成一次误停和一次误提交。已撤回单字热词。播放期间的孤立「新」与「行」一样跳过任务提交，带其他内容的句子继续等待最终转写。若部分转写已将停播口令和后续内容用标点分开，按 100 ms 的停播候选处理，追问仍由最终转写提交。保留配置为 `voice.realtime.stt.speechNoiseThreshold = -0.3`，只传给会话 ASR，语音 Agent 继续使用 DeepSeek Flash。

恢复保留配置后再通过原 FRP 复测两轮「行」和两轮带追问。两次「行」都无误停、无新增任务，其中一次命中网关短片段过滤。两次带追问分别在发出口令后约 **2.7、2.8 秒**由网关发出取消，设备约 **3.2、3.1 秒**记录取消。网关均在明确的部分转写后约 100 ms 发出取消，比这两轮的最终转写早约 3 秒。每轮只创建一个追问运行，均播放「巴黎」。轻声短口令仍未达到稳定停播。相关 92 个测试、TypeScript 类型检查和改动文件 ESLint 通过。

### iOS 受控故障

iOS 模拟器的真实麦克风帧驱动测试代理，代理在同一 FRP 语音流中换入合成 PCM。代理从原任务已创建的时刻停止下行，并将 Gateway 已作出的旧票据取消回执延迟 4 秒。改前两轮在检测后约 6.55–6.74 秒重新发出麦克风帧，但积压误触发了静音和识别重置，未收到第二条语音回复。改后检测至首帧为 2.15 秒，并完成第二轮转写、回复和下行 PCM。注入一次结构化旧票据冲突后重试成功，检测至首帧为 3.23 秒。直接断开 WebSocket 时，故障至首帧为 2.20 秒。每轮测试中两个独立语音输入各持久化一次。由于 iPhone 未连接，这一组使用模拟器。

### 普通话停顿和插话

- 带停顿样本检查前后两段转写顺序、末帧之前有没有提交、提交次数、Agent 任务数。验收轮还读取数据库中的语音用户输入，核对条数和提交身份。Cloud/Cloud 两次在「明天我想去上海……坐高铁比较方便吗」的 900 ms 停顿样本中提前提交。直连 500 ms 也在该样本提前提交，600 ms 和带续说提示的 700 ms 样本各通过一次。
- 双直连 800 ms 通过 600 ms 完整前半句、700 ms 未完成前半句，以及两组文案的 900 ms 停顿。「明天我想去上海」900 ms 通过三次预验证，其中两次检查持久化输入。「熊猫最爱吃什么……请只用两个字回答」900 ms 通过两次，1040 和 1100 ms 各通过一次，均核对持久化输入。1000 ms 在同一批复测中也通过，短句首音频中位数比 800 ms 多 176 ms。
- 插话使用第二份麦克风 PCM，在原回复首帧到达 240 ms 后开始发送。原回复的播放确认按时钟推进。以下时延从插话首个有效帧到收到原回复的 `barge_in` 取消事件。

| --- | ---: | ---: | --- |
| 「暂停一下」 | 1375 ms | 961、1099 ms | 一个原始任务，停播没有额外提交 |

### 落地配置

本机在线 Gateway 已启用阿里直连 `qwen-audio-3.1-asr-flash-streaming`、`qwen3-tts-flash-realtime` 和 `Cherry` 音色，判停为 `800` ms。通过原 FRP 复测，短句在 3063 ms 收到首音频，900 ms 停顿句在 2988 ms 收到首音频，均完整转写并持久化一个语音输入。另一次短句复测从持久化的模型回复中确认实际模型为 `deepseek/deepseek-flash`。DeepSeek 固定设置用于对照和复测会话。已有百炼凭证经本地供应商配置保存，独立进程在未加载 shell 凭证变量时也能解析直连语音路线。回到先前路线时，实时识别选 `xopc-cloud/stt`，实时合成选 `xopc-cloud/tts` 和 `default` 音色，判停设回 `1200` ms。

复测用法见[语音技术参考](../../reference/voice-runtime.md#measuring-the-15-second-target)及[基准脚本](../../../scripts/benchmark-voice-latency.mts)。

## 初测链路

手机通过 FRP 访问电脑上的 Gateway。助手语音使用独立的 WebSocket 传 20 ms PCM 帧，Gateway 接 XOPC Cloud 流式识别，最终转写交给 DeepSeek Flash，正文再交给 XOPC Cloud 合成。上行 PCM 为 256 kbps，下行为 384 kbps，未计协议开销。聊天使用独立的实时连接。

初测时本机使用 Cloud 识别和合成，默认语音模式为助手。显式请求自然语音返回 HTTP 503 和 `PROVIDER_UNAVAILABLE`，因此自然语音没有可用的时延样本。

## 本机测量

使用同一正在运行的 Gateway、同一 FRP、同一条 2.82 秒合成普通话和临时会话。拨号时延从发出第一条语音接口请求计到 `session.ready`。首音频从最后一个有效上行 PCM 帧发出计到收到第一个下行 PCM 帧。该基准模拟播放确认，采集、扬声器出声和开场问候均未计入。FRP 与本机直连样本串行采集，上游波动包含在观测值中。

| 条件 | 拨号到 Gateway 就绪 | 说完到首音频 | 说完到最终转写 |

| FRP，先预检 | 3217 ms | 4191、4413 ms | 1727、2098 ms |
| 同一 FRP，直接申请票据 | 2807 ms | 4131、4062 ms | 1799、2013 ms |
| 本机直连，直接申请票据 | 1641 ms | 3497、3441 ms | 1518、1512 ms |

## 本轮修改与验证

- iOS 在取票接口申请计时能力，减少一次 HTTP 往返。旧 Gateway 仍可通话，端侧省略未声明支持的可选播放计时。新 Gateway 保留旧客户端取票时的响应形状。新版源码 Gateway 通过真实本地 HTTP 验证了鉴权、旧响应、可选能力和票据取消。
- iOS 在麦克风授权后并行启动音频设备和语音 WebSocket。Gateway 单独准备开场问候，识别已就绪时可以先收音。只有端侧确认输出就绪后才允许播问候。用户先开口会取消待播问候，原来的请求正常提交。受控 WebSocket 测试阻塞合成，确认握手和用户请求都能继续。
- iOS 最多每 5 秒检查一次连接，连续 15 秒没有有效音频或控制入站时触发恢复。只保留一个待确认的 ping，写入阻塞期间仍继续检查。前台调度正常时，检测窗口为 15–20 秒。iOS 模拟器连到真实本地 WebSocket，服务端发出 ready 后保持连接并停止下行，端侧在 15.04 秒报告断线，期间只发了一个 ping。单元测试也覆盖了没有 pong 但音频仍持续下行的情况。Wi-Fi/蜂窝切换到恢复收音的耗时需要实测。

## 初测后的优化顺序

1. **先压助手首声。** 在隔离 Gateway 固定 FRP、DeepSeek Flash、普通话样本和会话历史，交替测 Cloud 与阿里直连流式 ASR、TTS。历史样本中，直连 ASR 将最终转写中位数从 1460 降到 779 ms，固定直连 ASR 后，直连 TTS 将首字到首音频中位数从 1029 降到 348 ms。保留 300/500 ms 判停对照，覆盖 600–900 ms 句内停顿并要求输入完整、每轮只提交一次。自然语音可用后，同一套样本单独测自然闲聊及需要工具的任务。[历史语音对照](../ada-voice-latency-20261107.md)
2. **把恢复耗时拆开。** 分别测硬断线到再次收音、静默断线到检测、检测到再次收音。现有恢复还会等待旧票据取消接口，网络切换时这个等待可能拖尾。后续给取消阶段独立时限，并按结构化会话冲突结果重试取票。确认已提交的任务回到原会话，过期麦克风帧和已播音频丢弃，任务不重复执行。
3. **对比连接路线。** 在认证配对下比较局域网直连、现有 FRP 和近端中继。助手通话独立比较 WebSocket/PCM 与 WebRTC/Opus，保持设备认证和通话控制，覆盖 UDP、TURN 和 TCP/TLS 回退。采集 RTT、抖动、丢包、播放缓冲和丢包隐藏量，用录回的麦克风及扬声器信号检查实际首声和插话停播。[WebRTC 传输](https://www.rfc-editor.org/rfc/rfc8835.html) · [Opus RTP](https://www.rfc-editor.org/rfc/rfc7587.html) · [WebRTC Stats](https://www.w3.org/TR/webrtc-stats/)
4. **继续压聊天发送。** iOS 的提交回执可能还没有 `activeRunId`，此时会发 `GET /run`。用已连接的会话事件提前订阅 `run.started`，验证事件能按会话及输入身份匹配，保留作业查询作为恢复路径，再用同一条 FRP 复测发送到首正文。[上一轮聊天对照](mobile-network-local-validation-2026-11-16.md)

下一轮每种路线分别采集冷拨号和热拨号，记录样本数、P50/P95 和成功率。网络场景至少覆盖稳定 Wi-Fi、蜂窝、切换、80/150/300 ms RTT 与 1/3/5% 丢包，真机覆盖扬声器和蓝牙。沿用普通话完整短句 1.5 秒首声目标，分别记录首个 PCM、播放调度和实际扬声器出声。另记录硬断到重新收音的 P95（暂定 3 秒目标）、静默断线检测窗口、插话到停播和任务重复次数。
