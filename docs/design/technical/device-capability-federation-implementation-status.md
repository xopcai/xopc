# Device capability federation implementation record

Updated 2026-11-05. This record distinguishes implemented behavior from remaining release gates. The complete P0–P7 plan is **not yet finished**.

## P0 — Contracts and baseline

Implemented: distinct Device principal, Provider local ID, connection epoch, catalog revision, exact contract digest, task execution reference and invocation identity. Raw MCP names remain reversible in Provider namespaces. Descriptions are untrusted data. Baseline protocol/client and deferred discovery suites passed before changes.

Review: an online device is neither an admitted Provider nor a ready resource. Source-device reads and selected execution targets have separate semantics. An absent actor never becomes an owner. Reconnect cannot silently change an execution target.

## P1 — Protocol, catalog and SDK

Implemented: Endpoint v3 only; `endpoint.tools.v3` is required by both peers before a device registers. Dynamic catalog replacement and readiness state with monotonic revision/sequence and TTL. The outer Realtime version remains v2. Atomic validation precedes store publication; exact digest admission precedes executable registration. Simultaneous connections cannot publish the same stable Provider. Offline claims persist in existing namespaced SQLite storage; online state does not persist. SDK supports Provider registration, withdrawal, catalog byte/tool limits and state updates.

Review corrections: lowered catalog budget to 128 KiB to fit the outer 256 KiB transport envelope; bounded schema depth/nodes and disallowed external references/regex; isolated schema compiler namespaces; retained native contracts while deleting the old parser/facade paths. Fresh databases use v270. Complete installed upgrade chain remains supported, with a regression covering principal and FK-dependent settings preservation.

Verified: protocol/client/realtime packages (64 tests before the final added cases; endpoint subset now 31); schema upgrade suite 80 tests, including every supported v202–v269 start and consolidated v217 baselines. Real HTTP + WS publication, approval, execution and withdrawal passed.

Review of catalog synchronization: the Gateway acknowledges the exact revision or returns a bounded rejection code. The SDK gates readiness and invocation on the current acknowledged revision and resends a complete snapshot on reconnect. Stale acknowledgements cannot activate a newer revision. The Bridge logs rejections without logging manifest contents. Remaining: production rollout matrix with older installed application binaries. Older Endpoint versions deliberately fail rather than downgrade.

## P2 — Actors, admission and grants

Implemented: accepted HTTP/command input identity is associated with the actual queued input/run, not the latest message. Current device scope/session revocation is rechecked. Provider admission API is owner/admin only and pins the complete digest. Existing single-call location consent was generalized to admitted Provider tools, with exact argument digest, connection and tool revision, expiry and one-use reservation. Device credentials cannot enumerate other Provider catalogs. Target selection itself never grants cross-device access.

Review corrections: removed selected-target-as-permission behavior; unrecorded channel/automation inputs fail closed for cross-device use. Existing native Desktop authority and per-call local confirmation remain enforced. Provider mutations require local confirmation.

Verified: actor queue isolation, unknown-run denial, precise grants/revoke/expiry/reconnect, Provider admission/revision rejection, and owner-selected execution through authenticated HTTP/WS.

Implemented and verified: owner-only Bridge enrollment issues scoped credentials. Signed HTTP/WS, access refresh, denied management access and owner-token-free reconnect pass on the real listener. Owner-only delegation endpoints persist an exact channel account, chat, sender and optional thread, or an exact automation definition, with a Provider digest, argument digest, expiry and explicit target. Run authority pins the connection and rechecks the grant at discovery and dispatch. Real HTTP/WS tests cover unauthorized device credentials, ordinary bus messages without verified ingress, wrong arguments, revocation during a run, old queued automation runs and changed automation actions. Delegation management is exposed through authenticated APIs.

## P3 — Discovery and task targets

Implemented: deferred `device_use` discover/select/release; bounded accessible candidates and fresh opaque references; existing `tool_search` dynamically registers admitted tools and hides withdrawn declarations within a turn. Selected targets pin principal, connection epoch, actor and transcript. Computer/Browser use the same selected-target precedence. Computer discovery pins its source before subsequent open. Active Computer/Browser resources prevent target replacement/release until confirmed stop.

Removed: binding-service, binding repository runtime/export, old binding API and consumers. Historical SQL assets/data remain for supported upgrades and are never read for execution.

Review corrections: owner generic-tool resolution now also respects a selected target; offline/expired selections remain unavailable instead of falling back. API targets require an existing UUID conversation and have independent lazy-bundle routing. Reads about the message source remain source-bound.

Verified: two real MCP child processes connected as Alpha/Beta via WS; authenticated owner approval, generic discovery, Alpha selection and execution; resource-busy switch denial; Alpha disconnect with Beta still online yields no tool fallback. Same-turn dynamic discovery/revocation and existing Computer/Browser unit suites pass.

The chat header displays and can explicitly change the execution target. Browser extension input no longer automatically overwrites it. The persisted target becomes unavailable after Gateway restart or device reconnect until explicitly reselected; active GUI calls recheck actor and connection before each action. Remaining: richer step/resource handles for simultaneous device contexts.

## P5 — Device-local MCP

Implemented: installed MCP SDK client with stdio/Streamable HTTP, paginated discovery, notification refresh, instructions, explicit policy allowlist, optional structured output, text/images/embedded resources/resource links, scoped read helper, progress/cancellation and invocation-attributed local form elicitation callback. HTTPS/loopback transport rules, bounded pagination and resource URI path boundaries are enforced. Gateway pi-owned MCP lifecycle remains unchanged.

Review corrections: no annotation-driven authorization, batch-read eligibility or automatic retries. Unsupported content/protocol features fail explicitly. CLI advertises no elicitation callback it cannot service. Writes are locally confirmed. Schema/name budgets are shared with the Gateway contract.

Verified: real Streamable HTTP SDK server and stdio MCP subprocess both passed discovery, approval, execution and result delivery through the authenticated Gateway and signed device WebSocket. The stdio adapter also refreshes descriptions, denies uninstalled tools, enforces resource URI boundaries and withdraws on close. The separate 181-test regression covered direct Gateway MCP, OAuth configuration, existing connectors, queued input, Computer and Browser, and Electron connection paths. CLI help loads successfully.

Gateway-routed MCP form input is an opt-in Provider feature. An authenticated chat answer returns to the original invocation and request ID. Scope and schema checks reject wrong users, invalid answers and duplicate submissions. A real stdio MCP fixture passed acceptance, decline and timeout. The timeout case also caught a late reply that incorrectly withdrew a healthy catalog. Transport errors and catalog refresh failures withdraw a Provider, while late RPC replies stay isolated to the invocation. Gateway restart can recover a form while the same device process still holds its original invocation. A disconnected device process or a lost terminal result can leave mutations with uncertain effects in the operation ledger. OAuth orchestration, sampling, roots, MCP Tasks, URL forms and interoperability beyond the installed SDK are outside the supported surface.

## P6 — Reliability and artifacts

Implemented: device writes reuse existing durable external-operation ledger with manual recovery and exact request/contract identity. Uncertain mutation dispatches, disconnects, timeouts, cancellation without durable stop evidence and invalid post-dispatch results report OUTCOME_UNKNOWN. They are not replayed automatically. Shared host retains unsettled local execution admission across reconnect. Invocation-scoped file upload validates grant path, expiry, byte budget and origin; audit UI labels unknown outcomes. Existing Desktop reliable operation receipts remain dedicated and protected.

Review: basic MCP cancellation acknowledges local promise settlement only; it cannot prove rollback or external hardware stop. The Bridge advertises durable operation receipts on its MCP providers and records the operation identity before invoking a mutation. It fsyncs a result digest before reporting success and does not store the result payload. An owner can query evidence from the same provider after reconnect. Evidence does not rewrite the Gateway's operation status or replay the call. A pending native resource cannot be freed by merely changing the selected device.

Verified native GUI: `pnpm exec tsx scripts/run-computer-network-flow-validation.mts` passed capture/reuse/unknown phases through three independent Gateway processes and three Electron processes, actual macOS native input and hosted GUI model. Each phase made one model request and one scenario native input; dropped-result phase reported unknown with no further input. All phases confirmed release and restored the isolated fixture baseline. The latest rerun after artifact, interaction, and delegation work passed all three phases. Evidence is in `/var/folders/28/dgsfghyj33xbpbt4l29st_tc0000gn/T/xopc-network-flow-9R7GTy`. First run failed because the test tried changing permission before explicitly draining its denied session; the fixture now requests confirmed stop before changing permission. Production guards were not bypassed.

Additional fault E2E: a real MCP process committed one counted write, then disconnected before its response. The Gateway reported OUTCOME_UNKNOWN, preserved the device target, and rejected a replay of the same operation after a signed reconnect and explicit reselection. The write count stayed at one. An MCP image also traversed the authenticated, invocation-scoped HTTP upload and model projection.

After reconnect with the same identity, the authenticated status route returned the device's succeeded receipt with its result digest. Cross-device artifact grants now bind a completed file in the current transcript to the selected receiving connection, Provider digest and tool. A one-use signed download verifies length and checksum on the receiver. The chat header exposes owner authorization and a request to copy into the chat. Real HTTP/WS E2E with two MCP devices verifies source checksum at the recipient, direct file access denial, replay denial and explicit revocation. The original phone-to-Mac hardware pairing scenario remains open.

Pre-dispatch device readiness waits use the existing clarification and session-input queues. E2E closes the listener and database and restarts both. An open wait survives, and an already queued answer reopens when its old connection is unavailable. After the owner selects the same device again, the persisted objective resumes through one authenticated dispatch. A waiting MCP form can reattach after Gateway restart using the exact invocation ID, request ID, device principal, Provider digest, transcript and owner run. The original MCP process and deadline must still be live. Recovery is scoped to owner invocations without transient file grants and requires a durable Provider receipt for writes. The Gateway persists the form checkpoint without persisting its answer and does not restart the original model turn. The chat displays the recovered result after terminal validation. A journal receipt does not provide exactly-once execution for physical hardware.

Provider tools can declare a common resource ID. The Gateway and host deny concurrent access to that resource even through different tool names. The host releases the lock only after the local operation settles. Independent resources can continue. Physical resource fencing after a host process crash remains adapter-specific.
