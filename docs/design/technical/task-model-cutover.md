# Task 模型重构与一次性切换

日期为 2026-11-13。本文确定目标模型、实施顺序和上线验收条件。

## 1. 设计决策

- Task 表达一个可持续推进的目标。人工待办可以没有执行记录、交付物或逐项检查。简单委托可以直接交付回复。只有任务需要时才增加来源证据、授权、目标位置或签收。
- 看板阶段、运行状态、操作结果、核验结论和投递状态各自有数据来源。服务端从它们计算一个用户可见状态和最多一个主操作。各端共用该判断。
- Personal Agent 的后台派发、过程通知和成果回传纳入同一次切换。过程通知走协作事件，最终成果走独立投递队列。
- 正式库执行一次事务迁移。所有生产读写路径同时切到新模型。旧格式解释仅存在于升级脚本，无运行时双读、双写、旧协议转换或延迟迁移。

## 2. 目标模型

下表定义逻辑实体。能够复用现有实体及主键的地方沿用原身份。成果记录复用现有产物引用，进度和投递继续使用各自的持久队列。

| 实体 | 主要字段与职责 |
| --- | --- |
| Task | `id`、`title`、`phase`、`resolution`、`specVersion`、`version`、`locale` 和时间。可选规划信息包含项目、优先级、截止日期和看板排序。来源、分配、项目关系沿用对应记录。 |
| TaskSpec | `taskId + version`、`brief`、`completion`、可选 `outputs[]` 和 `checks[]`，以及实际需要的约束和审批要求。原始用户请求保留在来源记录，宿主执行说明由执行层注入。明确保存回复或发布要求、是否需要证据审阅、是否需要选择最终成果，停止根据正文搜索工具名来决定执行流程。 |
| TaskRun | `runId`、父子与重试关系、要求版本、执行者、执行对话、分配代次、指令序号、上下文快照、状态、租约和幂等键。保留用户手动改阶段的版本保护。 |
| TaskResult | `resultId`、结果版本、来源运行、要求版本、适用的分配代次和指令序号，以及实际成果引用。任务可以有多个结果版本。当前结果由明确的版本和选择记录确定。 |
| CheckResult / Signoff | 核验记录关联要求版本、`checkId`、实际结果版本、证据 ID、方法和时间。人工检查保存操作者与判定。签收记录绑定具体结果及签收人，保留明确的确认动作。 |
| Wait | 保存有效阻塞的种类、关联任务版本或运行、原因、处理方、解除条件和处理状态。权限请求、澄清、依赖、暂停和操作结果待核对沿用各自的处理规则。 |
| Delivery | 保存向哪个对话投递哪个结果、消息或附件引用、状态、重试和去重身份。协作通知与成果投递使用独立队列。 |

### 成果与完成

`outputs[]` 中每个成果有稳定 ID 和类型。第一版支持**回复、产物、操作结果**。产物可包含工作区文件或现有图片、音视频等资源。只有明确要求落到某处时才写目标引用。操作结果记录受控操作的目标、执行回执以及影响是否已确认。工作区目标用授权范围内的工作区身份和相对路径表示。可预览副本、目标落盘和对话回传分别记录。

工作区文件以任务项目或发起 Agent 的已配置工作区为范围。执行前记录目标状态，结束时确认目标是新建或已变更的普通文件。签收时再核对同一个文件状态。缺失、未变、符号链接或后续替换都会保留待核验状态。旧任务只有目标位置能明确映射时才迁为结构化目标，旧记录保留原有证据。

`checks[]` 只保存必需条件。检查可以关联单个成果，也可以覆盖整个任务。检查要求声明可接受的证据来源，实际核验记录注明工具、模型或人工。格式、字段、目标存在性等事实优先直接验证。研究和查询使用适用的来源、范围、数据时点和覆盖依据。不同结果版本的通过结论不能自动拼接使用。当前要求、适用指令、最终成果或相关目标发生变化后，受影响的检查须重新确认。

新任务使用三种完成策略。自动完成要求已满足任务明确承诺的成果和必需检查，且没有有效阻塞。人工签收在达到这些前提后确认具体结果。人工待办由责任人显式完成，可以没有运行和产物。三者都允许无逐项检查，缺少检查本身不会触发完成。手动看板关闭单独记录，不补造核验或签收。

周期计划和持续跟进复用现有计划与跟进实体。周期执行有自己的运行和结果，计划独立决定下次执行。长期目标根据明确的停止条件或用户决定关闭。单轮完成不会停用计划，单轮无变化可以没有成果与通知。

| 场景 | 完成依据 |
| --- | --- |
| 纯文本答复、资料整理 | 实际回复满足要求，按要求回到原对话。无需额外文件或研究证据。 |
| 研究、连接应用查询 | 结果覆盖约定来源和范围。缺失覆盖、权限或关键证据时保留部分结果与缺口。 |
| 文件、图片、音视频 | 所需成果可访问。若指定位置，另行确认目标位置。异步作业完成与成果回传分别记录。 |
| 发送、发布、外部修改 | 事前授权符合范围，事后有实际影响的可确认记录。结果不明时进入核对，禁止把重放作为默认恢复动作。 |
| 人工待办、项目协调 | 责任人显式完成。依赖、截止日期和看板阶段按实际需要使用。 |
| 定时执行、持续跟进 | 本轮按任务类型判断结果，计划或目标单独判断是否继续。 |

### 状态、主操作与关闭

扩展现有 [TaskReadModelProjector](../../../src/tasks/task-read-model-projector.ts)。Gateway 提供状态、原因和最多一个主操作。操作引用具体等待、运行、结果或计划，包含执行所需的并发校验信息。首页、详情、任务对话和个人任务列表消费同一判断。列表使用同一投影的摘要。执行报告、旧结果、证据和变更在详情中按需展开。

状态优先级为显式关闭或暂停、需处理的有效等待、正在推进的运行或计划、未确认影响或失败、可签收、等待分配或尚未开始。已关闭但仍有运行时保留运行提示。多个阻塞继续保存，主操作按实际阻塞关系和稳定顺序选择。没有可用操作时可以只显示状态。授权、工作区核对和恢复只有在服务端具备对应能力时才提供动作。

自动关闭、签收和逐项检查共用服务端完成判断。动作处理器在事务内重验权限、版本、运行与阻塞。过期动作返回冲突及最新状态。旧运行可以占用执行资源，它的回执只有满足当前版本及交接条件时才可作为当前证据。对照 [现有关闭处理](../../../src/tasks/task-application-service.ts) 和 [验收接口](../../../src/gateway/hono/routes/tasks.ts) 移除各自重复的条件分支。

各端依据 Gateway 返回的检查 ID、当前成果 ID 和主操作提交判定与签收。已配对且当前会话仍有效的 Android、iOS 和 HarmonyOS 设备需要具备 `tasks.write`，签收记录保留设备身份。

## 3. Personal Agent 全链路

1. **交办。** `personal_task` 保存原始请求、发起对话、固定输入引用、显式指定的 Agent 或 Skill、所需能力和提交幂等键。返回持久化任务身份。后台分配验证能力、输入版本与授权后启动。重复提交复用原任务。
2. **执行与接续。** 执行 Agent 在任务对话中按固定版本推进。补充指令和问答关联同一任务与原问题，转交更新分配代次。运行开始时记录指令序号。确认收到补充指令只记录回执，结果只有在最终正文、选定产物或已保存的结构化内容经过采纳核验后才能沿用同一次运行签收。未确认时可在同一运行补查，触及不明操作影响时进入待核对。修订产生新要求或结果版本。取消、重试、暂停和恢复保留原幂等边界。
3. **进度。** 协作事件先持久化。普通进展更新任务卡；重要延迟、失败和待决问题按现有通知偏好进入发起 Agent 的处理队列。主 Agent 优先用已有上下文解决，确需用户介入时回到原对话询问。主 Agent 忙时延后过程通知。已提交输入恢复时先查既有状态。页面状态变化不产生新的过程消息。
4. **成果。** 独立队列按原对话、运行、要求版本、分配代次和指令序号核对目标。附件投递无需等待主 Agent 空闲，保留文字整理草稿及重试状态。仅接收最终结果的偏好不抑制成果。连接应用请求保持结构化结果，避免重复生成普通回复。成果投递与任务完成分别记录，部分成果可按原规则回传并标明缺口。

改造入口包括 [派发工具](../../../src/agent/tools/personal-task-tool.ts)、[分配服务](../../../src/tasks/task-allocation-service.ts)、[协作与过程通知](../../../src/tasks/task-main-update-delivery.ts)、[通知提交确认](../../../src/tasks/task-main-update-input.ts)、[成果交付](../../../src/tasks/task-result-delivery-service.ts) 和 [Gateway 调度](../../../src/gateway/service.ts)。

## 4. 一次性数据转换

保留任务、运行、对话、成果、通知和交付的既有身份。每个旧契约版本转换为同号 TaskSpec。旧字段与原始证据可留作历史档案，运行时只读取新实体。新装库直接使用最终结构。

| 数据 | 转换规则 |
| --- | --- |
| 任务、契约、项目关系 | 保留身份、阶段、关闭原因、时间和已有关联。只将旧可编辑正文用于迁移时的当前版本，避免补造历史正文。保留显式要求、约束、假设和审批范围。只转换能够确定的宿主交接约定。里程碑和父子关系保留已有记录，普通任务不再默认产生这些字段。 |
| 成果与目标 | 使用可信工作区、文件资源或交付记录建立引用。仅凭文件名、报告文本或预览卡不能确认目标或授权。无法唯一定位的目标保留原要求，相关未完成任务进入核对。 |
| 验收与策略 | 检查 ID 由任务 ID、原契约版本和原条件索引确定性生成。人工记录按版本、索引及原文核对，保留判定、撤销、备注、操作者和时间。自动核验只有在条件、证据与被检查结果均能唯一绑定时才计入当前通过。歧义记录保留为历史，未关闭任务只重查受影响的必需项。 |
| 旧完成策略 | `verified_auto` 转自动完成。`verified_then_review` 转有效核验后签收。`manual` 保留逐项人工确认要求，再显式签收。未关闭的旧签收类任务需执行新版签收动作，迁移不补造签收。已关闭任务保留原结论。 |
| 在途执行与授权 | 保留已选执行者、输入快照、分配代次、指令序号、计划、租约相关状态、授权和原始去重键。已排队与等待的工作沿用可确认的状态。无安全续跑边界的运行留下中断和核对事项，释放失效租约。仅有旧文本提示时生成通用核对事项，保留来源，不推定具体操作影响。 |
| 通知与成果 | 保留已发送标记、通知决定、待投递项、主 Agent 输入身份及重试记录、最终成果选择、原消息引用、待发文字回复和附件。转换所有仍会被消费的队列、计划、回调和投递载荷。切换后先查既有输入或消息记录，再决定是否续投。历史消息不作为重发来源。 |

转换在 SQLite 升级事务中完成。脚本使用确定性规则和数据库内证据，不调用模型、不访问外部服务、不执行或重放任务。结构错误及引用缺失应中止事务。证据含糊时按上表迁为可核对状态，并计入迁移报告。保留从 v202 起的受支持升级链，现有基线见 [schema.ts](../../../src/storage/sqlite/schema.ts)。增量迁移及初始化 schema 一起交付到 Node 和 Electron。遵循现有 [离线备份和事务升级](../../../src/storage/sqlite/schema-upgrade.ts)。

## 5. 实施顺序与切换

下列工作可以分批开发和验证，正式环境一次发布。

1. 定义最终 Gateway 协议、存储和状态规则。接通命令、核验、签收与结束事务，去掉正文关键字和客户端各自推断的状态规则。
2. 接通 Personal Agent 的交办、分配、协作通知、成果与文字回复。更新 Gateway、CLI、Agent 工具、Web、Android、iOS、HarmonyOS 及任务事件消费者。旧协议明确要求升级。
3. 完成单一增量迁移和新版初始化 schema。在副本反复演练受支持的起始版本，核对任务、要求版本、验收、运行、分配、等待和投递记录数量与归属。报告无法映射的证据、待核对的运行以及待续投条目。
4. 正式维护窗口暂停交办、调度及投递，等待在途处理到达可确认边界。停掉旧写入进程，创建 WAL 一致且落盘的备份。对正式库执行一次迁移，校验外键、数据库完整性、版本引用、现行结果及投递去重身份，全部通过才提交。
5. 启动新版，保持业务写入、调度和投递关闭，验证协议与数据读取。通过后恢复写入和后台处理。提交前失败由事务回滚，提交后但开放写入前可恢复备份。开放写入后按新结构修复，避免恢复旧库覆盖新写入。

## 6. 上线验收

| 场景 | 必须通过 |
| --- | --- |
| 普通答复与人工待办 | 纯文本成果回到原对话。人工待办可无 Agent 运行或产物，由责任人完成。 |
| 研究和查询 | 覆盖不足保持部分结果。变更指令或范围后，旧证据不能给新结果签收。 |
| 文件和异步媒体 | `TOOLS.md` 副本可打开，目标路径仍待核对时不会出现验收主操作。异步媒体作业结束、成果可用和回传状态各自准确。 |
| 外部操作 | 未授权时进入对应等待。结果未知时可核对，重启或切换不会重放已确认或影响不明的操作。 |
| 周期与长期工作 | 单次运行完成后保留下次计划。持续跟进无实质变化时保持安静。 |
| 派发与接续 | 重复交办只生成一个任务。已分配任务不重新选 Agent。排队、暂停、审批、转交和迟到回执保持正确归属。 |
| 进度通知 | 普通进展在任务卡可见。真正需要用户处理的问题回到原对话，回答返回同一任务。仅最终通知偏好有效。已提交待确认的消息接续处理且不重复。 |
| 成果与回复 | 已投递内容不重发，待投递成果和文字回复能续投。主 Agent 忙时附件可独立回传。跨会话访问被拒绝，过期结果不冒充当前成果。 |
| 历史与版本 | 三种旧策略、人工撤销、重复条件、同名证据、旧版本迟到结果和已关闭任务均有迁移用例。新结果不继承歧义证据，原始记录可追溯。 |
| 单模型与恢复 | 新库和迁移库使用同一生产路径。测试每个受支持的起始版本、事务失败和备份恢复。真实带鉴权 Gateway 验证跨端读取、操作和回传。旧协议拒绝，旧解析代码只在迁移路径。 |

上线后跟踪执行缺口进入人工验收的比例、简单任务从交办到结果可用的耗时、重复通知或成果数，以及用户因找不到结果再次询问或交办的比例。执行提速以直接核验场景的实际数据为准。
