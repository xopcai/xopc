# 实际 Gateway 更新与真实对话耗时对比（2026-10-29）

## 结论

实际运行的 Gateway 已更新为包含三项 await 路径优化的源码版本，PID **79715**，原端口 **18790**，健康检查为 ready。模型选择仍为 `xopc-cloud/auto`，thinking 仍为 `off`，没有更改全局配置。

真实请求中，请求模型前的准备阶段确实减少了约 **19 ms（P50）**。本轮客户端首字和完整回复耗时没有改善，不能宣称线上整体提速。模型调用的波动大于这次工程优化省下的时间。

## 测试条件

- 实际服务原本以 `node --import tsx/esm src/cli/bin.ts -- gateway --force` 运行，不是安装的 LaunchAgent 服务。本次按相同的源码运行方式更新，没有进行 npm 发布或版本号修改。
- 先确认实际服务没有正在运行的会话，再正常关闭。用临时源码快照启动未优化版本，测量完成后关闭基线进程，再从当前仓库启动优化版本。
- 基线快照基于提交 `57e30cb01eb0d75b96ef5b757229ca1236ca764b`，与优化版本只有以下 4 个运行时文件的相关变动：`run-verification.ts`、`run-turn.ts`、`direct-turn-helpers.ts`、`run-gateway-agent.ts`。文件 SHA-256 已写入原始结果。
- 基线 PID **78472**，优化后 PID **79715**。两个版本依次使用同一份实际配置和数据库，运行在同一个实际端口。
- 每个版本先进行 2 条预热，再测量 8 条正式样本。正式问题覆盖确认、计算、改写、事项优先级、两个小文本附件、红色图片和蓝色图片。
- 每条样本均为新建、预先 materialize 的临时测试会话，使用现有个人助手 Agent 配置和 `personal_main` 工具策略。测试只发送到这些新建会话，没有向原个人聊天发送消息、重置历史或修改原会话模型。
- 临时会话不用于积累长期记忆。完成后移除测试会话的 Personal 标记并归档，保留收据、Trace 和诊断记录。
- 两边每个正式案例的提示词 hash 相同，上传图片字节相同，所有正式执行均只调用了一次主模型。没有使用工具或创建后台任务。
- `auto` 是同一个请求模型标识，但不保证云端每次都路由到同一个实际上游。因此不能将两个时间段的模型延迟差异归因于工程代码。

这是小样本的一次真实对比，基线先跑、优化后再跑，没有做 ABBA 交替或大规模统计。新临时会话没有原个人助手的长历史，结果不代表所有真实工作负载。

## 指标定义

- **客户端首字**：发送 HTTP append 请求前的单调时钟，到官方 Realtime 客户端收到首个非空 `assistant_delta`。覆盖提交、调度、准备、模型出字和事件传输，不包含浏览器绘制。
- **完整回复**：相同发送时刻到客户端收到 `run_end`。另记录了最后文本与消息结束时间，原始值可查。
- **请求前准备**：Trace 中 `agent.run` 开始到第一次 `agent.answer` generation 开始。不包含根执行开始前的 Gateway 工作。
- **模型完整调用**：generation Span 的开始到结束，包含请求等待和输出；不能进一步区分云队列、网络和推理。
- P50 使用与现有分析一致的 nearest-rank 定义，8 个样本取排序后的第 4 个。不用此样本量声称 P95 或统计显著性。

## 实测结果

预热样本独立保留，未纳入下表。

| 指标 | 优化前 P50 | 优化后 P50 | 优化后减去优化前 |
|---|---:|---:|---:|
| 客户端首字 | 1,867.43 ms | 2,005.84 ms | **+138.41 ms** |
| 完整回复 | 2,110.10 ms | 2,128.98 ms | **+18.88 ms** |
| 请求前准备 | 63 ms | 44 ms | **−19 ms** |
| embedded 内部准备 | 47.78 ms | 30.01 ms | **−17.77 ms** |
| 模型完整调用 | 1,656 ms | 1,736 ms | +80 ms |

平均客户端首字为 **1,978.53 → 2,163.08 ms**；平均完整回复为 **2,136.84 → 2,331.12 ms**。平均模型完整调用为 **1,702.63 → 1,933.75 ms**。

所有 8 对样本的请求前准备都缩短了 **8～25 ms**；平均从 **68.75 ms 降到 51.38 ms**。模型调用平均多了约 **231 ms**。这个时间段的模型波动覆盖了本次节省下来的准备开销；不能用均值或分位数的简单相减精确拆解每条请求的全部原因。

### 逐案例客户端结果

| 案例 | 首字：优化前 → 后 | 完整回复：优化前 → 后 | 请求前准备：前 → 后 |
|---|---:|---:|---:|
| 简短确认 | 1,867 → 1,964 ms | 2,034 → 2,113 ms | 63 → 39 ms |
| 17 + 25 | 2,230 → 3,258 ms | 2,408 → 3,444 ms | 64 → 43 ms |
| 改写一句话 | 1,867 → 1,942 ms | 2,110 → 2,129 ms | 63 → 49 ms |
| 事项优先级 | 1,866 → 2,094 ms | 1,988 → 2,280 ms | 65 → 44 ms |
| 附件核对码 | 1,757 → 2,043 ms | 1,886 → 2,238 ms | 62 → 43 ms |
| 附件求和 | 1,952 → 1,795 ms | 2,158 → 2,018 ms | 62 → 49 ms |
| 红色图片 | 2,312 → 2,203 ms | 2,397 → 2,313 ms | 81 → 73 ms |
| 蓝色图片 | 1,978 → 2,006 ms | 2,115 → 2,114 ms | 90 → 71 ms |

计算题这一对的模型调用由 **1,968 ms 变成 3,057 ms**，同时准备由 64 ms 缩短至 43 ms，是模型波动掩盖局部工程收益的具体例子。

实际准备收益小于离线 Git 仓库基准中的结果。离线基准使用含未跟踪文件的 Git 仓库，而实际工作区、文件数量和 I/O 条件不同，不应将离线的 123～190 ms 直接当作线上每轮节省。
