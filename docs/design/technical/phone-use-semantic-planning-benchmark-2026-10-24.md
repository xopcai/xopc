# Phone Use：语义执行、分层执行与真实完成率对比

日期：2026-10-24。

后续恢复优化已暂停，当前状态见[暂停与恢复说明](phone-use-recovery-pause-2026-10-24.md)。本报告保留上一轮已完成评测的结果。

## 结论

两项实验能力已实现，并完成基线、语义单项、分层单项、组合四组真实 AutoGLM 对比。**本轮没有验证到整体完成率提升，分层单项和组合在开发集出现退化，因此两项配置默认均保持关闭。**

| 四组共同匹配集 | 现有实现基线 | 仅语义执行 | 仅分层执行 | 两者组合 |
|---|---:|---:|---:|---:|
| 原有任务：每组 12 个有效样本 | 9/12，75.0% | 9/12，75.0% | 6/12，50.0% | 5/12，41.7% |
| 留出任务：每组 6 个有效样本 | 6/6，100% | 6/6，100% | 6/6，100% | 6/6，100% |

留出集存在明显的天花板效应，不能据此证明优化有效。通讯录搜索的两组重复未形成四组共同可比样本，未纳入这张表，也未被算作模型失败。开发集与留出集分别报告，不合并宣称统一成功率。

本轮共发出 **308 次真实模型请求**：开发探索 67 次、正式开发集 193 次、正式留出集 48 次。正式评测产生 88 条试验记录，其中 79 次进入真实模型执行，9 条为初始化不匹配、零模型请求的记录。人工校准、初始化稳定性补充检查和模拟单元测试不计入模型完成率。

## 实现及适用范围

### 语义控件执行

实现位于 [semantic-controls.ts](../../../src/phone/semantic-controls.ts)、[contracts.ts](../../../src/phone/contracts.ts) 和 [runtime.ts](../../../src/phone/runtime.ts)。

- 新增 `tapElement`：使用观察对应的 `frameId`，按 `resourceId`、文字或描述的精确组合定位唯一、完整可见的非密码节点。
- 在派发前重新观察，并校验节点身份、几何位置、页面、控制权和应用范围；解析后通过已有执行路径派发 ADB 点击。
- 对普通坐标点击，只在命中唯一、大小受限的原生可操作节点，且中心位置没有歧义时，绑定节点并定位到中心；无法确定时保留原坐标。不会根据“最近的控件”猜测目标。
- AutoGLM 继续使用原有提示和观察输入，由执行端处理绑定。新增测试验证同一观察下，语义单项与基线发给 AutoGLM 的请求内容完全一致。结构化模型可接收显式选择器协议，但本轮未用另一种真实结构化模型验证其收益。
- 未解析的语义动作不能直接交给驱动；手动输入接口拒绝这种动作，避免把未派发操作记录为未知结果。

这版 AutoGLM 路径是“模型用坐标选择目标，执行端绑定原生控件并复核”，不是已经训练出模型主动生成语义选择器的能力。它也不能自动纠正落在控件边界之外的错误坐标。

### 完成条件驱动的分层执行

实现位于 [planning.ts](../../../src/phone/planning.ts)、[model-adapter.ts](../../../src/phone/model-adapter.ts) 和 [runtime.ts](../../../src/phone/runtime.ts)。

- 从调用方明确给出的 `completion` 条件编译阶段：输入任务拆为定位并聚焦字段、准确输入、最终检查；页面任务拆为寻找原始锚点、检查完整条件。
- 只按原生 UI 中完整可见的精确文字、唯一输入框值和焦点状态推进。模型收到当前阶段，仍返回标准单步动作；没有隐藏的额外规划模型请求。
- 不新增用户要求，不修改最终完成条件；阶段完成不等于整个任务成功。最终仍需原有独立完成验证。
- 没有明确完成条件时，不生成主机计划。计划只在一次 `run` 或 `step` 内存活，不写入持久报告。

这是一个有限的分层执行原型，尚不是通用任务规划器。它目前主要通过阶段上下文影响模型选择，没有把所有阶段转成确定的动作控制器。只有单一终态条件时，例如计时器显示 `00h 02m 30s`，导航与最终检查阶段可能共享同一谓词，无法表达数字按键顺序。

配置入口为顶层 `phone.semanticControls` 和 `phone.hierarchicalPlanning`，均默认 `false`。实验代码保留供后续验证，未修改用户的实际配置。

## 评测设计

基线是本轮开始时冻结的现有 xopc 实现，包含此前已保留的可靠性修复；不是原版 Open-AutoGLM，也不是直接以当前 Git HEAD 代替基线。候选的七个 Phone Use 源码模块使用不可变快照，正式开发集与留出集的候选哈希相同，结束后也核对了工作树源码与快照一致。

| 维度 | 设置 |
|---|---|
| 推理与设备 | 实际 AutoGLM Phone API、实际 ADB、专用 `XOPC_Android_Test_API_35` 模拟器，Android 15 |
| App | 设置、时钟、文件、通讯录，均为实际预装 App |
| 对比 | 基线、语义、分层、组合，独立开关 |
| 重复 | 每个任务每组 2 次 |
| 每次预算 | 最多 8 次模型请求、12 个动作、90 秒活跃执行预算；会话另有时限 |
| 完成判定 | 结束后两次独立原生 UI 观察，不能仅凭模型 `finish` 或运行时状态 |
| 初始化 | 比较完整原生 UI 指纹，最多两次重置重试；不匹配保留记录并排除配对统计 |
| 证据 | 代码与任务哈希、动作、原生事实、错误、实际调用数及机制使用计数；默认不保存截图和原始模型推理 |

四组共同匹配集要求同一个“任务 × 重复”内四组均具备一致的初始原生指纹。单项与基线的配对集可能更大，下面单独给出，不能混用分母。初始指纹一致不代表截图逐像素一致。

执行顺序使用轮换与反转，但并非随机试验；当前两次重复中，同一任务的首个执行组相同，不能称为任务级完整 AB/BA 平衡。

留出集未用于候选算法调优。首次真实留出调用前，依据零模型调用的人工快照补齐了禁止“新增城市”的动作检查，并将存储页的独立身份判定加固为原生工具栏标题，加上 Apps/System 条件。候选、任务目标和运行时完成条件未变。两个集合的测量脚本哈希因此不同，分别保存和报告。

## 留出任务与初始化覆盖缺口

| 未参与候选调优的任务 | 基线 | 语义 | 分层 | 组合 |
|---|---:|---:|---:|---:|
| 设置存储页，显示 Apps 与 System | 2/2 | 2/2 | 2/2 | 2/2 |
| 世界时钟页，不新增城市 | 2/2 | 2/2 | 2/2 | 2/2 |
| 通讯录整理页，显示管理 SIM 与屏蔽号码 | 2/2 | 2/2 | 2/2 | 2/2 |
| 通讯录准确查询搜索 | 无共同配对 | 无共同配对 | 无共同配对 | 无共同配对 |

通讯录搜索已有 3 次真实成功轨迹：基线 1 次、分层组 2 次；语义和组合没有形成有效模型试验。两个重复的共同配对均因初始化不一致被排除，不能宣称已完成该任务的四组前后验证。

已记录的初始事实中，相同 `Device` 文字的边界曾有 8 像素差异，底部标签有 1 像素差异；完整指纹还包含未展示的空节点，不能断言只有这两个差异。没有放宽指纹匹配或把不匹配计作模型失败。

正式评测后增加了一次仅测量初始化的补充检查：要求两次连续完整原生指纹一致，单次门限 15 秒，最多三次准备/重置；用四次零模型重置检查能否复现同一个参考状态。第四次仍失败，因此没有继续追加付费补测，也没有用新初始化方法替换原始留出结果。候选代码未修改。

## 机制使用、调用成本与失败原因

| 共同匹配集 | 组 | 实际模型请求 | 已完成的原生绑定点击 | 原生证据推进阶段 / 分配阶段 |
|---|---|---:|---:|---:|
| 原有任务 | 基线 | 44 | 0 | 0 / 0 |
| 原有任务 | 语义 | 49 | 17 | 0 / 0 |
| 原有任务 | 分层 | 45 | 0 | 16 / 28 |
| 原有任务 | 组合 | 40 | 11 | 12 / 28 |
| 留出任务 | 基线 | 11 | 0 | 0 / 0 |
| 留出任务 | 语义 | 9 | 4 | 0 / 0 |
| 留出任务 | 分层 | 10 | 0 | 12 / 12 |
| 留出任务 | 组合 | 9 | 4 | 12 / 12 |

机制确实被执行，不是只设置了开关。但开发集的语义组没有降低请求数；组合组请求较少，也伴随更多失败，不能解释成效率收益。完整调用与耗时见分析 JSON；耗时包含打开/关闭、独立终态观察与不变量检查，不是纯模型延迟。

已完成轨迹支持的具体发现：

1. **计时器主要不是点击定位问题。** 检查到的绑定前后坐标命中同一个原生数字控件，例如 digit 2、digit 3。组合组一例输入序列为 2、2、2、3，得到 `00h 22m 23s`；同时存在 `finish_reason=length`、输出达到 3,000 token 后截断。绑定没有解决数字状态选择与输出稳定性。
2. **阶段提示没有保证动作遵循阶段。** 设置搜索组合组曾在设置首页直接请求输入 display，没有先打开、聚焦搜索框；运行时以 `PHONE_INPUT_NOT_FOCUSED` 拒绝，零动作派发。
3. **导航失误仍然存在。** 显示设置分层组反复向错误方向滑动，页面不变，最终停止于 `no_progress`；关于手机、文件目录的一些 Back 返回了之前的时钟 App，随后因应用范围检查停止。
4. **不能把组合组更高的某个成功数归因于语义执行。** 关于手机任务没有触发原生绑定，分层与组合的单次差异无法证明绑定收益。单模拟器、小样本和固定顺序也限制因果判断。

正式评测中，`runtimeVerified=true` 但独立终态判定失败的记录为 0。抽检的设置值、文件校验和及禁止动作检查未记录违规。这不等于已验证所有业务负向约束；模型自行结束但未满足 UI 条件仍按失败计。

## 开发探索、验证与复验资料

开发探索没有并入正式完成率：V1 尝试模型在首个动作前返回计划块，12 次试验使用 34 次请求，规划相关组没有接受到有效计划；V2 改为主机阶段后做了 8 次试验、33 次请求。V3 保持 AutoGLM 的语义单项请求不变，才冻结为正式候选。V1 切换开发时源码保护检查阻止了下一次试验，已完成试验使用进程启动时载入的模块；这一轮保留为不完整开发诊断。

验证结果：41 个相关测试文件、345 项测试通过；根类型检查、定向 ESLint、完整构建通过。另有评测脚本专用类型检查、原生 oracle 测试与离线统计自检。没有修改生产账号、安装 App 或操作真实手机。实现与审查曾并行；真实模型试验按顺序使用同一专用模拟器，避免设备状态互相干扰。

## 下一步应优先解决的问题

下一轮应先验证可执行的字段聚焦/输入子目标、数值输入的中间状态，以及根页面 Back 的约束。还需修复跨重置的原生初始化稳定性，避免通讯录搜索这类任务持续损失比较样本。显式选择器需要另用确实支持该协议的真实模型验证；本轮结果不支持自动开启两项实验能力或宣称已提高一般真实任务完成率。
