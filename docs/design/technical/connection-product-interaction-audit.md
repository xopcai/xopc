# 连接恢复与产品交互整体梳理

日期：2026-10-14。范围：Web Chat、连接账号选择、ConnectionWait、普通输入队列和 Personal Request。本文记录源码核查与下一阶段方案，不代表下面的建议已经实施。

## 1. 结论与截图判断

当前恢复链路已有持久化、取消、版本校验、执行前检查和重启对账。剩余问题主要是：**聊天回复、连接操作区、输入处理和任务执行各自解释状态，尚未形成同一套产品契约。** 增加“正在验证工具”提示只能解决部分可见性问题。

新截图中，助手要求“授权后回复继续”，操作区却展示“已连接，正在验证工具”。如果聊天内容是授权前的历史，它可以保留，但必须明确当时的等待状态；如果用户刚发送“继续看下”，系统应解释当前目标的实际状态，而不是启动一轮缺少实时状态的模型回复。

截图不能证明 Slack 当时实际完成授权，也不能证明任务已经死锁。要确认该实例的事件顺序，需要 waitId、objectiveRevision、授权检查结果和 session input/run 的日志。本次结论区分了可直接从代码确认的行为与截图根因推测。

## 2. 当前实际做法

### 2.1 普通聊天路径

```text
用户目标 → 工具搜索 → xopc_require_connection
                   → 持久化 ConnectionWait + 检查点
                   → 当前模型轮结束，输入区显示连接操作区
用户连接/选择账号 → ConnectionRecoveryService 检查账号与工具
                   → 事务提交 connection_resume 输入
                   → SessionInputCoordinator 串行领取
                   → 再次检查、消费等待记录 → 恢复未完成工作
```

等待目标保存原始时间范围、已完成/未完成步骤、选定账号与版本。取消与异步检查使用持久化版本防止过期结果覆盖；恢复输入通过唯一键去重。重启后对未消费的恢复输入对账，已消费记录不自动重放。它们能减少重复执行风险，但不等于任意外部写操作具备 exactly-once 保证。

### 2.2 Personal Request / Task 路径

Personal Request 也通过 ConnectionWait 收集连接或账号，但完成后创建/恢复对应 Task，结果通过投递链路回到原聊天；它不再同时创建普通 `connection_resume`。已有 Task 的重新连接保留原账号和原 Task。

这两条执行路径可以保留。产品上应统一“原目标、选定账号、等待原因、排队/运行状态、结果位置”的含义；每条路径只能有一个执行调度者。ConnectionWait 继续负责连接恢复，不再引入另一套 ClarificationWait 恢复机制。

### 2.3 账号选择

已经实现 clarify 式内联单选：展示工作区与账号身份，不默认替用户选择，只绑定当前目标。确认后仍交给 ConnectionWait 验证、恢复。多个可用账号时一次只选一个账号；多账号合并检索尚未实施。

“已连接账号”与“为当前目标选定账号”需要分别表达。账号已经授权，不意味着用户已经确定本次查询哪个工作区。

| 阶段名称比证据更强 | recovery 在同步后进入 `checking.tools`，之后才综合验证 readiness；UI 无条件把该阶段显示为“已连接，正在验证工具” | 检查流程阶段被当成授权成功事实；未完成选账号/授权的 need 也可能存在 |
| 排队被描述成已执行 | Personal Request 的恢复投递文案为“正在继续处理”，触发点不是实际 worker 开始执行 | 用户无法区分已接受、排队、正在读取消息 |

## 4. 建议的产品契约

### 4.0 优先执行，只交接真实阻塞

用户要求读取或整理消息，即已授权在现有权限内进行必要读取。Agent 应直接使用可用工具，或提交已有授权账号的 Personal Request；不再询问“是否读取”“是否继续”。明确指定/当前目标绑定的账号优先，否则使用唯一符合权限的账号；多个账号无法确定时才交给用户单选。合理的默认只读范围可以说明后执行。

只有需要用户授权、无法消除的账号歧义、影响结果的关键缺失信息或主机确实要求审批时，才交接给用户。工具缺失与临时故障先核查和尝试授权范围内的可用路径，不能直接解释为未授权。连接操作完成后由主机自动续接，Agent 不要求用户回来发“继续”。

该原则已写入个人 Agent 的新建/升级提示、外部工具发现及连接请求契约，以及 Personal Request 提交反馈。搜索无结果不再断言“未连接”，可用工具返回直接执行的指令。后续已进一步修复输入协调器，见第七节；提示契约与运行时状态机分别承担理解和执行约束。

### 4.1 三种状态分别保存，统一展示

- **账号授权**：未连接、授权中、已授权、失效；同时记录当前目标绑定的账号。
- **任务能力**：尚未验证、验证中、可读取、权限不足、工具不可用、检查暂时失败。
- **目标执行**：等待选择/连接、待确认、排队、运行、完成、取消。

界面状态应由服务端基于这些事实投影；不要用一个 checking 阶段替代全部状态。临时网络错误不解释为授权失效；工具不可用不引导再次 OAuth。

模型每轮获得同一份有版本的目标快照：目标和范围、账号、连接/能力状态、执行状态、自动继续是否有效、需要用户做什么。该快照只能由可信运行时提供，不能来自用户可伪造的内部输入。

主机控制连接与执行状态提示；模型解释查询目标和结果。`xopc_require_connection` 成功后应明确“目标已保存，完成授权后自动继续，本轮停止”，禁止额外要求发送“继续”。搜索工具返回明确的缺口类别，不能仅凭空结果断言未连接。

### 4.2 新消息按意图处理

| 用户动作 | 建议处理 | 原目标变化 |
| --- | --- | --- |
| 点击“检查授权”、明确的“继续这个目标” | 交给 ConnectionWait，幂等检查或确认继续；不另开同目标模型轮 | 保持目标、账号和范围；需复核时仍完成必要确认 |
| 查询“现在到哪一步了” | 使用运行时快照回复进度 | 不撤销自动继续 |
| “只看今天”“改用工作账号” | 先冻结旧恢复，再合并修改；版本递增、重新检查/确认 | 真实修改目标 |
| “取消这个目标” | 事务取消目标和未消费恢复输入；运行中使用对应停止路径 | 取消目标，不断开账号 |
| 明确无关的新任务 | 正常处理新任务，保留旧目标；串行执行时显示排队原因 | 旧目标不被取消或无故要求复核 |
| “继续”指向不明或多个候选目标 | clarify 确认继续哪个目标 | 确认前不启动候选目标 |

第一阶段只支持明确按钮与严格限定的继续/状态控制意图。不要把所有含“继续”的自然语言用关键词判断后直接执行。开放式目标修改可以借助模型理解，但必须通过受版本约束的显式更新动作提交；不确定时暂停推进并澄清。

新输入与旧恢复同时到达时，协调器需要在同一会话锁/事务下决定顺序。目标修改、账号修改、取消先使旧版本不可消费；“继续”不能重复入队；执行已经开始则反馈正在执行，不再发起第二次运行。

### 4.3 一套面向用户的状态与动作

| 事实 | 主提示 | 操作与说明 |
| --- | --- | --- |
| 无可用连接 | 连接 Slack 后继续整理消息 | 连接并继续、取消；说明目标与范围已保存 |
| 多个可用账号且未绑定 | 这次使用哪个 Slack 工作区？ | 内联单选 + 确认并继续 + 连接其他账号；不自动选首项 |
| 等待授权 | 请在授权窗口完成 Slack 连接 | 重新打开授权、检查授权、取消 |
| 正在检查 | 正在检查 Slack 连接 / 消息读取能力 | 显示阶段开始时间或耗时、查看详情、取消；仅在已验证授权时标注“账号已连接” |
| 授权成立但缺少能力 | Slack 已连接，消息读取工具暂不可用 | 重试检查、相应权限/设置入口、取消；不重复授权 |
| 恢复已入队 | 已准备好，等待继续整理消息 | 若有前序执行说明等待原因；取消 |
| 实际执行已开始 | 正在检索 Slack 消息 | 任务进度、停止；ConnectionWait 操作区交接给已有执行状态展示 |
| 意图过期或范围需要确认 | 是否继续整理原范围内的消息？ | 展示账号和绝对时间范围，确认后继续 / 修改 / 取消 |
| 检查失败或重启中断 | 检查暂时失败，目标已保存 / 正在恢复状态 | 重试、取消；恢复本身不应静默更改账号或范围 |

状态事件进入历史时追加一次、带目标标识并去重；历史只表述“当时发生的事”。操作区展示实时状态。队列入队提示“等待执行”，worker 开始才提示“正在处理”，完成结果关联同一目标。

“跳过连接”需要明确产品含义。建议普通目标存在有效替代方案时显示“使用现有信息继续”；必须依赖该数据的 Personal Request 显示“取消此请求”，并说明未读取 Slack。不能用同一个按钮隐含两种结果。

“近期”等范围在首次接受时确定并展示，恢复时保持检查点中的绝对范围；未读等动态条件按执行时求值并说明。模型不能在用户只说“继续”后自行改变为另一个时间范围。

## 5. 截图场景应如何表现

```text
用户：看下 Slack 消息，有哪些是我最近需要紧急处理的。
助手/系统：需要连接 Slack。目标已保存，完成授权后会自动继续。
操作区：连接 Slack 后继续整理消息  [连接并继续] [取消]

用户：继续看下。
未完成授权：原目标仍在等待 Slack 授权，请在授权窗口完成连接。
已授权、能力检查中：正在检查 Slack 消息读取能力，完成后自动继续。
已排队：原目标已准备好，正在等待前面的执行结束。
已运行：正在整理 Slack 消息，无需再次继续。
```

这些回复基于当前目标快照；不能再让独立模型轮根据旧的“connection_required”生成“仍未连接”，也不能仅因发送这条控制消息撤销自动继续。

## 6. 落地顺序与验收

**P0：统一事实反馈与明确控制动作。** 修正搜索结果的授权推断；向模型提供权威目标快照与继续策略；按真实授权证据生成操作区标题；补齐停止本轮、不要求用户再发继续的契约。明确继续/检查/查询进度接入 ConnectionWait，保留原版本，不启动第二个执行。

**P1：统一输入意图与两条任务路径的交互。** 区分补充、无关任务、取消和不明确继续；保留原恢复的安全顺序。统一普通恢复与 Personal Request 的排队/运行提示、跳过含义、结果归属。完善阶段耗时与可操作失败说明。

**P2：再扩展账号体验。** 增加“修改当前目标账号”的明确入口与版本校验；之后评估记忆默认账号。多账号合并查询继续不做，避免扩大恢复、结果归属和权限语义。

验收不能只检查按钮或单个仓储方法，应覆盖以下完整旅程，并断言聊天回复与操作区的含义一致：

1. 授权前、检查中、排队时、运行中发送“继续”，同目标只恢复一次。
2. 授权完成同时收到取消/目标修改/账号修改，旧版本不再执行。
3. 检查、入队、领取未消费、消费后分别重启；无遗漏、无已消费目标重放。
4. 已授权但工具不可用、网络检查失败、过滤搜索为空，不错误要求重新授权。
5. 多账号选择前不执行；选择后账号不漂移；过期选择结果不覆盖更新目标。
6. 发无关消息不丢旧目标；指向不明确的“继续”不会猜测启动。
7. 普通目标与 Personal Request 都准确区分排队和运行；取消与跳过文案对应实际结果。
8. 页面刷新/实时重连后，快照与历史事件去重；失败状态仍可取消。

此前的测试与模拟 Gateway/浏览器验证覆盖了恢复机制的一部分，不包含真实 Slack OAuth 与消息检索，也未证明模型回复始终遵守状态契约。后续需要增加工具结果/模型上下文契约测试与完整交互测试，再执行一次真实 Slack 只读旅程验收。

## 7. 新消息与恢复协调器修复记录

- 两条输入接收路径（普通 submit 和 Web 原子 append）都已移除无条件恢复意图失效。普通输入优先于尚未消费的恢复输入，原目标、恢复意图和版本保留。
- 等待期间及已开始的连接恢复执行期间，无关消息不 interrupt，也不 steer 到原执行。已开始的工作不能倒退重放；新要求正常排队。明确取消原目标会关闭对应等待并请求停止匹配的活动执行。
- 简短、指向明确的“继续”“继续看下”“继续原目标”作为可信运行时生成的控制 payload 持久化，不启动同目标的新模型轮。存在其他未处理消息或 clarification 时，普通“继续”交给 Agent 澄清；含范围修改、附件或应用上下文的消息也不会被当成纯控制。
- 每轮模型获得当前 ConnectionWait 的动态快照。无关工作不修改目标；目标修改/取消通过现有工具提交，提交时取消旧恢复输入并递增目标版本。等待目标只能由 ConnectionWait 恢复，新模型轮不得自行重跑同一目标。
- 领取后网络检查期间收到输入时，恢复让出领取并保留同一恢复输入；处理完新消息后重新执行前检查。提交中的附件/上下文验证尚未完成时也不得越过恢复消费边界。
- Personal Request 和普通恢复均在事务中检查待处理消息，避免一条路径提前启动 Task、另一条仍等待用户修改。
- 控制指令采用输入幂等键；重启只重排可安全重试的内部控制和未消费恢复，不重放已消费目标。控制回复与完成标记在同一事务落盘；迟到回复必须匹配活动 run 和 transcript，不能写入重置后的新聊天。
- 账号选择、网络检查、继续和取消仍遵循原目标版本与执行前校验。准备阶段的旧取消指令不能取消后来修改的目标；编辑队列中的控制消息会清除旧控制 payload。

自然语言修改仍由 Agent 理解并显式提交工具动作，不用宽泛关键词自动改范围、账号或取消任务。取消不撤销已经完成的外部操作。真实 Slack OAuth 和检索旅程尚未在本次测试中运行。

验证：六个相关测试文件的 170 项回归通过；最后增加的等待状态用例随连接恢复套件 68 项通过，最终输入协调器 19 项复测通过。类型检查、修改文件 lint、Node 构建及构建附带的浏览器扩展校验通过。HTTP 回归使用真实监听端口和认证中间件，连接服务使用替身。

## 8. 后续 review 四项问题修复

1. **旧取消不能中断新版本。** 两条接收路径共用停止入口，要求取消已经落盘，且等待、目标版本、transcript 和活动执行都匹配。按 runId 去重停止请求。Gateway 向嵌入运行注册表传递预期 runId，防止异步停止派发期间会话已切换执行、按 conversationId 误伤新运行。
2. **重启不能越过未处理消息。** 普通新消息持久化与当前 waitId/objectiveRevision 绑定的屏障。重启保留 interrupted 屏障，同时为旧版本的在途消息补齐绑定。恢复输入不能领取或消费有匹配屏障的目标；后台暂停自动检查，不忙循环，不重放可能已完成的工具。界面和模型快照指出中断消息。用户重新提交并明确修改目标后旧屏障失效；或显式移除中断消息，保留原目标继续。其他目标及旧版本屏障不阻塞当前目标。
3. **个人请求清理不取消其他等待。** 重试取消清理时显式传递原 request.connectionWaitId，关闭原 Task 和 allocation，同时保留新目标。
4. **取消不占用提交锁。** 持久化取消后异步等待底层停止结果，后续消息可立即接收、正常排队。实际执行仍串行，停止请求按活动 run 去重，失败记录日志，不以清除租约的方式假装原运行已停止。

另补充了屏障与恢复身份的隔离：屏障 payload 是待处理消息的关联信息，只有 `kind='connection_resume'` 才继承原目标与所选账号，普通消息不能借屏障修改另一目标或继承其授权范围。

回归包含旧版本取消与新运行并发、慢速停止下两种输入入口的即时接收、连续重启保留屏障、删除屏障后单次恢复、改目标后旧屏障失效、旧请求取消重试与新目标并存，以及异步 abort 派发时运行租约切换。
