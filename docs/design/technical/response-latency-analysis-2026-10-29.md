# xopc 对话耗时分析（2026-10-29）

## 结论

现有样本显示：普通对话和 Personal Agent 的主要耗时位于模型调用；手机任务的主要耗时位于工具等待。多轮模型往返、失败请求的长时间等待，以及少数长工具调用构成完成时间的长尾。准备阶段目前不应作为首要优化对象。

这是对本机历史数据的分析，不是修改前后的性能对照实验。下文所有秒级耗时均为后端执行或模型完整调用耗时，不能解释成首字时间、首句时间或浏览器显示时间。

## 数据与方法

- 来源：本地 `traces/traces.db`、`xopc.db` 的 usage/input/run 元数据，以及 `logs/app-*.log`。通过只读 SQLite 连接读取，没有发起真实模型请求。
- Agent 执行样本时间：北京时间 2026-10-22 08:08 至 2026-10-29 00:43。
- 本地存量：1,631 条 Trace、5,136 个 Span；其中 186 个 `agent.run` 全部能关联到输入收据。
- 186 次执行包含：163 次 success、14 次 error、5 次 cancelled、4 次 suspended。成功样本中有 1 次 Trace 被配额截断，成功且完整的分析集为 **162 次**。所有其他状态和截断样本仍保留在 JSON 中。
- Trace ID 关联父子 Span；`runId` 关联执行、输入和日志；OTel Span ID 关联 AI usage。后台任务即使复用同一 Trace，也不合并进前台 run。
- 每个 Span 截取到所属根执行时间窗内。模型、工具、压缩和未归因时间按区间去重；压缩和工具拥有内部嵌套模型的耗时。`model.attempt` 是整个循环的容器，不与模型和工具相加。
- 占比是该分组内累计执行时间的占比，不是各请求占比的中位数。模型、配置、任务复杂度和软件版本均有混合，分组差异不代表因果关系。

机器可读结果：[response-latency-2026-10-29.json](./evidence/response-latency-2026-10-29.json)。内容仅包含允许的诊断字段，不包含提示词、消息正文、工具参数、工具输出或凭证。

### 准备阶段

成功完整样本中：

- 输入入库 → `agent.run` 开始：P50 **97 ms**，P95 **323 ms**，最大 **597 ms**。
- `agent.run` 开始 → 首次模型 generation 开始：P50 **134 ms**，P95 **243 ms**，最大 **402 ms**。
- Personal Agent 的上述两个阶段分别为 P50 **254/151 ms**、P95 **443/287 ms**。

两个阶段的分位数不能直接相加。输入到根执行的偏移包含调度、准备及可能的恢复过程，不能称为纯排队时间；`task_runs` 没有与这批根 run ID 匹配的独立队列样本。

在现有工作负载里，即使进一步优化准备阶段，也只能节省其中的几百毫秒，不能解释常见的数秒至几十秒等待。长附件、进程首次启动、高并发排队和其他未覆盖场景不能从这里排除。

### 模型调用与往返

根执行内、按 run 关联并完整落在执行窗口内的模型调用共 **903 次**；以下包含成功、失败和取消，不是仅挑成功调用。

| 请求模型标识 | 次数 | 完整调用 P50 | P95 | 最大值 |
|---|---:|---:|---:|---:|
| xopc-cloud / auto | 631 | 5.16 s | 14.57 s | 122.36 s |
| xopc-cloud / openai-codex/gpt-6.1-sol | 208 | 3.35 s | 8.38 s | 32.80 s |
| xopc-cloud / openai-codex/gpt-5.6-luna | 64 | 2.48 s | 4.09 s | 4.93 s |

`auto` 是请求标识，不代表同一个实际上游模型。以上并非相同问题、相同上下文、相同 thinking 的对照，不能直接得出切换模型后的收益。

- 成功完整执行的主模型调用次数：P50 **3 次**、P95 **9 次**、最大 **49 次**。
- 非手机工具执行：P50 **4 次**、P95 **14 次**；手机执行：P50 **5 次**、P95 **10 次**。
- `agent.answer` 的完整调用 P50 **4.14 s**，工具之后继续调用的 P50 **4.02 s**。工具即使只执行几十毫秒，随后的一轮模型生成仍可能需要数秒。
- 缩减不必要的模型往返值得优先评估；独立工具批处理和减少重复核验是否有效，需要结合任务质量验证，不能从调用次数推断所有轮次都能删除。

### 长尾实例

1. **无工具请求约 135 秒**：run `cb36a283-4a5a-417c-9ac3-dcb6baeb5eee`，Trace `634734494c0aea0b4d556ec48e83eb1f`。第一次 `agent.answer` **122.36 s 后 error**，第二次 **11.35 s 成功**。这条慢请求由模型请求失败和再次调用主导；现有数据不能再区分云网关、网络或具体上游处理环节。
2. **49 次模型调用、约 601 秒**：run `afed6e20-7707-4137-806e-64833ef72111`，Trace `8f7100e3722873eb85ec92c04c644f8e`。模型 **445.43 s**，工具 **62.30 s**，压缩 **90.94 s**。这是一次多轮任务，不应作为普通聊天的 RT。压缩在总体上占比较低，但能拖慢个别超长执行。
3. **手机工具长尾**：275 次手机工具 Span 的 P50 **502 ms**、P95 **90.01 s**，20 次超过 60 秒；其中包含失败、取消和等待协助。最长 3 次约 **1,800 秒**，不应全部当成设备动作耗时。应将设备执行、人工等待、恢复及超时分开测量，再决定超时和恢复策略。
4. **命令工具长尾**：172 次完整关联的 `exec_command` Span，P50 **598 ms**、P95 **60.11 s**，最长 **240.09 s**。任务中的命令等待同样会拖长完成时间。

工具 Span 的 success 依赖现有追踪包装器：作为普通文本返回的结构化失败可能仍被标记 success。因此不把 Span status 当作工具语义成功率。

### 缓存与推理数据不足

903 次模型调用都能关联 usage，账本里的 cache-read 和 reasoning token 计数均为 0。不能据此断言没有缓存或没有推理：这些字段可能未由上游返回或未被云链路透传。

应先验证云链路的缓存/推理 usage 透传，再讨论缓存命中率和 thinking 对耗时的影响。本次分析没有证据证明缓存未命中是主要瓶颈。

## 首字与前端覆盖缺口

历史日志中有 780 条 `first_model_request`、6 条 `first_model_text` 和 6 条 Gateway 首字记录，但与本次 186 个真实根执行的 run ID **零匹配**。这些未关联记录没有进入真实首字统计；不根据其极低的模型耗时推断线上表现。

本地 Trace 中也没有这批请求的首字属性。前端 `response-latency.ts` 的首字、首句及渲染延迟存放在进程内存，现有数据库没有持久化快照。因而目前能定位的是**后端完成耗时的主要来源**，还不能给出真实首字 P50/P95，也不能排除首字展示阶段的问题。

为后续请求复用既有计时，本次将以下数值写入 `agent.run` 的属性，并沿既有通路存入本地及可选的 Langfuse：

- `xopc.latency.embeddedPreparationMs`：embedded turn 内部准备耗时，起点晚于根执行开始。
- `xopc.latency.modelFirstTextMs`：产生首个非空正文的当前模型调用，从请求发起到该正文的时间。
- `xopc.latency.firstRequestToTextMs`：同一次 embedded attempt 的首次模型请求到首个正文的时间，包含这次 attempt 内先工具后文字的轮次；不包含之前失败的 fallback attempt。
- `xopc.latency.modelRequestNumber`：首个正文出现在这次 attempt 的第几次模型请求。

每个指标在根执行上保留首次记录，防止后续 attempt 覆盖。它们是服务端首个模型正文指标，不是浏览器可见首字，也不保证是最终答案而非过程说明。新字段需要运行更新后的源码/构建才能产生，不能补写历史请求。

## Langfuse 与查看方式

当前配置没有设置 `observability.tracing`，因此使用默认的本地追踪开启、Langfuse 导出关闭。未更改远程导出设置或上传历史数据。

已有入口：Gateway 控制台 `#/settings/tracing`。本地列表可查看 Trace，并按 Trace ID 打开详情。要在 Langfuse 看新数据，需在这里配置目标、凭证并启用导出；连接成功后新指标随根 Span 导出。当前本机 18790 端口没有 Gateway 服务，因此本次读取的是本地数据库，不是运行中 API。

## 后续优先级

1. **普通聊天**：在相同问题、上下文及 thinking 下，对比模型路由；重点追踪慢请求失败原因和重新调用前的等待。将总体预算与提供商超时策略对齐，避免慢请求耗尽大部分对话时间后才重试。
2. **工具任务**：按实际任务质量检查冗余往返、重复读取/核验；批处理独立操作。重点查看调用次数高的长任务，保留必要验证。
3. **手机与命令**：分开统计真实动作、外部进程、等待人工协助和取消恢复。约 90 秒或 30 分钟的长 Span 应先确认生命周期含义，再调整超时。
4. **首字覆盖**：更新运行版本后采集根 Span 的首字字段；同步采集浏览器侧首次正文和渲染延迟，以 runId 关联。历史数据无法替代这一步。
5. **缓存/上下文**：核实缓存与 reasoning usage；单独检查实际压缩执行及极端慢样本。暂不优先做毫秒级会话准备微优化。
