# xopc 品牌桌宠：现状调研与立体角色方案

日期：2026-10-17。状态：初始调研记录。范围：Electron 桌宠；不涉及 ChatGPT Work 宠物服务。

实施更新：用户确认以 Loopi Concept 05 的等粗圆环、白色核心和无肢体造型接入，正式采用分层 SVG 动画，替换三个旧内置角色，不保留旧角色兼容。共享图形见 `src/pets/loopi-artwork.ts`，运行组件见 `web/src/features/desktop-pet/loopi-desktop-pet.tsx`。下文的新增肢体、离线 3D 和保留旧内置角色等内容是此前的候选方案，已由本次确认方案取代。

## 1. 结论

可以把当前宠物换成由 xopc logo 演化的角色，保留现有任务状态、气泡、多会话提醒、拖拽和偏好设置。推荐首版采用 **统一 3D 模型制作 → 离线渲染透明序列帧 → 现有 v2 宠物包播放**。立体感来自模型、材质、灯光和动作，不要求桌面长期运行 WebGL。

建议角色暂名「Loopi」：让 logo 的深色长弧与蓝色短弧成为角色本体，保留圆环、缺口和分段关系，添加克制的表情和短肢体。先完成静态设计与三个动作样片，再制作全套 15 动作。名字和造型属于提案，并非已确认的品牌资产。

本次进行了源码与官方技术资料调研，没有启动桌面应用、测量性能或生成美术样片。下列性能指标与工期均为待验证目标或估算。

## 3. 视觉设计

### 推荐方向：软胶圆环小伙伴

- **主体**：厚实、圆润的分段圆环，视觉上类似软胶收藏玩偶。深石墨长弧 + 品牌蓝 `#007aff` 短弧；初始正面姿态沿用 logo 的比例和方向，动作只做轻微形变。
- **品牌识别**：保留两个弧段间的空隙和圆环负空间。不要把圆环填成球，也不要仅把 logo 印到普通机器人的胸口。
- **面部**：两只可读的大眼睛放在长弧前侧表面，不用面板填满中心。小嘴可选；眨眼、眼神和头部倾斜承担主要情绪。
- **肢体**：两只短胶囊手、两只豆形脚。静止时收拢，不破坏圆环剪影；身体占总高度约 75%–80%，避免普通大头机器人轮廓。
- **质感**：哑光软胶主体、略有光泽的眼睛、宽柔光高光、适度接触阴影。材质和灯光来自统一模型；不依赖厚黑描边制造形体。
- **视角**：接近正面的轻微 3/4 视角，固定相机和落脚基线；保留可读的圆环孔洞，避免透视过强挤掉短弧。
- **明暗背景**：以材质边缘高光保证深色桌面可见性，预烘焙轻微透明接触阴影；不跟随桌面主题把角色整体换色。
- **可爱来源**：较大眼睛、短肢体、动作预备、轻微挤压与回弹、自然停顿。避免持续跳跃、持续旋转、满屏粒子和持续发光。

候选方向比较：

| 方向 | 优势 | 问题 | 决策 |
| --- | --- | --- | --- |
| 分段圆环本体 | logo 辨识度高，可形成专属 IP | 需要验证环面上眼睛的小尺寸可读性 | 推荐 |
| 白色团子身体 + 环形头饰 | 容易做得可爱 | logo 更像装饰，角色通用感强 | 设计备选 |
| 通用机器人胸口贴 logo | 制作快 | 延续当前模板形象，品牌升级有限 | 不选 |

在正式动画前，出正面/侧面/背面设计、表情板，以及 40/112/157 CSS px 的浅深背景对比稿；验证去掉文字也能辨认 xopc。

## 4. 动作设计：沿用全部 15 个动作键

| 动作 | 表演方案 | 播放策略 |
| --- | --- | --- |
| idle | 缓慢呼吸、偶尔眨眼、手自然收拢 | 低幅度循环 |
| sleep | 微微蹲下，闭眼，蓝弧亮度收敛 | 安静循环 |
| wake | 睁眼、伸展、恢复站姿 | 单次，回 idle |
| greet | 眼睛看向用户，小幅挥手 | 单次 |
| prepare | 轻歪头、托腮，短暂停顿 | 单次或由控制器重入 |
| research | 拿小放大镜观察，眼神左右移动 | 循环 |
| read | 看一张小卡片，轻微翻动 | 循环 |
| create | 握短笔在卡片上画写 | 循环 |
| execute | 在小控制板上按键，身体轻微前倾 | 循环 |
| wait | 收起道具，摊手并看向用户 | 安稳循环，不催促 |
| success | 开心眯眼、一次小弹跳/挥手，蓝弧微亮 | 单次后回稳定姿态 |
| concern | 轻皱眉、停下动作，保持镇定 | 单次后稳定等待 |
| pet | 轻微压扁、眯眼、回弹 | 用户主动触发，单次 |
| pickedUp | 手脚下垂、惊讶表情，小幅摆动 | 拖动期间保持 |
| released | 落脚压缩、柔和回弹 | 单次，回到真实任务状态 |

推荐循环片段 12–24 fps，活动动作约 0.8–1.5 秒；idle 可采用更长、更低频片段。最终由样片确定，不把固定帧率当作可爱程度指标。

`pet` 动作虽已在协议中，但当前点击直接打开主窗口，需为抚摸另设显式交互，例如菜单动作或可关闭的长按；首版保留点击打开与拖拽语义，避免改变用户习惯。

## 5. 渲染路线与决策

| 路线 | 品质与能力 | 接入成本 | 局限 |
| --- | --- | --- | --- |
| 渐变 SVG / CSS 伪立体 | 可快速出形体概念，包小 | 低 | 多角度体积、遮挡、材质和动作上限低 |
| **3D 离线渲染序列帧** | 固定视角可得到统一模型、柔光和稳定形体 | 中，复用当前 v2 | 转向和表情需要提前制作，素材有解码成本 |
| 实时 Three.js + GLB | 自由转头、连续视线跟随、动作混合 | 高，新增渲染、资源协议和降级机制 | GPU 常驻、上下文恢复与桌面透明合成需实测 |

首版选离线渲染。Blender 官方输出文档支持 RGBA 图像输出，Film 透明背景适合生成合成素材；使用统一模型批量渲染可以控制跨帧一致性。[Blender Output](https://docs.blender.org/UATEST/manual/en/dev/render/output/properties/output.html)、[Film](https://docs.staging.blender.org/manual/en/latest/render/cycles/render_settings/film.html)。这说明制作链路可行，不代表已经验证当前项目的性能。

若未来明确需要实时视线、任意转向或可交互灯光，再增加独立 3D renderer。Three.js 的 [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader) 可加载角色资源，[AnimationAction](https://threejs.org/docs/pages/AnimationAction.html) 支持动作淡入淡出。即使升级也应保留序列帧降级资源，不能把两种格式混装进现有严格 v2 协议。

## 6. 首版技术设计

### 6.1 资源生产与协议

生产流程：品牌 SVG → 角色设计稿 → Blender 统一模型/绑定/表情 → 15 个命名动作 → 固定相机灯光批渲染 → 透明 PNG 帧 → 按动作拼接横向条带 → manifest → 自动校验 → 桌面预览。

建议原始渲染为 384×384；首轮接入每帧 320×320，覆盖最大约 157 CSS px、2× DPR 的需求。更高 DPR 单独评估。主体在画面内保留边距和一致基线，道具、影子、弹跳全部在同一固定包围盒内。不要按每帧内容独立裁切。

每动作独立 PNG/WebP 条带，优先 24 帧以内，避免把全部动作打成一个巨型图集。320×320×24 的 RGBA 解码理论约 9.4 MiB；15 条全解码约 141 MiB，尚未计 GPU、副本与 IPC，文件压缩小不等于内存小。idle 片段可用较少采样或分阶段制作；过长横条应拆片或减少帧数，不能依赖不确定的最大纹理尺寸。

沿用 v2 manifest：显式给出 `canvasWidth`、`canvasHeight`、`fps`、15 个完整动作，每条使用 `offsetX: 0, offsetY: 0`。首轮美术只做三个样片，但最终验收必须包含所有动作，不降低 validator 要求。

先以 `custom:xopc-loop` 包在测试状态目录验证，无需更改生成工厂；发布时再增加稳定的内置 id `xopc-loop`。建议源码素材目录 `assets/desktop-pets/xopc-loop/`，打包时复制至 Electron 资源目录，使用统一 manifest loader 读取。该路径为新增设计，实施时必须同时调整开发路径和实际打包脚本，验证安装包中可读取，而非只验证开发目录。

### 6.2 加载与 IPC

现有 loader 在每个动作中调用 imageToDataUrl，同一源也会重复读取；状态包含所有角色的完整素材，并被广播到所有窗口。SVG 时代可容忍的模式，换成大图后需要拆分：

1. 宠物列表/偏好状态仅携带 metadata 和缩略图。
2. 选中角色时单独获取定义，使用受控本地资源 URL；轻量状态更新不再重传所有二进制。
3. 按资源路径与版本缓存加载结果；只预加载当前角色的 idle、当前动作和必要下一动作，取消隐藏列表的持续动画。
4. 若引入 Electron 自定义资源协议，只允许已登记的内置目录与宠物目录，不提供任意路径读取；校验 URL、路径和 MIME。
5. 首个 POC 可沿用 Data URL 测视觉，但应记录 IPC 大小、首次加载和切换耗时；正式发布前按测量结果完成资源传输改造。

### 6.3 播放与动作调度

当前播放器存在需要在样片接入时验证/修正的细节：

- 所有普通状态叠加通用上下浮动；烘焙动作已含位移，叠加后会出现滑脚和双重起伏。品牌角色关闭通用 float，保留旧角色原有行为。
- 统一 `FRAME_BLEED_PX = 8` 可能把共用图集下一行带入显示；正式素材固定边界并移除/限定该补偿。
- 单次 CSS 播放缺少显式完成态，结束后可能回到首帧；相同动作再次触发也没有可靠的实例重启动语义。
- 部分交互按 700/1400 ms 定时恢复，与素材实际长度脱钩。

建议加入轻量动作控制器：`action + instanceId + startedAt + playbackStatus`，根据 `frameCount / fps` 和结束事件控制返回；非循环帧只播放 0..N-1，再保持末帧或交还任务状态。相同动作的新实例可以重播，同一任务普通数据更新不重复重播。

调度：拖拽期间 pickedUp 优先；释放播放 released 后立即按最新任务状态恢复。等待确认/错误不能被闲置招呼覆盖；运行中普通阶段设置短暂稳定窗口，避免频繁切动画，但等待/错误到达时应及时切换。任务事实和气泡不因动画防抖延迟。

静态跨帧淡化容易出现双眼、双手重影，首版采用统一姿态起止和短稳定窗口；不要承诺序列帧可以像骨骼动画一样任意平滑混合。

尊重应用 reducedMotion 与系统 prefers-reduced-motion；使用每动作具有代表性的静态帧，让状态文字仍可见。窗口隐藏、系统休眠和不需要预览时暂停播放。

### 6.4 校验与兼容

`src/pets/validator.ts` 目前仅对 SVG 读取真实尺寸，PNG/WebP 主要检查可读性，不能保证图像可解码和帧边界有效。应增加真实解码尺寸与条带范围检查，并限制源文件大小、单图像素、帧数与角色总解码预算；限制值通过样片测试确定。

离线方案无需升级 manifest schema。只给新用户默认选择 `xopc-loop`，保留现有用户选择和 enable 状态；缺失或损坏资源回退有效旧角色并显示校验信息。保持自定义 v2 包和三个原有内置角色兼容。

## 7. 实施拆分与验收

| 阶段 | 交付物 | 进入下一阶段条件 |
| --- | --- | --- |
| A：造型与样片 | 角色三视图、表情板、idle / execute / success 三个样片 | 40/112/157 px 可读，深浅背景可见，logo 识别度和可爱方向确认 |
| B：技术 POC | 测试目录内的 v2 包、独立条带、播放修正、加载与性能记录 | 透明边缘无黑白边，动作无串帧，无明显切换空白 |
| C：完整交付 | 15 动作、内置资源打包、IPC/缓存优化、默认选择策略、双语名称描述 | 安装包/开发环境都可用，旧选择保留，损坏包可回退 |
| D：可选实时 3D | GLB、独立 renderer、能力检测和序列帧回退 | 只有明确交互需求且性能测试通过才开展 |

粗估：熟悉角色制作的美术/技术美术投入下，A 约 2–4 人日；B 约 1–2 工程人日；C 约 3–6 美术人日加 3–5 工程人日。角色返工、素材生产工具、目标设备与审核轮次会影响周期，不是交付承诺。

必要验证：

- 包校验：15 动作齐全、PNG/WebP 解码、边界、资源预算、非法路径与损坏资源。
- 播放控制：最后一帧、相同动作重播、事件连发、拖拽释放、错误/等待抢占、减少动态。
- 业务回归：运行→等待→继续→成功/失败，多会话切换与会话跳转；主窗口关闭/重连时反馈链路是否持续，作为现有架构限制单独记录。
- 桌面实测：macOS/Windows 的透明窗口、深浅桌面、DPR/显示器切换、70%–140% 缩放、边缘拖拽、隐藏恢复；其他平台按正式支持范围补充。
- 性能记录：对比旧 SVG 与新角色的首次显示、动作切换、角色窗口进程内存、主进程内存、IPC 载荷、空闲 CPU/GPU；区分冷启动与缓存命中。
- 建议初始门槛：预加载后的动作切换不超过 100 ms；新增角色窗口稳定内存相对旧版本增量争取低于 50 MiB；隐藏时无持续动画。目标必须在同机同场景实测后决定是否达标。

核心决策：先把「属于 xopc 的立体角色」做对，再扩大角色的实时交互能力。首轮应评审角色样片与实际桌面效果，不能只看大尺寸概念图。
