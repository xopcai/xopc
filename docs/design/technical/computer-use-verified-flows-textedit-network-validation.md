# TextEdit over the real Gateway / desktop network

The existing [network matrix](./computer-use-verified-flows-network-validation.md) also has an opt-in TextEdit mode. It uses the same independent Gateway and Electron processes, real HTTP/WS transport, signed desktop identity, invocation-bound frame uploads, GUI-Plus inference, authorization checks and completed-result-loss proxy. It does not start the AppKit fixture or replace the native driver.

```sh
XOPC_FLOW_TARGET=textedit pnpm exec tsx scripts/run-computer-network-flow-validation.mts --textedit
```

Before running, open TextEdit Settings on **New Document**, with Author, Organization and Copyright empty. The native New Document observation must expose the five expected text fields, with the three property values empty; otherwise its frame is zeroed and inference is refused. Only this non-sensitive window may be sent to the configured direct DashScope GUI provider. Keep Settings locally visible throughout the test; its window can hide when TextEdit deactivates. Within the already authorized desktop open, the harness waits up to four minutes using only native app/window metadata for one visible Settings window on its current display Space, stable for at least one second. Keep TextEdit Settings on the same macOS desktop/Space as Codex during local preparation; switching to an off-Space window briefly is insufficient. Application activation metadata is diagnostic only, matching the production `prepare: false` visibility requirement. This avoids a separate preflight-to-network-open gap. This is a setup condition, not an action retry or an authorization grant. The subsequent ordinary open independently checks visibility again; a lost window still stops the phase.

The harness requests fresh native window candidates through the ordinary invalid-ref response without capturing pixels. It selects only a unique exact **Settings** title with the returned window ref. After the enumeration session drains, the explicitly bound open waits locally for readiness before calling the unmodified target resolver. Every observation independently checks that the selected native window still has that title before capturing pixels. Only native **New Document** / **Open and Save** radio-button activations reach the real driver. The normal broker validates current refs, grants, observations, process and geometry. No preference values, documents, coordinates, typing or keys are changed.

Capture must independently verify **HTML Saving Options** in the native observation after one scenario activation, release control and explicitly save the flow. Reuse starts fresh Gateway and desktop processes and requires the same persisted flow UUID and authenticated device principal, a fresh endpoint ID, fresh inference with untrusted hints and normal session/action authorization. Removing app access must deny with zero observations, inference or native inputs. Unknown-result validation withholds exactly one completed native act reply after positive native effect evidence; the real invocation deadline must produce unknown dispatch, zero rescue/replay, confirmed release and refusal to save. Each successful phase separately restores New Document and revokes isolated app access. Baseline verification at the beginning of a TextEdit phase shares the scenario lease and requires New Document already selected; it sends no setup input.

Every phase runs once. Missing native evidence fails even if the GUI model claims success; the optional read-only diagnostic probe does not promote a failed capture. The runner never repeats an uncertain input. Failures retain metadata-only diagnostics and leave the application state available for inspection. No screenshot, AX contents, token or private key is written to evidence.

## Current validation status

The TextEdit mode is implemented. Automated regression checks passed (440 tests, 9 skipped), root and runner TypeScript checks passed, and Electron main/preload builds passed. The real TextEdit matrix has **not passed**; no change has been committed on the strength of these runs.

After local foreground preparation, native metadata still identified Settings on Space 9 while the active Space for its display was 6 (`onCurrentSpace: false`), including samples with `isOnScreen: true`. The test readiness check therefore requires the window to remain on its current display Space as well as visible; it does not change production window admission. Earlier authorized foreground-preparation attempts were also refused by macOS.

The final capture attempt used Gateway PID 8887, desktop PID 9064 and actual TextEdit PID 93522. Its four-minute approved local readiness wait ended with Settings still off-screen and off-Space (9 versus 6), zero observations, model requests or native inputs, and confirmed release. Its Gateway, desktop and embedded driver processes exited. No flow was saved, so restart/reuse and unknown-result phases were not run. Fixture-network results do not count as TextEdit results. Continuing requires a stable Settings window on the same display Space; another readiness acknowledgement alone does not establish that condition.

Driver preparation now refreshes native app activation metadata after restoring a hidden app and rechecks the same process identity. It avoids deciding whether to activate the window from stale pre-restoration app state. Tests cover a newly active app, an app still inactive and a changed process. This does not convert a native foreground refusal into success or relax window visibility checks.
