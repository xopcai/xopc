**Phone Use：AutoGLM 失败定位与真实 App 配对验证（2026-10-24）**

本轮继续定位上一轮“进入关于手机并显示 Android 版本”失败，并检验针对性修复是否改变真实任务完成率。这里的“真实”指真实 AutoGLM API、生产 PhoneRuntime/ADB 驱动和实际 Android 原生 App；运行设备为专用 API 35 模拟器，不是真机，也不是 MockPhoneModel 或模拟页面。

**最终结论**

本轮没有验证到真实完成率提升。V1 为 15/21 → 9/21；V2 有效配对为 11/13 → 8/13，均出现回退。两个候选均已撤回，最终五个生产 phone 模块与本轮开始时逐字节相同；上一轮已落地的输入替换、完整 JSON 轨迹、有界修复和连续完成复核继续保留。本轮留下的是更严格的真实 App 评测、诊断与证据，以及避免无关验收条件的工具手册指导，不把这些称为完成率提升。

证据：[生产恢复校验](evidence/phone-real-app-restoration-2026-10-24.json)、[全部计数汇总](evidence/phone-real-app-combined-2026-10-24.json)。

**失败轨迹与原因**

对上一轮工作区实现重新复现，模型先正确执行两次向上滑动并点击 About；进入正确页面后，原生节点已有 Device name / Model，但版本行尚未完整显示。模型接着点击返回箭头 `[67,86]`，随后错误进入 System，最终耗尽 8 次模型请求。没有发生 About 页的滑动，因此这条轨迹不能归因于 About 页滑动过快。后续转场曾触发一次布局失效，保护机制正确丢弃了预测，它也不是最初走错路径的原因。

代码核实了两处与该行为有关的输入不足：旧适配器每轮只重建一个大 JSON 用户消息，把历史动作作为 JSON 数据发送，没有保留 AutoGLM 上游使用的 assistant 字面量动作轮次；完成状态只有固定的 pending 标记，没有直接指出“已在正确应用、哪些条件已满足、还缺什么”。这些输入差异是可验证的事实，但不能仅凭源码断言每一项各贡献了多少完成率；尤其不能把上游保留推理过程的历史，等同于只保留动作字面量的历史。

两组候选试验只改变模型适配层，不放松陈旧页面、应用范围、输入确认、取消、人工接管或未知派发不重试等控制，不加入 Settings 专用路径或硬编码动作。

**第一候选 V1：实验改动**

- AutoGLM 收到最近最多 8 步实际执行过的 assistant 字面量动作及下一轮观察结果；仅最新一轮带图，图片位于该轮文本之前。
- 人工动作、未知派发不伪装成模型已执行动作。长文本与插入语义无法准确表示为 AutoGLM Type 时，明确标为预览，不伪造截短后的历史操作。
- 将完成条件的已匹配文本、缺失文本、任选条件、应用与准确字段匹配结果放在最新截图旁；它们是观察进度，不是完成证明。
- 提示模型：部分页面条件已成立但目标未显示时，应先检查/滚动当前页，除非证据表明页面错误；没有在执行器里硬禁止 Back。
- 原生 UI 上下文仍限 40 个节点，但聚焦字段、完成条件相关节点和有文字节点优先，减少空点击容器挤掉目标信息的情况。
- 最终完成仍由既有连续两次新观察确认，并保留取消、控制权、授权复查。

相同旧目标、相同 8 次请求/55 秒预算的单次定向诊断中：修改前未完成，候选版在 About 页面继续滑动，独立检查版本行和身份文字通过。两次均用了 8 次模型请求；候选版仍有绕路。因此这只说明修改后出现一次成功；不能排除随机性与时序影响，也不能把这一对运行作为完成率结论。

证据：[脱敏诊断轨迹](evidence/phone-about-root-cause-2026-10-24.json)。诊断只保存动作和必要页面标记，不保存模型原始推理。

**正式真实 App 对照方法**

基线为本轮开始时的完整五模块工作区快照，SHA-256 与上一轮最终报告一致；不是更早的 Git HEAD。快照包含 runtime、model-adapter、adb-driver、contracts 和 reliability，基线导入重新绑定至自身模块，避免新修复泄漏。与共享基础设施交互时，仅在 contracts 字节完全相同时复用其错误类型。

[基线源码归档](evidence/phone-real-app-baseline-2026-10-24.tar.gz)包含源码与哈希清单。候选生产源码、任务、判定器在正式运行前冻结，运行中检查源码哈希。

7 类任务，各重复 3 次，每次新旧各执行一次，共计划 42 次运行；按任务与轮次交替 AB/BA。两臂相同目标、完成条件、8 次模型请求、12 个动作、90 秒活跃预算；整套上限为 300 次实际 API 请求、30 分钟。输入、任务重置和独立观察走真实 ADB。

| App | 任务 | 独立判定要点 |
|---|---|---|
| Settings | 进入关于手机显示版本 | About 页面身份、版本行与实际版本值完整可见 |
| Settings | 打开显示设置 | 正确页面及亮度条目可见，显示相关系统值不变 |
| Settings/Search | 搜索 display | 原生查询字段准确匹配，实际显示设置结果可见 |
| Clock | 打开秒表 | 标题确为 Stopwatch、秒与百分秒为零、尚未启动 |
| Clock | 配置 2 分 30 秒 | 原生时长准确为 00h 02m 30s，仍在未启动的配置状态 |
| Files | 从 Recent 找到 Downloads 文件 | Downloads 文件夹身份与测试文件名均可见 |
| Files | 搜索测试文件 | 查询字段准确、目标结果出现、另一测试文件不再显示 |

所有判定器都先在真实 App 上手工验证正例与未完成起点，过程不调用模型、不计入成功率。此前的版本任务额外要求 Model 同时可见；这不是用户看版本所必需。本轮用 About 页面身份替代该额外要求，并检查实际版本值。新旧两臂使用完全相同的新任务，故本轮只能作内部前后对照，不能把新任务结果直接与上一轮 1/2 横向计算提升。

每一条完成结果都要求两次独立终态观察，不以 finish 或 runtimeVerified 为准。显示任务检查四个系统值不变，Files 检查两个测试文件的哈希不变；Clock 的启动/加闹钟等明显越界动作、Files 打开测试文件等不符合目标的动作对两臂等价阻止，并计为失败。这些是评测共同控制，不冒充本轮生产运行时新增能力。

第二臂在模型调用前最多重置两次，使起点指纹与第一臂相同；仍不匹配的记录保留并单列，不能混入主要配对完成率。保留全部失败、提前结束、请求上限、超时与状态不匹配，不重跑计分失败以挑选好结果。

**结果与解释**

第一候选 V1 已完成全部 42 次运行，21 对起点均匹配，未发现错误完成声明或采样不变量违例：

| 任务 | 基线完成 | V1 完成 |
|---|---:|---:|
| 关于手机及版本 | 3/3 | 2/3 |
| 显示设置 | 3/3 | 3/3 |
| 设置搜索 | 3/3 | 0/3 |
| 秒表 | 3/3 | 3/3 |
| 配置计时器 | 0/3 | 0/3 |
| Files Downloads | 1/3 | 1/3 |
| Files 搜索 | 2/3 | 0/3 |
| 合计 | 15/21（71.4%） | 9/21（42.9%） |

V1 下降 28.6 个百分点，实际模型请求为 67 → 87，两臂累计执行耗时为 615.749 → 914.036 秒。因此拒绝将 V1 对话消息重排作为默认；完整轨迹仍由原有有界 JSON 方式提供，没有撤掉执行历史。

轨迹显示：About 的新版第三轮连续输出截断；设置搜索中原生字段已聚焦，新版却出现额外点击、返回、重新打开；Files Downloads 有已记录的 Back 离开 Files 返回之前的 Clock，再被应用范围保护停止；计时器两版都存在数字选择与状态规划错误。格式错误与截断也出现在原版，不能把每次错误都归因于同一根因。

证据：[V1 全部结果](evidence/phone-real-app-v1-2026-10-24.json)、[V1 逐步轨迹](evidence/phone-real-app-v1-traces-2026-10-24.tar.gz)、[V1 源码与冻结评测归档](evidence/phone-real-app-v1-source-2026-10-24.tar.gz)。固定任务的小样本只说明本面板，不代表第三方商业 App、网络波动、生产账号或跨平台总体完成率。

**第二候选 V2 的预设方向**

正式 V1 面板尚未结束时，已根据保留的开发轨迹决定：下一候选恢复原有单个 JSON 用户消息结构，不默认采用 V1 对话轮次重排；在原生 UI 中增加归一化中心点和明确的非密码输入焦点提示，补充“软件键盘不可见不等于无法输入”和“根页面优先使用应用内导航”的通用提示，并对齐上游 `top_p=0.85`、`frequency_penalty=0.2`。不增加动作、请求、时间预算，不添加 App 专用动作，不自动绕过应用范围拒绝。

V2 已完成 28 条记录，其中 27 次实际调用模型；一对 Clock 起点的非编辑列表焦点标记始终不一致，按预设规则排除整对后，主要比较为 13 对：

| 任务 | 基线完成 | V2 完成 |
|---|---:|---:|
| 关于手机及版本 | 2/2 | 1/2 |
| 显示设置 | 2/2 | 2/2 |
| 设置搜索 | 2/2 | 2/2 |
| 秒表（有效配对） | 1/1 | 1/1 |
| 配置计时器 | 0/2 | 0/2 |
| Files Downloads | 2/2 | 2/2 |
| Files 搜索 | 2/2 | 0/2 |
| 有效配对合计 | 11/13（84.6%） | 8/13（61.5%） |

V2 同样未提升，下降 23.1 个百分点。完整原始记录为基线 11/14、V2 9/14，不能用这个不平衡口径替代主要配对结论。全部 98 次 API 返回 HTTP 200：基线 47 次请求中 2 次因输出达到 3000 tokens 截断；V2 51 次中 7 次截断，另有 3 次正常 stop 但最终格式未被识别。参数、原生提示和上下文共同变化，不能把差异单独归因于 frequency_penalty 或某个中心点字段。

V2 的 About 失败轨迹在列表中已经观察到 About 条目，但继续反复滑动，说明“文本条件部分匹配”并不代表已经进入正确页面。Files 搜索的某些失败则输出不足 300 tokens、正常 stop，须继续定位协议包装，不应称为网络或 token 不足。

两轮均未出现已计分的错误完成声明，但模型能力候选没有收益，因而不将这些大范围提示/采样改动作为最终默认。保留所有失败，回到上一轮已验证实现，并仅对可证明的协议兼容缺陷作窄修复。

证据：[V2 全部结果](evidence/phone-real-app-v2-2026-10-24.json)、[V2 逐步轨迹](evidence/phone-real-app-v2-traces-2026-10-24.tar.gz)、[V2 源码与冻结评测归档](evidence/phone-real-app-v2-source-2026-10-24.tar.gz)。

V2 按组合方案计分，不把其中某一参数单独宣称为原因。预设复验仍用同样 7 类任务、同样判定器和基线，重复两轮、两臂配对，共 28 次；单轮上限不变，整套请求上限 200。两轮使每项任务的起始顺序恰好为 AB / BA。保留第一候选负面结果，第二组数据单独报告，不把开发过程中的较好样本拼成一个成功率。

**最后的协议定向诊断**

两次额外的 Files 搜索诊断不计入前后成功率，每次均为 3 次真实请求。正常 stop 的失败输出中，未发现 do/finish 调用、大小写/全角/转义变体、已知输入简写、完整 JSON 动作或可解析的既有动作 Schema；不是发现了一个只被 Markdown/答案前缀包装的合法命令。因此没有修改解析器去猜测普通文字的动作含义，也没有放宽语法或安全边界。

另一次诊断还记录到 3000 tokens 截断、85.71% 重复行。这证明存在长重复输出耗尽预算的失败，但不能据此把所有导航或格式错误都解释为同一原因。

证据：[第一次协议诊断](evidence/phone-real-app-protocol-diagnostic-2026-10-24.json)、[第二次结构诊断](evidence/phone-real-app-protocol-structural-diagnostic-2026-10-24.json)。只保存动作、必要 UI 事实和元数据，未保存模型推理原文或密钥。
