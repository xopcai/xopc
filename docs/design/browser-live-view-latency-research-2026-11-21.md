# 网易 UU 远程低延迟调研｜xopc 浏览器预览

2026-11-21 · 公开资料与技术设计 · [浏览器实时预览原方案](browser-live-view-product-technical-design.md)

首期决策已更新为 WebRTC 主路径，本文保留调研时的对照与论证。最新发布门槛以上方方案为准。

## 1. 我们能确认网易做了什么

按「网易出品、手机看电脑、小窗、游戏串流、低延迟」定位，最吻合的产品是 **网易 UU 远程**。网易开发者在 App Store 的说明确认了低延迟直连、只读观看、小窗、无线副屏、超级屏和 4:4:4 真彩，标称最高 4K 144 帧。小窗是否在每个平台都支持跨应用悬浮，公开说明未细分。最高画质是产品能力上限，不能据此推导常规手机、网络下的响应时延。[网易团队的 App Store 页面](https://apps.apple.com/cn/app/id1642306791)

**网易实现细节的证据边界。** 公开资料支持「存在直连和高帧率档位」。未找到网易对视频协议、硬件编解码配置、直连失败后如何调度、弱网重传、硬件和显示链路的明确技术说明，也未找到含原始数据的 UU 端到端测试条件。检索里有多个非网易域名自称官网，页面上的专有协议名和毫秒数字未采信。网易云游戏参加过论文测量，它是另一个产品，论文中的平台结果不能当成 UU 远程实测。

**机制交叉验证。** Parsec 公开了原生端的 UDP BUD、拥塞控制和 P2P 路径，并分别呈现采集/编码、网络 RTT、解码指标。Sunshine 公开了 Windows Desktop Duplication / Windows Graphics Capture、GPU 采集和硬件编码选项，Moonlight 区分解码、解码后等待、VSync 渲染。它们能解释同类产品实现低延迟的工程做法。以下归纳来自可验证的同类系统，属于对 UU 体验的解释，不能反推网易使用了同一实现。[Parsec 协议](https://parsec.app/blog/a-networking-protocol-built-for-the-lowest-latency-interactive-game-streaming-1fd5a03a6007) · [Parsec 指标](https://support.parsec.app/hc/en-us/articles/32381603663636-Stream-Overlay-Stats-and-Logging) · [Sunshine 采集与编码](https://docs.lizardbyte.dev/projects/sunshine/master/md_docs_2configuration.html) · [Moonlight 指标](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions)

## 2. 低延迟来自哪些地方

**画面延迟**从源端画面变化到观看端屏幕显示。它包含等待采集、编码及发送排队、网络、接收抖动缓冲、解码、合成与屏幕刷新。**操作延迟**从手指按下到看到远端结果，还包含输入上行、远端任务调度和应用绘制。**首帧**从点击查看到出现当前画面，受授权、连线、媒体启动和首个可解码帧影响。网络 RTT、单帧解码时间和帧率各自只描述链路的一部分。

| 环节 | 低延迟串流的做法 | 对浏览器小窗的意义 |
| --- | --- | --- |
| **画面采集** | 尽早从系统合成器或 GPU 拿到新帧，减少 GPU → CPU → GPU 拷贝。及时消费采集缓冲。 | 直接取目标标签媒体轨道，关注隐藏、最小化与休眠时的实际出帧。若轮询 5 fps 且页面变化均匀落在采样间隔，光等下一次采样就平均约 100 ms、P95 约 190 ms。30 fps 对应约 17 ms / 32 ms。这里只算等待采样。 |
| **编码** | 支持时使用硬件编码和低延迟模式，减少多帧前瞻、重排序和码率控制缓冲。移动端优先硬解。 | 画面持续变化时，让浏览器媒体栈直接编码。把 CDP 产出的 JPEG 逐帧解码再编码成视频，会引入额外工作。低延迟编码能力由平台和设备协商，浏览器内置栈的实现细节需实测。[NVIDIA NVENC](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-video-encoder-api-prog-guide/index.html) · [Apple VideoToolbox](https://developer.apple.com/videos/play/wwdc2021/10158/) |
| **路由与拥塞** | 一对一可走直连；不同运营商或 NAT 环境需要中继。实时媒体按链路能力调整发送量，重传要考虑帧的播放期限。 | Gateway 做信令和授权。WebRTC 优先选择稳定的 ICE 路径，允许 TURN/UDP 或受限网络的备用路径，按实际候选组合分别测量。即使 P2P，网络拥塞和无线重传也会造成排队。 [WebRTC TURN](https://webrtc.org/getting-started/turn-server) · [RFC 8834](https://www.rfc-editor.org/rfc/rfc8834.html) |
| **帧积压** | 网络跟不上时降低码率与采样。发送前丢弃过时采集帧；丢包后按参考帧依赖补救，必要时请求关键帧。 | JPEG 可按独立帧覆盖尚未发送的旧帧。写入 TCP 的旧字节无法跳过。视频帧也有依赖，不能把任意已编码的 P 帧当 JPEG 随意丢弃。 |
| **解码与呈现** | 抖动缓冲、解码和合成分别设预算，减少解码完成后等下一轮 UI 刷新的时间。 | 小窗和展开视图尽量复用媒体连接及解码器，切换渲染表面。以原生视频表面或 Web 视频元素显示，避免每帧推动整个聊天页面更新。 [Android 低延迟解码](https://developer.android.com/reference/android/media/MediaCodecInfo.CodecCapabilities#FEATURE_LowLatency) · [Moonlight 指标](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions) |

**为何「网络只有十几毫秒」还可能慢。** 一篇 NSDI 2025 论文测量了多款移动云游戏平台，再与其中一个匿名平台深挖渲染流水线。研究发现多个 VSync 等待叠加可引入接近 83 ms，将部分渲染阶段绕过并协调剩余同步后，被改造平台的交互延迟下降约 34%，稳定在 100 ms 内。xopc 不需要采用那套云游戏改造，但应该按阶段量出等待时间。例子也说明 144 fps 的约 6.9 ms 只代表帧间隔，无法代替实测端到端延迟。[NSDI 论文](https://www.usenix.org/conference/nsdi25/presentation/li-yang)

**为何「一开始很快，几秒后开始跟不上」。** 以 30 KB/帧、10 fps 为例，仅 JPEG 就需要约 2.4 Mbit/s。如果该媒体连接实际只能持续收到 2 Mbit/s，按此速率继续写入，1 秒积压约 50 KB，清空已产生的积压就额外需要约 200 ms 的发送量，后续还会继续增长。尽早降低发帧速率与帧大小，比提高客户端解码能力更能解决这一类落后。

## 3. 跟手之外，体验由哪几件事决定

- **点开即看。** 分别量冷启动和暖启动。已有授权的用户点打开后立即并行发起状态查询和媒体协商，源端尽早产生当前代次首帧。显示连接中的真实状态。可在确认授权后预热信令，媒体依观看需求启动。
- **网页文字清楚。** 小窗首要信息是正在做哪一步。展开先让中文、细线和输入框可读，静止时维持分辨率与清晰度，滚动时优先保持画面新鲜和帧间隔均匀。可试 WebRTC 的 text/detail 内容提示并逐端验证。4:4:4 只在有真实收益且端侧支持时评估。[W3C 媒体内容提示](https://www.w3.org/TR/mst-content-hint/)
- **弱网继续看到最新进度。** 以新鲜度、冻屏时长和恢复速度做判断。比起追完整滚动历史，更有价值的是停下来时尽快看到当前位置。状态独立显示「正在重连」「工作电脑离线」「已暂停共享」。
- **小窗展开和切端稳定。** 小窗与全屏在同一设备应复用连接，画面按任务代次清除，敏感跳转和撤销立即清帧。手机和 PC 同时看时，各自拥塞控制，一个端的弱网不会拖慢另一个端。
- **读与控的投入分开。** 首期只读关注最新操作。未来接管要单独测触摸到远端视觉反馈的完整闭环，再评估触控手势、文字输入、指针响应与服务端状态确认。

## 4. 对 xopc 原方案的调整建议

如果目标是 **UU 式连续预览**，把 **原生标签采集 → WebRTC 单向视频** 从远期选项提前到首轮技术验证，与原来的 CDP/JPEG + 独立 WSS 同场比较。CDP/JPEG 仍适合低频进度、无视频能力的源和受限网络。先验证源端是否能交出稳定的视频轨，再由实测决定各来源的上线路径。

| 来源 | 主动验证的路径 | 本阶段边界 |
| --- | --- | --- |
| **个人 Chrome** | 源电脑主动点击共享后，用 tabCapture 把任务标签变成 MediaStream，MV3 offscreen 持有媒体轨并直接进入 WebRTC。 | 验证扩展重启、目标换页、后台与最小化行为。本地手势是实际约束，远端手机无法代替。禁用自动扩大到其它标签。[Chrome tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture) |
| **Electron 内嵌浏览器** | 验证能否把已明确绑定的 WebContents 授权给受信任采集 renderer。确认身份绑定、隐藏时实际帧率和视频渲染。 | 这是候选路径。当前仍需核对任务到内嵌标签的完整执行链。现有 capturePage 适用于快照基线。[Electron WebContents](https://www.electronjs.org/docs/latest/api/web-contents#contentsgetmediasourceidrequestwebcontents) |
| **xopc 管理的无头 Chromium** | 用 CDP screencast 建立可交付基线，后台稳定性和时延先测清楚。高流畅度另评估专用画面源，例如隔离的单任务虚拟显示与编码发布链路。 | 无头实例的获取路径、容器 GPU 和硬编都需要验证；专用显示器也要保证始终只承载获准任务，避免抓取无关系统画面。 |

媒体层初期支持一对一，手机和 PC 都观看时再试一对二，记录直连比例、TURN 比例和源上行。直连连接按观看端单独销毁。Gateway 撤销后，源端关闭对应观看端的 PeerConnection，最后一个授权观看端退出时停止采集。观看端立即清屏，短租约也要覆盖信令断开。避免 Gateway 断连时媒体绕过授权继续播放。弱网降档时仍保留同样的任务隔离和清屏规则。

以 15–30 fps 作为活动页面的测试档，静止页降低发送频率。小窗和展开分别测试画质及耗电，遇到性能问题先量采集、编码、抖动缓冲和呈现。首轮 WebRTC 原生支持以 H.264 等各端共同支持的实际编解码组合验证。保留 Android、iOS 和 HarmonyOS 的能力探测，画中画另外验收；同设备 PC 已有可授权的本地标签时可直接打开原页面。

## 5. 怎么证实它快

**竞品真机实验。** 同一台 Windows PC 和同一部手机，分别跑 UU 只读观看、局域网远程操控、跨网远程操控。源端打开固定测试网页，显示帧计数或颜色翻转。局域网用高帧率摄影同时拍两屏，逐帧计时。跨地不能同框时，用可核对误差的时钟和源时码估算单向帧龄，或在观看端用单台相机测触摸到画面反馈。标注连接显示的 RTT、帧率和分辨率，分清哪些端侧指标可见。相机 240 fps 每帧约 4.2 ms，应记录拍摄、刷新与触摸触发的测量误差。

**xopc A/B。** 同一 Windows PC、同一目标 Chrome 标签、同一手机和网络，比较 CDP/JPEG/WSS 与 tabCapture/WebRTC 的完整方案；在能共享同一采集或编码条件时再分别隔离变量。覆盖局域网、跨城、蜂窝切换、UDP 受限、TURN/UDP、TURN/TCP 或 TLS、低带宽及混合丢包。测试静态文字、滚动、页面跳转及小窗反复展开，额外记录 10 分钟连续使用的掉帧、冻结时长、CPU 与耗电。

| 指标 | 建议首轮验证目标 |
| --- | --- |
| 点击查看到首帧 | 已授权暖启动 P95 ≤ 800 ms，冷启动 P95 ≤ 2 s |
| 源页变化到手机呈现 | 局域网 P95 ≤ 150 ms，稳定跨网 P95 ≤ 300 ms。按直连与中继分别出数 |
| 弱网持续新鲜度 | 统计 P50/P95/P99、每分钟冻结次数和总冻结时长。压测后降档，验证帧龄不会持续上涨 |
| 切小窗与全屏 | 连接保持、任务代次一致，无因重建会话导致的黑屏 |
| 执行影响与撤销 | Agent 动作 P95 增幅 ≤ 10%，正常连接下撤销到观看端清屏 P95 ≤ 1 s，另验失联后租约兜底 |

这些是 xopc 的提案目标，未验证达成。首帧及帧龄用外部观测验收，内部用采集/编码时间、选中的 ICE 候选、缓冲与解码指标定位。WebRTC 的抖动缓冲和解码耗时是累计指标，应对相同采样窗口分别取增量并除以对应计数。跨进程可先用同机单调时钟计时，跨设备不要直接相减未经校准的时间戳。[WebRTC 统计规范](https://www.w3.org/TR/webrtc-stats/)
