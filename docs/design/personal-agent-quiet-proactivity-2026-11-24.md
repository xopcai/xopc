# xopc 主动体验设计：Personal 对话与工作台

2026-11-24 · 产品设计第二轮

发现规则、生活与结构化工作的入口分工及走查，以[第三轮发现与交付设计](./personal-agent-discovery-and-delivery-2026-11-24.md)为准。

**用户照常用 xopc。该说的事，在个人助手里说一句。值得看、可以晚点处理的事，在打开工作台时已经备好。** 助手负责记住上下文、查变化、做准备、选择时机；用户在需要判断、授权或调整范围时才参与。

本轮更新了[第一轮个人跟进方案](./personal-following-product-design-2026-11-24.md)的默认路径。跟进记录继续提供持久性和可控性，用户交代事情、看到价值以及修改偏好主要发生在已有的 **Personal Agent 对话**和**工作台**。以下竞品观察基于 2026-11-24 可查的官方设计说明、产品文档、发行资料和应用商店。小豆使用媒体对公开演示的转述。没有逐款登录实测，因此产品的实际提前量、触发门槛、静音规则和误报表现仍待验证。「pork」按近名且定位匹配的 Poke 研究。

## 1. 七款产品具体把主动服务放在哪里

| 产品 | 用户实际接触到的产品形态 | xopc 可以采用的设计 |
| --- | --- | --- |
| **Meta Muse** | 一个长期主对话承载异步来消息，侧聊承载复杂主题。助手可以先发消息，用户可以直接在聊天里说调低或关闭主动。头像下可见简短状态，点开看活动和权限。Goals 管长期目标，Ideas 收低打扰建议，初期也有建议提示。 | 主对话可以自然承接主动后续。普通机会有安静的承载位置，用户需要核对时再看活动、理由和权限。xopc 工作台覆盖这个位置。 [Meta 团队设计说明](https://introducing-muse.com/) |
| **Instinct** | 官网用「发短信或打电话」介绍产品，买食材、买花、订周末回家的火车等例子都从联系人式的入口出发。官网展示了短信入口，未公开详细的主动投递规则。 | 一句交代、一句回报、在原处纠正。对话中的承诺用日常语言表述「我会在什么情况下告诉你」。 [Instinct 官网](https://instinct.com/) |

| **Grok Bot** | 官方文档把 Chat 当主入口。1.0 的工作场景说明里，Bot 能发现待做的工作，准备材料，跟进未完事项，在需要人判断时把人拉进来。已有授权下减少重复询问，敏感操作另行确认。 | 一条消息最好附带已经完成的准备。把两项可选方案及依据带到用户面前，用户可以直接选、说想怎么改，或打开成品。 [Grok Bot 1.0](https://x.ai/news/grok-bot-1-0) · [产品文档](https://docs.x.ai/grok-bot/overview) |

| **灵光 2.0** | 「帮我管」让用户把描述自然的长期事务交出去，例如买手机、等降价；有值得行动的变化才提醒。在「帮我管」可回看进展、清单及下一步。 | 用户交付的是「我在等什么」这件事。即使没收到提醒，主动打开过往结果时也知道检查到了哪里。把类似状态收进现有详情。 [开发者提供的 App Store 介绍](https://apps.apple.com/cn/app/%E7%81%B5%E5%85%89-%E8%83%BD%E7%AE%A1%E4%BA%8B%E7%9A%84%E4%B8%AA%E4%BA%BA%E5%8A%A9%E7%90%86/id6751496092?platform=vision) |

这组产品公开呈现了三种可结合的做法：**和联系人一样低摩擦地交代（Instinct、Poke），把接续和进展放回长期关系（Muse、灵光），在对方注意力最贵的时候只拿真正需要判断的事来问（Today、Grok Bot）。** 对 xopc 来说，关键决策是把「发现相关」和「值得开口」分开。Microsoft 的通知延迟研究也提供了一个可操作思路：能等的提醒可以等到当前任务结束，有明确期限的提醒则要衡量等待成本。这里用已存在的应用状态、用户设置和业务期限即可。 [Microsoft Research，通知延迟研究](https://www.microsoft.com/en-us/research/publication/balancing-awareness-interruption-investigation-notification-deferral-policies/) · [HAX，按上下文选择时机](https://www.microsoft.com/en-us/haxtoolkit/guideline/time-services-based-on-context/)

## 2. 第一次价值怎么发生

**Onboarding 的默认出口就是日常使用。** 用户在已有引导里确认助手可用的上下文与权限。第一次打开 Personal 还是直接聊天。用户打开工作台、已有一条满足条件的发现时，看到发现本身。已有用户按同一方式进入。候选在后台有据可循，不需要占一个页面，也不因为用户跳过首次引导而补发。

| 已知状态 | 用户见到什么 | 接下来发生什么 |
| --- | --- | --- |
| 有允许用于此目的的上下文，并能就地做出有用的对照或整理 | 在工作台内容出现的原位置放一条结果。例：「试点待确认的 4 项里，只有离线恢复会影响周五发布。我把待决问题和原讨论放到一起了。」 | 可就地查看、继续问或略过。用户说「接下来只盯这个」后才建立长期检查。 |
| 当前对话已谈到同一件事 | 先回答原问题。如果已经找到有用信息，在这一轮答复里自然补一句。 | 用户只是在谈兴趣时可看到相干建议。用户明确委托后才按合适的范围持续查。 |
| 用户一句话给出明确委托，现有权限够用 | 回一句「我看发布看板到周五。新增阻塞、或者需要你定的事，我会来告诉你。」 | 条件、来源和期限随回执可核对。重复提交复用同一件事。承诺基于实际能够读取、检查的来源。 |
| 委托缺一个关键条件，或需要接入新来源 | 在这一轮只补一个必要的问题。例：「你说的阻塞，是发布看板里的 `release-blocker` 吗？」需要新增授权时，在这里解释要读哪处和用途。 | 用户可一句话回答。现有授权能力不足时可接受更窄的来源，或只完成当次有证据的部分。 |
| 没有足够依据或今天没有新价值 | 保持普通聊天与工作台。 | 后面出现真实证据再判断。已确认事项的覆盖状态可以在原详情里查。 |

第一次体验可以来自一次已有范围内的好分析。例如用户刚导入发布周报，助手在工作台把两份有权使用的材料对齐，给出一个决定点。「一次性理解」只允许其授予用途内的处理，留存也遵守该授权；首次采用该来源持续读取时，仍需要清楚交代。兴趣和背景可支持推荐，用户明确委托才建立长期监控。健康只接受用户主动提出且数据范围清楚的回顾，例如已记录的活动，不从会话推断健康目标或给出医疗告警。

## 3. 何时去哪里

| 情况 | 首次呈现 | 需要满足的条件 |
| --- | --- | --- |
| 用户正讨论同一件事 | **当前回复的一部分** | 变化能帮助完成这轮对话。用户不必看第二条独立消息或重新问背景。 |
| 明确约定「一有 X 变化告诉我」，且已命中；或者有已允许主动联系的责任，等下次主动查看明显会错过处理窗口 | **Personal Agent 对话** | 有可信变化和适用的时效。通过当前授权、主动模式、时区、免打扰、活跃对话状态和统一预算。优先准备事实和可选下一步。 |
| 重要但可以等、可以使用的准备结果、对目标有帮助的探索 | **工作台** | 用户过后看依然有价值。尽量挂到已有的关联项目或任务。与明确交付或待判断相关的行优先，探索型内容按已有布局静默出现。 |
| 无变化、证据不全、同一信息重复、期限已过去 | **静默** | 对仍有效的已委托事项记录检查或来源状态。若另有实质影响，例如今后无法再覆盖发布阻塞，按覆盖中断处理。 |

### Personal 对话里，一句话说清为什么此刻值得看

```text
你等的 iOS 审核刚通过。现在只剩 Android 的离线恢复，
会影响今天 17:00 的试点范围。我把两个发布选项整理好了。  [看两个选项]

来自试点发布 · GitHub #184                                [为什么现在告诉我]
```

- 复用正常的助手气泡、头像与时间。发送时写在当前对话末尾。用户正在输入、看历史、听语音或处理前台回合时，主动消息等待自然空档。处于历史位置时继续保留阅读锚点；回到底部或使用现有新消息跳转才定位到新内容。
- 先说变化，再说和用户的关系。处理入口只在有可继续的动作时出现，通常一个主动作就够。详情和来源藏在可发现的弱提示里。不要用空泛的开场、报告标题、长草稿、多枚按钮或单独通知样式占据对话。
- 用户可以直接接一句「为什么是 Android？」或「以后只等它通过再和我说」。引用、解释和调整都落到同一个事项。目标有歧义时只确认「是这次，还是以后都这样？」。
- 这里的「推送」优先指对话内送达。新增系统通知不在本轮默认路径上。显式提醒和原有用户请求的结果走各自既有承诺。

### 工作台上，先给能扫一眼的结果

```text
需要你处理
试点范围今天 17:00 前要定                   两个发布选项已备好  ›

试点发布
已整理试点未确认项                             4 项里有 1 项会影响范围  ›

为你准备
一个 35mm 街拍练习                             10 分钟练前后景构图  ›
```

这三行示意不同内容各自贴在哪个已有位置。日常可能只有一行，也可能整天没有新增内容。探索型内容首版可占工作台一个次要位置，选一条有新意、且能用到的结果。没有结果时不占高度。积极反馈可提高相似价值的排序，阅读时长和点击不单独决定兴趣。常规信息更新不产生工作台任务红点，也不在用户正滚动或操作列表时突然重排；到下一次进入或主动刷新再应用新排序。

点击一条进入现有详情，先看准备好的结果，然后才可展开依据、覆盖和过去的变化。「和助手讨论」打开 Personal 并引用该条，焦点回到输入框。跳转和引用由用户发起，不自动代发问题或在对话新增一条主动消息。看完、延期、处理或结束可以原地操作，也可以自然语言说出来。

## 4. 两个入口只消费同一次更新

1. **每次只选一个触达位置。** 同一事实变化有一个稳定条目。工作台静默展示的更新可以在对话里引用，聊天先送达的更新可以在项目或工作台详情找到。每次送达只有一个入口产生相应的新消息提示。
2. **实质变化或已约定的期限才值得再次出现。** 用户看过「已发现离线问题」后，标签重复改动不再触达。确立了新的截止时间、出现新的决策人或问题解除，都可作为实质变化重新评估。若待决事项此前只在工作台静默出现，到了经约定的提醒窗口仍未解决，可按同一条目的新时机升级一次。升级要说清期限或后果，这次新消息提示只出现在 Personal。
3. **消息的生命周期随事项走。** 登录后补看旧消息时，保留发送时的事实并链接最新状态。已解决、已过期或来源权限撤销后，详情明确显示当前状态。迟到的后台工作只可重新判断当前有效性，过期机会留在历史。多个端共享已读、待处理和停止状态，分别记录看到与解决。
4. **合并重复、校验前台时机。** 账号、事项、同一变化的语义键用来去重，批量变更可汇成一个决定。现有对话空闲与免打扰判定用于最终发送。后台生成完成后、连接恢复后、排队送达前重新检查版本、授权和截止时间。若静默期结束时窗口已过，保留业务结果状态或下调至工作台详情。

轻量控制从内容旁进入。「这条先放下」只作用于当前更新，「这类放工作台」改变以后交付位置，「这件不用盯了」停止这件事。支持撤销误操作。用户当前在看长文、编辑或通话时保留焦点，消息也尽量只在已有的无障碍新消息提示中宣布。用户可以全局说「最近别主动找我」，系统回一句明确说明站内工作台和聊天各自怎么变。已委托且仍有检查承诺的事项如遇来源断开，详情应显示影响范围和最后成功时间。只有覆盖中断会影响近期决定且用户允许主动联系时，才带着补救方式到聊天里问一次。

## 5. 四个产品走查

| 情境 | 希望看到的连续体验 |
| --- | --- |
| **工作，范围决策** | 用户照常讨论发布。两个已授权问题只构成一次工作台准备。用户说「今天过不了就跟我说」。到决策窗口且条件命中时，Personal 发一条与时限相关的消息，带可核对的选项。用户在聊天里说「Android 延后」，原工作台条目标为已处理。 |
| **爱好，拓展边界** | 用户在两次聊天聊到用 35mm 拍街头、画面太平。一次符合来源范围的已有内容给出一个固定机位练习。工作台只写「10 分钟练前后景」，打开有步骤和原始参考。用户做完回来发两张照片，助手接着这次练习聊；用户没打开时保持安静。 |
| **日常，等消息** | 用户说「这个周末的工作坊如果再放名额告诉我」。能检查则复述真实覆盖和截止时间。看到主办方公告后说「多了周日 15:00 一场，还能报名」，附原链接，是否报名由用户决定。发现时席位已满，只在详情记录实际状态。 |
| **健康，明确请求的记录回顾** | 用户说「周日有空帮我看看我记的三次散步」。用户选定记录，覆盖足够时私有工作台出现一次客观回顾。数据缺失时注明是记录不足。长期保持或更改频率由用户交代。 |

## 7. 怎么判断真的丝滑

优先验证**一次打开、一次接续和一次拒绝**。制作原型时给参与者一个正在聊的任务、一条工作台准备，以及一个正在等待的高时效变化。观察他们是否能知道为什么出现、是否需要回复、能否直接继续、能否控制以后同类的出现。单步试用可以发现跳转和理解问题；两周观察才能看到频率与信任是否稳定。

| 观察什么 | 怎么核对 |
| --- | --- |
| **先感到有用** | 首个实际价值出现前新增了几次配置操作？中位数目标为零次独立的主动功能配置。必要授权单列，避免用省点击掩盖信息缺失。 |
| **少打断** | 按条对照「这个时候希望收到吗？」区分有用但不急、有用且及时、完全无关。配对看误打断和错过窗口，数字同时报告。首版为额外的主动聊天设保守初值，每人每天至多一条；原有明确约定的提醒、交付和系统异常由各自规则处理，测试时单列。 |
| **接得上** | 问「为什么」「帮我选第二个」「以后放工作台」时，保留用户浏览位置，跟对事项，最多一轮确认有歧义的指代。 |
| **悄悄做成了事** | 代看用真实事件表对照命中、时效与用户自行查看次数。兴趣用练习尝试、引用和用户日记来判断是否意外有用。打开次数只用于理解分布。 |
| **敢放心交出去** | 验证来源撤权、跨设备、并发输入、预算为零、免打扰、旧事件重放和来源失败。重点看两入口重复提醒、过期冒泡、关联错误、停止后重启四类问题。 |

**下一轮设计验收**：先把「工作台静默放一条成果」和「Personal 在明确窗口发一句」做成同一真实事项的两条路径。用发布阻塞验证可接续和截止时间，用街拍验证探索可以有价值也可以被忽略。连续观察多少次用户会自然接着聊、抽时间用上，或把原来自己做的检查交出去。
