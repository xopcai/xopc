# Benchmark 驱动 xopc Harness 持续自我迭代建设方案

日期：2026-10-23。状态：第一阶段实施中，进展与验收见[实施记录](./benchmark-driven-harness-evolution-stage-one.md)。第一阶段：统一评测证据、并发快速验证、开发者 Dashboard，以及执行收敛与可靠交付试点。

本文定义实施方向、交付拆分和验收条件；具体已实现能力以实施记录和运行手册为准，尚未验收的设计与性能目标不能作为当前能力的说明。历史成绩归属于当次冻结源码、模型和协议，不能代表当前 HEAD。

## 1. 目标与建设原则

建设一个可反复运行的工程闭环：真实问题进入 benchmark，agent 根据轨迹提出可证伪假设并修改 harness，独立评测决定是否晋级，真实使用继续提供反馈。这里的自进化指可追踪、受预算约束、可回滚的 harness 改进，不涉及模型权重自训练，也不预设每轮都会提升。

Harness 包含提示与上下文、工具契约、记忆与检索、调度与委托、状态管理、验证、恢复和交付。评测基础设施负责衡量这些机制，二者保持独立权限和版本。

本建设必须同时实现三个结果：

1. **能力可持续增长**：改进在未见场景有效，并保持既有产品能力；已知题提分不足以晋级。
2. **验证足够快**：分层筛选、并发、增量运行和可信证据复用缩短反馈周期，同时记录完整搜索消耗。
3. **开发者可以持续跟进**：人在 Dashboard 看见当前工作、证据、变化、失败原因和晋级依据，不需要逐个查找本地 JSON。

原则：复用现有评测栈；先客观结果再主观评分；开发集与独立验收分离；协议/评分器变化与产品变化分开；未知值不记零；原始证据不覆盖；真实模型、脚本模拟、校准和计划分别展示。

### 2.2 当前阻碍持续迭代的问题

- 证据散落在版本化 baseline、独立 `.xopc-evals/*/evals.db`、summary 和报告中；缺少机器可查询的“最新完整且适用基线”。
- `completed`、自动评分通过、确认通过、待复核、源码漂移和晋级成功的含义不统一。现有页面的跨实验总通过率不能作为产品能力总分，EQ 特征也不能被平均 score 代替。
- 通用 runner 串行，部分专题脚本并发；没有跨实验共享的 provider/凭据额度及 CPU/桌面资源治理。
- 相同问题以独立实验重复建设；缺少失败 → 假设 → patch → 开发评测 → 验收 → PR/版本的连续记录。
- 工作扩展存在未完成试验，对话和记忆有未通过独立门禁的候选；必须保留这些状态，不能以最后一条或最高分结果替代。
- Dashboard 缺少实时跟踪和证据语义，是第一阶段交付内容，不能留到自动优化完成后再补。

## 3. 能力地图与评测分层

### 3.1 两个正交分类

每个 case 同时标注 `scenarioTags` 和 `capabilityTags`；suite 继续保留原 id/version，不按新分类重写历史成绩。

| 用户场景 | 成功结果 | 跨场景能力 |
|---|---|---|
| 日常交流 | 合适回答、必要澄清、遵循当前偏好 | 意图、事实边界、范围、表达 |
| 研究与决策 | 可溯源结论、冲突与未知明确 | 检索、证据绑定、综合、验收 |
| 数据与文件 | 正确、可下载、可复现产物 | 执行、验证、发布、版本 |
| 编码与项目 | 修复/功能正确、已有行为保持 | 发现、编辑、测试、收敛 |
| 长期工作 | 跨会话/压缩/重启后继续正确工作 | 记忆、状态、需求更新、交接 |
| 异步委托 | 前台响应与后台最终可靠交付 | 路由、调度、恢复、通知 |
| 外部应用 | 授权范围内实际业务状态正确 | 控制、回执、幂等、不确定状态 |

能力地图还标记缺少真实模型证据、仅模拟环境、待复核和未覆盖区域；没有成绩不显示为零分。

### 3.2 三层执行

| 层级 | 测什么 | 执行位置 |
|---|---|---|
| L0 机制回归 | 状态、版本、权限、发布、去重、预算、恢复不变量 | 本地改动/PR 必跑的快速确定性检查 |
| L1 受控能力 | 固定任务、模型、工具与环境下的能力及效率 | 候选开发筛选与跨场景迁移 |
| L2 产品闭环 | 真实入口至最终可用结果，含异步执行与下载 | 独立验收、发布候选与后续小范围验证 |

固定快照题用于可重复比较；另维护按真实使用抽样的正常任务和经授权的探索任务。故障题不替代正常工作分布；探索结果经审查、脱敏、可复现后才进入固定 suite。

## 4. 统一证据协议与索引

### 4.1 两层存储

保留每次运行的原始数据库、manifest、JSON、日志和内容寻址产物；新建可重建的本地索引，例如 `.xopc-evals/control/index.db`。索引不是第二个轨迹事实源，保存来源定位、哈希、规范化摘要和控制面关系。

拟新增 `evals/control/` 容纳 registry、历史导入、实验计划、调度、索引及晋级策略；继续调用已有 runner/adapters/store。首次实现先拆清模块边界，不复制已有执行引擎。存储契约中可通用的部分归入现有 protocol/storage 包。

| 对象 | 必需内容 |
|---|---|
| Benchmark | id/version、场景/能力、adapter、层级、证据类型、owner、评分/预算协议、数据集家族和 split |
| EvidenceBundle | 来源路径与哈希、suite/selection/grader/lockfile hash、源码快照、配置及工具/技能策略指纹、模型/推理身份、环境和请求口径 |
| Experiment | 计划总数、已入队/运行/结束数、变体、重复次数、执行顺序种子、资源预算、冻结门槛 |
| Trial | 稳定 task/family/repetition/variant id、独立 attempt id、执行状态、质量结论、用量覆盖、trace/artifact 引用 |
| Assessment | 原始评分、重评分、评分器版本、证据支持、复核状态和原因；新结论引用旧结论，不覆盖 |
| Improvement | 问题、假设、预期、改动面、parent candidate、源码 diff、实验、PR/commit、实际收益、决策与回滚目标 |
| Decision | 采用策略版本、证据集合、硬门禁、比较结果、未解决项、决策者/时间；追加式审计 |

未知历史字段保存 `unknown` 并披露缺失原因，不根据目录名猜模型、日期、完成状态或隔离保证。绝对路径只用于本机定位；可分享摘要使用 bundle-relative 引用和稳定 ID，验证路径与内容哈希。

### 4.2 状态与证据类型分开

- `evidenceClass`：`deterministic`、`harness_calibration`、`live_controlled`、`live_product`；另用 `lifecycle=planned` 表示计划，不生成执行成绩。
- `executionStatus`：queued/running/completed/failed/interrupted/cancelled/timed_out/budget_exceeded。
- `assessmentStatus`：pending/passed/failed/manual_review/unavailable。
- `validity`：valid/invalid/unknown，另记 source_drift、protocol_error、incomplete 等原因。
- `promotionStatus`：not_evaluated/eligible/rejected/promoted/rolled_back。

此为控制面投影，不立刻改写既有 `RunStatus`。试验执行完整不表示质量通过；暂时退出不表示失败清零；无待审也不表示已经晋级。

成绩分母固定为预先声明的任务及重复次数；运行进度与质量通过率分别展示。缺失/取消/失败有独立计数，不能只以已结束或可评分项重算更高成功率。未知费用/cache 细分记 null；EQ 显示原生特征及协议，不伪造总分。

### 4.3 历史导入与新运行

历史导入先支持 coder、Personal delivery、style、memory 的显式目录清单和 adapter-specific importer。停止递归扫描源码快照、fixture、node_modules 和工作区副本。其他专项登记为已知证据/待适配，不能悄然遗漏。

按 bundle 内容哈希及源 experiment/trial id 幂等导入；重评分与恢复评分建立 lineage，不能变成额外模型样本。支持来源缺失/移动/损坏、正在写入的部分摘要、重复导入和来源格式升级。活动运行使用原子快照/watermark；聚合快照显示生成时间和覆盖范围。

基线选择分开提供 `latestAttempt`、`latestCompleteValid`、`latestPromoted`。可比较条件包含 suite/fixtures/grader/预算、模型/推理、运行环境和相关策略；不同源码是有意处理变量，其余不匹配时只并列展示并列出原因。模型升级轨道与 harness 修改轨道分开。

## 5. 快速执行与并发验证

### 5.1 按依赖图执行，避免整套串行

```mermaid
flowchart LR
    A[冻结计划与源码] --> B[静态检查与 L0]
    B --> C[并发开发场景 L1]
    C --> D[保护回归与成对比较]
    D --> E{开发门槛}
    E -->|通过| F[独立场景 L1/L2]
    E -->|失败| G[保留证据并结束本轮]
    F --> H[决策与 PR 证据包]
    H --> I[后续小范围运行与反馈]
```

互相独立的 case、变体和重复可并发；同一对话的 follow-up、同世界的学习/查询、同一 Task 的修订/恢复按因果顺序执行。配对 arm 在预先固定的 block 中交错或随机化，避免所有 A 跑完才跑 B。长任务和短任务采用公平队列，不能让一个大 memory 批次占尽交互调试资源。

### 5.2 两级额度与资源隔离

1. **任务 admission**：限制活跃场景、Gateway 进程、CPU grader、磁盘和桌面实例；默认并发值由预检容量决定。共享真实桌面的任务使用互斥资源键，不能盲目并发。
2. **物理请求 lease**：按 provider/凭据配额组和用途限制 generation、judge 请求；覆盖主模型、router、reviewer、记忆抽取、schema repair、内部重试及辅助调用。流式响应直到 EOF/cancel 才释放，不能以一个 turn 代表一个请求。

先复用 Personal 的共享池协议；第一阶段让试点 adapter 接入同一个 endpoint，记录外发请求与 usage 的核对结果。所有实验/worker 共享 provider 硬上限；generation/judge 是分类额度，如果底层共用 provider 额度还需共同父级上限。不得各启动一个池后仍声称全局限流。

429/overload 触发有界退避、降低 admission 和请求目标；不自动换模型。worker 死亡需要 heartbeat、租约撤销和真实在途请求排空见证；仅 TTL 过期不能证明外部请求已结束，更不能立即重复执行有副作用的任务。池不支持取消排队/可靠租约时，第一阶段补齐后才用于通用并发。

每个 worker 独立源码快照、DB、工作区、conversation、endpoint、profile、端口和故障注入对象。可共享只读依赖/fixture 与现有 credential refresh lock，不能复制 refresh token 或共享可变产品默认状态。case 启动/结束校验 profile 和源码，避免 W12 一类身份跨题污染。

### 5.3 快速验证策略

- **先便宜后昂贵**：grader 正负校准和 L0 先执行；开发失败不打开独立验证，不执行完整昂贵套件。
- **增量选择**：按改动模块和能力标签选开发题与保护题；完整晋级仍跑预声明相关回归，选择清单留档。若改动无法可靠定位影响范围则扩大回归。
- **预备环境**：按 lockfile/工具链哈希准备只读依赖和 fixture bundle；复用干净模板，不复用已跑过的可变状态。冷/热启动分别记时。
- **证据复用**：同一回答可供零模型重评分；缓存键覆盖答案、输入、grader、协议和环境。改变产品源码不能复用旧候选输出证明新版本通过。
- **评分流水线**：候选完成后即可排队 grader，与其他场景执行重叠；独立验证的金标仍不向优化进程开放。
- **预算到顶停止 admission**：同时限制 campaign、候选和 trial 的请求/token/时间；停止后取消或排空在途请求。无法预知的最终 token 超出保留为超预算，不宣称账单硬封顶。
- **恢复有记录**：manifest 相同且证据完整的完成项可跳过；中断项单独 attempt，原始尝试/费用保留。不确定外部副作用先核实状态，禁止自动重放；有效低分不能重抽样替换。

候选中止、任务暂停和整个 campaign 取消是不同动作；暂停停止新 admission，按协议排空/取消后保留 checkpoint，恢复前验证源指纹和资源状态。

### 5.4 速度指标与初始工程目标

第一阶段建立串行基线，再在相同完整合成矩阵、同机器、同预算下检验并发，速度目标不是现有成绩或生产 SLA。

| 指标 | 第一阶段目标/口径 |
|---|---|
| 确定性快速检查 | 首个有效失败结果目标 ≤ 60 秒，试点 fast lane 目标 ≤ 5 分钟；CI/本机分别报告 |
| 并发收益 | 8 个独立、等长、延迟受控场景在 scene=4 时，矩阵耗时目标 ≤ 串行 60%；计入启动和评分，硬额度不超限 |
| 真实模型反馈 | 报告首条可评分结果、首条有效失败、整轮完成时间及队列/推理/工具/评分分解；先建基线，再定目标 |
| 停止与资源 | 中止后不启动新请求，最终 active/queued=0；未知外部状态显式保留 |
| Dashboard 更新 | 活动状态可见延迟目标 ≤ 3 秒；SSE 断线可从持久事件游标恢复 |

速度对比包含失败与中断开销，并展示并发、机器负载、缓存和 provider 限流；不能把少跑题、少重复或更多请求额度算成 harness 能力收益。

## 6. 面向开发者的 Dashboard

### 6.1 产品定位与入口

第一阶段扩展 `evals/coder/apps/web/`，仍通过现有 `pnpm run eval:coder:web` 启动。默认绑定本机，提供开发者独立工作台；先不增加主 Gateway 生产页面或新路由。页面与 CLI 使用同一查询/聚合服务，避免两套成绩逻辑。

将内嵌 HTML 拆为可维护的页面和前端资源，第一阶段不以引入新前端框架为前置条件。遵循仓库 UI 设计中的 slate/blue、清晰边框和 skeleton 加载；数据规模扩大后采用分页和虚拟列表。后续若进入 `web/`，直接复用语义 token、Select、skeleton 等已有组件，避免第二套样式体系。

### 6.2 第一阶段必须可用的五个视图

| 视图 | 开发者要回答的问题 | 必需内容 |
|---|---|---|
| 概览/能力地图 | 哪些能力有证据，哪些正在退化？ | 场景×能力、证据类型、最近完整/晋级基线、覆盖缺口、数据时间；不显示跨协议总能力分 |
| 运行中心 | 现在跑到哪里，为何慢/停住？ | DAG、计划/结束/待审数、active/queued、worker、generation/judge/provider 额度、降速、预算、最近事件 |
| 实验比较 | 这次改动真的更好吗？ | baseline/candidate、匹配性、逐 case 成对 win/loss/tie、硬门禁、质量/效率、全部失败和待审、源码/协议 diff |
| Run 证据 | 这道题到底发生了什么？ | 需求、最终结果、时间线、工具与验证、产物/下载证据、usage、原始/重评分、注释和错误来源 |
| 改进记录 | 我们为什么做这次修改，是否采用？ | 问题→假设→候选→实验→门禁→PR/commit/回滚；第一阶段允许人工录入，后续 agent 自动追加 |

```text
执行收敛试点 / candidate-03     Running     源码 frozen     证据 live_controlled
计划 24  | 已结束 8 | 运行 4 | 等待 12 | 待审 1 | 协议错误 0
Generation 3/4  Judge 1/2  Provider shared 4/6  CPU grader 1/2
阶段：L0 ✓ → 开发评测 RUNNING → 保护回归 WAIT → 独立验证 LOCKED
当前失败：E01 范围越界 → run / trace / diff / 原始评分
比较：完整配对 3/12；结论 pending，不能晋级
预算：累计请求 / token / 时间；费用 unknown；停止原因与恢复入口
```

筛选支持 suite/version、场景/能力、模型、源码、证据类型、validity、时间及 owner；URL 保存筛选和实验/run ID，可直接分享本机定位或导出脱敏报告。与问题有关的“原始评分”和“复核评分”并列，不隐藏坏结果。

### 6.3 查询、实时与人机操作边界

- 跨库索引提供分页列表、按需 run 细节和产物读取；不把全部轨迹一次发送到浏览器。artifact 读取限制到登记 bundle，验证相对路径/哈希，禁止任意文件读取；HTML/脚本以文本展示，不直接执行。
- SSE 发布控制面事件：queued、started、checkpoint、assessment、pool_changed、budget、decision；来源没有实时事件时轮询原子摘要，并显示更新时间/来源延迟。
- 第一阶段 Dashboard 以只读跟踪为主；开发者用 CLI 启动/暂停/恢复，页面展示命令和状态，不让“看进度”依赖控制按钮完成。
- 后续开放 UI 写操作时使用同一控制服务，检查 Origin/CSRF、绑定本机访问令牌、幂等 commandId 和 revision。模型消耗与自动发布遵循持久实验预算和授权，不把匿名 localhost 端口当成执行权限。
- 原始业务内容与凭据不进入公共摘要；脱敏不是公开所有轨迹的许可。本地详细证据与可分享导出分离，导出保留 hash/来源引用和脱敏说明。

## 7. 第一阶段试点：执行收敛与可靠交付

### 7.1 试点问题及选题

验证 agent 是否能识别工作完成、用有效证据结束、只交付当前要求的成果，并在中断/遗漏/需求变更后可靠恢复。先形成完整可操作闭环，再扩大自修改范围。

| 试点轨道 | 复用场景 | 主要检查 |
|---|---|---|
| A 执行收敛 | core C01/C02；growth E01/E02/P01；work W08 | 最新需求完整、代码/产物正确、验证真实有效、已有工作未被改坏、完成后能停止 |
| B 可靠交付 | core F01/F02；Personal P0/P1/P2；冻结 live mixed adapter；work W09 作为后续扩展 | 原 Task/Run 身份、产物字节、认证下载、修订采用、无重复执行、未知副作用不伪装成功 |

core/growth 是直接 agent，Personal 是异步产品工作流，分别比较和展示；不能合并成单一成功率。W08/W09 当前大套件未完成不妨碍后续作为独立试点，但须先冻结有效 fixture、评分和隔离，不继承无效历史分数。

第一阶段先接入 core/growth 指定子集和 Personal 冻结 mixed 工作流；W08/W09 是扩展项，不以重跑完整 37 题×3 阻塞首个闭环。原 suite 不改题不改预算；试点 selection 独立版本化，报告明确为子集。

### 7.2 核心指标与判定

- **硬结果**：行为/数据正确、当前要求全部覆盖、保护文件不变、验证证据适用当前工作区版本、文件可下载且会话隔离、完成状态真实。
- **可靠恢复**：故障确实注入、同 TaskRun 恢复（按原契约）、无丢失/重复外部效果、有限重试/continuation、结果修订正确。
- **收敛诊断**：模型请求/token/耗时、相同稳定版本的重复成功调用、最后有效验证至交付耗时、验证后无关修改。重复调用和工具数量是诊断信号，不单独判错；除非用户契约明确限制次数。
- **体验保护**：前台首文字/完成延迟、重复通知、必要澄清保留；文件到达不能抵消错误结论或无关写入。

试点候选每次只验证一个明确机制假设，例如“在未变化的工作区复用有效验证证据是否减少收尾开销”。先固定模型、预算和配置；模型升级另开轨道。至少冻结一个不修改产品的 baseline capture，然后才开始候选实验。

开发筛选建议每场景 1 次，候选冻结后独立结构场景至少 3 次；这是起步预算，不构成稳定性/显著性证明。验收前根据 baseline 波动预注册最终重复次数、最小有价值收益和相关回归容忍界，不能看结果再扩大/缩小分母直到通过。

第一阶段晋级需同时满足：证据有效完整；预声明硬门禁全部通过；没有未决阻断复核；独立场景结果支持目标收益；相关保护项无阻断退化。以质量相当下的效率改进或明确能力改进作为收益，不用速度抵消质量失败。证据不足记 `insufficient_evidence`，不默认等于通过。

### 7.3 用例增长与评测自身验收

每个失败转为：最小复现、机制迁移、正常保护、故障边界四类中的适用用例。按世界/任务结构拆分开发与验证，不按同模板改姓名随机拆分；记录 familyId 和已见状态。第一阶段建立至少一个未用于开发的新结构验证家族/试点轨道，并在候选冻结后开封。

评分器先跑参考解、典型错误、等价有效方案、假完成、缺验证和越界产物控制；变形检查包括输入扰动后重新计算、删除后再生成、重新读取下载字节。不能把 agent 自己写的测试或回复作为唯一真相。

若验收失败并被分析，该集转为开发回归；另建新的验证集，不从已开封结果选择另一个候选。优化进程不能读取封存 fixture/gold 或改变晋级策略；阶段服务隔离可见目录与 API。Git 过滤无法提供足够边界时，验收置于独立执行账号/容器或 CI job。

## 8. 持续自我迭代控制流程

每轮 Improvement 保存：问题与来源、证据引用、失败归因及其不确定性、可证伪预测、允许修改模块、保护项、源码 parent、预算、预声明评测选择/晋级规则、停止条件。

角色是权限边界，不要求每项工作都创建多个 LLM agent：

| 角色 | 可做 | 不可做 |
|---|---|---|
| 诊断/优化器 | 读开发证据、提出假设、隔离修改、跑开发评测、创建带证据 PR | 读封存 gold、放宽门禁、删除失败、自己给自己晋级 |
| 执行/评测服务 | 按冻结计划调度、评分、记录指纹和资源 | 使用 candidate 私有判断代替客观验收 |
| 晋级服务/开发者 | 按独立证据决策、记录原因、关联版本与回滚 | 静默替换历史评分或把未完成记录认定成功 |

自动化逐步开放：先自动整理/诊断与人工 patch，再自动生成隔离候选和 PR，最后对成熟改动面开放有限自动晋级。第一阶段不自动合并/部署；提示、工具证据与上下文等低影响候选先试。权限、遗忘、外部写入与存储机制保留更严格审查和完整回归。

研究预算与正式评估预算分别记录，再合计 campaign 全消耗；保留失败候选数量和基础设施开销。观察候选晋级率、独立迁移率、真实问题复发率、回滚率、单位确认收益的时间/成本；不以 PR 数、题量或最高开发分作为自进化成效。

## 9. 分阶段实施计划

阶段按验收推进，不以日期承诺完成；第一阶段按下列顺序交付可运行薄片，每个薄片都更新 Dashboard。不同模块可并行开发，但契约先冻结、集成后统一验收。

### 阶段一：统一证据 + 快速并发 + 人的 Dashboard + 两条试点

| 编号 | 工作包与拟议落点 | 依赖 | 可验收交付 |
|---|---|---|---|
| S1-01 | `evals/control/registry/`、协议与 schema；补 suite owner/标签/证据类型 | 无 | 现有主要评测族都可登记；计划/未知/校准不伪装模型成绩；schema 与 importer fixture 测试 |
| S1-02 | 只读历史 importer、可重建索引、查询服务 | S1-01 | coder、delivery、style、memory 显式导入；幂等、部分运行、重评分去重；最新尝试/完整/晋级三种视图 |
| S1-03 | 扩展现有 Dashboard，先概览/实验/run，再运行中心/改进记录 | S1-02；运行事件与 S1-04 对齐 | 五视图、跨库筛选、直接链接、分页、时间线和原始证据；UI 显示完整性/待审/未知 |
| S1-04 | 通用 admission 调度、共享请求池、worker 隔离与取消/checkpoint | S1-01 | 试点的物理调用覆盖、CPU/桌面资源、预算、profile 隔离、暂停恢复；活动事件进入 Dashboard |
| S1-05 | A/B 试点 manifest、baseline、开发/独立数据与校准 | S1-01；执行依赖 S1-04 | 收敛和交付两轨固定子集与 L0/L1/L2 证据；运行前冻结门槛，不改历史 suite |
| S1-06 | 一个机制假设的候选闭环与决策报告 | S1-03/04/05 | baseline→patch→开发→保护→独立验收→采用/拒绝；完整 PR 证据包；拒绝也是有效结论 |

推荐顺序：S1-01 → S1-02 + S1-04 + S1-05 数据/校准准备 → S1-03 与首次 baseline → S1-06。这里的并行指实现与独立 case 调度，不能越过同实验因果依赖或未到达的验收门槛。

第一阶段 DoD：

- 开发者从一个入口看见各评测族最新证据和来源，能明确区分未完成、待审、无效与已晋级。
- 同一计划可通过 CLI 执行并在 Dashboard 连续跟踪；断线重连/服务重启后历史与终态仍一致。
- 受控并发目标通过，真实试点有完整请求/usage 对账；并发上限、暂停、取消、预算和独立 profile 均有执行证据。
- 至少一次完整候选实验覆盖执行收敛与可靠交付保护；独立验收得出明确决策，不能要求为了完成阶段而一定采用候选。
- 历史导入和新执行原证据不被改写；缺失/失败不消失；封存集不向优化器开放；源码漂移阻止晋级。
- 形成维护说明：如何登记、导入、启动、查看、比较、暂停/恢复、重评分和导出；文档中的未来命令在实现后才替换为可复制命令。

### 阶段二：把真实使用接入 benchmark，并扩展场景

交付真实反馈/用户纠正入口、授权脱敏与最小复现流程、失败聚类和用例审核；把记忆、对话、配置、Computer Use 等 adapter 完整纳入调度/请求核对。补足跨会话、压缩、重启和长任务场景，连接任务结构级 holdout 轮换。

DoD：新问题可追踪到 case 与修复实验，正常任务和故障任务覆盖均可见；至少两类新增场景完成真实模型与产品闭环验收；历史非标准报告不再是唯一查证入口。

### 阶段三：自动诊断与隔离候选搜索

交付诊断报告生成、实验契约模板、受限模块候选修改、预算内并发筛选、消融、独立验收及带证据 PR。新建 optimizer 不接触封存 gold；重评分、模型升级和 runtime 修改分别建实验。

DoD：多轮候选搜索均可复现，失败/无收益候选完整保留；对照人工作业时间与真实消耗，证明自动流程缩短达到有效决策的周期，并报告验收集消耗和选择偏差。尚不自动发布。

### 阶段四：有限自动晋级与持续运行反馈

对达到成熟度的改动类型开放预授权范围内的合并/小范围部署，关联发布身份、观测窗口、降级和回滚。多模型/多预算/多环境验证迁移，按需求逐步支持远程 worker，不在初期引入分布式数据库和复杂集群。

DoD：晋级有明确可执行规则，实际回退可恢复已知版本；真实复发率/介入负担下降与开销有完整证据；尚未成熟的高影响改动继续由开发者决策。

## 10. 验证、运维与持续追踪

验证分层，不通过单纯扩大真实模型次数弥补基础设施缺陷：

1. **无模型测试**：schema/importer/指标；grader 正负控制；缺失/损坏/重评分；pause/resume、worker 崩溃、请求池降速/取消、额度与未知状态。
2. **真实本地集成**：SQLite+独立 worker+认证 HTTP/realtime+流式脚本模型；核对请求实际并发、辅助调用、EOF 释放、终态与产物隔离。
3. **Dashboard 验收**：导入混合证据 fixture，查询/分页/链接/断线恢复；保证 manual_review、incomplete、unknown 和 source_drift 不显示为绿色通过；详情恶意文本/路径不能变成执行或任意文件访问。
4. **真实模型试点**：baseline/candidate 配对，冻结源与预算，覆盖真实后台交付、认证下载和故障恢复；实际 UI 运行中可追踪至最终决策。
5. **CI**：PR 跑确定性和控制面集成；获授权的真实模型 job 使用预声明配额，上传脱敏证据；周期运行以后续明确配置的计划为准，本文不创建自动任务。

建议每周开发者在 Dashboard 查看：能力覆盖变化、当前冻结基线、阻断失败、待复核队列、候选谱系、预算与反馈时延。工作清单按用户影响×复发频率×机制覆盖×可验证性排序；无法稳定评分的问题先补校准/证据，不让低可信分数驱动自动修改。

第一阶段成功的标志：开发者能快速、连续地看见一个真实问题如何变成可复现评测，一个 harness 修改如何被并发验证，以及它为什么被采用或拒绝。
