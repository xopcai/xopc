# 移动端第二、第三 Tab 信息架构评审

日期：2026-09-17。范围：当前原生移动端源码、产品定义与数据契约。本文是评审和目标方案，尚未修改页面或新增服务端能力。Chat 与设置保持不动。结论来自代码和产品原则，未经过真实用户研究或使用数据验证。

## 结论

四个入口可以保留，第二、第三页需要重新定义内容选择与动作闭环，而不是继续添加模块。

- Chat：交代、追问、修改。
- 第二页「进展」：此刻哪些事值得我关注，助理已经帮到了哪里？
- 第三页「资料」：哪些内容值得留下，我如何找回并继续使用？
- 设置：偏好、连接和管理。

暂不以改名代替产品调整。「进展」应从运行状态页转成重要事项与帮助结果的页面；「资料」应从文件分类页转成成果和资料的统一找回入口。不建议把第三页只命名为「成果」：用户主动保存的材料也是长期理解和后续工作的基础。

产品依据：[Product philosophy](../product.md) 的 Keep what matters moving，以及[场景优先产品方案](./proactive-scenario-product.md)。后者明确反对把后台运行、订阅与状态机直接映射为用户日常界面。当前移动端未充分体现这一方向。

## 当前结构的问题

| 位置 | 代码事实 | 对用户价值的影响 |
|---|---|---|
| 进展 | 待处理、background、最近关闭任务，再加任务/项目/工作流/自动化入口 | 混合注意力、运行监控和管理导航，缺少明确主次 |
| 进行中 | 将 background 全部作为运行状态行展示 | 服务端实际包含 running、scheduled 和信息类 insight；建议和计划可能被误读成执行进度 |
| 后台事项 | 服务端限量返回 background，移动端未使用 backgroundCount 展示其完整性 | 用户无法判断是否还有未展示事项；简单使用“全部任务”不能覆盖自动化与工作流 |
| 最近结束 | 最近五个 closed 任务，仅展示标题和 resolution | 已关闭不是成果；取消、重复、无交付物记录占据首屏，真正交付的内容不可直接消费 |
| 资料 | 文件/笔记/收件箱三个管理入口在内容之前 | 用户首先面对分类选择，不是要找的东西 |
| 最近文件 | 请求八项，展示三项，图片有大预览，其他内容主要显示文件名 | 更新时间和文件格式主导注意力，无法证明这些是重要成果；图片天然获得更大空间 |
| 最近笔记 | 按更新时间取六项，与文件分块 | 内容用途相同也被按存储类型拆开；缺少跨类型找回与续用入口 |
| 两页关系 | 缺少统一成果身份与“新结果→长期保存”的消费状态 | 重复展示难治理，用户仍需回到聊天里重建上下文 |

对应源码：`ProgressScreen.tsx`、`LibraryScreen.tsx`、`progress-sections.ts`、`RecentFileCard.tsx`；后台投影见 `src/tasks/home-query-service.ts`。

## 第二页：围绕重要事项组织，不围绕模块组织

以下是优先级，不是四块永久占位的卡片容器。没有内容的分组不渲染；没有待办也不制造提醒。

1. **需要你决定**：明确阻塞后续工作的选择、授权、补充信息。显示为何现在需要、影响以及可直接执行的动作。重要授权完整可达，不为了“首屏最多三项”截断。
2. **已为你准备**：助理已经完成、现在可用的帮助。例如有来源的会前简报、已生成的跟进草稿、验证过的交付物。内容是主角，不是任务状态。每项一个主要动作：查看、采用、继续修改或审核发送。
3. **值得关注的变化**：确实影响当前目标的风险或变化，必须解释影响和建议。用户可以稍后处理或说明不相关；处理后退出当前注意力视图。
4. **正在跟进**：压缩成简短摘要或少量条目，说明当前一步、阻塞条件或下一次检查条件。详细运行过程进入事项详情，不用日志或无依据百分比占首页。

默认排序：明确需要用户且时间敏感的事项优先；其次是当前场景可使用的成果；普通后台运行退后。相同层级结合用户明确关注、关联目标、期限和实质变化排序。采用可解释规则，不直接让模型用一个不透明分数决定全部顺序。

### 卡片必须回答的问题

- 这是什么事？属于哪个项目、会议或沟通上下文？
- 为什么现在与我有关？
- 助理已经实际做了什么？证据或内容在哪？
- 我点一下能得到什么，或者推进什么？

不是每张卡都要把四段文字完整展开，但不能只剩标题、“处理中”和跳转箭头。按场景提供最小内容：简报给要点，草稿给正文片段，风险给影响与依据，决定给选项及后果。

### 管理入口

任务、项目、自动化和工作流保留可达，但从内容流退出，收纳到页头的「全部事项 / 管理」入口。项目是上下文和长期方向，适合从相关卡片进入。用户通过一次真实帮助建立长期安排，不先被要求配置工作流。

「最近结束」不再常驻首屏。成功且有实际交付的内容进入“已为你准备”；取消、重复等进入事项历史。主动失败只有在需要用户干预或影响目标时进入注意力区。

## 第三页：统一找回成果与资料

目标是“我知道来这里能找到并继续用”，不是“我知道它存在哪种模块”。

推荐结构：

1. **搜索**：按内容、标题和关联事情找回。应覆盖已交付成果与用户材料；过滤条件可用类型、项目、时间、来源。不要把有限的本地最近列表过滤包装成全量搜索。
2. **继续使用**：用户最近真正打开、编辑、引用过的内容；显式置顶可在前面展示。当前只有更新时间，不能直接假装成最近使用。
3. **内容集合**：同一结果列表，提供「全部 / 助理成果 / 我保存的」筛选，不做三份重复内容源。项目等进一步作为筛选或集合。
4. **待整理入口**：用户捕获、尚未处理的材料只在确有待处理内容时显示简短提示。需要用户做决定的整理建议进入第二页，原材料仍在第三页。

默认收录：明确交付给用户的成果、用户主动保存或上传的材料。临时文件、缓存、执行日志和中间产物不因“最近修改”自动占据首页；完整文件浏览放在更多入口。是否为成果必须来自交付记录或明确保存行为，不能只根据扩展名、路径或生成来源猜测。

内容行应提供：有意义的标题、内容摘要或预览、关联事情、来源和可用性。按可用能力提供打开、继续修改、引用到对话、分享等操作。缺失或过期诚实显示，不提供必然失败的按钮。修改内容时携带原对象身份和必要上下文，而不是只把文件名放回聊天。

### 为什么不只做成果页

AI 生成不自动等于高价值；用户保存的合同、会议笔记或项目背景可能更重要。第三页应保留两类对象，但通过来源筛选和统一内容表达消除“文件、笔记”之间的人为割裂。

## 两页如何形成闭环

以假设场景说明：

Chat 交代“帮我准备明天的客户会” → 第二页出现有来源的会议准备内容和待确认问题 → 用户阅读或修订 → 简报作为同一个内容对象在第三页找回 → 下次点“继续修改”带着该对象回到 Chat。

同一成果在第二页代表“现在有一项帮助值得看”，在第三页代表“它一直可以被找回”。不是复制两份内容：需要共享内容 ID、版本、来源和消费状态。

- 第二页卡片被已读、采用、稍后或失效处理，不等于删除第三页的内容。
- 任务、运行、通知和成果描述同一件事时按业务身份关联，不用标题去重。
- 只有实质更新才重新进入注意力区；排序和红点不因后台轮询或纯更新时间刷新而抖动。
- 普通生成结果可以留存，但不必全部触达用户。通知数量不作为价值指标。

## 数据能力与实现边界

| 能力 | 已确认的基础 | 实现时需要补的部分 |
|---|---|---|
| 待决定和运行状态 | Home 有 kind、summary、recommendation、动作与总数 | 按语义分组，保留关键动作；完整集合的入口与关联去重 |
| 可验证的任务结果 | TaskRunReceipt 有摘要、证据、验证结果、剩余工作与下一步 | 当前任务列表只返回任务、运行态和 attention；需要批量结果投影，避免移动端逐条拉详情 |
| 可使用的成果 | TurnOutcomeDeliverable 有身份、类型、来源文件、可用性和能力 | 跨会话、任务的可分页成果索引及来源关联；不要每次在手机遍历聊天记录 |
| 场景化帮助 | proactive 契约有 whyNow、workDone、evidence、recommendation 和 artifact | 对齐现有场景服务的用户侧接口及移动端详情/动作；当前两个 Tab 没有完整消费这些语义 |
| 搜索 | 移动端已有跨笔记、会话、任务等搜索，文件有独立查询 | 统一成果检索边界与分页；现有搜索并非完整成果搜索 |
| 继续使用 | 文件有 modifiedAt，笔记有 updatedAt | 最近打开/引用/编辑事件、显式置顶与状态；定义同步范围 |
| 看过、采用和提醒状态 | proactive 卡片有状态与版本基础 | 将交付、注意力卡与内容对象关联；定义实质更新和失效规则 |

不新建另一套任务、成果和提醒系统；扩展已有正式契约和投影，不引入旧新逻辑并存的兼容层。来源授权范围、对象能力与用户反馈必须贯穿聚合和检索。

## 实施顺序

**P0：纠正现有语义与首屏权重。** 第二页区分 running / scheduled / insight，保留动作，处理总数和入口；管理导航退出内容流；取消“所有结束事项就是成果”的展示。第三页降低目录入口优先级、补清楚的内容来源，保留诚实的“最近更新”标签。不要在数据不齐时直接改名为“成果中心”。

**P1：补齐价值闭环。** 建立跨会话的成果与场景结果投影、统一搜索、查看/采用/继续修改和注意力消费状态。第二页真正交付帮助，第三页真正可找回和复用，这是本轮架构调整的关键。

**P2：基于真实使用改进。** 引入最近使用、用户明确关注、稍后/不相关反馈与场景节奏。上线前不预设“用户每一天必须得到三张建议卡”。

## 验收

- 每个第二页条目能说明相关事情、出现原因、已有帮助和下一步；否则不进入主要内容区。
- 不把计划执行当正在运行，不把取消/重复当成果，不把任意文件当正式交付。
- 需要批准的操作可直接进入完整审阅，读取一张卡不会自动批准动作。
- 一个新成果可以从第二页打开；处理后可以从第三页搜索找回，并带上下文继续修改。
- 相同业务事项不以任务、运行、通知重复刷屏；重新进入页签不会重置已处理状态。
- 无连接、加载失败、尚无数据分别表达；没有值得关注的内容时保持安静，不用通用建议填满。
- 首次用户通过 Chat 完成真实的小目标，不先被要求整理资料或配置自动化。

先建立基线再验证改动：需要用户的事项处理成功率、成果首次打开/采用/复用率、找回任务完成率与耗时、重复提醒率、不相关反馈率、重要事项实际推进情况。不同指标有明确分母；不以 Tab 点击量、卡片数量或自动生成任务量代替用户价值。
