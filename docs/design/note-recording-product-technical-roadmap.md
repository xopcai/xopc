# 笔记录音：从可信保存到原话与行动

日期：2026-10-15。状态：后续产品与技术推进方案，未代表新增能力已经实现。以当前工作区实现及[专项验收](./note-recovery-special-acceptance.md)为基线。

## 目标与交付原则

用户放心录下完整内容，结束后能快速找到原话，并把重要信息变成后续行动。

主流程：放心录 → 随手标重点 → 结束即可离开 → 回来找到原话 → 确认后形成行动。

先完成可保存、可找回、可核实、可确认的完整体验，再扩展模型能力。原音是数据源；转写、章节、纪要是可重建结果；用户的标记、校对和手写内容独立持久化。声纹、复杂模板、公开知识库、翻译、录音硬件及突破两小时上限暂不纳入。

鸿蒙沿用同一产品与数据契约，但按用户最新要求，本轮不安排鸿蒙设备测试；现有主机测试不能作为真机验收替代。

## 共用技术契约：先把状态和时间说清楚

### 四条独立状态线

保留现有服务端 DiscussionStatus 兼容性，新增明确的进度投影，避免将所有状态塞进一个枚举。

| 状态线 | 关键状态与数据 | 展示依据 |
| --- | --- | --- |
| 采集 | 请求权限、等待首帧、录制、暂停、中断、停止中、停止 | 原生采集/MediaRecorder 事件与音频帧健康度；不能依据计时器推断 |
| 本地保存 | 保存中、已提交、失败；连续可恢复范围、待提交尾部 | 已完成持久化事务及音频分片连续性 |
| 原音同步 | 未同步、离线、上传、校验、服务端原音可用 | 已确认的连续分片及最终附件确认；上传 100% 不等于服务端可用 |
| 派生处理 | 转写范围、章节范围、整理、退避、失败、完成 | 持久化检查点、已发布结果与所用输入版本 |

客户端本地保存状态由本地存储负责；Gateway 仅声明已接收到的数据。服务端不能替客户端宣布“本机保存成功”。

### 连续保存范围

为每段音频维护 sequence、captureEpochId、媒体起止位置、字节数、哈希及提交状态。`localSavedThroughMs` 表示从当前录制起点可恢复的连续媒体前缀：遇到缺片、缺少可验证时间或提交失败立即停在此前边界，禁止使用最大序号或最大 endedAt 代替。

鸿蒙依据已提交 PCM 样本数；Web 需要核验实际编码时间与分片边界。目前基于采集时钟记录的 durationMs 不能直接升级为精确媒体保存承诺。先做一个技术验证：Chrome WebM 能否从已提交容器块提取稳定的媒体时间；不能证明时显示保守边界/“保存时间确认中”。MP4/其他容器单独验证，禁止用 timeslice 固定五秒或 dataavailable 回调时间推算真实音频长度。

采集活跃时间、媒体位置、现实时间分开保存。暂停及异常中断写事件；音频恢复后新建采集 epoch，原音内的媒体定位不因系统时钟变化或暂停而漂移。显示中断带及实际中断时长，不把拼接后的播放时间误称为现实时间上的连续录音。

### 稳定身份与版本

- 本地 recordingId 先于网络创建，沿用 clientRequestId 幂等建 Discussion/Note。同一份录音重试、恢复、导入已同步部分不再创建新 Note；完全离线首次录制可先显示本地条目，联网后绑定一次。
- 原音定位至少包含 recordingId、captureEpochId、audioAssetId/哈希、媒体范围。转写证据包含 transcriptRevision、segment IDs 和一组独立范围；跨版本不能仅靠 sequence 重新定位。
- 用户标记使用客户端 UUID、revision 和持久化同步队列；删除保留同步 tombstone。校对和重生成不能删除标记或改变其原音锚点。
- 人工编辑与模型结果继续沿用现有 edit ledger；旧逐字稿、旧分析和已创建 Task 的来源快照保持可追溯。

## 第一批补完：P0 可信状态和恢复入口

本批完成“用户知道保住了什么”，作为后两批的前置门槛。

**录音面板。** 计时、实际输入电平、暂停、标重点、结束居于主要位置，实时文字默认作为辅助。没有新文字但采集健康时显示“转写稍有延迟，录音继续”；只有采集确实活跃才显示录音指示。电平为零可能是安静，不能单凭静音判断麦克风中断。

默认一行保存状态，点击查看保存、同步和 AI 处理详情。结束按钮复用现有幂等 stop Promise：停止采集 → 尾段产生/超时判定 → 本地写入队列屏障 → 提交停止元数据。只有屏障成功才显示“录音已在本机保存，可以离开此页面”。屏障失败或尾段超时，改为“录音已停止，已保存至 XX:XX”，保留具体异常及恢复操作。

| 情况 | 产品行为 | 技术边界 |
| --- | --- | --- |
| 断网 | 离线录音；继续/暂停/结束 | 原音不依赖在线建会话或 STT；同步独立重试 |
| 麦克风中断 | 明确中断及已保存范围；继续/保存已录部分 | 冻结计时，收尾旧 epoch；重新授权、收到真实首帧后才进入新 epoch 的 recording |
| 存储失败 | 停止采集；查看/释放空间后重试/导出 | 保存边界不推进；重试失败不删除已有原音；标记单独写入失败不能冒充音频保存失败 |
| 尾段/停止异常 | 显示已确认部分与可能未保存的尾部 | 超时释放采集资源，禁止显示整段保存成功 |

**恢复列表。** 放到笔记页“待恢复录音”，展示录制时间、网关归属、已确认可恢复时长、同步状态与失败原因。每条提供恢复并同步、导出、丢弃；当前只取首条的浮层改为列表入口。按用户选中的 recordingId 操作，跨网关先提示关联，不自动发往其他网关。丢弃需明确范围，清理本地录音不应顺带删除已成功的 Note。

**继续录制。** 同一 recordingId 下追加新 epoch，保留中断事件。同一 WebM 文件的后续采集不能假定可以直接字节拼接；每个 epoch 是独立可校验原音，使用统一播放 manifest 映射多个资源。若已有原音已封存，则追加新资源并产生新的录音 manifest 版本，已有资源哈希及历史证据不变。第一批先完成这种追加格式验证，再开放“继续录制”；此前仅提供保存已录部分，避免一个没有正确落盘能力的继续按钮。

**本地导出。** 单资源可解码则导出原容器；多 epoch 或不能合并时导出原音文件加 manifest/标记/中断说明的恢复包，不能把多段容器直接连接后命名为一个音频。导出逐片读取，避免两小时原音一次载入内存。

**离开语义。** SPA 切页可继续当前页面生命周期内的上传。关闭浏览器、进程退出或完全离线时，只承诺已提交原音可恢复；再次打开后继续同步。服务端确认原音附件后，后续转写与分析才真正脱离客户端生命周期。第一批不引入 Service Worker，不承诺 Web 离线冷启动和关闭浏览器后持续上传。

**完成标准。** 保存成功文案在提交屏障前绝不出现；采集停止不再显示录音；缺片时保存边界不越过缺口；多条恢复、导出、重复恢复、断网和停止异常都有可操作结果。原音提交到服务端后，关闭客户端仍能完成处理；此前关闭则重开续传同一 Note。

## 第二批：P1 证据联动、重点标记与确认行动

### 统一回顾状态

Note 详情组织为概览、原文、我的标记；移动端标签配固定播放器，Web 在空间允许时并排显示。先从现有 discussion-note-sections 拆分播放器、原文、证据卡和分析视图，共用一个以 noteId 为键的 review state：当前资源/epoch、播放位置、选中证据、查询、选中结果、原文锚点、标签及各视图滚动锚点。

切换标签、打开/关闭证据侧栏不重建播放器；回到同一 Note 恢复位置。多资源播放依据 manifest 映射时间；资源被删除则保留文本证据并提示原音不可用。恢复播放位置不代表自动播放。

点击结论 → 展开其版本化原文 → 点击播放对应范围。多处依据逐条显示，不使用最早 start 到最晚 end 包住全部内容。播放器支持该范围结束后暂停或用户主动连续播放。没有词级时间戳时定位到可验证的整段，并明确范围粒度，不能显示看似精确的句子起止时间。

### 持久化标记

区分时间点标记和原文选区标记，共用 annotation 模型：id、recordingId/discussionId、类型（重点/问题/补充）、epoch/媒体范围、可选版本化原文引用、用户说明、revision、同步状态。首次本地保存先于“已标记 XX:XX”的成功反馈，不等待网络；失败明确提示可重试，单独标记失败不主动停止健康的原音采集。

标记落在尚未确认原音范围时保持原始位置；异常后如对应音频未保存，明确显示“该位置原音未保存”，不悄悄吸附到附近一句话。转写出现后按同一 epoch 的范围关联附近原文；用户后续校对或重生成时重新解析展示，但保留原始锚点及历史引用。

第一步只交付标记、说明、问题类型、原文关联和播放。随后补“解释这一段”“提取行动项”“比较前后说法”，所有回答引用实际选择的原文；用户说明单独标为上下文，不能自动当作录音事实或他人承诺。

### 校对后的更新与任务确认

校对后比较分析输入 revision 与最新 transcriptRevision，受影响卡片显示“原文已更新”；历史原话仍可查看。初版允许整份纪要重分析，复用现有章节缓存；显示哪些内容可能变化，并保留人工编辑。精确到单卡片的局部重算放在证据依赖索引完成之后。

行动项先进入候选卡。用户确认标题、项目、负责人和日期后，调用现有 convert 通道；扩展其确认输入，不绕过 TaskApplicationService 新建第二条创建路径。负责人必须区分“录音中提到的人”和可分配的产品账号；未知、模糊或相对日期不能静默转成承诺。候选确认使用 expected organization revision 和 action ID，事务中完成创建与关联。

继续沿用 existing action→Task 幂等键；确认响应丢失、重复点击、批量部分失败均回显已有 Task。来源包含 Note、原音范围、转写版本和证据；重新分析不自动重建已关联任务。人工主动恢复已删除任务另设明确操作，不能由后台重试隐式完成。

**完成标准。** 一条结论的多处依据分别可读可听；标签/搜索/播放器位置稳定；标记断网及强杀后可恢复；校对后能识别旧分析；未确认不创建任务，重复确认只产生一条关联任务，Task 能回到原 Note 和当时的原话。

## 第三批：P1 长录音定位与阶段性可用

### 先做确定性的定位

默认简短概览和章节目录，原文分页/按时间范围加载。章节展示起止位置、摘要、重点数、待确认行动数和覆盖状态，点击后同时定位原文与播放器。现有章节来自处理分批结果，不能直接承诺是高质量话题分章；先支持稳定的时间段回顾，再依据话题边界生成派生章节，并保留其输入版本。

统一 Note 内搜索首先支持原文关键词；结果带版本、分段 ID、命中高亮、前后文、原音范围和分页游标。服务端搜索全部已发布原文，不能在浏览器只过滤当前加载页后显示“无结果”。标记及用户说明可同入口分类展示，保留来源区别。

搜索结果独立选中，点击定位、可直接播放，播放器标出各命中位置。规范化处理标点、大小写和中文检索；SQLite FTS 的分词/运行时支持先验证，采用可用的确定性全文索引方案，避免默认英文 tokenizer 漏掉中文。未索引完成时说明已搜索范围，不谎报全量命中。

### 分开发布可用内容

公开音频可播放范围、转写已确认范围、章节已发布范围及失败区间。范围使用区间列表，并另给连续前缀；`completedChunks` 或时长之和不能证明内容完整。

当前 live 转写可读、最终转写检查点内部保存、分析章节内部缓存三者边界不同。先提供稳定只读的阶段性发布层：已确认分片立即可搜索；章节在 schema/证据校验后单独发布，带 source revision、generation、范围及 provisional。内部缓存不直接充当面向用户的结果。

最终转写或新 generation 完成时原子切换正式版本；旧结果在切换前保持可读，旧搜索结果与证据不跨版本拼接。人工标记与校对不被阶段性发布覆盖。用户始终能知道“可播放全部 / 已转写哪些 / 还有哪些未整理”。

原音完整附件就绪后优先开放播放，不等待纪要。录制中或仅部分上传的 WebM 不默认可随机播放；需要有效容器初始化段和可播放分片索引，作为后续能力单独验证。后端长录音解码、STT 和分析使用有界队列，前台录音与原音落盘优先；一个长任务等待网络不能阻断其他原音保存。

**完成标准。** 两小时样本无需全量加载逐字稿；能通过关键词或章节找到指定话题并回放上下文；可识别未转写/未分析范围；剩余处理失败时已发布部分继续可用。语义问答以此为基础追加，不作为关键词定位的依赖。

## 验收与观测

| 场景 | 必须满足的结果 |
| --- | --- |
| 断网录制、跨页、强杀重开 | 已提交连续前缀可恢复；保持同一录音/Note 身份；页面准确说明尚未同步部分 |
| 存储满、事务回滚、缺片、尾段超时 | 保存边界停在真实位置；不能显示整段已保存；可导出已有部分 |
| 中断后重新授权/首帧迟迟不到 | 仍显示等待或中断；首帧后才恢复录音；时间轴保留缺口 |
| 标记早于转写、未同步、落在丢失尾部 | 标记保留；状态可解释；不能伪造原文关联 |
| 校对、重生成、多范围证据 | 旧证据可查；新旧版本不混用；人工内容保留 |
| Task 创建成功但响应丢失 | 重试返回同一 Task；项目/负责人/日期以确认值为准 |
| 两小时样本搜索/章节/播放/处理失败 | 按需加载；定位正确；已发布部分可读；明确未覆盖范围 |

每次提交记录非内容类指标：连续保存落后量、尾部提交耗时、采集已停但 UI 活跃的持续时间、恢复成功率/失败原因、重复 Note/Task 数、首次可播放/可搜索/可回顾耗时、搜索延迟和主线程长任务。日志使用 recordingId/discussionId/generation 等身份字段，不记录原音、完整原文或用户说明。

建议初始性能目标（待基线实测后固化）：停止后本地屏障 p95 ≤2 秒；正常前台下原音保存落后 p95 ≤8 秒；本机两小时样本关键词检索 p95 ≤500 ms（不含网络）；已加载内容跨视图定位 p95 ≤300 ms。设备、浏览器、样本规模与网络条件必须随结果记录，不将目标数字写成已达到的承诺。

每批先通过确定性故障测试，再跑真实浏览器交互和隔离供应商验收。Web 增加至少两小时实时采集、Chromium/目标 Safari 容器差异、前后台与低存储专项；鸿蒙真机验收保持待安排。所有首批上线范围均按实际验收平台声明，不能将单一浏览器/主机测试扩大成全平台可靠性结论。
