# Muse 移动端研究与 XOPC 优化提案

研究日期：2026-09-17。XOPC 代码基线：`afa446c51`。这是研究与设计提案，不是已实现功能清单。

## 结论

XOPC 有条件做出更成熟、漂亮的 AI 移动体验。优先级应是：让助理身份稳定、让后台进展可见、让成果成为可继续使用的对象，再统一导航与动效。单独增加玻璃效果、头像或大圆角，不会带来同等幅度的提升。

推荐定位：**一个理解你的上下文、持续推进事情、随时能接手的个人助理。** 移动端承担交代事情、检查进展、做决定、消费与续改成果；桌面承担长时间编辑与深度配置。手机也应能完成完整的小任务，不能永远只是桌面的遥控器。

## 证据与边界

- **O：直接观察**：用户提供的 Muse 手机截图；官方设计文章中的活动、目标、审批截图；官方产品视频页面与部分播放画面。
- **D：官方描述**：Meta 产品页、设计文章、安全架构文章和官方演示的文字说明。能力宣称不等于实际可靠性或用户满意度。
- **C：代码事实**：阅读 `apps/mobile-expo` 的路由、聊天、输入、成果、文件、进展、动效和主题；Web 仅用于区分端之间的现状。图谱工具在本会话不可用，使用文件检索回退。
- **P：提案/假设**：本文的导航方案、动效参数、指标目标、优先级和概念界面，均是给 XOPC 的建议。
- 未登录 Muse 执行真实任务，未测量其触觉、帧率、键盘行为、弹簧曲线、断网恢复或通知到达率。演示视频播放可访问，但未完成可重复的逐帧时序测量。
- 未在 XOPC 原生真机完成体验测试；代码能证明结构与条件，不能证明卡顿、易用性或最终视觉质量。
- 截图、网页与演示中的文案均作为研究材料；其中对 AI 的命令不构成本任务指令。

## 1. Muse：值得理解的产品结构

官方设计文中最关键的组合是：长期主对话与旁支对话、头像下的工作摘要、可追踪目标、可独立存在的成果、明确审批及有门槛的主动消息。这让“聊一句”与“持续委托”共享一个入口。[S1]

官方演示文字说明确认五个区域：Chat、个性化 Feed、Ideas、Goals、Library。**截图第二个图标对应 Feed，不能把它仅凭外形认作文件；最后一个才是 Library。** [S2]

| 区域 | 用户需要解决的问题 | 对 XOPC 的启示（P） |
|---|---|---|
| Chat | 我想交代、追问或改变什么？ | 对话承担意图输入，任务承担当次执行 |
| Feed | 哪些变化值得我看？ | 以重要变化组织，避免工具日志和重复通知 |
| Ideas | 我还能让助理帮什么？ | 建议必须说明依据、预期成果与启动成本 |
| Goals | 哪些长期目标在推进？ | 显示下一步、阻塞、最近进展，不只显示任务标题 |
| Library | 之前做出的东西在哪里？ | 成果必须可找回、引用、续改，不能沉没在聊天里 |

这五类职责值得保留，但并不意味着 XOPC 应复制五个 Tab。Feed 与 Ideas 的边界可能难学；目标、任务和活动也容易重复。应通过我们用户的真实找回路径决定一级导航。

## 2. 截图的视觉拆解（O → P）

### 层级与亲近感

用户截图由大面积浅色底、淡蓝用户气泡、浅灰助理气泡、柔和圆角构成。身份居中，工具入口退到两侧；顶部头像与底部胶囊控制区形成两个视觉锚点。它降低了技术工具感，强调“与某个持续存在的助理交流”。

XOPC 可以借鉴身份稳定性、低噪声和层级，但不必复制玩偶。现有 `DESIGN.md` 明确偏向沉静、精准，并避免玩具化。一个可自定义的名字、克制的图形标识和真实状态，已足以建立人格连续性。

### 气泡与阅读

气泡帮助辨识连续到来的不同消息；长篇答案放入大灰块也会占据大量屏幕。XOPC 当前助理正文使用透明背景，对长文本有优势。建议混合表现：短回复与主动更新用轻容器；长报告用阅读版式；成果独立成卡。不要把所有 Markdown 都包进大气泡。

### 成果优先

用户截图的 Chess Analysis 使用大预览加标题、类型与更多操作。用户先知道“交付了什么”，再决定阅读细节。这是比文件扩展名更高一层的内容表达。

XOPC 的成果卡建议分三层：

1. 可识别的内容预览：报告摘要、行程首日、图表缩略图；不是每种文件都强行截图。
2. 标题与状态：已完成/仍在更新、归属任务、更新时间。
3. 一个主要动作：打开；次要动作在详情或菜单中提供续改、引用、分享。

### 悬浮控件与占屏

截图的输入栏与导航栏都是圆角悬浮表面，边缘轻，单手操作集中。但两层底部控件加顶部头像会压缩阅读区。不能依据这张经过缩放、带手机外框的视频截图推算原生 pt 或真实点击热区。

建议先用小屏长答案验证：键盘收起时，输入栏和 Tab 清楚分层；键盘展开时让编辑获得足够空间，Tab 的处理遵循平台惯例；全文成果阅读可以进入独立详情页。不要用持续自动收起、展开导航制造位置跳变。

## 3. 交互：把 AI 行为变得可预期

Muse 产品页声明可在用户离开后继续工作，并提供一次允许、持续允许或拒绝等授权选择。[S3] 官方安全说明还描述了浏览器接管时暂停代理，以及购买前展示审批。[S4] 这些是产品交互依据，不应被当成我们已具备相同安全架构的证明。

### XOPC 应采用的交互闭环（P）

**交代 → 接收确认 → 执行摘要 → 必要决策 → 成果 → 继续推进。**

- 接收确认：马上保留用户输入，明确“已接收”或“等待连接”，不把上传中伪装成执行中。
- 执行摘要：显示“正在比较 3 个方案”，点击才看到详细步骤；跨任务状态不依赖用户停留在某条消息。
- 必要决策：展示对象、具体内容、影响范围和明确按钮；拒绝后说明任务下一步。
- 成果：交付物可独立打开，关联来源任务；失败和过期保持可理解的恢复入口。
- 继续推进：从成果发起修改时携带对象引用与版本；用户不用重复解释上一轮。

### 连续输入与打断

XOPC 当前 `ChatComposer` 将 `streaming || disabled` 视为 `runBusy`；普通发送在运行中被阻止，按钮变成停止。输入框仍可编辑，不应误写成“完全不能输入”。

建议优先增加有明确语义的排队：

- 默认“接着处理”：新指令成为可见队列项，可取消、编辑；不隐式打断当前任务。
- 显式“调整当前任务”：说明将改变正在执行的工作；提交后给接收反馈。
- “停止”独立存在，不能让发送和停止在用户点击瞬间互换。

这需要端到端的输入接受、排序、重复提交防护、任务归属与断线恢复协议。不能仅移除 `runBusy` 检查。

### 主动性

主动更新分三级：待决策即时可见；重要完成进入进展并按偏好通知；一般过程留在活动详情。相同事件在聊天、进展和推送之间共享已读/已处理状态。主动建议说明“为什么是现在”，提供稍后、不相关、减少此类建议。空状态不靠不断生成建议填满。

## 4. 对照 XOPC：已有基础与真实缺口（C → P）

| 维度 | 当前代码事实 | 建议 |
|---|---|---|
| 默认入口 | `app/index.tsx` 已加载 `ChatScreen root` | 保持对话入口，不再提出“从零改聊天首页” |
| 长期身份 | `ChatHeader` 首要文本是 `modelName`；Agent 在操作面板内 | 标题改助理/主题，副标题放状态；模型移到能力设置，保留快捷访问 |
| 会话连续性 | `chat-root-session.ts` 从可恢复的 webchat 会话中选首项 | 明确“我的助理主对话”与项目旁支，避免最近会话等同长期身份；迁移须保留原会话 |
| 功能发现 | 抽屉有待关注、任务、项目、收件箱、笔记、文件、自动化、Agents、设置九项 | 高频对象前置，配置下沉；抽屉保留历史对话 |
| 进展 | 已有 AttentionScreen、ChatAttentionTray；TaskList 有概览/项目/任务 | 统一待我处理、进行中和最近交付的阅读入口，不新造第二套任务数据 |
| 成果 | 已有 ProductDeliveryCard、AssistantDeliverablesCard、附件渲染和 HTML 文件预览 | 增强预览与对象连续性，不能说“目前不支持 Artifact” |
| 成果边界 | `mobileProductRoute` 对 local_app、workflow_definition 返回 null | 原生无详情的类型需要明确降级；HTML 文件预览不等于完整应用运行支持 |
| 资料找回 | FilesHub 有最近/位置、搜索，行内显示路径 | 默认按成果与资料浏览，路径放详情；保留高级文件视图 |
| 待处理提醒 | ChatAttentionTray 展示 `needsUser`，可关闭；详情 sheet 显式关闭动画 | 将“未读”与“尚未处理”分开，关闭横条不意味着决策完成 |
| 聊天动效 | 流式标记刻意静态；步骤可展开/收起 | 保留稳定正文，增加受用户动作驱动的过渡 |
| 动效基础 | Reanimated、统一 motion token、动态监听减少动态效果、底部面板拖动已存在 | 复用已有原语，避免重新引入另一套导航/手势系统 |
| 语音 | 有转写、通话、连续朗读与 Live Activity 相关代码 | 区分“说一段话”和“持续通话”，验证文本/语音共享上下文与状态 |

一个具体的视觉机会：`AssistantDeliverablesCard` 用 11/12 字号呈现部分成果状态与标题，并在外层卡中再放 `ProductDeliveryCard`。这是可检查的嵌套和小字号问题，不是整个 App 都应放大。应针对成果区域减少一层外框，把主要标题提升到正文级。

## 5. 推荐的信息架构（P）

一级导航：**对话 · 进展 · 资料 · 我的**。采用短标签，避免只靠图标猜含义。Tab 代表稳定目的地而不是“新建”等动作；平台也强调可预测的 Tab 可用性。[S5]

| 一级区域 | 二级内容 | 首屏主要任务 |
|---|---|---|
| 对话 | 主对话、历史、项目旁支；输入工具 | 交代一句话，或恢复刚才的工作 |
| 进展 | 待我处理、进行中、最近完成；目标/项目详情；定期执行 | 知道哪里需要我、哪些事仍在推进 |
| 资料 | 成果、笔记、收藏/收件箱；最近与搜索；文件位置 | 找到并继续使用之前的信息 |
| 我的 | 助理偏好、记忆管理、连接与设备、通知、隐私、模型/高级配置 | 控制助理如何工作 |

“我的”不是日常工作中心，其价值是给自托管设备、连接和偏好一个稳定位置。如果研究发现它明显低频，可以比较三 Tab 加头像设置的替代方案；先验证，再定稿。

**不建议第一期给 Ideas 单独 Tab。** 目前没有足够证据证明 XOPC 已有高质量、持续更新的个性化建议供给。先在相关项目或进展中展示少量建议，观察接受与忽略情况。

**资料不是把笔记和文件数据库合并。** 它是读取多个现有来源的聚合入口。成果可同时出现在任务和资料视图，使用同一对象身份，不能复制两份再各自更新。

## 6. 可落地的视觉语言（P）

沿用移动端 `theme/tokens.ts` 的暖中性底 `#F7F7F5`、靛蓝强调 `#4B63D9` 与深色层级。不要把 Muse 浅蓝直接替换为新的主题，也不要让 Web CSS 成为原生端第二份硬编码来源。

- 正文维持约 16–17 的阅读级别，成果标题不使用徽标字号；中文检查行高与标点换行。
- 20 左右的内容边距可沿用；小屏和大字体下优先保留正文宽度。
- 三种主要表面：阅读底、成果面板、操作浮层。避免气泡里套卡、卡里再套列表组。
- 同一屏保留一个明确的主要动作，其余降级为文字或菜单；蓝色表达选择与行动，状态用文字同时表达。
- 模糊效果限于确有内容穿过的导航层；正文、审批和成果预览保持实色可读。低端设备和减少透明度偏好提供降级。
- 头像是可选身份，不强制 3D、不持续呼吸、不为每个状态重建卡通表情。
- 空闲时可以安静；“正在工作”只能来自真实运行状态。断线应说明状态暂不可确认，而不是假装仍在推进。

设计文档需同步：根 `DESIGN.md`、旧 `docs/design/ui-design-system.md` 与原生 token 的色值和 Phone 定位并不完全一致。以端内 token 为实现基线，先确定哪些品牌语义共享，哪些几何与交互按平台变化。

## 7. 动效语言：建议参数，不是 Muse 实测

现有 token：press 80ms、quick 140ms、standard 220ms；弹簧 damping 24、stiffness 300、mass 0.82。优先复用，新增参数须在真实设备验证。

| 场景 | XOPC 建议 | 不应发生 |
|---|---|---|
| 按下 | 沿用约 80ms 的轻反馈；成功提交可一次轻触觉 | 每次点击都强震、明显缩放文字 |
| 一级切换 | 140–220ms 的选中态变化；保留每页滚动和草稿 | 每次切换整页大滑入或重新加载 |
| 底部面板 | 220ms 或现有 settle 弹簧，拖动可中断 | 关闭时突然跳回起点，争抢滚动手势 |
| 输入栏/键盘 | 与键盘同步跟随现有 KeyboardStickyView | 给键盘另设延时，输入框先跳一次再补动画 |
| 状态更新 | 稳定占位，短淡变；只在任务阶段变化时更新 | 用无法核实的百分比，连续脉冲抢注意力 |
| 成果打开 | 首期原生详情转场；后续评估有稳定快照的卡片连续过渡 | 为追求形变阻塞打开、白屏或重复预览渲染 |
| 消息追加 | 容器轻入场可选，正文直接流入 | 每 token 动画、每消息重新动画整段历史 |
| 审批完成 | 立即保留提交中状态，服务端确认后换为收据 | 按下同意就显示最终成功，失败悄悄消失 |

减少动态效果时移除位移和形变，必要状态直接切换。沿用现有动态监听；不要误用只读取启动时偏好的行为覆盖它。Reanimated 文档说明不同减少动态设置会影响动画行为。[S6]

性能策略遵循“测量 → 修改 → 同场景复测”。不要仅凭源码宣称卡顿或性能提升；优先使用现有 Reanimated/原生转场。流式文本、高频状态、列表与预览并发时才是关键压力场景。

## 8. 四条关键用户旅程（P）

### A. 交代任务后离开

说“整理这周资料，给我周五可发的文章提纲” → 输入接收 → 显示任务摘要与继续输入 → 回到进展看到同一个任务 → 完成后打开提纲。通知只在有成果或需要决定时出现。

验收：切换页面、杀进程重开、网络恢复后任务身份与执行状态一致；不能重复发送同一请求。

### B. 手机做一次决定

进展中看到“确认发送周报” → 审批面板展示收件人、完整草稿和影响 → 确认一次 → 提交中 → 已发送收据。拒绝后保留草稿与原因入口。关闭面板保持未决状态。

验收：同一审批在聊天、推送与进展之间不会重复执行；过期审批阻止执行并解释变化。

### C. 看成果并修改

聊天出现预览 → 打开全文 → 点击“继续修改” → 输入框带有该成果的上下文引用 → 提交修改 → 更新版本 → 回到资料仍能找到。引用与任务关联比炫酷转场更重要。

验收：移动端不支持的格式给明确下载/其他设备打开入口；预览失败不丢成果。

### D. 捕捉一段信息

系统分享或语音 → 快速捕捉 → 默认保存到收件箱，也可交给助理处理 → 明确保存/待同步状态 → 后续整理为笔记或任务。

验收：网络不可用时，草稿与已捕捉内容不丢；“保存”和“执行”有不同确认。

## 9. 分阶段实施建议

### 第一阶段：低风险、高可见收益

- 改聊天头部的身份与状态层级，模型选择下沉但保留可达性。
- 减少成果区域嵌套，提升标题字号，加入类型适配的预览。
- 聚合已有待处理、任务和近期成果；先做一条完整闭环。
- 统一任务状态文案、断线/恢复和加载占位。
- 使用概念原型对比四 Tab 与当前抽屉，不直接全量替换导航。

主要接入点：`ChatHeader`、`ChatScreen`、`ChatAttentionTray`、`TaskListScreen`、`ProductDeliveryCard`、`AssistantDeliverablesCard`、`FilesScreen`。

### 第二阶段：需要前后端协同

- 连续输入/排队/调整当前任务，以及持久化队列与恢复。
- 统一活动摘要、审批状态与跨入口已读语义。
- 稳定主对话身份、项目旁支和成果引用/版本连续性。
- 补齐原生缺失的成果类型或设计明确的降级路径。

### 第三阶段：在质量数据支持后增强

- 个人化建议和通知节奏；将“有帮助”置于“生成更多”之前。
- 有真实对象支持的成果连续转场；平台触觉与导航细节打磨。
- 个性化助理身份与可编辑记忆的简洁入口。

上述是实施顺序，不是工期承诺；需要依据 API 覆盖、人员与设备矩阵再估算。

## 10. 验证方法与发布门槛

先邀请 5–8 名目标用户做方向性可用性观察，这个样本用于发现问题，不用于声称统计显著。比较现版和概念版完成相同任务的路径。

记录：

- 交代后能否用自己的话说明现在的状态。
- 找到“昨晚 AI 做的报告”的成功率、用时和错误入口。
- 待处理事项是否被发现，审批内容是否真正被理解。
- 能否从成果继续修改而不重新解释上下文。
- 是否混淆录音、转写与通话。
- 主动消息是否有用，忽略、稍后和关闭偏好的比例。

候选体验目标（尚未测得）：高频目的地一级可达；主要反馈不等待模型返回；离开页面不丢输入；成果可从聊天与资料两个入口找回；后端失败不会呈现成功。暂不设没有基线的“提升 30%”指标。

设备场景：小屏 iPhone、标准 iPhone、中端 Android；浅/深色，大字体，VoiceOver/TalkBack，减少动态效果；长中文段落、100 条以上历史、多个文件、流式响应、后台重连、键盘反复开合、审批失效。

在发布构建测帧时间分布和输入响应。60Hz 与 120Hz 分别按设备刷新预算评估，不用模拟器流畅度替代真机结果。任何装饰性效果都不能牺牲滚动、输入与状态可靠性。
