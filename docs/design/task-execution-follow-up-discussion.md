# Task 执行与持续跟进：产品讨论记录

状态：讨论中，尚未定稿。
开始日期：2026-10-27（Asia/Shanghai）。
最后更新：2026-10-28。

本文持续记录本次产品讨论。用户明确提出的方向、助手建议和未决问题分别记录；未被用户确认的建议不视为产品决策。本文不是实施授权或后台监控配置。

## 用户提出的产品方向

- Task 是具有目标和验收条件的对象。
- 任务可能已经处于执行过程中。
- 可以配置自动化来执行任务。
- 也可以配置自动化持续跟进任务进展，并向用户推送消息。
- 持续记录讨论进展，在同一份方案上继续讨论。

## 本次讨论的交互基础

以下来自此前任务页改动及用户要求，作为讨论背景，不代表完整产品模型已经确定：

- 任务左侧优先呈现当前需要用户处理的事项和主操作。
- 用户在任务页内设置执行时间，并可进入对应自动化。
- 已有计划应显示规则和下次执行时间，支持页内修改、取消，避免重复创建。
- 当前取消计划的实现是停用后续定时触发，保留自动化记录，允许重新启用。

## 正在讨论的建议，尚未确认

### 对象关系

以 Task 为目标和验收的载体，区分两个面向用户的配置入口：

| 配置 | 作用 |
| --- | --- |
| 自动执行 | 在合适时间让 Agent 执行或继续推进任务 |
| 持续跟进 | 检查进展、成果和阻塞，并在需要时通知用户 |

两类配置可以共存，也可以单独使用。是否共用现有自动化底层、是否引入独立产品对象，均待定。

任务执行者可以是用户、Agent 或双方协作，这是助手提出的扩展解释，尚待确认。

### 跟进内容与证据

建议每次跟进回答：发生了什么变化、哪些验收条件已有依据、当前阻塞是什么，以及下一步由谁处理。

进展应来自可验证信息；没有更新时明确说明未知，避免从“用户未回复”推断“任务未推进”。具体信息来源、收集方式和记录结构尚未确定。

### 通知策略

建议无重要变化时保持安静；需要补充信息、授权、决策、处理截止风险或验收时再通知。阶段成果可按用户选择汇总。通知尽可能携带对应处理入口。

通知渠道、频率、重复提醒和用户控制方式尚未确定。

### 生命周期边界

建议区分“周期性推进同一目标”和“周期性生成新任务”：前者在原任务内积累进展；后者每个周期形成新的目标、交付物和验收结果。

建议自动执行尊重手动暂停、正在执行、等待审批和关闭状态；跟进是否继续、何时停止及是否允许采取行动，待讨论。

### 初步范围建议

助手建议先做有依据的进展检查、阻塞提醒和待验收通知，再讨论跟进后的自动行动。用户尚未确认优先级。

## 任务详情页的信息精简讨论（2026-10-28）

### 用户本轮要求

- 当前页面文字信息过多，希望尽可能简洁呈现，先讨论设计优化。
- 设计讨论阶段不写代码。随后用户明确要求“按照以上方案优化”，授权实施本节的信息精简方案。

### 实施记录

用户已确认按方案优化。页面将交付结果、明确待办和验收放在默认视图，完整报告、验证依据、任务目标与管理默认折叠；待验收时把暂停和时间设置收至更多操作。人工判定后显示来源和“更改判定”，全部通过且无等待或执行阻塞时才可完成任务。

验收标准保留全文，不自动缩写或修改。短且不含内部标识的单段结果可以直接展示；现有长报告保留完整入口，不在前端推断业务摘要。剩余工作、下一步和需要用户决定的结构化信息保持可见。尚未引入新的摘要生成字段或改写历史报告。

### 截图中观察到的问题

- 执行总结重复展开 Criterion、Claim 和验证结论，下方验收区又重复呈现标准、依据和模型审阅原因。
- `Research claim: c-*`、`Criterion 1` 及英文诊断句占据主要阅读空间，却无法直接帮助用户打开交付物或作出决定。
- “结果有帮助”与“确认通过”同时出现，反馈和验收的区别不够直观。
- 待验收时，“暂停推进”“设置执行时间”与验收操作竞争注意力。
- “文案已准备好”与“是否允许对外发布”混在长段落里，容易错过需要用户裁定的真实问题。
- 部分验收标准本身过于宽泛；单纯折叠文本无法解决标准不明确的问题。

### 建议的默认阅读顺序

默认视图优先回答：交付了什么、还有什么需要我决定、哪些标准待验收。完整执行报告、证据和管理信息按需展开。

| 区域 | 默认呈现 | 按需查看 |
| --- | --- | --- |
| 顶部 | 任务名、待验收状态、主操作“去验收” | 更多操作中放暂停、重新执行、执行时间管理；已有计划保留简短入口或下次执行提示 |
| 交付结果 | 交付物入口 + 一句具体结果，如“已生成一句介绍和两条短文案” | 完整执行报告、历史结果 |
| 需要你决定 | 仅在确有决策时显示：如“源资料对是否公开发布存在冲突，请确认发布范围” + 对应处理入口 | 冲突来源和原文 |
| 验收 | “验收 · 0/2”、每项简短标题、状态、人工判定入口 | 标准全文、依据、自动核验说明、人工判定记录 |
| 执行记录与管理 | 折叠入口 | 历史、计划详情、任务属性与关系、诊断信息 |

交付物应能直接打开；没有可打开的有效位置时明确显示“位置待确认”，不把文件名展示为已验证的链接。没有实质结果摘要时直接显示交付物，不生成空泛的“已完成”。

### 本例的文字线框（示意，不代表已核实交付结果）

```text
撰写拾光发布短稿                  待验收    [去验收] [更多]

交付结果
发布短稿.md                      [打开]
一句介绍与两条短文案已准备。

需要你决定
源资料对是否公开发布存在冲突。     [确认发布范围]

验收 · 0/2
○ 短稿已保存，包含约定文案          [确认通过] [未通过]
  查看标准与依据
○ 约束与证据已检查                [确认通过] [未通过]
  查看标准与依据

                         [验收通过，完成任务]（条件未满足时禁用）

执行记录与任务管理 ›
```

线框中的验收标题仅用于信息层级示意。真实标题须忠实于原标准；“明天发布可用”这类带业务含义的限制不能在精简时被删除。重要条件应在行内显示，完整原文可展开查看。第二条宽泛标准仍需后续明确，不能通过改短标题声称问题已解决。

### 验收区的具体交互建议

1. 每项默认只显示标题、当前状态及人工判定入口；依据以“查看依据 · N 条”进入，计数只表示依据数量，不暗示可靠性。
2. 状态使用“待验收 / 已通过 / 未通过”，同时说明来源，如“用户确认”或“自动核验通过”。模型审阅保留在详情中，不与人工判定混用。
3. 人工通过后显示“已通过 · 用户确认”，将重复的通过按钮收敛为“更改判定”；允许修正误操作。保存中禁用重复提交，失败时在该项附近提示。
4. 标准全部通过且无其他阻塞时，启用“验收通过，完成任务”。未满足时显示简短原因，如“还有 2 项待验收”；不能只用一个无解释的禁用按钮。
5. 顶部“去验收”负责定位到验收区；任务关闭与逐项判定仍是两个明确动作，避免确认某一条就意外完成任务。
6. “待核验”本身放在验收行；确实需要用户做业务决定的问题应始终可见，不能随诊断信息一起折叠。验收任务与授权发布应分别处理，不能用验收通过自动推定发布授权。
7. “结果有帮助 / 没帮助”建议从主流程移至完整执行报告，避免与验收操作竞争。

### 文案与数据呈现边界

- 不在默认视图展示内部 Claim ID；详情中优先使用可理解的来源名、文件名和证据内容，原始 ID 仅在诊断信息中保留。
- 相同诊断原因只解释一次。本例可概括为“自动核验未完成：验收标准过于宽泛”，并提供完整说明；不能将其翻译成“结果不合格”。
- 完整报告保留可查看入口；精简默认视图时，不应靠截断正文隐去关键风险、缺口或待决事项。
- 需要业务决定的内容优先来自明确的结构化待办；不能仅凭页面截取长报告中的一句话，就认定任务已具备可操作的决策入口。
- 建议生成阶段分别产出简短结果、待决事项和详细报告；展示层采用确定的层级与展开规则。对于既有长报告，先保留原文入口，不能假设已具备可靠摘要。
- 如需重写宽泛的验收标准，应作为单独操作向用户展示变更；不得在视觉精简时静默改变当前验收条件或继承旧判定。

### 建议优先级与评审标准

建议先确定默认信息层级，再讨论更复杂的摘要生成或批量验收。本轮不建议增加“一键全部通过”，先保证每项内容与实际风险清楚可见。

设计评审时检查：

- 在常用窗口宽度下，无需展开报告即可找到交付物、看到关键待决事项并开始验收。
- 同一验证原因不在结果和每条验收项中重复铺陈。
- 不打开详情也能辨认人工与自动判定，不将依据数量当作验证通过。
- 长标准可以自然换行，窄屏按钮可换行；不靠缩小字体或横向滚动压缩内容。
- 待验收、部分通过、全部通过、存在阻塞及已关闭状态均有明确主操作。

本轮已确认默认顺序为“交付结果 → 需要你决定 → 验收 → 折叠记录与管理”。本次实施保留验收标准全文；未来如需生成短标题，仍需保证条件完整且原文可查。

## 当前待定问题

1. 第一优先场景是跟进用户亲自执行的任务，还是检查执行 Agent 的工作？是否需要同时覆盖？
2. 跟进可以读取哪些信息：任务动态、执行对话、交付物、外部系统，或用户主动反馈？
3. 跟进只观察与提醒，还是可以自动推进下一步？如何划定授权边界？
4. 任务目标、验收条件和进展由谁维护？人工记录与 Agent 判断如何区分？
5. 执行计划、跟进计划如何在任务页配置和管理？
6. 暂停、关闭、重新打开任务时，两类计划分别如何变化？
7. 通知何时发、发到哪里、如何避免重复打扰？
