## 用户提出的产品方向

- Task 是具有目标和验收条件的对象。
- 任务可能已经处于执行过程中。
- 可以配置自动化来执行任务。
- 也可以配置自动化持续跟进任务进展，并向用户推送消息。
- 持续记录讨论进展，在同一份方案上继续讨论。

## 本次讨论的交互基础

以下来自此前任务页改动及用户要求，作为讨论背景，不代表完整产品模型已经确定：

- 任务左侧优先呈现当前需要用户处理的事项和主操作。
- 用户在任务页内设置执行时间，并可进入对应自动化。
- 已有计划应显示规则和下次执行时间，支持页内修改、取消，避免重复创建。
- 当前取消计划的实现是停用后续定时触发，保留自动化记录，允许重新启用。

## 正在讨论的建议，尚未确认

### 对象关系

以 Task 为目标和验收的载体，区分两个面向用户的配置入口：

| 配置 | 作用 |
| --- | --- |
| 自动执行 | 在合适时间让 Agent 执行或继续推进任务 |
| 持续跟进 | 检查进展、成果和阻塞，并在需要时通知用户 |

两类配置可以共存，也可以单独使用。是否共用现有自动化底层、是否引入独立产品对象，均待定。

任务执行者可以是用户、Agent 或双方协作，这是助手提出的扩展解释，尚待确认。

### 跟进内容与证据

建议每次跟进回答：发生了什么变化、哪些验收条件已有依据、当前阻塞是什么，以及下一步由谁处理。

进展应来自可验证信息；没有更新时明确说明未知，避免从“用户未回复”推断“任务未推进”。具体信息来源、收集方式和记录结构尚未确定。

### 通知策略

建议无重要变化时保持安静；需要补充信息、授权、决策、处理截止风险或验收时再通知。阶段成果可按用户选择汇总。通知尽可能携带对应处理入口。

通知渠道、频率、重复提醒和用户控制方式尚未确定。

### 生命周期边界

建议区分“周期性推进同一目标”和“周期性生成新任务”：前者在原任务内积累进展；后者每个周期形成新的目标、交付物和验收结果。

建议自动执行尊重手动暂停、正在执行、等待审批和关闭状态；跟进是否继续、何时停止及是否允许采取行动，待讨论。

### 初步范围建议

助手建议先做有依据的进展检查、阻塞提醒和待验收通知，再讨论跟进后的自动行动。用户尚未确认优先级。

## 当前待定问题

1. 第一优先场景是跟进用户亲自执行的任务，还是检查执行 Agent 的工作？是否需要同时覆盖？
2. 跟进可以读取哪些信息：任务动态、执行对话、交付物、外部系统，或用户主动反馈？
3. 跟进只观察与提醒，还是可以自动推进下一步？如何划定授权边界？
4. 任务目标、验收条件和进展由谁维护？人工记录与 Agent 判断如何区分？
5. 执行计划、跟进计划如何在任务页配置和管理？
6. 暂停、关闭、重新打开任务时，两类计划分别如何变化？
7. 通知何时发、发到哪里、如何避免重复打扰？
