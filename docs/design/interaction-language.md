# xopc 交互与表达规范草案 v0.1

2026-10-25。基于全路由与常用链路诊断形成的交互与表达规范，补充现有设计系统的行为和语言规则。沿用语义 token、项目选择控件、骨架屏及模态尺寸，不引入另一套视觉系统。实施及验证范围见 [体验修复与回归摘要](ux-regression-2026-10-25.md)；规范的有效性仍需真实用户测试。

## 1. 产品应让用户逐步建立的理解

**把事情交给助手；需要长期推进时成为任务；相关资料放在项目里；需要重复执行时设置自动化。** 普通问题不用先创建任务或选择专业智能体。

| 对象 | 面向用户的含义 | 边界 |
|---|---|---|
| 对话 | 讨论、提问和交办的地方 | 一轮回复结束不代表整个任务完成 |
| 任务 | 有明确目标、进度和结果的工作 | 有验收与交付，不把临时问题强制升级为任务 |
| 项目 | 长期关联的任务、对话和资料 | 不自动代表一个新智能体，也不暗示资料只在本地处理 |
| 自动化 | 按条件或时间触发已有动作 | 已启用不代表正在执行；本地服务离线时不承诺持续运行 |
| 智能体 | 可选的专长与协作方式 | 普通起点有默认助手，内部调度尽量不要求用户理解 |
| 能力 | 助手能使用的模型、工具与连接 | 已安装、已授权、可用和已验证分别表达 |
| 应用 | 用户创建并可反复使用的小工具 | 开发对话、草稿与已发布应用区分 |
| 我的 | 关于你的偏好、记忆与数据控制 | 区分关于你、工作资料、候选记忆与生效记忆 |

建议默认入口按用户目标组织，保留高级路径。不要在验证前直接合并“小A/智能助手/指挥家”；先用默认入口和角色说明测试是否降低选择困难。

## 2. 统一显示名，精确 ID 按需展开

| 当前变体/实现语言 | 默认表达 | 何时保留原词 |
|---|---|---|
| Agent / agent | 智能体 | 日志、配置键、开发文档可显示 Agent |
| Smart Assistant | 智能助手 | 用户自行取的名字不强制翻译 |
| Standard / auto | 标准 | 显示名下可展开 `xopc-cloud/auto` |
| 工具 ID：exec_command 等 | 运行终端命令 | 详情/搜索/权限审查保留 ID |
| Coder Project / Skill | 应用项目 / 开发能力 | 高级开发视图再显示技术对象 |
| Gateway | 本机服务；涉及远程时说明“运行 xopc 的电脑” | 管理员配置、CLI 和日志保留 Gateway |
| 插件 | 一整套可安装能力 | 不替代账号授权或消息通道 |
| 连接飞书 | 连接飞书资料 / 从飞书收发消息 | 根据具体目标命名，不能二者混用 |
| 归档 / 删除 / 移除 | 根据真实结果使用准确动词 | 归档可找回；删除说明影响；移除指解除关联 |

不把行业必需词强行通俗化，不翻译第三方正式商标。技术名可以搜索到，但不应是普通用户唯一的辨认方式。

## 3. 每个动作都符合“意图—范围—状态—下一步”

| 阶段 | 必须回答 | 示例 |
|---|---|---|
| 操作前 | 会发生什么，影响谁 | “连接后，研究助手可以读取你选择的知识库。” |
| 有范围或副作用时 | 资料/账号/设备/费用边界 | “会将选中的文件内容发送到所选模型服务；可先预览。”必须与真实契约一致 |
| 等待中 | 当前真实阶段，是否可取消 | “正在验证模型连接…”；没有测量不要给预计秒数 |
| 完成后 | 实际完成的是什么 | “服务配置已保存；尚未验证模型调用。” |
| 下一步 | 一个明确动作 | “返回手机设置并测试模型” |

默认一个主动作，次动作承担返回/取消。若没有单一明显下一步，应先澄清用户目标，而非堆出同权重按钮。

## 4. 状态模型必须分层，不用一个绿色标签代替所有完成

### 工作结果

| 真实状态 | 推荐表达 | 禁止混同 |
|---|---|---|
| 请求已接受但未执行 | 已接收，等待开始 | 已开始、正在处理 |
| 正在执行 | 正在处理 | 必然成功、即将完成 |
| 需要用户输入 | 等你确认：说明具体问题 | 泛称“卡住了”且没有动作 |
| 依赖外部系统 | 等待服务响应，可取消 | 让用户为不可控制的等待背责 |
| 执行中断且有产出 | 本轮已中断；已有部分结果 | 单独显示“失败”抹去文件，也不直接标成功 |
| 本轮正常结束 | 本轮处理结束 | 任务已验收、结果已送达 |
| 产出待验收 | 结果已生成，等待检查 | 已完成全部工作 |
| 验收通过 | 任务已完成 | 已送达某外部渠道，除非有送达凭证 |
| 用户停止 | 已停止；保留/未保留哪些内容 | 作为系统故障显示 |

任务顶层摘要为主；对话中的轮次、文件写入和后台执行仅补充说明。后台真实状态不同，应解释各自含义，不通过改色掩盖差别。

### 能力可用性

统一检查 **已安装 → 账号已连接 → 权限满足 → 执行端在线 → 已验证可用**，不要求所有能力都有账号步骤；不适用的步骤跳过。

- “凭据已保存”只说明保存。
- “凭据就绪”不能代替账号仍有效、工具可执行或模型测试通过。
- “已启用”说明策略开关；离线或缺依赖仍须单列。
- 验证应注明时间、范围与是否使用测试数据；过期证据不继续显示为刚刚验证。
- 用失败项直接定位修复；成功后返回原任务，不在多个设置页中让用户自行拼接状态。

## 5. 配置规则

1. 所有影响行为的设置显示范围：“全部智能体”“仅此智能体”“仅此对话/自动化”。复用现有两层配置，不发明递归继承。
2. 单独配置显示“覆盖全局”，并能明确恢复跟随；恢复前提示实际差异。
3. 自动保存仅用于适合立即生效、可恢复的轻量偏好，显示保存中/已保存/失败；复杂或有副作用的设置保留显式保存与摘要。
4. “测试连接”“保存配置”“启用能力”“开始运行”分别命名。不得靠保存暗中执行或发布。
5. 需重启时分成“已保存，等待重启生效”，明确影响和安全操作时机。按需安装的依赖不统一报成紧急故障。
6. 转入设置携带来源、目标能力与返回路径；浏览器 Back、关闭和正文返回行为一致，保留未提交输入。无来源链接回到合理列表。
7. 同一服务共享身份与详情；安装包、资料账号、机器人通道和模型服务的授权范围仍独立，不能互相冒充。
8. 默认显示推荐路径，工程参数展开；批量模板先预览差异，不能因追求简单自动扩大权限。

## 6. 创建流程统一到场景，而不是普通聊天预填

| 用户入口 | 场景标题 | 起步 | 确认点 |
|---|---|---|---|
| 对话创建任务 | 创建任务 | 描述结果、示例 | 目标、验收、范围 |
| 对话创建自动化 | 创建自动化 | 描述何时做什么 | 触发、时区、动作、授权、费用和送达 |
| 创建智能体 | 创建智能体 | 职责与协作偏好 | 可用能力、默认范围 |
| 创建应用 | 创建应用 | 描述要解决的问题 | 可用草稿与正式发布/导航可见性 |

按钮写“对话创建/手动设置”，不让“创建”隐藏跳转方式。对话式路径必须显示当前场景和是否已生效；不把内部提示词作为用户需要发送或理解的正文。专家路径允许直接填写，不强制每次对话。

## 7. 授权、隐私与费用说明

展示“处理哪些资料 → 在哪里执行 → 发送到哪个服务 → 谁可使用 → 什么后果 → 如何撤回”。只说已经核实的边界；“只读”不等于“不上传”，“本地优先”不等于所有能力离线。

- 项目理解：预览读取范围与排除项，说明模型与去向，可跳过；本地路径与模型处理位置分开。
- 插件安装：展示新增组件、工具范围、可用对象、账号/依赖要求；认证发布者不等于操作权限已批准。
- 自动化：创建前展示首次运行时间、时区、执行端、外部副作用与结果去向；声明服务离线的行为。
- 分享：展示分享对象、有效期、访问限制、托管位置和撤销方式；获取资料的接收者也要有失效恢复路径。
- 费用：真实零、估算、已确认部分、预留和未知分别表达。未知显示“费用待确认”；不要格式化为零。Credits 和 USD 不做没有依据的换算。
- 通知：区分主动联系偏好、明确任务结果和系统推送权限；说明关闭页面/服务后能否送达。

## 8. 错误与空状态模板

| 场景 | 模板 | 主要动作 |
|---|---|---|
| 首次为空 | “还没有项目。把相关对话、任务和资料放在一起。” | 创建第一个项目 |
| 筛选无结果 | “没有符合这些条件的项目。” | 清除筛选 |
| 无效详情 | “找不到这个项目，它可能已被删除或移动。” | 返回项目 |
| 功能不支持 | “此功能需要 xopc 桌面版。” | 返回原任务/查看适用版本 |
| 服务暂时失败 | “暂时无法打开此分享。可以重试，或向发送者索取新链接。” | 重试 |
| 保存失败 | “更改尚未保存。你的输入仍在。”仅在真实保留时使用 | 重试保存 |
| 部分结果 | “已生成候选文件，但尚未通过验收。” | 查看文件与未满足项 |
| 需要重试但有外部副作用 | “上次可能已产生变更，请先检查结果。” | 查看上次执行 |

先说用户后果和下一步，技术错误码/请求 ID 可复制但按需展开。不把收到 HTML 的 JSON 解析器输出作为用户文案，不把取消当失败，也不把“尚不支持”写成“没有找到”。

## 9. 控件与页面行为

- 可见标题与控件语义名称一致；错误、帮助和单位与字段关联。输入后标签仍存在。
- 使用现有 Select/PopoverSelect；不要另建选择器系统。
- 模态尺寸稳定、内部滚动、固定操作区；焦点留在顶层弹层，背景 inert，关闭后恢复。
- 每个可分享/可恢复的详情有稳定 URL；筛选与配置分区尽量可定位。源码已经支持但运行构建未生效的，先验版本再修代码。
- 主干内容使用现有语义颜色；实际计算普通文本对比度达到 4.5:1，不能只检查默认主题 token。
- 列表区分首次空、无匹配、加载、错误、离线；骨架表达加载，不能把短暂未返回数据当作零。
- 后台/流式场景不给无依据的完成承诺；过程可展开，默认突出结果、等待原因与下一步。

## 10. 如何验证这套规范有效

先选“找回失败任务结果”“配置手机”“连接飞书资料/消息”三个场景做可逆原型，再用相同目标、相同资料做前后走查。记录用户是否知道下一步、是否选错入口、是否返回修改、是否正确理解授权/费用/完成状态。让新手与熟练用户分别完成，避免以牺牲专家效率换取表面简洁。

每次新增路由或功能至少附一条用户目标链路，说明正常、首次空、失效链接、拒绝授权、网络失败和取消/恢复行为。对配置、权限、数据处理边界和状态模型的修改，使用隔离 fixture；规范本身不改变产品政策、运行时授权或用户设置。
