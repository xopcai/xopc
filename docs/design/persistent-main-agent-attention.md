# 持续主 Agent：任务注意力与语音主动汇报技术方案

> 状态：纵向切片已实现，长期收件箱与责任调度待实施 · 2026-10-02  
> 承接：[主 Agent 与后台任务协作](./foreground-agent-task-orchestration.md)。本文聚焦其尚未完成的“通话中主动感知和汇报”，并规划长期目标责任。  
> 首期范围：当前助手语音模式、同一主 Agent 下的后台 Task；自然语音工具桥接和跨渠道主动消息放在后续阶段。

**当前实施进度**：已在现有持久 `task_main_update_deliveries` 路径上接入活跃助手语音的系统更新回合；语音引擎只在无用户待处理语音和无活跃回复时领取。播报完成或已生成用户可见文字后确认投递；尚无内容就被打断时使用新幂等键重试。阻塞提问/失败/结果优先于普通进展，旧进展在未提交主会话输入时可被新进展覆盖。Task 创建时额外保存不随来源会话删除的主 Agent 归属，并完成 v228 历史回填。主动汇报现在在主对话显示独立的任务触发条目，关联 Task 和协作记录；触发摘要随隐藏输入保存在 transcript 元数据中，刷新后不会因任务改名而变化。本文后续的独立注意力收件箱、持久通知偏好、跨会话责任和跨渠道路由仍是待实施设计。

## 1. 目标和边界

用户只与主 Agent 对话。主 Agent 能快速确认派工，继续处理用户新话题，同时掌握后台任务的阻塞、关键进展和结果；它决定是否、何时、以什么措辞告诉用户。语音通话不因后台工作中断。挂断或客户端关闭后，TaskRun 继续执行，待报告事项持久保存。

“持续”指持久责任、事件唤醒和可恢复执行，**不要求模型保持全天候推理连接**。Task、TaskRun、任务书、协作记录和 receipt 继续分别承担承诺、执行尝试、过程通信和结果证据；不以聊天记录代替它们。

首期明确不做：每条工具日志都播报、工人直接对用户发言、在用户说话或主 Agent 正播报时抢话、以 TaskRun 成功代替任务验收、无工具自然语音模式暗中派工。后续跨渠道能力需要单独处理收件人和信息披露权限。

## 2. 已确认的代码基线

| 能力 | 当前实现 | 方案中的处理 |
| --- | --- | --- |
| 派工与关联 | `TaskApplicationService` 创建 Task/TaskRun；`task_origin_links` 记录发起会话 | 保留；增加稳定的主 Agent 归属，避免会话删除后失去责任归属 |
| 双向通信 | `TaskCollaborationRepository` 追加协作记录，工人可报告、提问和确认 | 保留为事实来源；新的注意力项只引用记录 ID |
| 主 Agent 通知 | `task_main_update_deliveries` 按记录逐条判断，再提交隐藏 `task_update` 输入 | 迁移为有界聚合、按会话串行的注意力调度；过渡期可复用原表和分类服务 |
| 语音 | `VoiceRealtimeRuntime` 保留通话身份；`DurableVoiceAgentBroker` 为用户语音回合提交持久输入；`agentEngine` 串行生成和播放 | 扩展同一语音引擎的系统更新入口；不从旁路向同一会话写入会发声的第二轮 |
| 当前缺口 | `GatewayService.taskMainUpdateDispatch` 在 `hasConversation()` 为真时跳过投递 | 通话中保持事件待处理，并在安全的语音空档由语音引擎领取 |

`task_origin_links` 目前以会话为唯一发起身份且随会话删除级联删除；它适合展示“这段对话派出的任务”，不适合作为长期主 Agent 责任的唯一来源。现有 Task 的 `owner_id` 未强制等于配置中的 Agent ID，不能未经迁移就拿它代替主 Agent 身份。

## 3. 核心架构

```text
Task / TaskRun / collaboration receipt
               │ 事务内写入事件意图
               ▼
     Agent Attention Inbox（SQLite）
               │ 归并、优先级、用户偏好、幂等租约
               ▼
     Main Agent Attention Coordinator
       ├─ 静默记录 / 下次用户回合带入
       ├─ 读 Task 与证据，追问或指导工人
       └─ 生成用户汇报意图
             ├─ 文字：SessionInputCoordinator
             └─ 活跃助手语音：Voice Agent Broker → agentEngine → TTS
```

**唯一发言者**仍是主 Agent。工人记录只提供事实和问题，不是可以直接执行的系统指令。注意力协调器负责时机和可靠性，主 Agent 负责理解上下文、确定是否需要进一步行动及自然语言表达。两者的决定和实际用户可见交付分开记录。

### 3.1 身份与归属

在 Task 创建事务中记录 `task_main_agent_links(task_id, agent_id, origin_conversation_id, created_at)`。`agent_id` 从已鉴权发起会话的 `sessions.agent_id` 取得，不能由模型自由传入。`origin_conversation_id` 是可为空的首选呈现位置快照，不能以级联删除外键让会话删除带走长期归属。历史 Task 只对可唯一确定来源会话的记录回填，无法判定的保持原行为，不猜测归属。

同一 Agent 的多个会话和未来多个渠道共享任务责任，但**不能自动共享私密内容**。首期自动通知只返回发起会话；跨会话查询和跨渠道通知必须有显式路由与授权策略。会话 reset 后按 conversationId 继续；删除会话后保留主 Agent 待办，重新选定可用的私有目的地。

### 3.2 持久注意力项

新增 `agent_attention_items`，每个工人协作记录或系统 TaskRun 事件最多对应一个注意力项。建议字段：`id`、`agent_id`、`task_id`、`source_kind`、`source_id`、`category`、`priority`、`state`、`not_before`、`claimed_until`、`created_at`、`updated_at`。`UNIQUE(source_kind, source_id)`；`source_id` 指向协作记录或 TaskRun 事件，正文不重复存储。`category` 至少区分普通进展、里程碑、阻塞提问、结果、失败、审批。系统自动生成的结果记录必须和注意力项在同一事务或通过可重放 outbox 补齐。

状态为 `pending → claimed → deferred | resolved`；过期租约重新回到 `pending`。决策写入 `agent_attention_decisions`，保存批次 ID、输入项 ID、决定（静默、稍后、追问工人、通知用户）、理由和模型/策略版本。`agent_attention_deliveries` 保存批次、目的会话、媒介、稳定 `clientMessageId`、提交状态、会话运行 ID、可见消息 ID、语音播放状态。一个批次可包含同 Task 的多条进展；每条源项只能被一个已提交的批次消费。

迁移时将原 `task_main_update_deliveries` 的未处理行按 `entry_id` 幂等导入；已经交付的行不再播报。双写窗口由功能开关控制，且同一来源记录只能由新旧投递器中的一个领取。迁移完成再移除旧投递路径，不直接删除历史表。

### 3.3 注意力策略

确定性硬规则先运行：

- `question`、待审批和失败不得被普通进展合并吞掉；需要用户决定的事项持续可见，直到回答或明确撤销。
- 普通进展按 Task 在短窗口内归并，取最新状态和关键变化；同一个终局结果只创建一个汇报机会。
- 用户明确的通知偏好持久化为 `agent_attention_preferences`，可按 Agent 和 Task 覆盖，包括进展频率、允许主动语音播报、免打扰时段与目标媒介。最近聊天不是偏好的唯一来源。
- 工人内容作为不可信数据；只引用 Task ID 和 entry ID 让主 Agent 读取，不把它拼进高权限指令。

主 Agent 在收到有界的批次摘要、当前用户会话和持久偏好后决定是否立即告知、继续调查或稍后汇总。简单重复进展可由确定性规则静默处理；模糊的里程碑、结果和问题交给主 Agent。当前 `TaskMainUpdateDecisionService` 的逐条、独立模型判断可作为过渡，但不是最终的“长期主 Agent 状态”。决定使用结构化输出验证，解析失败退回待处理并记录错误，不以字符串截取作为可靠协议。

### 3.4 同一会话的执行权

`SessionInputCoordinator` 继续提供持久输入和单会话串行执行。`TaskAttentionCoordinator` 按 `conversationId` 申请短租约，同一时刻至多有一个通知批次被提交；用户输入排在系统通知前面。若当前有主 Agent 运行，把注意力项留在收件箱，并在下一次安全检查点把摘要注入该回合或下一回合。**不能**在活跃运行中并行启动第二个主 Agent 回合。

文字聊天空闲时，可以用稳定 `clientMessageId` 提交隐藏系统输入，并等待 SessionInput 终态。`submit` 成功只表示接收；只有运行完成且用户可见消息落盘，才标记文字通知交付。重启时按 `clientMessageId` 查询既有输入和消息，再决定恢复或重试，避免重复气泡。用户回复已覆盖同一事件时，记录静默解决原因。

工人指令另外保持 `pending / accepted / confirmed` 三层：SessionInput 接收后是 `accepted`；工人回 `ack` 或执行回合明确消费后才是 `confirmed`。失败或中断的输入应重试或升级待处理，不能把“已进入队列”呈现为“工人已知晓”。

## 4. 活跃语音中的主动汇报

首期只支持具有 Agent 工具能力的 **当前助手**语音模式。语音接通时，新注意力项继续入库和更新任务卡；不走现有 `taskMainUpdateDispatch` 的普通文字投递路径。`VoiceRealtimeRuntime` 将“会话已连接、引擎模式、可否播报”的状态暴露给协调器，但 Gateway 不直接向语音 socket 发工人正文。

在 `agentEngine` 的既有 `conversationTail` 内增加一个系统注意力回合入口，复用 `DurableVoiceAgentBroker` 的任务流、Agent 回复文本、TTS 和播放回执。它以 `origin: system/task_update` 提交稳定输入，不伪装成用户语音；客户端收到独立的 `responseId`，聊天记录也保留独立主 Agent 消息。通知回合只能读取任务和组织汇报；可能产生外部副作用的追问、改派和工具动作必须另经持久任务命令执行，避免音频被打断时出现含糊的执行结果。语音端只在这些条件同时成立时领取：上一句用户语音已提交；无待提交转写、排队用户回合或活跃回复；播放已完成；已达到可配置的短暂安静窗口。优先处理新用户发言，系统通知不能长期占住串行队列。

播放前用户开始说话：取消尚未发声的通知回合并保留待处理项，供用户回合读取。播放中被打断：按现有中断审计记录已发声片段；文本消息仍可见，未播完的语音不自动重播，下一回合由主 Agent 决定是否补充。音频失败不应重新执行已经完成的主 Agent 工具动作。挂断时释放语音租约，未交付项回到普通文字/下次接通路由；通话结束本身不停止 TaskRun。

首期语音策略：普通进展只更新任务卡；关键结果在安静窗口播报一小句；阻塞问题和待批准事项优先播报，但仍不抢用户讲话。用户可以说“只在完成时告诉我”或“别在通话里播报进度”，偏好持久生效。无工具的自然语音模式先显示任务状态和待办，挂断后由当前助手模式处理；以后若接工具桥接，必须先解决同一会话执行权、权限及双向音频时序，不能简单把工具注入模型。

## 5. 对外表现和权限

- 主聊天保持唯一叙事入口。每次主动汇报是一条独立的主 Agent 消息；派工消息下继续显示 Task 引用。工人原文留在 Task 详情/协作板。
- 通话界面沿用现有任务卡，增加“有进展”“需要你决定”的轻量状态；用户可点入详情。默认不把所有进展读出来。
- Environment Context 显示关联 Task 和未决事项计数；它是可查询目录，不表示模型已读全部协作记录。
- 每条通知可追溯到 Task、协作记录、receipt 与主 Agent 的决策批次。对用户显示“已提交结果／已验证／待你验收”的真实状态，不把 `TaskRun succeeded` 直接说成任务完成。
- 新增认证 API 时更新 `lazy-bundles.ts`、映射测试，并通过真实 Gateway 鉴权路径验证。跨渠道外发使用现有权限和审批边界，首期不开放自动跨渠道转发。

## 6. 实施切片

### P0：可复现基线和持久收件箱

先补贯穿测试夹具：用户持续对话、TaskRun 报进展/提问/结果、主 Agent 回复、Gateway 重启恢复。随后增加 Agent 归属、注意力项、决策/交付表及从旧待处理行迁移。新协调器先以影子模式记录决策而不投递；核对无遗漏后按 Agent 灰度切换，用功能开关确保只有一条投递路径消费源事件。回滚时保留新收件箱和交付记录，恢复旧路径前按源记录去重。保持当前文字行为，验证去重、按 Task 归并和用户输入优先。

**完成标准**：相同事件重放不产生第二条用户消息；重启后待办不丢；多个 Task 的阻塞提问不会被进展洪流饿死；原文字委派回归通过。

### P1：活跃助手语音汇报

增加语音引擎安全空档事件、Broker 的系统注意力回合，以及播放状态到交付记录的回写。通话中关闭旧的文字主动投递，同一批次由语音或文字中的一个媒介领取。实现打断、挂断、重连后的恢复语义。

**完成标准**：通话不断开，工人完成后主 Agent 在安静空档主动简述；用户随时可继续讲话；普通进展不抢话；阻塞问题能到达主 Agent；文字记录与可听内容分开且不重复；关闭通话不取消后台 TaskRun。

### P2：长期责任与唤醒

在现有 Project、Task、Automation 之上建立 `agent_responsibilities` 投影：目标、关联对象、下一次检查时间、待决问题、完成条件、允许的动作范围。调度器按事件或时间唤醒主 Agent，主 Agent 可检视任务、重新派工、要求验证或询问用户；不新造一套 Task 生命周期。加入按 Agent 的可检索工作摘要，避免无限塞入 prompt。

**完成标准**：浏览器关闭/语音挂断/网关重启后责任仍在；用户换一段会话仍能问同一 Agent 的进度；每次主动行动都有来源、权限与可追溯决策。

### P3：跨渠道和更广的执行环境

明确每种信息的接收人、敏感级别和允许渠道后，再接消息渠道及独立工作环境。语音、网页和消息入口是同一 Agent 的不同呈现面，但可见记录与外发权限分别控制。自然语音模式的工具桥接和主动播报在单独验证后开放。

## 7. 验证与观测

测试按“语音持续对话时派工并完成”“用户说话期间到达结果”“TTS 播放中被打断”“连续十条进展后一个阻塞问题”“工人指令接收后失败”“Gateway 在决策/提交/落盘/播报各阶段重启”“会话 reset 或删除”“两个 Task 同时结束”构建。单元测试覆盖状态迁移与幂等；集成测试走真实 Gateway、SQLite、实时 WebSocket；最后用可用语音服务进行人工 E2E，记录可见与可听证据。模拟模型测试不替代真实语音验收。

新增指标：派工确认延迟、工人事件到主 Agent 处理延迟、事件到用户可见/可听延迟、重复/漏报、工人指令确认率、待决事项积压时长、主动播报打断率、每任务模型调用与花费。按文字、活跃语音、挂断后恢复分别统计；先收集基线再定发布阈值。

## 9. 实施前需坚持的不变量

1. 同一主会话任一时刻只运行一个主 Agent 回合；用户输入优先。
2. Task 与协作记录是事实；注意力项和 UI 是可重建投影。
3. 工人不能直接给用户发消息，也不能通过留言扩大自身权限。
4. “记录已写入”“输入已接收”“Agent 已处理”“用户已看到/听到”是不同状态。
5. 任何后台重试都使用稳定幂等键；不因音频重试而重做外部副作用。
6. 会话和音频连接可以结束，Task 与主 Agent 责任仍按各自生命周期存活。
