# 主动性短期优化：让现有跟进可靠、可理解、少打扰

日期：2026-09-16。状态：待实施的产品与技术方案。

本方案是 [主动服务平台长期方案](./proactive-platform-product-and-architecture.md) 的近期实施范围。当前不建设市场、服务包安装、社区生态、行为自动启用或新的通用调度引擎。先改善现有项目、会议、邮件、讨论跟进与 Heartbeat；普通 Automations 保持独立。

## 1. 这轮要交付什么

用户能明确知道：**助理在关注什么、最近检查到了什么、接下来等什么、为什么现在找我，以及我处理后是否还会继续。**

三项产品目标：

1. 看得懂：没有成果时，也能区分正常等待、没有新变化、执行失败、资料陈旧和暂停。
2. 提醒准：根据最新资料、真实行动时限与事项状态提醒；打开应用不等于已经看到某项结果。
3. 跟得住：调整要求、回复决策、任务完成、会议改期、邮箱恢复同步后，都按清楚的规则继续或结束。

本轮保留现有场景、页面和执行方式。只新增必要的状态投影、策略检查、观察记录及小范围持久等待信息。权限不扩大，自动项目动作仍限已授权的创建待办，邮件发送仍走原连接器确认。

## 2. 现状证据与问题分类

以下来自本轮核对的当前源码；历史 review 文档可能记录过不同阶段，不能仅凭其“已完成”描述判断当前页面能力。下列风险是代码路径分析，不等同于已复现的线上事故。

| 当前实现 | 产品问题或风险 | 短期处理 |
|---|---|---|
| `Delegation` DTO 只有启用、检查中、要求等；`delegationNextTrigger` 返回固定说明 | 用户无法看到最近一次检查结论、真实下次时间和失败恢复信息 | 扩展只读状态投影，保留简洁默认界面 |
| `saveSettings` 每次都将 `next_due_at` 写为当前时间 | 仅修改提醒方式也重排检查；配置与调度耦合 | 按字段变化处理，通知变化不触发分析 |
| `presence` 只记录整个应用活跃，投递端据此静默 | 用户在别的页面也可能被认为已看到相关成果 | 区分应用活跃、相关对象可见与具体成果已读 |
| 摘要在应用活跃时可直接将队列标记 consumed | 既没生成摘要，也没有用户已读证据，摘要机会可能丢失 | 持久化摘要与场景入口；活跃只影响通知方式 |
| 邮件视图读取同步状态；扫描基于线程指纹及 due/waiting | “读取本地缓存”容易被误解成“刚确认邮箱没有回复” | 执行前引入同步健康／新鲜度门槛 |
| `mailFollowUpView.enabled` 来自共享订阅，未合并具体线程 status | 单线程暂停状态需要前后端联合解释；跨线程动作要防误影响 | 服务端给出线程级 effectiveState，保留共享配置结构 |
| Heartbeat 独立定时、调用常规 Agent、直接通过 MessageBus 投递 | 关闭跟进不等于停止巡查；结果与失败难统一查看 | 统一控制门槛和运行摘要，原执行器保留 |
| Heartbeat 仅保存最近文本及时间到内存去重 | 重启丢去重状态，且无明确投递目标时用户看不到检查结果 | 保存检查结果、去重键和投递原因 |
| 项目时间扫描已有指纹；分析已有来源复核；成果已有过期／撤回 | 基础机制存在，不宜重写 | 将同一规则补齐到扫描、摘要和最终投递并建立回归 |

不预设当前已经发生重复发信、越权或关键提醒漏报；这些作为场景测试验证。当前只读执行与项目审批边界应原样保留。

## 3. 产品方案

### 3.1 “助理跟进”做小幅增强

继续使用 `/assistant-work`，保留跟进中、已暂停、已结束。增加运行受阻的轻量提示；受阻不自动归类为“用户暂停”。

每项默认展示四行：

```text
官网改版 · 交付跟进
关注：影响周五上线的阻塞，先准备解决建议
最近：14:20 已检查，没有新的交付风险
接下来：16:20 再检查；有任务变化时也会检查
```

若有成果，优先显示成果和需要用户做的动作。只有重试、离线、资料陈旧等影响承诺的情况才在列表显露；完整进展记录留在详情。

邮件示例：

```text
供应商报价 · 邮件跟进
等待：对方回复，或明天下午 3 点重新确认
资料：邮箱最近成功同步于 14:15
当前：邮箱同步暂时失败，暂时无法确认是否已有回复
```

“检查过了”和“资料同步过了”分别显示，禁止把本地扫描时间当成外部资料更新时间。

### 3.2 详情回答五个问题

| 问题 | 内容与操作 |
|---|---|
| 关注什么 | 现有自然语言要求、具体项目／会议／邮件来源 |
| 可以做到哪里 | 现有项目权限说明；邮件明确“准备草稿，发送需确认” |
| 最近发生什么 | 最近有效检查、无变化、成果更新、失败及重试，不展示原始日志堆栈 |
| 接下来怎么办 | 明确等待事件、约定时间或下一次尝试；没有准确时间时不伪造时间 |
| 如何调整 | 修改要求、提醒方式、项目间隔、暂停、恢复、结束、可支持的立即检查 |

“立即检查”复用当前队列：正在运行时定位已有运行；已有可重试运行时提前其尝试，不创建第二个并行检查。邮箱需要更新资料时提供“更新资料后检查”，复用连接器同步并受节流约束。讨论事项仍等讨论事件，短期不增加通用强制重放。

### 3.3 状态按事实呈现

后端组合三条互不混淆的状态轴，前端只显示最重要的一条并能展开说明：

| 状态轴 | 取值示意 |
|---|---|
| 安排 | 跟进中、暂停、结束 |
| 执行健康 | 等待条件、排队、检查中、准备重试、需要处理、资料待更新 |
| 当前成果 | 无新变化、已有成果、待用户决定、实际动作已确认、结果未知 |

已准备成果和最近一次检查失败可以同时存在；旧成果保留但标出时效，不能被“失败”整体覆盖。没有卡片不等于没有运行，也不等于运行成功。

展示优先级：结束／暂停 → 需要用户修复或来源失效 → 待决定 → 可用成果 → 正在检查／自动重试 → 正常等待。详情始终可同时看到各状态轴。

### 3.4 把后台检查与提醒控制分开

在现有提醒偏好页增加两个控制：

| 控制 | 短期作用范围 | 不包含 |
|---|---|---|
| 暂停自动检查 | 场景跟进的新扫描／分析／自动动作、Heartbeat 新轮次 | 用户主动对话、普通 Automations、系统记忆维护 |
| 暂不推送提醒 | 场景跟进与 Heartbeat 的系统自动结果通知；成果继续可查 | 用户在对话中明确请求的发送、独立自动化通知、系统故障告警 |

页面明确列出范围，并提供“查看独立自动化”入口。不能把按钮命名为“停止所有后台工作”。

暂停保留各事项的启用状态；恢复不重新打开原本由用户单独暂停的事项。执行中显示“已阻止新检查，当前检查正在结束”；可取消的只读运行尝试取消，不能撤回已发生外部动作。结束后旧运行的结果按暂停／版本策略保存但不自动执行或推送。

静音控制的是系统通知，不能伪称它限制了常规 Agent 的任意外部工具。Heartbeat 若利用普通工具主动发送，应在工具派发层识别 heartbeat 来源并应用自动消息策略；无法覆盖的外部脚本副作用不承诺可被静音，需另行收窄清单和权限。第一批 UI 不使用“保证不会再有任何外部消息”这类文案。

### 3.5 Heartbeat 放进同一视野，仍保留清单入口

助理跟进页增加一个“日常巡查”条目，详情沿用现有 Heartbeat 设置和 `HEARTBEAT.md` 编辑，不新增另一套配置表单。

展示：是否启用、清单是否有效、最近尝试、最近成功、下次计划、当前活动时段、最近结果、投递去向与未提醒原因。

没有目标渠道时，显示“巡查结果保存在这里，尚未配置外部提醒”，而不是静默丢掉结果。清单为空显示“未安排巡查内容”；清单读取失败显示具体可操作状态，不等同于无新发现。

Heartbeat 和场景跟进不进行基于自然语言的自动合并。对重复检查同一项目的清单提供明确调整入口；只有有同一业务对象及同一行动的可靠身份时，才能合并提醒。短期不让模型猜测两段文本是否同一安排并删除其中一个。

## 4. 四项提醒质量改进

### 4.1 资料新鲜度先于模型判断

项目使用本地权威状态，继续做分析前后版本复核；会议和邮件额外检查来源成功同步时间、覆盖范围、是否有进行中的增量同步和最近失败。

初期采用服务端场景常量定义可接受延迟，参考连接器预期同步周期并在真实联调中校准，不向普通用户增加一组复杂阈值。时间戳不足以证明范围完整：同步成功但不覆盖该日历／线程时仍不能断言无事件。

邮件到了约定时间，但最新有效同步早于该时间：先等待或请求一次受限同步，成功后重新判断。同步失败时显示“无法确认是否收到回复”，不生成“对方仍未回复”的确定断言。需要提醒用户恢复连接时，一次性显示恢复提示，不每轮重复催。

### 4.2 前台活跃不代表已读

将现有 presence 扩展为应用活跃、相关对象可见、具体卡片版本已展示／已读。具体已读使用显式交互或经过可见性验证的前端事件，不仅根据列表数据已加载。

| 用户状态 | 呈现策略 |
|---|---|
| 正在看该事项／成果 | 原地更新，通常不额外推送 |
| 应用在前台，但在别的页面 | 保留应用内通知及入口；普通外部推送可短暂延后 |
| 不在应用中 | 按重要程度、时效、预算与渠道投递 |

短暂延后必须保留队列和 `recheckAt`；下次重新判定已读、有效期和行动期限。不能仅凭应用活跃写成永久已通知。超过行动期限后不补发过期提醒。

摘要先保存真实摘要对象及成员，再决定是否推送。即使正在使用应用，也能从工作台打开该摘要；没有内容的摘要不创建。第一版使用已有成果确定性汇总，不增加摘要模型调用。

### 4.3 按同一事项更新，减少重复

复用当前 correlation 与卡片生命周期，加上明确对象身份：项目 ID、日历账户＋事件发生实例 ID、连接账户＋邮件线程 ID。

仅对“同一对象＋同一问题／动作＋相同有效版本”去重。不要只按标题，也不要把同一项目里的不同风险合并。无结构化问题身份时保守保留成果，使用既有指纹去重，不承诺模型语义级去重。

新来源版本更新原事项成果，保留用户编辑与过往决策。同一事项从建议升级为需要决定，或真实截止时间进入新窗口时，允许重新评估提醒；不能因第一次已经通知而永久压制。

### 4.4 最晚行动时间与有效期

为会议、邮件到期跟进及有真实截止点的项目成果补充 `actionableUntil`，与卡片展示 `expiresAt` 分开。

提醒推迟到免打扰结束后已经无意义：保留过往记录，但取消推送。会议改期重算窗口，取消撤回卡片与待发提醒。项目在别处完成后撤销旧风险提醒。短期默认不自动突破免打扰。

所有渠道和摘要在最终投递前调用同一个最新状态检查，避免首次排队时通过检查后就永远有效。

## 5. 执行与续办：补齐现有闭环

### 5.1 变更分类

| 用户修改 | 运行影响 |
|---|---|
| 提醒方式／静音／渠道 | 重新评估待发通知，不改变下次检查时间 |
| 项目检查间隔 | 以最近检查和新间隔计算下次时间；已到期只排一次 |
| 关注要求 | 发布要求版本；项目合并排一次新检查；会议／邮件仅在有效工作项内重算 |
| 暂停 | 停止新检查及待发通知；保留原计划和状态，不清空用户要求 |
| 恢复 | 检查当前真实状态，合并一次到期检查，不重放所有错过时点 |
| 结束 | 停止后续跟进、撤销待发提醒；保留成果，不把相关任务标为完成 |

短期不新增通用 TriggerIntent 表。使用已有批次、运行、项目 `next_due_at`、邮件 `due_at` 和日历窗口去重键；只补“条件变化后下一次何时检查”的最小字段。

### 5.2 失败恢复和等待

复用已有重试次数和 run 身份。可重试故障显示下次尝试；重试耗尽显示恢复动作；鉴权失效、来源陈旧、用户输入缺失各有不同说明。

项目继续支持现在检查。邮件／日历在成功同步事件后重新检查相关到期事项，避免因为上次指纹已经记录、这次内容没变而永久跳过恢复；必要时将“新鲜度恢复版本”纳入资格重新评估。恢复连接只触发相关来源，不唤醒整个工作区。

运行结果保持内部类型：`no_change / prepared / decision_required / blocked / failed / cancelled`。优先使用现有 run 状态和 `outcome_reason` 映射，不要求迁移所有成果到长期方案的统一结果表。

用户回答决定后回显实际动作及状态。创建待办显示真实任务链接；任务结束后更新原卡片。邮件草稿续办携带原线程、连接账户、当前草稿版本；供应商返回成功后才显示已发送。超时且无法确认时显示“发送结果待确认”，不自动重发。

### 5.3 轻量个性化

保留自然语言纠正和版本化要求；补充少量可操作反馈：“不相关”“太频繁”“太早／太晚”“已在别处处理”。先记录原因并引导具体调整，不自动训练排序或重写所有 Prompt。

“这次不用”只收起本次；“这个项目少提醒”调整该项目提醒；“不再跟进”结束明确事项。邮件多个线程共用订阅，线程级要求应写入对应 follow-up，不能因为某条邮件反馈改变所有线程。

不新增主动推荐弹窗、不根据历史行为自动启用安排。对话中用户明确要求“以后继续这样做”仍走现有工具建立委托。

## 6. 技术设计与最小改动

### 6.1 三个内部组件，继续使用既有运行管线

```text
现有事件／Temporal Worker／Heartbeat
                ↓
   admission：当前允许检查吗？资料够新吗？
                ↓
      现有 Agent／队列／动作执行
                ↓
    status projection：用户能理解的事实
                ↓
 delivery decision：展示、延后、推送或取消
```

| 组件 | 职责 | 建议落点 |
|---|---|---|
| AdmissionPolicy | 暂停、新鲜度、来源授权、过期和原有运行限额 | 扩展 `src/proactive/policy/` 与 `execution/authorization.ts` |
| FollowUpStatusQuery | 汇总运行、计划、来源与成果，只读、不启动工作 | 新增 `src/proactive/status.ts`，扩展 `experience.ts` |
| DeliveryDecision | 场景、Heartbeat 系统结果统一做提醒判断与原因记录 | 扩展 `inbox/delivery.ts`、`notification-policy.ts`、`notifications/` |

不将普通 Automation 的 Agent 指令改走 proactive executor；不增加服务包、注册中心、执行插件接口或第二套消息队列。

### 6.2 状态 DTO

建议扩展现有 overview／详情返回，语义示意：

```ts
interface FollowUpStatus {
  arrangement: 'active' | 'paused' | 'ended';
  health: 'waiting' | 'queued' | 'running' | 'retrying' | 'blocked';
  reasonCode?: string;
  lastAttemptAt?: string;
  lastSuccessfulCheckAt?: string;
  lastOutcome?: string;
  next: {
    kind: 'scheduled' | 'source_change' | 'source_sync' | 'user_decision' | 'none';
    at?: string;
    reason: string;
  };
  source?: { lastSuccessfulSyncAt?: string; freshness: 'fresh' | 'stale' | 'unknown' };
  delivery?: { state: string; reasonCode?: string; recheckAt?: string };
  activeRunId?: string;
  latestResultId?: string;
}
```

一个会议服务可能有多场会议；列表级状态汇总，详情按具体会议事项展开，不能只用订阅最新一张卡代表所有会议。恢复同步的状态同样按来源或线程判断，避免一个邮箱失败污染另一个账户。

运行设备状态来自当前 Gateway 连接；客户端失联仅显示“连接已断开，无法确认后台状态”，不能断言服务器已经停机。最近成功检查用后端持久时间，不用页面刷新时间。

### 6.3 存储增量

优先复用 `proactive_runs`、`proactive_schedule_state`、`proactive_follow_ups`、卡片及通知队列。

- 全局控制增加明确的 `checksPausedUntil`／`notificationsMutedUntil` 及无限期状态表达；兼容旧 `level=off`／`pausedUntil` 的映射必须保持原先禁用语义。老接口写入需更新统一控制源，避免两个独立真值。
- presence 增加当前相关对象引用，具体卡片可见／已读记录版本；短期 TTL，不保留页面浏览轨迹。
- 卡片／提醒增加可选 `actionableUntil`；延迟决策保存 `recheckAt` 和原因，不把延迟写成已投递。
- 若现有 run 结构不能表达 Heartbeat，新增一个有界 `heartbeat_checks` 记录：轮次、会话／配置版本、开始结束、结果状态、去重键、产物引用、投递决定。它只记账，不承担另一套调度。
- Heartbeat 结果正文采用有长度与保留期限制的已有产物机制或本地记录，不复制完整会话。内容读取遵循当前工作区权限。
- 来源水位优先查询现有同步记录；确实缺覆盖范围时在来源层补字段，不用 UI 文本推断同步成功。

多状态写入在本地事务内完成，模型和网络操作在事务外。运行完成更新校验 attempt／版本，暂停或配置更新后的旧结果不能覆盖新要求。

### 6.4 Heartbeat 接入约束

保留原间隔、活动时段、清单、默认 Agent 选择及会话选项。增加开始前 admission、结束记录和统一通知决策。`HEARTBEAT_OK` 转成“已检查，无需提醒”，不创建内容卡片。

去重持久化，键包含工作区、目标和归一化正文；跨重启保持当前去重窗口。检查结果和投递状态分开，无目标、发送失败不能记成已成功送达。真实发送走现有 outbox／通知适配，不再建立不受跟进静音策略约束的第二条结果投递路径。

现有目标支持渠道＋chatId，不能为了复用仅有 Telegram 的主动渠道实现而丢失其他渠道。给现有 MessageBus 目标增加受策略控制的持久投递适配；只有宿主已有发送确认才记确认送达，否则显示“已排队”。

应用现有跟进每日预算／免打扰到历史 Heartbeat 会改变提醒行为，应在升级说明及设置中明确展示；保留原渠道，取消隐式新订阅。没有显式启用的巡查不因页面归并被启用。

### 6.5 接口和前端

优先扩展 `/api/proactive/overview`、现有 preferences、订阅详情和 Heartbeat 状态接口；若没有合适详情接口，再补查询型状态／有限历史端点。不要为只读状态增加可运行代码的通用命令接口。

状态在检查结束、来源同步、暂停和通知决定时发 realtime 失效事件；保留当前轮询兜底。前端复用既有卡片、设置、Skeleton 与 Select，复杂详情固定外框、内部滚动。

新增或变更路由同步更新 `lazy-bundles.ts`、作用域授权和映射测试，使用真实 Gateway 鉴权请求验收。所有写入保留 expectedRevision 与幂等键。

## 7. 实施顺序

不预估未经代码评估的周数，以四个可独立验收的批次推进。

| 批次 | 交付 | 主要代码范围 | 完成条件 |
|---|---|---|---|
| A：状态可信与低成本修复 | 真实最近／下一次状态、失败原因；设置变更分类；项目间隔展示 | `experience`、`scenarios/control`、`temporal/schedule`、proactive 前端 | 改提醒不重排检查；无变化／失败／等待可区分；下次时间来自持久计划 |
| B：提醒与资料质量 | 新鲜度 admission、事项级 presence、摘要保留、投递前统一复核 | `follow-ups`、`temporal/worker`、`execution`、`inbox`、`notifications` | 旧邮箱资料不产生确定无回复结论；前台不吞摘要；取消／过期不推送 |
| C：Heartbeat 纳入控制 | 两类全局控制、巡查运行记录、去重持久化、原渠道投递适配 | `gateway/heartbeat`、policy、通知与设置 | 重启不重复提醒；无渠道可查结果；暂停新检查有效；原目标渠道保持可用 |
| D：续办与反馈收尾 | 同步恢复继续、任务结果回流核验、线程级纠正、少量反馈原因 | actions／cards、follow-ups、连接器同步事件、前端 | 用户处理后不被旧提醒催；恢复来源可继续；线程反馈不改其他线程 |

A、B 是第一轮最小交付，直接解决当前可见问题。C 在统一投递规则稳定后接入。D 优先补当前链路的缺口，不重做已经通过验收的卡内决策和成果编辑。

## 8. 验收场景

| 场景 | 必须看到的结果 |
|---|---|
| 项目无新变化 | 显示最近有效检查与下次时间，不伪造新成果 |
| 只修改提醒方式 | 原检查计划不变，待发提醒按新设置重评 |
| 同时点两次检查 | 复用已有运行或幂等请求，不创建并行模型调用 |
| 分析时修改要求／暂停 | 旧运行不能覆盖新要求或触发自动动作／新推送 |
| 应用前台但在另一页 | 仍有应用内结果入口；重要提醒没有被当成“已读”永久丢弃 |
| 摘要到点时用户在线 | 摘要对象可读，活跃状态只决定是否额外推送 |
| 邮件到期、同步陈旧 | 显示资料待更新，不声称对方没有回复 |
| 邮箱恢复、线程正文未变 | 到期事项仍能重新判断，不被旧指纹永久挡住 |
| 两个线程共用一个订阅 | 暂停／纠正其中一个不改变另一线程 |
| 会议改期／取消 | 旧窗口和提醒失效；新窗口正确生效或停止 |
| 免打扰结束时会议已结束 | 不补发旧会前提醒 |
| 项目任务已在其他端完成 | 原跟进卡更新，旧待办建议不再重复催办 |
| Heartbeat 重启 | 相同已处理结果不重复排通知；结果可追溯 |
| Heartbeat 无目标／投递失败 | 如实显示已检查与未送达原因，不称已提醒 |
| 全局暂停再恢复 | 原本单独暂停的事项仍暂停；过期检查不成批重放 |
| 客户端断线 | 只说明无法确认后台状态，不谎报设备停机 |
| 邮件发送超时 | 已有连接器若不能确认结果，明确待核对，不自动重复发送 |

验证顺序：小范围规则测试 → 隔离数据库生命周期与重启测试 → Web 交互 → 真实鉴权 Gateway → 授权的真实邮箱、日历与设备投递联调。前四项通过不能替代最后一项。设计阶段不声称这些场景已经验收。

## 9. 观察指标与退出条件

第一轮不做推荐算法，也不增加模型调用来评判每条模型输出。先用确定性原因和现有反馈观察：

- 应提醒但未在行动期限前交付的已知案例数。
- 重复推送、过期投递、陈旧来源导致的错误判断数。
- 已检查无新变化、资料待更新、运行失败的占比及可解释性。
- 每次采用成果的模型用量与重复检查量；改通知设置不应带来新增分析。
- 用户能否不看日志就说明“现在在等什么”，能否找到最近成果和恢复入口。

确定性门槛：上述权限、暂停、幂等、失效、版本冲突回归全部通过。体验门槛：项目、会议、邮件三条真实场景与至少一个实际通知渠道完成端到端联调；Heartbeat 原有目标适配通过回归。准确性和打扰改善以小范围真实使用基线比较，不虚设成功率。

## 10. 与长期方案的衔接

保留三项将来可复用的边界：检查资格、用户状态投影、提醒决策。它们未来可以接服务包，但短期不为未来市场增加安装协议、复杂绑定层或全新工作项引擎。

这轮结束后，现有主动性的承诺应是：**事情有人持续看着；没有新发现也说得清；资料不可靠时不乱判断；该提醒时不会因为用户开着页面而被吞掉；用户处理后不会再被旧状态追着催。**
