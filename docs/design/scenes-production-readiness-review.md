## 原始发现（已修复）

### P1：邮件变化检测失败被吞掉，用户仍看到正常状态

位置：`src/scenes/mailObservations.ts:68`、`src/scenes/runtime.ts:68`。

观察器捕获来源读取／授权异常后，只更新内存退避和 `unavailable` 计数；运行时只使用扫描游标，没有持久化来源错误。之前产出的草稿仍显示为正常成果，诊断仍取上一条运行的状态。

隔离复现：先生成草稿，再令邮件观察 provider 抛出连接错误，扫描返回 `unavailable: 1`，成果仍为 `unread`，诊断 `last_reason` 仍为 null。这不表示已发生越权读取，但用户无法知道“留意新回复”已经中断。

验收要求：记录最后观察成功时间、错误类别、下次重试及连续失败；来源不可用时明确提示旧成果待核实；提供重连／重试入口。授权失效、429、网络超时需能区分，恢复后状态自动更新。

### P1：相同证据重复检查会重新发布相同成果

位置：`src/scenes/repository.ts:580`、`src/scenes/agentExecutor.ts:30`。

每次成功运行直接撤回旧 presentation 并创建新成果／通知身份，没有比较上一次有效成果；模型输入也不包含上一次结果。不同检查请求的幂等键不能解决内容重复。

隔离复现：完全相同的目标、证据和模型输出，执行两次合法检查后，模型调用 2 次、成果 2 份、旧 presentation withdrawn、新 presentation unread、通知出站记录 2 条。实际发送还受权限／预算／免打扰约束，因此此复现不声称设备已收到两次。

验收要求：至少相同有效上下文和相同成果不重置已读／反馈、不创建重复提醒；真正新增信息或新的计划周期仍可生成成果。需要显式建模周期，避免把家庭周计划的跨周执行永久去重。

### P1（产品流程）：开启成功不等于已经开始持续工作

位置：`src/scenes/service.ts:44`、`web/src/features/scenes/scenes-page.tsx` 的 CreateScene。

新建只提交目标、范围和权限，然后直接进入 active。家庭资料／检查计划以及邮件截止时间仍需在详情内另行配置；没有这些配置时，场景可以长期显示“已开启”但不会自动完成首次检查。页面虽有“开启后可设置检查时间”的说明，仍未给出清晰的完成引导。

验收要求：把必要资料和时间纳入开启流程，或保持“待完成设置”并显示明确下一步；开启完成后能说明下一次运行时间及是否已经完成第一次检查。不要偷偷增加未经授权的邮箱范围或模型调用。

### P2：诊断把暂停／已过期的时间展示为下一次检查

位置：`src/scenes/metrics.ts:24`、`web/src/features/scenes/scene-diagnostics.tsx:22`。

诊断无条件取 schedule cursor 或 watching work item 的 due_at，UI 直接显示为“下次定时检查”；没有考虑 activation 暂停／完成、截止时间已触发或来源等待状态。

隔离复现：把已有截止时间的场景暂停后，诊断仍返回该截止时间；UI 不使用 activation.status 过滤。现有截图也出现了暂停状态下的过去时间。

验收要求：区分约定截止时间、下一次实际运行、下一次重试；暂停／完成时明确不会继续运行，时间不能伪装为未来排期。

### P2：成果依据仍是内部 ID，不能供普通用户核实

位置：`web/src/features/scenes/outcome-card.tsx:53`。

成果卡直接拼接 `scene-notes:<uuid>`／mail evidence IDs，缺少来源名称、生成时间和查看原始资料入口。这些 ID 对用户没有可解释性，无法支持核验建议。

验收要求：显示可理解的来源标题和时间；邮件可回到授权线程、资料可回到该场景输入。仅暴露已授权信息，不为展示依据而持久化整封邮件正文。
