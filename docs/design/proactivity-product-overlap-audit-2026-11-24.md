# xopc 主动体验产品审查

2026-11-24 · 产品评审建议 · 基于当前仓库和 11 月 16–22 日项目周报

## 结论

**保留「用户能把原来要自己惦记的一件事交给助手」的价值，把这份方案收敛为现有能力的统一体验。** xopc 已有能力发现、持续推进、定时执行、筛选事件并打扰用户。现阶段新增一套「关注事项」页面、执行流程和主动消息体系，会让同一件事更难找到、更难停，也使现有价值更难感知。

用户真正需要的是三件事。助手在他交代之前，可以用允许的资料先准备一点有用的工作。用户愿意交出去时，在原处说一句就能形成明确承诺。后来只在有新价值时拿到结果，并且能在原处查、改、停。**只有这些动作比现状更省力、更可信，才有产品增量。** 原型里的发布和街拍用于验收这些动作，通用规则按依据、委托、结果和时机运行。

## 2. 哪些是真重叠，哪些需要保留区别

### 优先解决三处用户可感的冲突

1. **同一件工作已有发现入口和持续目标入口。** Onboarding 可以给工作方向，「交给我」会给观察建议和「设为持续目标」，Personal 也会提取跟进。给用户新增一种「关注事项」及其独立列表，会让人分不清在三处看到的是同一件事、一个草稿还是已经承诺执行。建议工作结果汇回原项目或任务。尚未有归属时从当前会话或现有工作台详情接住，等用户确实要持续时再补归属。 [工作建议配额与候选](../../src/home-intelligence/host.ts) · [工作台持续目标](../../web/src/features/tasks/follow-up-workbench.tsx)
2. **同一业务变化可以进入两个主动判断链路。** Gateway 将同一 Automation 事件交给 Personal 和 Hub。Personal 会对相关的已激活任务／项目关注唤醒，Hub 自己做事件匹配、分流并可写入 Personal。同一变化若满足两边的条件，有重复判断与触达风险。目前看到的是两个入站和发布路径，实际重复推送的频率仍需复现。更明确的差异是两个路径分别计数。Personal 对推断消息用配置额度，Hub 使用独立计数且以 `Math.max(1, settings.dailyMessages)` 设下限。Hub 也没有在最终发布处按 `follow_up` 模式要求明确委托。零条或仅明确跟进，应在普通主动消息路径上表达同一件事。 [Gateway 事件分发](../../src/gateway/service.ts) · [Personal 发布预算](../../src/personal-agent/proactivity/service.ts) · [Hub 发布预算](../../src/proactive-hub/triage-service.ts)
3. **用户的停止和调整按入口分散。** 「暂停观察」本来会保留已经确认的托管，Hub 的静音作用在事件规则，Personal 反馈又可以是本条或关注主题。这些底层差异有理由。需要的是从眼前的条目清楚告诉用户「这次先不看」「以后放工作台」「整件事停止」各自改变什么。工作台和 Personal 引用同一事项时，处理同一条结果的行为应一致。独立授权的执行仍按自己的约定管理。 [观察生命周期](./long-term-observation-stage-abc.md) · [Inbox 反馈](../../web/src/features/proactive/proactive-inbox-card.tsx) · [Personal 反馈接口](../../src/personal-agent/proactivity/routes.ts)

### 从用户的一句话出发，保留三种不同承诺

| 用户的意思 | 所需承诺 | 沿用位置 |
| --- | --- | --- |
| 「有变化告诉我」 | 关注有明确来源和触发条件的变化，符合时交付一条结果 | 已有 Personal 跟进或 Automation 观察，依来源和触发能力选择。Hub 可帮助筛选和投递。 |
| 「每周五帮我准备一份」 | 周期性拿到一个可用成果，来源不齐时说明缺口 | 已有 Automation 或工作台托管，结果回到约定入口。 |
| 「帮我推进到完成」 | 有明确终点，需要执行、处理缺口及验收 | 已有持续目标与 Task。相关更新指回同一任务。 |

用户可以在一段对话里自由表达三种意思。保持原有权威对象和取消／验收语义。只有识别错了会改变承诺时，才问一句「你想变了再告诉你，还是每周都要一份？」用户已明确要的任务结果、约好的提醒以及可选的主动发现，分别保持各自的交付义务。静音一般主动消息不能隐去答应交付的文件。

## 3. 这套体验真正值得做的地方

| 价值 | 现有能力之间常见的摩擦 | 用户能直接感知的改善 |
| --- | --- | --- |
| **先见结果，再决定是否托付** | 用户要先读一条建议、点开始、切到另一页，才知道能否真的帮忙。 | 在范围允许且信息充分时，工作台出现一份已经用得上的对照或草稿。或者在正在进行的对话里自然补一个可用事实。把继续查看或委托留给用户。 |
| **少操一份心** | 明知道有 Automation，依然需要自己翻找项目、定义监控、猜执行能否覆盖，或再三回来刷新。 | 一句「如果还没确认就告诉我」，助手回清楚看什么、何时来和什么时候结束。下一次用户想自己刷新时，能从结果或详情知道助手实际查到了哪里。权限失效能被发现。 |
| **需要我的时候才叫我，并让我能接着做** | 同一变化可能在任务提示、Inbox、Personal 及渠道出现。用户先去判断是否重复，再去找材料。 | 一条消息包含发生了什么、为何此刻需要我、已经准备了什么。点开是原资料，回复一个决定，工作台原事项随之更新。 |
| **生活兴趣上有一点意外的收获** | 记住用户兴趣容易演变成泛资讯或周期填满。 | 只有确实贴合现在的目标、能尝试或推进的话才用于当前对话。希望持续收到时用户可以明确约定频率。没有好内容时可以整周安静。 |

**价值强弱的判断。** 可靠地代看一个用户本来反复检查的事项，或及时带着准备好的选项找他决策，价值优先。它们会改变真实行为，也能验证现有链路是否跑通。帮助用户拓展兴趣有价值，但更容易被普通搜索建议替代。先通过相关对话衡量是否有人试用和主动追问，再考虑扩大后台主动查找。单纯多了一个候选、一次点击或一条简报，不能证明用户得益。

## 4. 建议怎么砍，怎么做第一轮验证

| 决策 | 产品建议 |
| --- | --- |
| **保留** | Personal 和工作台两个默认界面。已承诺的结果回原处。现有项目、Task、Automation 和跟进以各自真实状态为准。 |
| **收敛** | 对同一事实变化选一个首发位置，另一处可以引用同一条。统一普通主动消息的开关、提醒上限和已处理判断。现有条目详情就地显示约定、来源、最后成功检查与暂停／结束。优先连接现有对象及投递状态，按走查结果判断是否需要额外持久化。 |
| **暂缓** | 独立的关注中心、多层管理列表、每个主题一个长效配置对象、默认的每日简报、默认跨渠道推送、大规模兴趣挖掘。它们需要先证明两处现有入口无法承接真实需求。 |
| **首轮只验一条贯通路径** | 用一件用户已经在反复检查的事走完「已有证据 → 工作台准备 → 一句委托 → 条件命中时 Personal 告知 → 在同一处处理或停止」。用已有真实可读来源。另选一个普通兴趣，验证对话能接续且无合格结果时保持安静。场景可换，判断和控件共用。 |

用现有版本作对照。让用户拿一件实际正在查的事，先用现有入口完成，再走新的衔接体验。记录从交代到明确承诺用了几步、有没有再次手动刷新、关键变化有没有及时送达、从提醒到决定是否还要切屏找材料。访谈问「你敢交出去、少查一次吗？」和「你能一眼知道它现在有没有在帮你查吗？」。小样本先验证理解、重复触达和错过窗口，长期留存与真实节省时长留到持续试用验证。

**放行条件。** 先证明用户能一句话交代、从两处都能回到同一结果、只有一个提示、停止后不再出现、来源失效能被说清楚。若现有 Automation 已经能让用户同样轻松地完成，就交付衔接与默认体验的改进。若跨入口状态仍对不上，优先解决它，再增加主动覆盖面。
