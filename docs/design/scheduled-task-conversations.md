# 定时任务与配置对话

## 对象与约束

用户管理一份长期委托。任务定义（Automation）、配置对话（Session）和每次运行（AutomationRun）分别保存。

- 配置对话先于任务存在，初始为草稿；没有有效配置时不创建或启用占位任务。
- 每个任务有一个可恢复的主配置对话；重复打开复用它。一次配置对话只关联一个任务。
- 配置关联保存于现有 Session.customData.automationSetup，不改变数据库版本。使用 SQLite 写事务原子地查找、创建和关联；不依赖 URL、名称、用户消息或 localStorage 判断任务身份。
- conversationMode 只控制实际运行时的上下文；配置对话不会作为后台执行会话。
- 当前任务卡片、编辑表单与任务列表读取同一个服务端实体。工具创建成功才显示卡片；保存失败保留输入；删除后的卡片显示已不存在。
- 对话和表单都使用 updatedAtMs 作为 expectedRevision，旧编辑不能覆盖新配置。运行沿用已接受的执行快照。

## 完整流程

1. 新建：左侧“新建任务”打开轻量弹窗（说明、重复、时间，高级默认收起），点击创建保存实际任务；名称默认根据说明生成。场景卡片继续进入配置草稿对话，用户发送后开始对话配置。右上角不重复放置创建按钮或创建方式菜单。对话草稿不进入已启用任务列表。
2. 澄清：仅补齐缺失的目标、时间、范围和结果要求；明确的创建请求可直接保存。模型不得把“修改本次结果”误判成“修改以后所有运行”。
3. 创建：通过统一自动化 capability 原子创建任务并关联当前配置对话 → 返回真实任务交付 → 在对话里显示当前任务卡片（名称、频率、时区、下一次运行、状态、打开/编辑）。同一配置对话再次 create 应提示 update，防止重复创建。
4. 修改：从列表或任务卡片继续讨论 → 打开主配置对话 → 每轮注入当前配置及版本 → 使用 get/update 修改同一 ID → 卡片重新读取当前配置。删除后的配置对话不偷偷创建替代任务。
5. 表单：卡片或列表打开同一个轻量编辑弹窗 → 修改普通文本任务说明、频率、时间；时区、模型、通知和执行上下文按需展开 → 携带原版本保存 → 成功后刷新卡片/列表；冲突时保留草稿，提示重新读取。
6. 结果：每次运行以结果条目插入任务页内的对话时间线，按实际时间排序；运行中、成功、失败及送达问题直接呈现，详情按需打开。执行记录保留独立 ID 和快照；只有明确要求改变未来任务时才更新长期配置。
7. 暂停/恢复：修改任务启用状态，不抹掉配置讨论，也不等于取消当前运行。删除后已有配置讨论可回看，但显示任务已删除。

## 页面和持久化

任务页：左侧任务名称与时间；未选择时右侧灵感；选中后右侧直接显示该任务的主配置对话，底部固定输入区，对话内容内部滚动。页头直接复用完整 Chat 工具栏，包括聊天标题、智能助手、聊天菜单、会话信息和文件工作区；定时任务通过对话或列表更多菜单编辑；任务行的更多菜单提供暂停/恢复、立即运行、编辑、复制私有任务链接和删除。新建草稿与场景卡片进入同一个任务页内对话，创建成功后自动选中实际任务；不会跳去普通聊天页。聊天：草稿显示简短引导，普通聊天的历史任务交付复用可编辑任务卡片。

配置对话元数据：`automationSetup: { automationId?: string; focusedRunId?: string }`。无 automationId 为草稿，有 ID 为已关联（即使任务后来被删除也保留 ID）。普通聊天创建任务不强制变成专属配置对话；用户首次“继续配置”时建立独立主配置对话。

旧任务按首次打开懒创建配置对话。不存在的会话关联可重建，不能因失效链接阻止用户编辑任务。普通聊天的工具调用、xopc_use 与直接 automation 工具均经过同一能力层约束和关联逻辑。

## 验收

- 同一任务重复打开返回同一配置对话，数据库重开后仍有效。
- 草稿创建失败不关联任务；成功与关联同时提交；重复创建不产生第二个任务。
- 两种工具都能读取和修改当前任务；明确绑定的任务身份不能通过消息伪造或切换。
- 卡片打开真实 ID，表单和对话更新后显示新时间；并发旧保存返回冲突而非覆盖。
- 暂停、删除、缺失任务、加载和网络错误都有可理解的状态。
- 新 API 经过带认证的 Gateway lazy-bundle 实际路径测试。

## 任务级执行助手

- 执行助手保存在任务的 `action.agentId`，空值跟随默认助手；配置对话的助手不随之切换。高级设置提供“执行助手”，并提示从下次运行生效；对话按可用助手的名称解析到真实 ID，修改时保留其余配置。
- 接受运行时保存任务快照，正在执行的任务继续使用原助手。新选择不可用时保存失败并保留输入；助手在执行前被停用时明确报错，不自动换人。
- 连续模式从持久运行记录及会话路由识别上一个执行助手。同一助手延续原执行会话；换助手或切回原助手均新建执行会话，避免意外恢复旧上下文。附带最近一次成功结果（最多 4000 字符、完成时间、运行 ID）作为历史参考，明确禁止把其中内容当作新指令或授权。失败重试前仍可接收最近成功结果。
- 2026-10-25 实际验收任务 `04017293-f73`：默认助手输出验证码；高级设置改为研究助手并移除任务说明中的验证码，研究助手在新会话中成功从交接信息读取验证码；对话修改回默认助手，保持暂停、连续运行、时间和说明不变。运行中修改快照及切回时创建新会话由隔离数据库回归测试覆盖。

观察并修复的问题（频率未知，均为实际复现）：

- Major / feedback：通知策略为 all，但 destinations 为空时没有站内通知。现在开启通知即隐含一个站内投递，保留额外渠道，none 不增加投递；避免与显式 gateway_event 重复。三种策略已补回归测试。
- Major / navigation：长对话发送时外层 overflow-hidden 容器可能被程序滚动，工具栏和输入区一起移位。任务 Chat 外层改为 overflow-clip，消息视口建立定位上下文。复验多轮发送后，外层 scrollTop=0、工具栏 top=72、输入 dock bottom=viewport=1304。
- Major / feedback：流式回复缺少时间戳时，在混合运行结果的时间线中排到旧结果前。现在沿用前一条对话时间排序，消息操作索引保持不变；已补回归测试。
- Minor / recovery：失败结果缺少就地下一步。增加“对话修复”，绑定具体失败运行并填入可发送的修复问题；常见模型/助手故障用简短本地化文案，详情保留原始错误。
- Minor / information architecture：已完成的一次性任务被“已暂停”筛选包含。现在两类分开，原有紧凑下拉增加“已完成”；已实际验证排除及包含关系。
