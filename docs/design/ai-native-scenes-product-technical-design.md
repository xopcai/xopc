## 1. 产品决定

> 把一个 Slack 问题交给 xopc，它接住上下文、组织排查与开发、持续吸收后续讨论，并把代码、分支和验证结果关联回同一个事项；只有需要用户判断、授权或恢复阻塞时才主动通知。

1. 第一用户就是提出需求的用户，第一来源是 Slack，第一闭环是排查与编码交付。
2. 优先保证明确接手的 thread 跟到底，再扩展指定频道内的新事项发现；不从全工作区扫描开始。
3. 用户面对「开发事项」，内部复用 Task，不新增与 Task 并列的 Issue／WorkItem 状态系统。
4. Scene 管持续委托，Task 管具体工作，TaskRun 管执行尝试，工作区与分支是事项的执行资源。
5. 默认架构路线是 xopc 内部 BYOK Agent 直接执行；用户可明确选择 Codex 等执行器。第一条闭环只交付一种执行方式，不假设外部 Codex 集成已经存在。
6. 简单工作直接执行，复杂或稳定流程按需复用 Workflow，不要求每个事项生成 DAG，不新造 Scene 编排引擎。
7. prompt／Skill 负责业务理解与动态步骤；权限、执行身份、持久状态、分支归属、预算和验收由运行时保证。
8. 首版到「编码可交付」为止：代码、约定验证与剩余问题可检查。不默认推送、创建 PR、回复 Slack、合并或部署。
9. 已授权的内部任务整理、指定工作区修改和约定测试不逐步重复审批；范围扩张及高影响动作单独批准。
10. Scene／Extension 能力包、其他来源和非编码交付是后续扩展，不是本轮前置工程。

## 2. 三个问题与用户价值

| 当前问题 | 用户正在承担的工作 | xopc 应提供的结果 |
| --- | --- | --- |
| Slack 消息跟不过来 | 找出需要自己处理的请求，区分重复与新问题 | 明确接手的事项不丢；逐步在授权频道发现新事项 |
| 上下文不断复制给 Codex | 收集原文、补日志、观察回复、反复转述 | 有版本的工作说明，持续更新到原开发任务 |
| 分支混乱 | 回忆分支对应需求、进展及能否继续 | 来源、事项、仓库、工作区、分支、执行和验证双向可追溯 |

首个价值标准不是创建了多少 Task，而是用户不再充当 Slack 与开发执行器之间的信息搬运者和进度协调者。

## 3. 首版用户流程

### 3.1 开启委托

用户可以说：

> 帮我跟进这些 Slack 线程。先排查，确认是问题且在这个仓库范围内就修复、跑测试；方案冲突和范围变化问我，不要自行推送或合并。

首次只补齐三类业务决定：Slack 账号／thread 范围；目标仓库与基线／执行策略；允许操作及需要人判断的边界。复用已有 Project、Agent 模型和明确仓库配置，不要求每个事项重新配置。用户不需要理解事件名称、Cron 或工作流节点。

OAuth、模型可用性、工作区执行安全及 Gateway 在线状态需要预检。连接账号不等于授权全频道扫描，也不等于授权编码。无法确定仓库、基线或现有工作区归属时询问，不猜测。

### 3.2 接手一个 thread

1. 用户提供 thread 链接，或从已授权来源选择“持续跟进”。
2. 读取可见线程和必要附件，说明是否完整；缺权限／附件失败不伪装成完整上下文。
3. 检查已有事项，存在则关联来源，不重复建 Task。
4. 形成工作说明：问题、证据、假设、验收条件、仓库和允许操作。
5. 创建／关联 Task，验证执行边界，绑定工作区和分支，开始真实排查。
6. 展示接手状态和初步发现，不只显示“监控已开启”。

### 3.3 持续吸收讨论

例：登录白屏已开始排查，Slack 新增“仅企业账号出现，个人账号正常”。该证据进入原 Task 的工作说明修订，再投递给原执行器；不另开一个无关开发任务。

| 新信息 | 自动处理 | 需要用户的条件 |
| --- | --- | --- |
| 日志、截图、复现补充 | 更新证据，在执行检查点读取 | 不可读且确实阻塞 |
| 已确认范围内的验收补充 | 更新说明和受影响验证 | 扩大授权、兼容范围或承诺 |
| 相互矛盾的方案 | 保留冲突依据，暂停受影响部分 | 必须确定方向 |
| “先别做了”或转向要求 | 核实发言者权限及与委托关系 | 普通参与者不能直接撤销用户委托 |
| 重复催问、闲聊、机器人状态 | 合并／忽略，不重新派发 | 无 |
| 编辑、删除、推翻旧证据 | 将相关结论标为陈旧并核查 | 影响目标、授权或已交付结果 |

正在执行时，新增信息进入持久队列，在工具结束、测试结束、修改下一文件前等安全检查点处理。记录哪些修订已入队、已送达、已确认应用；不能把“已发送”显示为“已纳入修复”。关键变更未处理时不能报编码完成。

Slack 内容是资料，不直接拥有更改用户授权的权力。谁能确认需求可以显式配置；有争议的目标变化由用户决定。

### 3.4 交付与后续

交付卡显示改了什么、仓库／工作区／分支、处理的需求版本、真实验证、未验证项和来源链接。区分执行回合结束、代码产出、验证完成和业务事项关闭。排查证明无需改代码时提供证据，不为制造产出强行修改。

在约定跟进窗口内继续观察。新消息推翻原验收则需复查，独立新增需求另立相关任务，扩张范围需确认。已合并／归档分支不自动继续写入；必要时建立新的执行绑定并保留沿革。结束的 Task 不因任意新消息无限自动重开，持续 Scene 可以承接后续明确工作。

## 4. 事项卡与注意力

开发事项列表复用 Task 产品面，Scene 提供来源及委托上下文，不建立第二个任务真相源。

```text
企业账号登录后白屏 · T-142
正在验证修复 · 最近成功同步 Slack：2 分钟前
当前需求 v4 · 执行已确认应用 v4
仓库 web-console · 分支 codex/T-142-enterprise-login
下一步：企业账号回归检查 · 当前无需你处理

查看 Slack | 查看代码 | 查看验证 | 查看执行记录
```

分支名仅为示例，实际遵守仓库约定。需要人时只提出具体问题、推荐选项及影响，例如“旧版协议是否纳入本次修复”，不把整件工作退回用户。

列表可筛选需关注、执行中、等待、可交付和已结束，这些是已有 Task 状态的产品投影。支持查看来源／工作说明／更新／diff／验证，回答问题，暂停、恢复、结束。未实现 Slack 回写时只提供草稿，不能声称已通知参与者。

正常进度安静入账。默认仅判断、审批、关键资料缺失和需要人工恢复的阻塞通知；“代码可交付”是否提醒按用户偏好。连接失效不是“无变化”，静音不等于隐藏故障。

## 5. 首版范围

必须支持：单用户／Gateway；明确 thread 的读取与观察；Task 关联；版本化说明与输入确认；一种受控执行器；单事项单仓库、独立工作区与活动分支绑定；验证回执；必要通知；已有分支只读盘点与人工关联。

多个 Task 先有界排队，按资源隔离和预算逐步并发。闭环稳定后再增加指定频道内新事项发现、明确关系的多 thread 合并、第二执行器及受审批 push／PR／Slack 回写。

本轮不做：全工作区／私信扫描、自动合并／部署、无人确认清理或重写历史分支、默认多 Agent 比较、跨主机联邦、多仓库自动协调、全邮箱发现、任意 Scene 编译器、新 DAG 编辑器和能力包市场。

## 6. 实现基线与缺口

下表是 2026-09-21 开发前调研基线，不是当前待办清单；后续完成事实见实施记录。

| 基础 | 已知状态 | 待补齐 |
| --- | --- | --- |
| Scene | activation、模板、范围、只读成果、调度、健康及通知存在 | Slack 观察、Task 关联、受控开发执行 |
| SceneAgentExecutor | 单次推理，`tools: []`，禁止工具及委托 | 通过权限化 Task／Agent 接入，不能直接开放完整工具箱 |
| Task／TaskRun | 契约、内部 Agent dispatch、等待及回执基础存在 | thread、需求版本和开发资源贯通 |
| Workflow | agent 节点、工具集、Skill 和运行记录存在 | 不假设顶层 Run 已有跨天 waiting；长期等待复用 Task／Scene |
| Connector | 账号与访问策略基础存在 | 读取工具不等于 Slack 事件和恢复同步已具备 |
| 外部 Codex | 未确认完整派发、更新、停止及回执适配 | 模型 provider 不等于外部 Codex 任务集成 |
| Git 绑定 | 未确认完整“Slack—Task—工作区—分支”链路 | 先核查既有 workspace 能力，再补关联 |

Gmail／家庭只读场景保留，按原门禁维护。本轮不重新删除场景数据或执行旧 Proactive 迁移。Gmail 专属验收不是 Slack 原型开发的前提；共享运行时变更必须回归已有能力，各功能正式发布仍遵守各自门禁。

## 7. 架构与领域责任

```text
Slack 读取／事件／恢复补同步
           ↓
身份校验 → 持久接收与去重 → 线程变更合并
           ↓
Scene：委托范围与授权
           ↓
Task：说明修订、证据、验收和来源关联
           ↓
TaskRun：执行尝试 → 开发资源绑定 → 内部 Agent／可选执行器
                                      ↕
                          新讨论队列 → 检查点 → 应用确认
                                      ↓
                  代码／测试／回执 → 事项状态／决策 → 后续观察
```

| 对象 | 唯一责任 |
| --- | --- |
| SceneActivation | 持续委托的目标、范围、授权、预算与开启状态 |
| Task | 具体工作目标、验收和完成事实 |
| TaskRun | 一次执行的身份、租约、等待、恢复和回执 |
| SourceLink | Task 与 thread 的关联，不维护任务状态 |
| BriefRevision | 工作说明及证据快照，不覆盖用户授权 |
| ExecutionBinding | 仓库、工作区、分支与执行会话的资源归属 |
| UpdateDelivery | 讨论变化投递及应用确认 |
| Workflow | 按需执行方法，不拥有整个持续委托 |

后四项是建议逻辑契约，优先复用已有关系／元数据，不意味着必须新增四套实体或四张表。物理 schema 与 API 在实现前核查冻结。Scene 的既有轻量 WorkItem 可承载观察游标；编码工作的状态只以 Task 为准。

## 8. 来源与上下文同步

### 8.1 稳定身份与完整性

SourceLink 至少包含连接账号、Slack workspace、channel、thread root、原链接、同步游标／修订、最后成功读取时间和健康状态。不能仅凭消息文本、频道名或联系人显示名关联。

支持一个 Task 多个 thread、一个 thread 拆多个 Task，但记录明确关系和消息范围；跨 thread 合并优先使用引用或用户确认。读取区分最新完整、部分可见、陈旧、撤权和未知。消息删除使相关证据失效，保留最小审计沿革并遵守内容保留／删除策略。

### 8.2 事件接收与恢复

事件或有界增量轮询输出同一变更契约。按连接器能力、权限和部署预检选择首版方式，不让用户写 webhook。Slack 事件订阅不是向 Slack 发送消息的 Incoming Webhook。

入口校验来源、解析主体、持久入队后迅速确认，不等待模型。事件用连接身份与源事件 ID 去重，轮询用稳定消息 ID 与修订指纹；游标只在对应变化已耐久保存后推进。

事件只是唤醒线索，必要时补读 thread，处理分页、编辑、删除、乱序、限流和断线缺口。恢复后合并补同步，不把旧历史重新当新任务。短时变化有界合并，按已委托对象索引分流；没有变化不调用大模型，等待不空转。

### 8.3 说明修订

建议快照：objective、problem、evidenceRefs、hypotheses、confirmedDecisions、acceptanceCriteria、constraints、repoBinding、openQuestions、sourceWatermarks、revision。

更新使用期望版本；执行开始固定快照，新增讨论追加修订而非静默改写。保留事实、假设和用户决定的区别；来源正文不能升级为系统指令或授权。

### 8.4 投递与应用协议

建议状态为 `pending → delivered → applied`，另有 `superseded / rejected / failed / unknown`，属于待实现协议。

- 绑定 Task、当前 TaskRun、执行会话、目标 briefRevision 和稳定幂等键。
- delivered 只代表接口接纳；applied 需要检查点或执行器明确确认及证据。
- 发送不确定先查询，不重复注入。较新快照可合并补充，但不能丢掉取消、冲突和约束。
- 过期 TaskRun 的确认不得更新当前尝试；重试继承待处理变化，阻止旧写者继续修改。
- 交付前比较已应用版本与最新有效验收版本；关键变化未处理则保持待同步／需复查。

## 9. 执行器、权限与恢复

### 9.1 一种执行器先跑通

内部 Agent 默认通过现有 Gateway runner 执行。Codex 只有用户明确选择且具备可靠接口时替代进入第一批，不以不可靠 UI／终端状态猜测完成。

预检至少检查启动、稳定会话身份、输入更新、结果观察、停止、恢复查询、产物／验证与权限限制。不能支持的能力明确降级或阻止无人值守，不能无提示切换执行者。

同一工作区只允许一个活动写者。复杂流程可以选已有 Workflow，多 Agent 不是首版成功条件。

### 9.2 权限沿链路收窄

有效权限是宿主、账号、Scene、Task 与执行器能力的交集：允许读的线程／附件／目录、可写工作区、命令、网络、凭据、Git 操作、外部动作和预算。

内部 Agent 与 Workflow 子节点继承同一或更小边界，不能获取普通聊天的默认完整工具集。外部执行器无法落实边界时不能宣称已经沙箱化。

预授权允许指定工作区读写与约定测试。独立 worktree 不是安全沙箱：测试脚本、包安装和 shell 也可能联网、删除文件或调用生产系统，需要命令／网络／凭据和执行环境约束。未授权的高风险脚本不自动运行。

不传递无关 Slack token、生产密钥或其他项目资料。仓库、日志、附件和讨论均视为不可信输入。

### 9.3 停止与恢复

暂停／撤权使后续派发、待执行动作和旧授权版本失效，并请求停止当前执行。停止是否真正完成要核实；失联呈现未知，不能立刻启动第二个写者。

重启后核对来源水位、工作说明、活动尝试、执行者存活、工作区 HEAD／修改和动作回执。确认没有活动写者才接管。长等待保存 resume 条件并结束当前推理回合，不依赖聊天历史保存工作事实。

## 10. 工作区与分支治理

### 10.1 稳定绑定

ExecutionBinding 建议字段：taskId、taskRunId、repoId／规范路径、workspaceId／路径、branchRef、baseRef、baseCommit、executorKind、executorSessionId、bindingRevision、ownership、状态及可选 PR。

Task ID 是关联主键，分支名只是标签。重试优先复用已核实归属的资源，保留执行沿革；禁止标题模糊匹配后直接写工作区。

### 10.2 新事项

1. 解析明确仓库和基线策略，检查 Git 状态、权限、磁盘与冲突。
2. 为 Task 预留资源绑定和幂等创建身份。
3. 复用既有 workspace 能力建立独立 worktree／分支，记录实际 base commit。
4. 回填绑定后才允许执行器修改。
5. 超时先核对实际资源，不能盲目再创建或清理未知目录。

首版每事项默认一个仓库，跨仓库需求须确认。独立 worktree 不自动包含原工作目录未提交修改；需要这些修改时由用户明确选择并可审查处理方式。

### 10.3 已有混乱分支

先只读盘点 branches、worktrees、HEAD、未提交修改与已有 PR／会话证据，提出关联候选。用户确认后才允许继续执行，无法关联标为待关联。

不为整理列表自动 rename、reset、rebase、merge、delete、stash 或提交。保留用户修改，不凭相似分支名认定资源归 xopc 所有。

### 10.4 冲突和收尾

不同 worktree 仍可能有逻辑冲突，相关 Task 显式标注依赖与集成风险。基线变化、用户修改和已合并分支触发重新核对，不能静默变基。可交付后保留 diff 和资源，不自动清理。

push／PR／Slack 回写是独立批准的动作，审批绑定目标及版本，内容改变使旧批准失效。归档 Task 不删除分支；清理需明确目标、dirty／未推送检查、活动使用者核对及单独授权。

## 11. 完成定义与回执

建议回执：Task／Run、appliedBriefRevision、sourceWatermarks、仓库／工作区／分支、baseCommit、可用的 headCommit 或 diff 标识、修改摘要、检查命令／退出结果／证据、未验证项、阻塞与剩余工作。没有 commit 时不得虚构 SHA。

验收区分未验证、部分验证、通过和失败；工具成功不直接等于业务达成。可交付需满足：

- 约定范围的修改完成，或有证据证明无需修改。
- 最新有效验收修订已处理，来源健康足以支撑结论。
- 必须验证已执行；不能执行的检查有记录，接受例外需要明确决定。
- 资源与产物可访问，无未说明的阻塞。

运行结束、代码可交付、用户接受、合并和上线是不同阶段。后两者未在范围内时不可代为声称完成。

## 12. 持久化、接口与观测

复用单 Gateway／SQLite、Task、Scene 与通用通知。新增字段和关系走保留用户数据的普通迁移，不借本轮重复清空旧实验或现有场景历史。

关键原子边界：事件与游标、来源关联与幂等 Task 创建、说明修订与更新队列、资源预留与归属、回执与任务状态。Git、执行器和 Slack 在事务外操作，通过操作身份及恢复核对解决崩溃窗口，不承诺跨系统 exactly-once。

复用 TaskRun 租约和版本约束；过期执行不能写新结果。重试有上限，模型／连接器成本按 Scene／Task／Run 归属。

UI 与 Agent 工具共用应用服务，按需增加接手 thread、查看同步、关联资源和查看回执操作，不新造平行 API 产品。新增鉴权路由必须配置 lazy-bundle matcher、映射测试，并经过真实 Gateway 鉴权链路验收。

日志关联 activationId、taskId、taskRunId、sourceLinkId、briefRevision、bindingId 及阶段，不记录凭据或无界正文。诊断展示最后成功同步、待处理修订、执行身份、工作区、预算、阻塞及恢复动作。

Gateway 关闭／设备休眠期间不承诺持续工作，恢复后补同步并展示覆盖缺口。常在线宿主以后按实际需要选择，不默认增加云服务。

## 13. 验证与推进

先选用户自己的 3—5 个真实 thread 及相关仓库／分支，覆盖简单修复、持续补充、冲突决策和已有分支关联。固化脱敏回放样本，真实读取和写入分别授权。

| 验证重点 | 可观察结果 |
| --- | --- |
| 接手和去重 | 重复点击／事件只有正确的一个 Task；缺数据明确显示 |
| 连续讨论 | 补充进入原任务，有应用版本证据，不要求用户复制 |
| 资源管理 | Task 可定位工作区／分支，分支可反查来源 |
| 过期回报 | 旧尝试、旧需求的成功不覆盖当前状态 |
| 恢复 | 不重复派发写者，不丢待处理变化 |
| 权限 | 撤权、恶意消息、越界目录／命令不扩大范围 |
| 编码完成 | 代码与验证真实，未验证和未上线明确区分 |
| 历史保护 | 未关联分支、用户修改不被整理操作破坏 |

衡量同一用户改造前后的消息复制、手动查看 thread、补充指令次数、分支反查耗时、错配／遗漏、返工及每事项成本。目标是减少搬运和监督，不凭小样本推导市场留存或承诺百分比。

顺序：真实样本及执行器预检 → 明确 thread 接手／只读排查 → 资源绑定与受控编码 → 持续讨论、恢复与验收 → 历史分支关联及受限发现。每步都做纵向验收，不先建设全平台。

## 14. 扩展路线

- 新来源适配后仍提供 Task 来源及变化，不复制事项系统。
- 业务方法沉淀为 prompt／Skill 和验收示例，不硬编码每类问题的步骤。
- 新执行器满足相同身份、更新、权限、停止和回执要求。
- 非编码场景保留持续 Task，把 Git 绑定替换成真实需要的资源。
- 用户用自然语言调整已有场景，权限扩张单独确认；成熟方法再分享。

长期 Scene 可成为增强 Extension 的能力包，但包定义、激活实例、凭据、授权和历史必须分离。先用 Slack 开发闭环证明价值，再由第二个真实需求抽取共性，不为未来统一延迟当前问题。
