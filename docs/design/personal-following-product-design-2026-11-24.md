# xopc 个人跟进产品与交互设计

2026-11-24 · 产品提案 · 基于仓库代码、项目周报和竞品官方资料

主动内容的呈现、首次使用和默认交付以[第二轮 Personal 对话与工作台方案](./personal-agent-quiet-proactivity-2026-11-24.md)为准。本篇保留跟进的生命周期、来源授权与试点背景。

## 1. 用户把什么交给助手

**用户可以把一件自己原本要反复查看、或者想持续探索的事交给助手，并约定什么值得告诉自己。** Onboarding 用已有上下文找到第一件，日常对话持续发现新的机会。每次回访都能回答四个问题：它在替我看什么，已经看到什么，为什么这次值得告诉我，我怎么改或停。

| 用户的需要 | 用户实际委托的内容 | 用户收到的价值 |
| --- | --- | --- |
| 释放注意力 | 「到试点发布前，帮我盯发布阻塞。只告诉我新增、解除，以及我需要拍板的事。」 | 知道变化会浮上来，可以减少自己刷新看板的次数 |
| 拓展自己的边界 | 「我想系统学街头摄影。每两周找一个贴合我当前练习的案例或可试的小实验。」 | 获得原本不会主动搜索的东西，并知道可以怎样用上 |

首版统一叫「跟进」，用户无需先选类别。「有关键变化时」和「定期给我精选」是两种交付方式。一个阶段中的项目与长期兴趣都可以选任一种。用户看到的是事项、明确的交付承诺、来源与状态。系统侧仍用 Project 记录工作目标，用 Task 处理有验收结果的单次工作，用 Automation 和事件订阅执行检查。

| 产品对象 | 它回答的问题 | 示例 |
| --- | --- | --- |
| 用户理解 / 记忆 | 助手知道我什么？ | 我在练街头摄影，手头主要用一支 35mm 定焦 |
| 跟进 | 我希望助手持续替我留意什么，何时回来？ | 每两周选一个我周末能做的街拍练习 |
| 自动化 / 事件订阅 | 什么时候运行，读取哪一处？ | 隔周周五检查所选来源，找到合格结果才产出 |
| Task | 这次要完成和验收什么？ | 根据一条推荐整理一页拍摄练习清单 |

一次性且结果明确的请求走现有提醒或 Task。长期跟进有稳定 ID，可以跨会话回看。同一项目可以有不同跟进条件，例如「发布阻塞」与「试点用户提出需我决定的问题」，按条件与范围区分。

## 3. Onboarding 与日常对话

### 已有上下文：提出一件具体的事

把建议接在深度理解的「确认对你的认识」之后，作为该页末尾的可跳过区块。完成认识确认和开始跟进是独立动作。结果尚未就绪时，按原流程进应用，候选之后可在工作台静默出现。首次最多展示一条主建议，有明显不同的另一条时提供「换一个」。旧用户在工作台或相关对话结尾首次看到建议，无需重走 onboarding。

```text
可以帮你盯一下试点发布吗？

你在「试点发布」项目里标了两项待确认，我可以留意之后的变化。
GitHub 试点看板 · 新增或解除发布阻塞时告诉你 · 发布后结束

[看看怎么跟进]  [暂不跟进]
为什么建议这件事？
```

点「为什么建议这件事？」展示用户有权打开的 1–2 条依据和日期，例如本人在项目里确认的目标、该项目的待决项。公共链接和内部资料有各自的可见范围。`暂不跟进` 收起本次建议，进入冷却期。`这件事已结束` 或 `这与我无关` 抑制同范围候选，后续用户可主动重新添加。

### 上下文不足：允许用户一句话交代

若没有可信候选，提供可跳过的问题「有一件你最近老在查，或者很想持续了解的事吗？」输入留在聊天里。用户能直接说「试点发布前，如果有新的阻塞告诉我」或「隔周挑一个街拍练习」。目的不清时只追问一项最影响结果的信息，如「你想盯的是试点看板上的阻塞，还是所有相关 PR？」先给具体选项，也允许直接开始普通聊天。

### 日常发现：让建议落在原话题下

| 信号 | 行为 |
| --- | --- |
| 明确提出跟进，主体、来源和交付均清楚且已有合适授权 | 用现有明确委托路径直接创建，回复简短回执及调整入口。同一请求重试只创建一次。 |
| 明确要跟进，但来源、时间窗口、外部授权或条件会影响承诺 | 给可编辑预览，只确认缺口。新增来源时展示具体范围与用途。 |
| 近期开放事项，例如项目目标、用户确认的待决问题或期限 | 可产生草稿候选。以用户确认仍未结束、存在可观察状态、助手可以代查为准。 |
| 长期兴趣 | 优先采用用户主动声明的长期目标。衍生推断至少有跨本地日期的独立用户证据作为首版基线。收藏、浏览记录、文件标题或会议邀请只能辅助判断，第三方信息不能单独把话题归给用户。 |
| 单次提问、引用示例、助手生成内容、重复导入、已经结束的任务 | 保持静默。可纠正归属，新的明确委托才可恢复已终止事项。 |

排序先看证据和归属，再看重复查看的负担、当前目标、是否有可读来源与具体结果。职业、项目、生活和兴趣用同一套标准。项目上下文只在原项目或用户获准的私有管理面可见。首版建议预算为 onboarding 一次、日常每人每周最多两条候选，设为试点参数。聊天内提示放在用户原问题已回答之后，候选本身不发系统通知。

## 4. 确认页、第一次结果与管理

### 确认页：用一句话核对承诺

主按钮「开始跟进」，同屏可调整「条件」「来源」「交付」「结束条件」。Web 用现有对话内详情面板，移动端用底部面板，较长内容内部滚动。二级权限信息可展开，主按钮附近直接显示任何会改变后台持续性的条件。

| 设置 | 试点发布 | 街头摄影 |
| --- | --- | --- |
| 要关注的事 | 试点发布阻塞 | 周末能完成的街拍练习 |
| 哪些值得告诉我 | 新增或解除发布阻塞，或出现需要我决策的问题 | 每两周最多一条。必须给具体做法，适合 35mm 定焦，且周末能在本地完成。相似内容略过 |
| 会查看什么 | 已授权的指定 GitHub 仓库和项目范围，从标签或已接入的明确状态判断 | 约定的公开摄影来源和本人已确认的练习目标 |
| 何时到我这里 | 关键变化进入工作台，有明确处理窗口时按用户设置升级 | 隔周汇总，没有合格发现就跳过 |
| 何时结束 | 用户关闭，或关联的试点发布达成 | 长期，用户随时暂停或结束 |

确认后创建跟进并显示覆盖回执：「已开始跟进。最近检查：今天 14:10。若有新增或解除的发布阻塞，会出现在工作台。」时间只来自实际运行。尚未检查则显示预期窗口，连接未完成显示「等待连接」，本地网关离线时显示「设备上线后继续」。适配器只有轮询时用「每 X 小时检查」，有事件时注明来源及延迟预期。持久化确认与后台配置存在短暂延迟时，先显示「正在开启」。若已有相同跟进，回到原事项并允许更新条件。

### 首次结果：证明跟进真的有用

开启后在来源已获授权时尽快做一次只读检查。首次跑出来的是**基线**，打开详情可见，早已存在的变化不冒充新事件。首次有实质结果才可显示「发现」。当没有结果时，回执说明查了哪里和下一次检查窗口，详情保留覆盖状态。首用走查将「已确认且成功检查」与「已交付有用结果」分别计量。

```text
试点新增一项发布阻塞
测试团队把「离线恢复」标为阻塞。试点前需要决定是先覆盖 Android，还是两端一起修。

为什么现在 · 14:18 首次加上 release-blocker
跟进条件 · 只看新增、解除和需你拍板
来源 · GitHub #184，14:18 标签变更

[打开事项]  [和助手讨论]  [调整跟进]
```

探索型结果采用同一结构：例如「本周可试一次固定机位练习」，说明它如何补足用户以前只练移动抓拍的问题，给一个十分钟可执行的起步动作，以及原始参考。把事实、助手解释、建议动作区分在详情中。一个足够好的发现胜过为了更新而凑几条链接。探索中可偶尔推荐相邻方向，推荐理由要能回到同一个目标，用户可要求收窄或关闭探索。

### 管理页：用户能独立核对

工作台「跟进」区显示正在跟进的事项和最近有用的变化，点「管理跟进」进入列表。Project 内显示所属项目的跟进，Personal 中可说「你现在在帮我盯什么？」并打开同一记录。移动端可从助手进入「跟进」；在接入范围内共享服务端状态。

- 详情展示承诺、来源覆盖、最后一次成功检查、下一次计划检查或事件覆盖、结果历史，并就地提供「调整」「暂停」「结束」「立即检查」。在已授权、来源可用且预算允许时，用户可以立即检查。
- 「暂停两周」暂停检查与交付，恢复前不回放过时更新。恢复后重新检查最新状态，若仍有可行动变化，按同一条件处理。结束会停止后台检查与待投递项，保留可访问的历史。「结束并删除」按数据删除策略移除历史。
- 「这条不相关」只处理本条；「以后只看官方更新」修改本事项的来源或条件；「停止跟进」结束整个事项。沉默或未点击可降低推荐打扰频率，但不推断偏好或结束已确认的跟进。涉及新增来源、范围扩大或通知升级的自然语言修改要在回执中明示，并在需要时确认。
- 多端或多入口看到同一条更新时，详情引用同一个事项与更新 ID。同一条更新的已读、延后与处理结果同步；静音通知仍可在详情查看记录。

## 5. 什么值得发，发到哪里

| 判断顺序 | 规则 | 示例 |
| --- | --- | --- |
| 允许 | 当前授权允许该来源、用途、处理方式和交付面。事项仍生效。 | 来源被收回，检查停止，详情标记「连接已失效」。 |
| 可信且有变化 | 有原始证据、时间和覆盖范围，与上次记录相比有新事实或新的可用办法。 | 同一篇报道转载、同一事件重放、只改页面时间戳，均合并或略过。 |
| 与用户目标相干 | 能减少一次人工检查、避免错过决策窗口，或者带来具体可试的新方向。 | 泛泛的行业新闻略过。关键阻塞解除，即使无需立即操作，也能让用户判断可否继续发布。 |
| 符合打扰约定 | 检查与通知独立。依据时效窗口、免打扰和用户选的渠道决定。 | 普通发现进汇总。已约定且会错过决策的变化可以升级。同话题密集变化合并。 |

**首版投递建议**

- 静默记录检查结果，亦可注明覆盖不全。用户打开详情时能区分「检查成功、未命中」「部分来源不可用」「尚未检查」。
- 非紧急的洞察复用 Pulse/Digest。只有有实际内容才生成简报。试点将探索型事项默认聚合到每周或隔周的汇总时间，沿用用户时区。
- 明确待决、有时间边界的变化、或可验收的交付进入 Loop Feed 的投影。当前可复用工作台上的 Agent Inbox 承接；Loop Feed 作为产品规划的呈现面，按同一条目投影。全局任务总览用于查找所有任务和执行状态。跟进列表负责管理承诺。
- 只有用户已允许的高时效条件才进入 Personal 对话或通知。首版新功能默认站内交付；单事项开启通知仍受全局免打扰和预算限制。候选、普通探索和健康内容不在锁屏展示详情。可将每人每天最多一次跟进打断作为试点初始上限。超过预算的内容延至下一可用窗口，到期失效的消息不再投递。
- 事件到达、准备完成、用户实际收到分别记录。来源故障聚合后在工作台向有权处理的人报告一次；短暂抖动按既有恢复策略重试。用户可以从详情确认覆盖中断了多久，必要时自行接回。

探索和代看共享同一入口，各自按不同价值标准评估。代看强调漏报、时效与范围可信；探索强调新颖、可试与用户后续反馈。两类都默认接受安静周期。

## 6. 来源、授权与健康

- 一次性 onboarding 许可只在其允许的用途、字段和保留期内生成候选；长期读取需要来源具备并允许对应的持续用途。连接存在、语义相关和用户同意开始跟进是三个独立判断。私密范围优先显示简短归因，如「你在 11 月 20 日的个人对话提到」，详情按现有访问规则展开。
- 建议证据和实际跟进来源角色不同。已确认事项如果有独立的用户委托和可用来源，删除原始建议依据后可隐去该依据并继续独立委托。若删除或撤销的是执行依赖，停止相关读取与待发布内容。撤权后权限要在检查、生成、发布和重试时重新验证，事件重放不能恢复旧授权。
- 项目按照授权后的项目范围对照事件。发现与私密资料有关时，用允许的最小字段准备结果，个性化上下文不随搜索直接发给第三方。`local_only` 沿用已有后台远程模型限制。公共来源的首次查阅也受产品可用能力与用户确认的范围约束。
- 健康跟进留到独立试点，从用户明确提出的生活习惯或活动回顾开始。例如「每周帮我回顾自己记下的三次散步」。先支持用户选定的手工记录，再评估独立的健康数据接入。产品只展示可核对的记录、范围和覆盖情况；诊断、预警和治疗建议不纳入该路径。断开数据权限立即停止处理，敏感内容默认仅在私有应用内可见。用户信息只在约定的处理与保存范围内流动。
- 首版以只读检查、整理和准备草稿为主。外发、购买、修改项目状态等动作走现有 Task 或审批确认，跟进本身的权限止于用户选定的检查和交付。

产品只维护一份用户可理解的跟进承诺。技术上优先在现有 attention 模型上扩展显式委托、稳定归属和生命周期，订阅与 Automation 是执行投影。落地前需要验证该扩展对现有临时跟进的兼容性。任何新持久化设计都应让暂停、撤权和更改条件能取消旧版本的检查与待发消息，也能在进程重启和请求重试后恢复一致状态。

建议的纵向链路：授权证据 → 候选 → 用户确认保留规则 → 事件订阅或按时检查 → 价值与时机判断 → 返回有依据的价值 → 在同一事项上调整。候选被拒绝、事项暂停或已结束各有明确作用域，包括跨聊天重复推断的抑制。已确认跟进可以关联当前 Project，用户始终能从项目、对话、工作台进入同一详情。

## 8. 首版范围、验证与决策标准

| 阶段 | 可验收交付 |
| --- | --- |
| P0：桌面 / Web 纵向试点 | 从 onboarding 或对话提出一次建议，支持一句话创建。有一个项目事件型跟进和一个公共来源精选型跟进。两者都能编辑条件、暂停或结束。在工作台展示结果与源证据。选定真实仓库和至少一个可用的公开来源完成走查。 |
| P1：连续使用 | 同一跟进状态进入移动端。承接项目和 Personal 的管理入口，加入跨事项汇总、站内时效升级，以及多来源覆盖中断恢复。 |
| P2：扩展 | 接更多经验证的来源，加入对自动新增来源的显式授权，以及更丰富的探索。健康按独立的权限和内容展示流程验证。 |

首轮招募 12–16 位用户，覆盖有发布或项目协调责任的人，以及有明确技能、兴趣目标的人。先走查两个模拟场景，再用用户本人选择的事项做两周日记研究；允许使用测试账号。研究分别对照「自然语言手动创建」与「有依据的 onboarding 候选」的理解与激活，以及「固定简报」与「仅有合格发现才交付」的用户感受。小样本主要找失败模式，不用作留存或因果结论。

- **激活**：可呈现建议的用户中，分别记录建议看见、理解、确认、首次成功检查、首次价值交付。记录用户是否能准确复述检查对象、触发条件、范围及停止方式。
- **代看效果**：记录与已知真实事件对照的命中、漏报和时延。访谈用户是否减少了原来需要自己查看的次数，区分用户自行发现与助手率先发现。覆盖中断期间单列，作为漏报原因之一。
- **探索效果**：收集用户对新颖性、适用性和尝试意愿的评价，记录实际尝试、保存和就地追问。单独统计同质、重复或泛化内容。用户主动标记比点击更能说明价值。
- **负担与可靠性**：关注关闭打扰、撤权后投递、重复触达、来源失效时的虚假平静、用户更改条件后的旧版本投递，以及每个活跃事项的检查和模型成本。用结构化原因做分析，避免在遥测中存原文。

试点前验收：用户能从同一条更新回到触发条件与源证据；项目变更可在真实网关经已授权来源到达；关闭或撤权后的旧队列不再送达；网络重连或事件重放只交付一次；候选零系统通知；无变化、来源失败、权限撤销这三个状态有各自明确的呈现；结束后不会在新聊天里被重新推断并启用。首轮将「至少 80% 的参与者能独立弄清并停止跟进」及「零已知撤权越界、重复打断」作为预设验收门槛。长期价值和频率阈值在试点建立基线后再定。

## 建议先定的产品取舍

1. **Onboarding 只争取用户愿意交给助手的第一件事。** 首次体验应能轻松跳过。保留既有认识确认，给一条具体建议和一条自然语言入口。
2. **跟进承诺应该一直可见。** 用户能在同一处看到来源、条件、当前覆盖和结果，随时停下。挂靠现有工作台和 Personal，项目内提供投影。
3. **先同时验证代看与探索。** 用「试点发布阻塞」验证可信委托，用「摄影练习精选」验证主动之外的新增价值。优先验证资料、价值和停止操作，再扩展领域与通知渠道。
