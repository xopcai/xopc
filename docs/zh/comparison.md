# xopc 处在什么位置

xopc 位于个人知识系统、长期工作管理和 Agent 运行时的交叉位置，但它并不等同于其中任何一部分。它是一个本地优先的私人 AI 助手：逐渐形成对一个人的可检查理解，并长期陪这个人推进重要事情。

这里说明的是产品边界，而不是给厂商排名。

## 与相邻产品类别的区别

| 产品类别 | 通常优化什么 | xopc 的不同之处 |
| --- | --- | --- |
| **通用聊天助手** | 在一次对话中回答当前请求 | xopc 保留可治理的用户理解、Project、Task、决定和运行记录，让工作可以跨越时间与入口继续。 |
| **编码 Agent** | 在代码仓库中读取、修改并验证工作 | xopc 可以支持编码，但范围是一个人更完整的目标、关系、承诺、文件、消息和周期性工作。编码 Agent 可以成为其中一种执行工具。 |
| **AI 员工或角色 Agent** | 承担预先定义的组织角色或委派工作队列 | xopc 围绕一个人不断变化的意图展开。它不会在开始时假装认识用户，而是通过纠正和明确授权逐渐获得主动性。 |
| **任务管理器** | 保存用户已经澄清和整理好的任务 | xopc 接受还不完整的想法和证据，帮助找到相关目标与背景，并形成下一个可信行动。 |
| **自动化平台** | 连接触发器、集成与确定性动作 | xopc 把自动化与个人上下文、Task 状态、证据和授权层级连接起来。自动化是执行能力，不是产品身份。 |
| **个人知识系统** | 捕获、关联和检索信息 | xopc 区分事实与推断，治理什么值得记住或忘记，并使用可信理解帮助行动。 |

## 定义 xopc 的差异

### 一段会逐渐变好的关系

xopc 从安全默认值开始，不声称已经认识用户。理解来自明确授权的数据源、共同完成的工作和用户纠正。真正有价值的不只是完成一条消息或一个任务，而是下一次协作能否从更可靠的上下文开始。

### 管理意图，而不只是任务

输入可以是清晰请求、模糊想法、文件、链接或来自已连接工作的信号。xopc 帮助它关联目标或 Project；需要持续执行时形成 Task；识别阻塞，并保留决定与证据。

### 本地优先的所有权

配置、状态、对话、日志、Agent 文件和工作区默认保存在 xopc 状态目录中。模型、服务商、远程访问、数据源、工具和能力边界由用户决定。

本地优先不表示云端模型永远不会收到数据。请求需要时，相关上下文会发送给选定的云端服务商；必须留在设备上的工作可以使用本地模型。

### 可以检查和纠正的理解

事实、推断和协作规则彼此独立。用户可以查看、确认、纠正、拒绝或删除理解。过期与矛盾内容可以重新进入检查流程，而不是永远在后台影响行为。

### 必须逐渐赢得的主动性

xopc 理想的主动过程是：观察、提醒、建议、确认后执行，再到明确授权的低风险自动化。模型认为自己很有把握，并不意味着可以直接执行高影响外部动作。

### 多种入口中的同一个助手

桌面、网页、终端、手机和消息通道可以访问相同的 Agent、Conversation、Project、Task 和用户理解。不同入口不必变成几个互相失忆的助手。

## 适合选择 xopc 的情况

- 希望一个私人助手在数月使用中逐渐变得更有帮助；
- 希望理解和记忆可以被看见、纠正和删除；
- 希望直接交给 AI 混乱输入，而不是先维护完美的任务系统；
- 希望用 Task 与 Project 保存重要工作及其证据；
- 希望使用自己的云端密钥或本地模型；
- 希望获得可自托管、MIT 许可、可以扩展的系统；
- 希望主动帮助保持建议优先并尊重授权边界。

## 可以优先选择更窄工具的情况

- 只需要在一个代码仓库中完成代码修改；
- 只需要无状态问答或文档生成；
- 已经拥有清晰的结构化任务，不希望 AI 解释上下文；
- 希望使用完全托管的企业工作平台，而不是本地系统；
- 不希望自行管理模型、凭据、存储、更新或远程访问。

更窄的工具可以与 xopc 共存。xopc 保留个人意图和持续上下文，专业工具负责其中一个执行环节。
