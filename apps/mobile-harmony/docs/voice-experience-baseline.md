# 实时语音基线与第一阶段交付

日期：2026-10-08。模型接入延后，是否经过 `xopc-platform` 待讨论。本阶段只修改鸿蒙现有 v3 PCM 链路；没有改变 Gateway 协议、供应商、模型、判停参数和默认路由。

## 已实施

- 上行分别记录 PCM 时长、线上字节、实际排队等待、峰值等待与丢弃时长。新收到的 120 ms 音频批次不会因协议头开销误判为拥塞。
- 维持原有 120 ms 拥塞触发水位，300 ms 为 PCM 排队容量及发送前过期上限；容量检查在分帧分配之前执行。未发送队列在静音时清理，已经进入原生 `send` 的帧无法撤回。严重过期停止会话并提示 `INPUT_DROPPED`，不在原会话中悄悄补发旧语音。
- 用户静音、连接状态、审批、澄清与拥塞共同决定输入状态。拥塞恢复不会覆盖用户静音或等待审批；旧会话的审批响应不能影响新会话。
- 同一次采集拆出的 20 ms 帧递增采集时间；以 read 完成减去音频时长估算第一样本时间，尚未采用硬件采集时间戳。
- 启用 barge-in 的会话中，服务端 `input.speech_started` 在 AI 仍有未播音频时触发可逆降音量：60 ms 渐变至原音量的 25%，对应语句停止后 120 ms 恢复。它不是本地近讲检测，响应时间仍受网络与 provider VAD 影响，也不改变原来的最终取消判定。
- 每轮完成或取消输出 `Voice timing:` JSON，使用单调时钟，区分首包收到、Renderer 缓冲、硬件播放进度。drain 结束只表示完成，不能冒充首声。既有流控确认格式保持兼容。
- 原生录音焦点恢复事件不再误报为采集中断；真正的停止或暂停仍走恢复处理。

## 日志与统计

在连接设备后保存完整 hilog（可按设备选择参数指定目标）：

```sh
hdc hilog > /tmp/xopc-voice-hilog.txt
# 测试完成后结束日志采集，再分析
node scripts/analyze-voice-timing.mjs /tmp/xopc-voice-hilog.txt > /tmp/xopc-voice-timing.json
```

分析器按 `mode` 和音频 `route` 分组，输出完成状态数量及各指标样本数、nearest-rank P50/P95/P99；坏 JSON 单列计数，缺少采样值输出 null。避免将同一次通话的重复日志导出拼接到一起。不同工具场景、设备、网络和测试轮次应使用独立文件，目前程序不会自动辨别这些条件；取消轮与完成轮也需结合 outcomes 解读。

| 指标 | 口径及限制 |
| --- | --- |
| speechStopToResponseMs | 客户端收到服务端语音停止事件至收到 response.created |
| speechStopToAudioReceivedMs | 同一停止事件至客户端收到首音频，仅首次上报现有 session.metric |
| audioReceivedToBufferedMs | 收到首包至 Renderer 首次确认写入，包含前一回答尚在排空时的等待 |
| audioReceivedToPlaybackProgressMs | 收到首包至首次观察到硬件播放位置前进；通常按 40 ms 轮询，不是声学首声 |
| bufferedDurationMs / playedDurationMs | 已缓冲与已播放时长；后者可能通过最终 drain 确认 |

停止事件已经包含上游判停等待，以上统计**不能**证明“最后用户语音样本至实质首声”的端到端 SLO。真正的端到端与插话反馈需要同步录制测试现场声音，并标记用户结束、用户插话、AI 实质首声、降音量和停止旧回答。

## 真机验收矩阵

固定房间、摆位、设备音量与测试语料；至少两款目标鸿蒙设备，逐路由记录系统版本、应用构建、Gateway 版本和当前 provider。优先跑已有系统通信用途 AudioKit 3A 基线，未经 A/B 测试不叠加软件 AEC/AGC。

| 场景 | 操作 | 记录与通过条件 | 当前结果 |
| --- | --- | --- | --- |
| 多回合 | 100 轮连续追问，包含前一播报结束时立即发言 | 回答或明确错误数量、无永久静音/串轮/静默失败 | 待真机 |

| 外放回声 | 不说话让 AI 播报，再进行双讲 | 误转写、错误响应、用户吞字、回声残留 | 待真机 |
| 近讲与干扰 | 明确打断、附和、咳嗽、电视、旁人讲话、重复 AI 用词 | 误 duck、不可逆误打断、意图与实体准确率 | 待真机 |
| 路由 | 听筒、外放、USB/有线、蓝牙及通话中切换 | 分路由延迟、音质、实际输出设备、麦克风连续性 | 待真机 |
| 弱网 | 受控延迟/抖动/带宽限制、断连再恢复 | 等待与丢弃量、不补发旧语音、恢复与重说体验 | 待真机 |
| 状态竞争 | 用户静音期间网络恢复；审批/澄清期间网络恢复 | 全程保持静音，解决等待后按用户意图恢复 | 自动回归通过；待真机 |

建议 SLO、声学语料和样本规模见仓库 `docs/design/harmony-realtime-voice-excellence-research.md`。没有设备实测时，不填写延迟和抗噪声效果的达标结论。

## 后续决策

先用本阶段基线找出主要耗时。模型接入独立讨论：`xopc-platform` 是否承担实时媒体代理、长期密钥和短期票据、供应商会话生命周期、工具桥与审批、并发配额、地域入口、可观测性与成本核算。确定这些责任后再设计 adapter，避免先把供应商协议写死到手机。

本地近讲检测、前置缓冲、AEC 替代方案、OHAudio/C++、RTC/Opus、动态判停参数均待基线与方案验证；本阶段没有宣称完成这些工作。
